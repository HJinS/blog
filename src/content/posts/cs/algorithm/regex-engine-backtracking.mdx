## 개요

[앞 글](/posts/cs/algorithm/shortest-path-dijkstra-bellman-ford)까지는 입력이 커져도 시간이 예측 가능한 알고리즘을 봤다. 이번 글은 반대로, 입력이 몇 글자만 늘어도 시간이 폭증하는 경우를 다룬다. 주인공은 매일 쓰는 정규식이다.

이 글이 답하는 질문은 두 가지다.

- 겉보기에 짧고 평범한 정규식이 왜 서버 CPU를 통째로 먹을 수 있는가?
- 같은 정규식을 선형 시간에 처리하는 엔진은 무엇이 다르고, 그 대가는 무엇인가?

---

## 1. 먼저 숫자부터: `(a+)+$`에 `aaaa...b`를 넣으면

패턴 `(a+)+$`는 "a가 한 개 이상 붙은 덩어리가 한 번 이상 반복되고, 그 뒤가 문자열 끝"이라는 뜻이다. 입력이 `aaaa`처럼 a로만 이루어지면 바로 매칭된다. 문제는 끝에 `b`가 하나 붙을 때다. `b` 때문에 `$`가 절대 만족되지 않으니 결과는 "불일치"인데, 엔진은 그 사실을 확인하려고 모든 경우를 시도한다.

a의 개수를 n이라 하면, 엔진이 따져 보는 "a를 덩어리로 나누는 방법"은 `2^(n-1)`가지다.

| a의 개수 n | 나누는 방법 수 | 비고 |
|---|---|---|
| 5 | 16 | 눈 깜짝할 새 |
| 10 | 512 | 여전히 빠름 |
| 20 | 약 52만 | 아직은 체감 어려움 |
| 30 | 약 5.4억 | 초 단위로 넘어감 |
| 40 | 약 5,500억 | 초당 1억 번 시도한다고 가정하면 약 1.5시간 |

n이 10 늘 때마다 시도 횟수가 약 1,000배가 된다. 마지막 행의 시간은 "초당 1억 번"이라는 가정에 따른 어림값이다. 실제 속도는 엔진과 하드웨어마다 다르지만, 증가 모양은 그대로다. 입력 길이를 한 글자 늘릴 때마다 시간이 두 배가 된다.

이 글의 나머지는 이 표가 왜 나오는지, 어떻게 피하는지를 설명한다.

---

## 2. 정규식은 어떻게 실행되는가: NFA

정규식을 실행하려면 먼저 패턴을 기계로 바꾼다. 정규식은 유한 오토마타(finite automaton), 즉 "상태와 글자를 읽을 때의 전이 규칙으로 이루어진 단순한 기계"로 표현된다. 그중 NFA(비결정적 유한 오토마타, nondeterministic finite automaton)는 한 상태에서 같은 글자를 읽고도 갈 수 있는 길이 여럿일 수 있는 기계다.

`(a+)+`를 NFA로 바꾸면 선택지가 생기는 지점이 분명해진다.

```text
          a
      +-------+
      v       |
 S --> [A] ---+      안쪽 a+ : a를 계속 먹는다
       |
       +--> 바깥 반복 : 덩어리를 끝내고 새 덩어리를 시작한다
```

a를 하나 읽었을 때 선택지가 둘이다. 같은 덩어리에서 a를 계속 먹을지, 덩어리를 닫고 새 덩어리를 열어서 먹을지다. 이 선택지가 a 하나마다 붙어 있다는 점이 모든 문제의 뿌리다.

여기서 질문은 하나로 모인다. NFA를 어떻게 실행할 것인가? 답은 두 갈래다.

- 길을 하나씩 가 보고 막히면 돌아오는 방법(백트래킹)
- 갈 수 있는 모든 길을 동시에 따라가는 방법(Thompson 방식)

## 3. 백트래킹: 한 길씩 가 보고 막히면 돌아온다

백트래킹(backtracking)은 선택지에서 첫 번째 길을 골라 끝까지 가 보고, 실패하면 직전 선택지로 돌아와 다음 길을 시도하는 방식이다. Perl, PCRE, Java, Python, JavaScript 같은 많은 엔진이 이 방식을 쓴다. 예를 들어 V8 팀은 자기 엔진 Irregexp를 백트래킹 엔진이라고 설명한다.

핵심 아이디어는 한 문장이다. 성공할 때까지 모든 길을 차례로 시도하고, 실패하면 되돌아간다.

`(a+)+$`를 `aaab`에 적용해 보자. a 세 개를 덩어리로 나누는 방법은 4가지다.

```text
시도 1:  [aaa]           -> 다음은 b, $가 아니다   실패, 되돌아간다
시도 2:  [a][aa]         -> 다음은 b               실패, 되돌아간다
시도 3:  [aa][a]         -> 다음은 b               실패, 되돌아간다
시도 4:  [a][a][a]       -> 다음은 b               실패, 불일치 확정
```

성공하는 입력이면 첫 번째 길에서 바로 끝날 수 있다. 그래서 평소에는 빠르다. 하지만 불일치를 확정하려면 모든 길이 실패했음을 보여야 하므로 전부 시도해야 한다. a가 n개면 `2^(n-1)`번이고, 1절의 표가 그 결과다.

이를 의사코드로 쓰면 더 분명하다.

```text
match(node, i):
    if node == ACCEPT: return true
    for next in node.choices:                 // 선택지마다
        if next.consumes(s[i]) and match(next, i+1): return true
    return false                              // 모두 실패 -> 호출자가 다음 선택지를 시도
```

재귀로 들어가며 선택지를 스택에 쌓기 때문에, 입력이 아주 길면 스택 사용량도 입력 길이에 비례해서 커진다. Russ Cox는 이 때문에 a 10만 개짜리 입력에서 Perl이 스택을 다 써 비정상 종료(segmentation fault)하는 예도 보였다.

### 왜 이런 방식이 널리 쓰이는가

시간이 지수로 늘 수 있는데도 백트래킹이 주류인 이유가 있다.

- 구현이 단순하다.
- "먼저 시도한 길을 우선한다"는 규칙 덕분에 탐욕(greedy)·게으른(lazy) 수량자 같은 직관적인 매칭 의미를 줄 수 있다.
- 캡처 그룹, 역참조(backreference), lookaround 같은 확장 기능을 자연스럽게 얹을 수 있다.

대가는 최악의 경우 시간이 지수라는 점이다. 이 비용은 평소에는 드러나지 않다가 특정 입력에서 한꺼번에 터진다.

## 4. Thompson 방식: 모든 길을 한꺼번에 따라간다

Ken Thompson이 1968년에 제안한 방식은 길을 하나씩 가지 않는다. 대신 "지금 도달할 수 있는 NFA 상태의 집합"을 들고 있다가, 글자를 하나 읽을 때마다 그 집합 전체를 한 번에 앞으로 옮긴다. Russ Cox의 글 "Regular Expression Matching Can Be Simple And Fast"가 이 방식을 자세히 설명한다.

핵심 아이디어는 한 문장이다. 어떤 경로로 왔는지는 기억하지 않고, 지금 있을 수 있는 상태만 기억한다.

`(a+)+b`를 `aaa!`에 적용하면 이렇게 진행된다.

```text
입력:        a         a         a         !
상태 집합:  {s0}  ->  {s1,s2} -> {s1,s2} -> {s1,s2} -> {}
                                                       (집합이 비었다 -> 불일치)
```

같은 상태에 서로 다른 경로로 도착해도 집합에는 한 번만 들어간다. "aaa를 어떻게 나눴는가"라는 정보가 사라지므로 경우의 수가 폭발하지 않는다. 시간은 글자 하나당 상태 수 m 이하이고, 되돌아가기가 없으니 전체는 `O(n*m)`이다. n은 입력 길이, m은 패턴 크기다.

```text
// Thompson 시뮬레이션
states = closure({start})
for ch in s:
    states = closure(step(states, ch))   // 상태 집합 전체를 한 번에 전진
    if states is empty: return false
return ACCEPT in states
```

Cox의 글에 나온 수치가 차이를 잘 보여 준다. 패턴 `a?` n개 뒤에 `a` n개를 붙인 정규식을 `a` n개짜리 문자열에 적용하면, 백트래킹 엔진은 `?`의 선택 조합 2^n가지를 시도한다. n이 29일 때 Perl은 60초 넘게 걸렸고, Thompson 방식의 NFA 구현은 약 20마이크로초에 끝났다. 글은 이를 약 백만 배 차이로 설명한다. n이 100이면 Thompson 구현은 200마이크로초 미만인데, 백트래킹은 10의 15제곱 년이 넘게 걸린다고 한다.

DFA(결정적 유한 오토마타, deterministic finite automaton)는 한 상태에서 글자 하나를 읽으면 갈 곳이 하나뿐인 기계다. 상태 집합 하나를 DFA 상태 하나로 보고 캐싱해 두면 글자당 비용을 더 줄일 수 있다. 필요한 상태만 그때그때 만드는 이 방식을 lazy DFA라 한다. RE2, Go의 `regexp`, Rust의 `regex` 크레이트가 이처럼 유한 오토마타로 매칭하는 계열이고, Go와 Rust 문서는 입력 길이에 선형인 시간을 보장한다고 명시한다.

## 5. 트레이드오프: 안전한 시간 vs 풍부한 기능

두 방식은 어느 쪽이 낫다기보다 무엇을 포기하느냐가 다르다.

| 항목 | 백트래킹 엔진 | Thompson/DFA 계열 |
|---|---|---|
| 대표 구현 | PCRE, Java, Python `re`, JavaScript | RE2, Go, Rust `regex` |
| 최악 시간 | 지수 가능 | `O(n*m)` 보장 |
| 역참조, lookaround | 지원 | 대부분 미지원 |
| 단순한 패턴의 평균 속도 | 빠름 | 안정적이고 DFA 캐싱 시 매우 빠름 |
| 메모리 | 재귀 깊이와 스택 | 상태 집합과 DFA 캐시 크기 관리 필요 |
| 사용자 입력을 패턴이나 대상으로 받을 때 | ReDoS 위험 | 시간 상한을 예측할 수 있음 |

선형 시간 엔진이 역참조를 지원하지 못하는 이유는 상태의 정의에 있다. 역참조 `\1`은 "앞에서 매칭된 바로 그 문자열"을 요구한다. 그러면 현재 상태만으로는 부족하고, 앞에서 무엇을 캡처했는지까지 상태에 포함되어야 한다. Cox에 따르면 역참조가 있는 매칭은 NP-완전(NP-complete) 문제다. 다항 시간 알고리즘이 알려져 있지 않으므로, 상태 집합만 따라가는 방식에는 넣을 수 없다.

그래서 실무에서는 "기능이 필요한가, 최악 시간 보장이 필요한가"를 먼저 정한다. 외부 사용자가 패턴이나 입력을 마음대로 넣는 곳이라면 선형 엔진이 안전한 기본값이다.

## 6. 실제 장애: Cloudflare 2019-07-02

이 문제는 이론에 머물지 않았다. 2019년 7월 2일, Cloudflare는 WAF(웹 방화벽, web application firewall) 관리형 규칙 업데이트에 들어간 정규식 하나 때문에 큰 장애를 겪었다. 공식 포스트모템에서 확인한 내용은 다음과 같다.

- 13:42 UTC에 배포가 시작되었고, 포스트모템은 원인을 XSS 탐지 규칙에 들어간 과도하게 백트래킹하는 정규식으로 꼽는다. 문제 구간으로 지목된 조각은 `.*(?:.*=.*)`이다. 한 패턴 안에서 `.*`가 겹쳐 나오면 "어디까지를 앞의 `.*`가 먹고 어디부터 뒤의 `.*`가 먹는가"가 모호해져 1절의 `(a+)+`와 같은 구조가 된다.
- HTTP/HTTPS를 처리하는 CPU가 거의 100%까지 치솟았다. 코어가 남은 서버도 처리 프로세스에 닿지 못해 502 오류를 돌려줬고, Cloudflare는 트래픽의 약 80%를 잃었다고 밝혔다.
- 규칙은 "simulate" 모드로 배포됐지만, 실제 트래픽에 대해 정규식은 그대로 실행됐다.
- 규칙은 점진 배포 없이 전 세계에 한꺼번에 퍼졌다. 표준 운영 절차가 전역 배포를 허용했고, 단계적으로 내보내는 일반 소프트웨어 배포 절차를 건너뛴 것이다.
- 14:02에 WAF 전체를 끄는 글로벌 종료(global terminate)가 제안되어 14:07에 실행됐고, 14:09에 트래픽과 CPU가 정상으로 돌아왔다. 총 27분이다. WAF는 한 도시에서 시험한 뒤 14:52에 전 세계에서 다시 켰다.
- 몇 주 전 WAF 리팩터링 중 정규식의 과도한 CPU 사용을 막는 보호 장치가 실수로 빠져 있었다. 한 가지 원인이 아니라 여러 원인이 겹친 사고였다.

개선 항목으로는 CPU 보호 장치 복구, 3,868개 WAF 관리형 규칙 전수 점검, 규칙별 성능 프로파일링을 테스트에 추가, 시간 보장이 있는 re2나 Rust 정규식 엔진으로 전환, 점진 배포 도입이 올라왔다.

교훈은 두 층이다. 정규식 자체는 백트래킹 엔진의 구조적 약점을 건드렸다. 배포 방식은 설정 변경도 코드 배포만큼 단계적으로 내보내야 한다는 점을 보여 준다.

## 7. ReDoS를 만났을 때: 진단과 방어

이런 문제를 ReDoS(Regular expression Denial of Service)라 한다. 서비스를 멈추게 하는 입력으로 정규식을 공격하는 것이다. 위험한 패턴의 전형은 세 가지다.

- 중첩된 반복: `(a+)+`
- 겹치는 선택지의 반복: `(a|aa)+`
- 모호하게 이어지는 `.*` 연쇄

증상은 특정 요청만 응답이 오지 않고, 해당 스레드의 CPU가 100%에 붙으며, 입력을 한두 글자 늘렸더니 시간이 폭증하는 것이다. Node.js처럼 이벤트 루프가 하나뿐인 환경에서는 서버 전체가 멈춘다.

원인을 의심할 때의 진단 순서는 간단하다. 느린 요청의 입력을 재현하고, 길이를 조금씩 늘려 시간이 지수로 늘어나는지 본다. 스레드 덤프나 프로파일러에서 정규식 엔진 프레임이 상위에 있는지도 확인한다.

방어는 층층이 쌓는다.

| 방어 | 효과 | 주의점 |
|---|---|---|
| 패턴 고치기(중첩 수량자 제거) | 근본 해결 | 의미가 같은지 테스트 필요 |
| atomic group, possessive quantifier | 한 번 매칭한 부분을 확정해 되돌아가기 금지, 분할 경우의 수 제거 | 매칭 의미가 바뀔 수 있다 |
| 입력 길이 제한 | 지수의 밑을 작게 유지 | 근본 해결은 아님 |
| 매칭 타임아웃 | 폭주를 끊음 | 엔진이 지원해야 한다(지원하지 않는 엔진이 많다) |
| 선형 엔진으로 전환 | 최악 시간 보장 | 역참조, lookaround 포기 |

배포 쪽에서는 카나리·점진 배포, CPU와 지연 지표에 따른 자동 롤백, 위험한 기능을 즉시 끄는 킬 스위치, 배포 전에 최악 입력으로 하는 성능 테스트가 필요하다. Cloudflare 사례가 바로 이 목록의 반대 사례다.

## 결론

- 정규식은 NFA로 바뀌어 실행되고, 실행 방식에 따라 최악 시간이 달라진다.
- 백트래킹 엔진은 길을 하나씩 가 보므로, 모호한 패턴과 "거의 맞지만 끝에서 실패하는" 입력이 만나면 시도 횟수가 `2^(n-1)`처럼 폭발한다.
- Thompson 방식은 상태 집합을 한꺼번에 전진시켜 `O(n*m)`을 보장한다. 대신 역참조 같은 기능을 포기한다.
- Cloudflare 장애는 정규식의 약점과 전역 동시 배포가 겹친 결과였다. 사용자 입력이 닿는 곳에는 선형 엔진을, 설정 배포에는 단계적 롤아웃과 킬 스위치를 둔다.
