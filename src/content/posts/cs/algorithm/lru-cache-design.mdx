## 개요

[앞 글](/posts/cs/algorithm/hash-table)에서는 해시 테이블이 키 하나를 평균 O(1)에 찾는 원리를 봤다. 이번 글은 해시 테이블에 연결 리스트를 붙여서 만드는 대표적인 자료구조, LRU 캐시를 직접 설계한다.

이 글이 답하는 질문은 두 가지다.

- 캐시가 꽉 찼을 때 "가장 오래 안 쓴 것"을 O(1)에 찾아 버리려면 어떤 구조가 필요한가?
- 실제 시스템(Java, Redis, Caffeine)은 왜 교과서 LRU를 그대로 쓰지 않는가?

---

## 1. 캐시가 꽉 차면 무엇을 버릴까

캐시는 크기가 정해져 있다. 메모리를 무한히 쓸 수 없으니 상한(capacity)을 둔다. 상한에 도달한 상태에서 새 항목이 들어오면 기존 항목 하나를 내보내야 한다.

이 동작을 축출(eviction)이라고 한다. 무엇을 내보낼지 정하는 규칙이 축출 정책(eviction policy)이다. 정책이 나쁘면 곧 다시 쓸 항목을 버리게 되고, 캐시 적중률(hit ratio)이 떨어져 결국 DB로 요청이 쏟아진다.

대표적인 정책 세 가지를 한 줄씩 비교하면 이렇다.

| 정책 | 버리는 항목 | 기대는 가정 | 약점 |
| --- | --- | --- | --- |
| FIFO (First In First Out) | 가장 먼저 들어온 항목 | 오래된 데이터는 덜 쓴다 | 자주 쓰는 항목도 순서가 되면 버린다 |
| LRU (Least Recently Used) | 마지막 사용이 가장 오래된 항목 | 최근에 쓴 것은 곧 또 쓴다 | 한 번 훑고 마는 대량 조회에 핫 데이터가 밀린다 |
| LFU (Least Frequently Used) | 사용 횟수가 가장 적은 항목 | 많이 쓴 것은 계속 쓴다 | 예전에 많이 쓴 항목이 계속 남는다 |

LRU가 가장 널리 쓰이는 이유는 "최근에 쓴 데이터는 곧 다시 쓴다"는 시간 지역성(temporal locality)이 대부분의 서비스에서 잘 맞기 때문이다. 인기 상품, 로그인한 사용자 세션처럼 일부 키에 접근이 몰리는 패턴에서 특히 잘 동작한다.

정책끼리의 적중률 비교와 Belady 모순은 [페이지 교체 알고리즘 글](/posts/cs/os/page-replacement-algorithms)에서 다뤘다. 이 글은 LRU를 **어떻게 빠르게 구현하는가**에 집중한다.

## 2. 요구사항: get과 put을 O(1)로

캐시는 요청 경로 한가운데 있다. 모든 요청이 캐시를 거치므로 캐시 연산이 느리면 서비스 전체가 느려진다. 캐시를 쓰는 이유가 빠르게 응답하기 위해서인데, 캐시가 항목 수에 비례해 느려지면 의미가 없다.

그래서 목표는 한 문장이다. **`get`과 `put`을 항목 수와 무관하게 O(1)에 끝낸다.**

두 연산의 동작을 정확히 적어 보자.

- `get(key)`: 키가 있으면 값을 돌려주고, 그 키를 "가장 최근에 쓴 항목"으로 표시한다. 없으면 `null`을 돌려준다.
- `put(key, value)`: 키가 이미 있으면 값을 바꾸고 가장 최근 항목으로 표시한다. 없으면 새로 넣는데, 꽉 차 있으면 가장 오래 안 쓴 항목을 먼저 버린다.

여기서 중요한 점은 **`get`도 순서를 바꾼다**는 것이다. 읽기만 했는데 내부 상태가 변한다. 이 사실은 8절의 동시성 문제로 그대로 이어진다.

이 동작을 O(1)에 하려면 세 가지가 모두 O(1)이어야 한다.

1. 키로 항목 찾기
2. 항목 하나를 "가장 최근" 자리로 옮기기
3. "가장 오래된" 항목을 찾아서 지우기

## 3. 해시맵만으로도, 리스트만으로도 안 되는 이유

자료구조 하나로 세 가지를 다 해결할 수 있는지부터 보자.

**해시맵만 쓰는 경우.** 각 항목에 마지막 사용 시각을 함께 저장한다고 하자. 1번(찾기)과 2번(시각 갱신)은 O(1)이다. 그런데 3번이 문제다. 가장 오래된 시각을 가진 항목을 찾으려면 전부 훑어야 한다. 항목이 100만 개면 축출 한 번에 100만 번 비교한다.

**리스트만 쓰는 경우.** 사용한 순서대로 줄을 세우면 3번은 쉽다. 맨 끝이 가장 오래된 항목이다. 하지만 1번이 O(n)이다. 키 하나를 찾으려면 리스트를 처음부터 따라가야 한다.

**시각 + 힙(heap)을 쓰는 경우.** 최소 힙은 가장 작은 값을 항상 맨 위에 두는 트리 구조다([힙과 타이밍 휠 글](/posts/cs/algorithm/heap-timing-wheel)에서 자세히 다룬다). 마지막 사용 시각을 기준으로 최소 힙을 만들면 가장 오래된 항목은 바로 보인다. 그러나 `get` 때마다 시각이 바뀌므로 힙 안의 위치를 고쳐야 하고, 이것이 O(log n)이다.

| 구조 | 키로 찾기 | 최근으로 옮기기 | 가장 오래된 것 지우기 |
| --- | --- | --- | --- |
| 해시맵 + 시각 | O(1) | O(1) | O(n) |
| 연결 리스트 | O(n) | O(1) (노드를 이미 알면) | O(1) |
| 해시맵 + 힙 | O(1) | O(log n) | O(log n) |
| 해시맵 + 이중 연결 리스트 | O(1) | O(1) | O(1) |

표에서 보듯이 해시맵은 "찾기"에 강하고 리스트는 "순서"에 강하다. 둘의 약점이 겹치지 않는다. 그래서 **두 구조를 동시에 들고, 해시맵이 리스트의 노드를 직접 가리키게 한다.**

## 4. 해시맵 + 이중 연결 리스트 구조

핵심 아이디어는 이것이다. **리스트는 사용 순서를 들고, 해시맵은 키에서 리스트 노드로 가는 지름길을 든다.**

용량 2인 캐시에 B와 A가 들어 있는 모습을 그리면 이렇다. 왼쪽이 가장 최근, 오른쪽이 가장 오래된 쪽이다.

```text
                 map["B"]             map["A"]
                    |                    |
                    v                    v
+------+       +---------+          +---------+       +------+
| head | <---> | B  |  2 |  <---->  | A  |  1 | <---> | tail |
+------+       +---------+          +---------+       +------+
 dummy         most recent          least recent       dummy
```

각 노드는 네 칸을 가진다.

```text
+------+-----+-------+------+
| prev | key | value | next |
+------+-----+-------+------+
```

세 가지 설계 결정에는 각각 이유가 있다.

**왜 이중(doubly) 연결 리스트인가.** 노드를 리스트 중간에서 빼려면 앞 노드의 `next`를 고쳐야 한다. 단일 연결 리스트는 앞 노드를 모르므로 처음부터 따라가 찾아야 하고, 이것이 O(n)이다. `prev` 포인터가 있으면 앞 노드를 바로 알 수 있어 O(1)에 뺄 수 있다.

**왜 노드에 key를 다시 저장하는가.** 값만 있으면 될 것 같지만, 축출할 때 문제가 생긴다. 리스트 끝에서 지울 노드를 골랐으면 해시맵에서도 지워야 한다. 그러려면 그 노드의 키를 알아야 한다. 노드에 키가 없으면 해시맵 전체를 뒤져야 한다.

**왜 더미(dummy) head와 tail을 두는가.** 더미 노드는 데이터를 담지 않고 양 끝에 항상 붙어 있는 경계 노드다. 더미가 없으면 "리스트가 비었을 때", "첫 노드를 지울 때", "마지막 노드를 지울 때"마다 `null` 검사와 head/tail 갱신 분기가 따로 필요하다. 더미가 있으면 모든 실제 노드에 항상 앞뒤 이웃이 있으므로 삽입과 삭제가 분기 없이 같은 네 줄로 끝난다.

## 5. Kotlin 구현

위 구조를 그대로 코드로 옮긴다. 리스트 연산은 세 개면 충분하다. 맨 앞에 붙이기(`addFront`), 떼어 내기(`unlink`), 그리고 둘을 합친 맨 앞으로 옮기기(`moveToFront`)다.

```kotlin
class LruCache<K, V>(private val capacity: Int) {

    init {
        require(capacity > 0) { "capacity must be positive" }
    }

    private class Node<K, V>(val key: K?, var value: V?) {
        var prev: Node<K, V>? = null
        var next: Node<K, V>? = null
    }

    private val map = HashMap<K, Node<K, V>>()
    private val head = Node<K, V>(null, null) // 가장 최근 쪽 더미
    private val tail = Node<K, V>(null, null) // 가장 오래된 쪽 더미

    init {
        head.next = tail
        tail.prev = head
    }

    val size: Int get() = map.size

    fun get(key: K): V? {
        val node = map[key] ?: return null
        moveToFront(node)
        return node.value
    }

    fun put(key: K, value: V) {
        val node = map[key]
        if (node != null) {          // 이미 있는 키: 값만 바꾸고 최근으로
            node.value = value
            moveToFront(node)
            return
        }
        if (map.size == capacity) {  // 꽉 찼으면 가장 오래된 노드를 버린다
            val lru = tail.prev!!
            unlink(lru)
            map.remove(lru.key)
        }
        val created = Node(key, value)
        map[key] = created
        addFront(created)
    }

    private fun addFront(node: Node<K, V>) {
        node.prev = head
        node.next = head.next
        head.next!!.prev = node
        head.next = node
    }

    private fun unlink(node: Node<K, V>) {
        node.prev!!.next = node.next
        node.next!!.prev = node.prev
        node.prev = null
        node.next = null
    }

    private fun moveToFront(node: Node<K, V>) {
        unlink(node)
        addFront(node)
    }
}
```

더미 노드는 키와 값이 없으므로 `Node`의 `key`와 `value`를 nullable로 두었다. 실제 노드는 항상 값이 채워져 있다. `put`에서 축출을 새 노드 삽입보다 **먼저** 하므로 캐시 크기는 한순간도 `capacity`를 넘지 않는다.

모든 연산이 해시맵 조회 한 번과 포인터 몇 개 수정으로 끝난다. 반복문이 없으니 `get`과 `put` 모두 O(1)이다(해시맵 조회는 평균 O(1)이다).

### 손으로 따라가기: 용량 2

용량 2인 캐시에 아래 연산을 순서대로 실행한다. 리스트는 왼쪽이 가장 최근, 오른쪽이 가장 오래된 쪽이다(더미는 생략했다).

| 단계 | 연산 | 결과 | 리스트(최근 -> 오래된) | 해시맵 키 |
| --- | --- | --- | --- | --- |
| 1 | `put(A, 1)` | 새로 삽입 | A | A |
| 2 | `put(B, 2)` | 새로 삽입 | B, A | A, B |
| 3 | `get(A)` | 1, A를 앞으로 | A, B | A, B |
| 4 | `put(C, 3)` | 꽉 참, 끝의 B 축출 후 삽입 | C, A | A, C |
| 5 | `get(B)` | `null` (이미 축출됨) | C, A | A, C |
| 6 | `put(A, 10)` | 기존 키, 값 교체 후 앞으로 | A, C | A, C |
| 7 | `put(D, 4)` | 꽉 참, 끝의 C 축출 후 삽입 | D, A | A, D |

3단계가 LRU의 핵심이다. A가 B보다 먼저 들어왔지만 방금 읽혔으므로 살아남는다. 같은 연산을 FIFO로 돌렸다면 4단계에서 A가 버려졌을 것이다.

3단계에서 포인터가 실제로 어떻게 바뀌는지 따라가 보자. 시작 상태는 `head <-> B <-> A <-> tail`이다.

1. `unlink(A)`: A의 앞인 B의 `next`를 A의 뒤인 `tail`로 바꾼다. `tail.prev`는 B로 바꾼다. 이제 리스트는 `head <-> B <-> tail`이다.
2. `addFront(A)`: `A.prev = head`, `A.next = B`로 둔다.
3. 원래 첫 노드인 B의 `prev`를 A로 바꾼다.
4. `head.next`를 A로 바꾼다. 결과는 `head <-> A <-> B <-> tail`이다.

4단계의 축출도 짚어 보자. 리스트가 `head <-> A <-> B <-> tail`이고 크기가 2다. `tail.prev`는 B이므로 B를 `unlink`하고, B 노드에 저장해 둔 키 `"B"`로 해시맵에서도 지운다. 그다음 C를 맨 앞에 붙인다. 4절에서 노드에 키를 저장한 이유가 바로 이 순간이다.

이 구현은 위 표의 7단계를 그대로 확인하는 테스트와, 용량 1~5에서 무작위 연산 2만 번씩을 Java `LinkedHashMap`(다음 절)의 결과와 비교하는 테스트를 로컬 `kotlinc`로 컴파일해 통과시켰다.

## 6. Java LinkedHashMap으로 대신하기

직접 짜는 것은 원리를 이해하는 데 좋지만, JVM에서는 이미 같은 구조가 표준 라이브러리에 있다. `LinkedHashMap`은 해시 테이블의 모든 항목을 이중 연결 리스트로 꿰어 둔 맵이다.

핵심은 생성자의 세 번째 인자 `accessOrder`와 `removeEldestEntry` 메서드다.

```java
class LruCache<K, V> extends LinkedHashMap<K, V> {
    private final int capacity;

    LruCache(int capacity) {
        super(16, 0.75f, true);  // accessOrder = true
        this.capacity = capacity;
    }

    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > capacity;
    }
}
```

**`accessOrder = true`.** 기본값 `false`는 삽입 순서를 유지한다. `true`로 주면 접근 순서를 유지한다. 접근한 항목이 순서의 맨 뒤로 가므로, 맨 앞이 가장 오래 안 쓴 항목(eldest)이 된다. 5절의 구현과 방향이 반대일 뿐 같은 구조다.

**`removeEldestEntry`.** `put`과 `putAll`이 새 항목을 넣은 **뒤에** 호출한다. `true`를 돌려주면 맵이 맨 앞 항목을 지운다. 기본 구현은 항상 `false`라서 아무것도 지우지 않는다. 위 코드는 Javadoc의 예시와 같은 방식이다. 5절 구현과 달리 순간적으로 `capacity + 1`개가 되었다가 줄어든다는 차이가 있다.

무엇이 "접근"인지도 정확히 알아야 한다. Javadoc에 따르면 다음 메서드만 접근으로 친다.

- `get`, `getOrDefault`, `put`, `putIfAbsent`, `compute`, `computeIfAbsent`, `computeIfPresent`, `merge`
- `replace`는 값이 실제로 바뀔 때만 접근이다.
- `keySet`, `values`, `entrySet` 같은 뷰를 순회하는 것은 순서를 바꾸지 않는다.
- Java 21에 추가된 `putFirst`, `putLast`는 위치를 직접 정할 뿐 접근으로 치지 않는다.

가장 조심할 점은 스레드 안전성이다. `LinkedHashMap`은 동기화되어 있지 않다. 게다가 Javadoc은 접근 순서 모드에서는 **`get`만 해도 구조 변경**(structural modification)이라고 명시한다. 읽기 전용으로만 쓰는 것 같아도 여러 스레드가 동시에 `get`하면 내부 리스트가 깨질 수 있다. 문서가 권하는 방법은 `Collections.synchronizedMap`으로 감싸는 것인데, 이러면 모든 연산이 락 하나를 거친다. 이 문제는 8절에서 다시 본다.

## 7. 실제 시스템의 근사 LRU

정확한 LRU는 접근할 때마다 리스트를 고쳐야 하고, 항목마다 `prev`와 `next` 포인터를 들고 있어야 한다. 64비트 포인터라면 두 개에 16바이트다. 작은 키가 수억 개인 시스템에서는 이 메타데이터만으로 상당한 메모리를 쓴다.

그래서 큰 시스템은 정확한 순서를 포기하고 **"대체로 오래된 것"을 싸게 고르는** 근사(approximation)를 쓴다.

### Redis: 샘플링 LRU

Redis는 `maxmemory` 상한에 도달하면 `maxmemory-policy`에 따라 키를 축출한다. 정책 종류 비교는 [Redis 비교 글](/posts/dev/cache/redis-summary)에 정리되어 있으니, 여기서는 `allkeys-lru`가 **어떻게** 동작하는지만 본다.

Redis 문서에 따르면 Redis는 정확한 LRU를 계산하지 않는다. 키를 몇 개 무작위로 뽑아서 그중 마지막 접근이 가장 오래된 키를 축출한다. 문서는 정확한 LRU를 쓰지 않는 이유로 메모리 비용을 든다. 모든 키를 하나의 순서로 엮어 두지 않아도 되니 키마다 붙는 메타데이터가 줄어든다.

뽑는 개수는 `maxmemory-samples`로 정하고 기본값은 5다. 숫자로 감을 잡아 보자. 순수 무작위 샘플링만 한다고 가정하면, 축출된 키가 "최근에 쓴 절반"에 속하려면 뽑힌 5개가 모두 최근 절반이어야 한다. 그 확률은 0.5의 5제곱, 약 3.1%다. 샘플을 10개로 늘리면 약 0.1%로 떨어진다.

여기에 Redis 3.0부터는 축출 후보를 모아 두는 풀(pool)을 함께 유지한다. 이전 샘플링에서 본 좋은 후보를 버리지 않고 기억해 두므로 정확한 LRU에 더 가까워진다.

`redis.conf`의 설명은 트레이드오프를 그대로 보여 준다. 기본값 5로 충분히 좋은 결과가 나오고, 10은 정확한 LRU에 매우 가깝지만 CPU를 더 쓰며, 3은 빠르지만 덜 정확하다. 최댓값은 64다.

| `maxmemory-samples` | 정확도 | 축출 1회 비용 |
| --- | --- | --- |
| 3 | 낮음 | 가장 쌈 |
| 5 (기본값) | 충분히 좋음 | 보통 |
| 10 | 정확한 LRU에 매우 가까움 | CPU 더 씀 |

운영에서 하나 더 기억할 것이 있다. `maxmemory-policy`의 기본값은 `noeviction`이다. 이 정책은 키를 버리지 않고 쓰기 명령에 에러를 돌려준다. Redis를 캐시로 쓴다면 정책을 명시적으로 바꿔야 LRU 축출이 일어난다.

### 리눅스: Clock

운영체제의 페이지 교체도 같은 이유로 정확한 LRU를 쓰지 않는다. 메모리 접근마다 리스트를 고치는 것은 불가능에 가깝기 때문이다. 대신 하드웨어가 켜 주는 참조 비트 1개만 보고 시계 바늘을 돌리는 Clock 알고리즘을 쓴다. 자세한 동작은 [페이지 교체 알고리즘 글](/posts/cs/os/page-replacement-algorithms)에서 다뤘다.

두 근사의 공통점은 같다. **접근 경로의 비용을 거의 0으로 만들고, 그 대가로 축출 순간의 정확도를 조금 포기한다.**

## 8. 동시성: 락 하나가 병목이 되는 문제

5절의 구현을 여러 스레드에서 쓰려면 어떻게 해야 할까. 가장 쉬운 방법은 `get`과 `put` 전체를 락 하나로 감싸는 것이다.

문제는 2절에서 본 사실, **`get`도 쓰기**라는 점이다. 일반적인 맵은 읽기끼리 동시에 진행해도 안전하다. 그런데 LRU에서는 읽을 때마다 노드를 리스트 맨 앞으로 옮긴다. 그래서 읽기 락과 쓰기 락을 나눠도 소용이 없고, 모든 `get`이 같은 배타 락을 잡아야 한다.

결과적으로 캐시 적중이 많을수록, 즉 캐시가 잘 동작할수록 락 경합이 심해진다. 코어가 32개여도 캐시 연산은 한 번에 하나씩만 진행된다. Caffeine의 설계 문서도 이 점을 짚는다. 접근할 때마다 리스트를 수정해야 하는데, 이 수정은 동시에 효율적으로 처리하기 어렵다는 것이다.

### 흔한 대안: 샤딩

캐시를 키의 해시값으로 N개 조각(shard)으로 나누고, 조각마다 독립된 LRU와 락을 둔다. 키가 조각에 고르게 퍼지면 락 하나를 두고 다투는 스레드가 대략 N분의 1로 준다. 대신 축출은 조각 안에서만 LRU다. 전체로 보면 가장 오래된 키가 아니라 "그 조각에서" 가장 오래된 키가 나간다. 이것도 일종의 근사다.

### Caffeine: 읽기를 기록만 하고 나중에 반영한다

Java 캐시 라이브러리 Caffeine은 다른 길을 택했다. 핵심 아이디어는 **읽기 때 리스트를 바로 고치지 않고, 읽었다는 사실만 버퍼에 남겨 뒀다가 나중에 한꺼번에 반영한다**는 것이다.

1. `get`은 동시성 해시맵에서 값을 찾고, "이 항목을 읽었다"는 이벤트를 읽기 버퍼(read buffer)에 넣는다. 읽기 버퍼는 스레드별 해시로 고른 여러 줄(stripe)로 나뉘어 있어 스레드끼리 덜 부딪힌다.
2. 읽기 버퍼는 손실을 허용한다(lossy). 버퍼가 꽉 차면 이벤트 일부를 버린다. 이 이벤트는 적중률을 높이는 데만 쓰이므로 조금 잃어도 정확성에는 문제가 없다.
3. 쓰기 이벤트는 잃으면 안 되므로 별도의 쓰기 버퍼에 넣는다.
4. 버퍼가 차면 한 스레드만 락을 잡고 쌓인 이벤트를 축출 정책에 일괄 반영한다. 이미 다른 스레드가 락을 잡고 있으면 기다리지 않고 지나간다. 이 정리 작업은 설정된 executor에 넘겨 처리한다.

이렇게 하면 락은 여전히 하나지만 요청 경로에서 그 락을 기다리는 일은 거의 없어진다.

### Caffeine의 정책: W-TinyLFU

Caffeine은 축출 정책도 순수 LRU가 아니다. LRU는 한 번 훑고 마는 대량 조회에 약하고, LFU는 과거 인기에 오래 묶인다. W-TinyLFU는 둘을 섞는다.

- 새 항목은 먼저 작은 LRU 구역인 윈도(admission window)에 들어간다.
- 윈도에서 밀려난 항목은 큰 Segmented LRU 구역(main space)으로 들어가려 한다. 이때 TinyLFU 승인 정책(admission policy)이 들여보낼지 결정한다.
- 판단 근거는 빈도 스케치(frequency sketch)다. 항목마다 정확한 카운터를 두는 대신, 4비트 카운터를 쓰는 Count-Min Sketch로 과거 사용 빈도를 확률적으로 추정한다. 확률적 자료구조는 [확률적 자료구조 글](/posts/cs/algorithm/probabilistic-data-structures)에서 다룬다.
- 윈도와 메인 구역의 크기 비율은 고정이 아니라 hill climbing 최적화로 적응적으로 정한다.

정리하면 Caffeine은 "최근성은 작은 윈도가, 빈도는 스케치가" 맡도록 나눴다. 그리고 동시성 문제는 정책과 분리해 버퍼로 풀었다.

| 방식 | `get` 비용 | 정확도 | 동시성 |
| --- | --- | --- | --- |
| 직접 구현 + 락 1개 | O(1) + 배타 락 | 정확한 LRU | 모든 연산이 직렬화 |
| `synchronizedMap(LinkedHashMap)` | 위와 같음 | 정확한 LRU | 모든 연산이 직렬화 |
| 샤딩 LRU | O(1) + 조각 락 | 조각 안에서만 LRU | 조각 수만큼 병렬 |
| Redis 샘플링 | 접근 시각 기록만 | 근사 LRU | 단일 스레드 명령 처리 |
| Caffeine | 버퍼에 이벤트 기록 | W-TinyLFU | 요청 경로에서 락 대기 거의 없음 |

## 결론

- LRU 캐시는 "찾기"에 강한 해시맵과 "순서"에 강한 이중 연결 리스트를 함께 들고, 해시맵이 리스트 노드를 직접 가리키게 해서 `get`과 `put`을 O(1)로 만든다.
- 이중 연결이어야 노드를 O(1)에 뗄 수 있고, 노드에 키가 있어야 축출 때 해시맵에서도 지울 수 있으며, 더미 노드가 있어야 경계 분기가 사라진다.
- JVM에서는 `LinkedHashMap(accessOrder = true)`과 `removeEldestEntry`로 같은 구조를 바로 얻지만, 접근 순서 모드에서는 `get`도 구조 변경이라 스레드 안전하지 않다.
- Redis와 리눅스는 메모리와 접근 비용 때문에 정확한 LRU 대신 샘플링과 Clock 같은 근사를 쓴다.
- LRU의 진짜 약점은 읽기가 곧 쓰기라는 점이다. Caffeine은 읽기를 버퍼에 기록해 두고 나중에 반영하는 방식으로 락 경합을 피하고, 정책은 W-TinyLFU로 바꿔 적중률을 높였다.
