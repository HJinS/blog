## 개요

[앞 글](/posts/cs/algorithm/heap-timing-wheel)에서는 힙과 타이밍 휠로 "다음에 처리할 일"을 고르는 방법을 봤다. 이번 글은 데이터를 통째로 줄 세우는 정렬을 다룬다. 정렬은 이미 라이브러리 함수 한 줄이라 깊이 볼 일이 적다. 그래도 어떤 알고리즘이 들어 있는지 알아야 하는 순간이 온다. 결과 순서가 이상하거나, 정렬이 갑자기 느려지거나, 예외가 터질 때다.

이 글이 답하는 질문은 두 가지다.

- 정렬의 안정성(stability)은 무엇이고, 왜 퀵소트는 이를 지키지 못하는가?
- 표준 라이브러리는 왜 순수 퀵소트나 머지소트가 아니라 TimSort 같은 하이브리드를 쓰고, 그 TimSort에는 어떤 버그가 있었는가?

여기서 안정성은 "키가 같은 원소끼리 정렬 전 상대 순서를 그대로 유지하는 성질"이다. 마지막에 다룰 내용은 널리 쓰이고 오래 검증된 알고리즘에도 논리 구멍이 있었다는 실제 사례다.

## 1. 비교 정렬의 한계와 선택 기준

정렬 알고리즘을 비교하기 전에 하나만 짚고 가자. 원소끼리 "누가 앞인가"만 비교해서 순서를 정하는 방식을 비교 정렬(comparison sort)이라 한다. 퀵소트, 머지소트, 힙소트가 모두 여기에 속한다.

비교 정렬은 아무리 영리해도 최악의 경우 `n log n`번 가까운 비교가 필요하다. 이유는 이렇다. 원소 3개를 섞는 방법은 3! = 6가지다. 비교 한 번은 결과가 둘(앞/뒤) 중 하나이므로, 비교 2번으로는 최대 4가지만 구분한다. 6가지를 가려내려면 최소 3번이 필요하다. 원소가 n개면 가능한 순열은 n!개이고, 이를 가르는 데 필요한 비교 횟수는 `log₂(n!)`, 즉 `n log n` 규모다. 비교 대신 값 자체를 이용하는 계수 정렬이나 기수 정렬은 이 한계를 피한다. 대신 키가 작은 정수 같은 조건이 붙는다.

그러면 "다들 `n log n`이니 아무거나 쓰면 되나?" 그렇지 않다. 점근 복잡도(asymptotic complexity)가 같아도 실무에서는 다음이 갈린다.

| 기준 | 질문 |
|---|---|
| 안정성 | 같은 키의 순서가 유지되는가 |
| 추가 메모리 | 입력 외에 얼마나 더 쓰는가 |
| 최악 입력 | 특정 입력에서 `n²`로 무너지는가 |
| 부분 정렬 데이터 | 이미 어느 정도 정렬된 입력에서 빨라지는가 |

이 글의 나머지는 이 네 줄이 알고리즘마다 어떻게 다른지 따라가는 과정이다.

## 2. 안정성: 두 번 정렬해 보면 보인다

안정성이 왜 필요한지부터 보자. 사람 네 명의 목록이다.

```
(Cat, 30)  (Bob, 25)  (Amy, 30)  (Dan, 25)
```

"나이순으로 정렬하되, 나이가 같으면 이름순"으로 만들고 싶다. 한 번에 비교 함수를 짜는 방법도 있지만, 정렬을 두 번 하는 방법도 흔하다. 덜 중요한 키로 먼저 정렬하고, 더 중요한 키로 다시 정렬한다.

```
1) 이름순 정렬:  (Amy,30) (Bob,25) (Cat,30) (Dan,25)
2) 나이순 정렬:  ???
```

2단계의 결과는 정렬 알고리즘이 안정적인지에 따라 달라진다.

```
stable:    (Bob,25) (Dan,25) (Amy,30) (Cat,30)    names stay in order
unstable:  (Dan,25) (Bob,25) (Cat,30) (Amy,30)    names may swap
```

나이가 같은 사람끼리 1단계의 이름 순서가 남아야 원하는 결과다. 안정 정렬은 이를 보장하고, 불안정 정렬은 보장하지 않는다. 두 번째 결과도 "나이순"으로는 틀리지 않았다. 틀린 것은 우리가 기대한 이름 순서다. 그래서 이 문제는 테스트에서 가끔만 드러난다.

Python 공식 문서도 같은 방식을 권한다. 정렬이 안정적이므로 보조 키로 먼저 정렬하고 주 키로 다시 정렬하면 복합 정렬이 된다고 설명한다. Java의 `Arrays.sort(Object[])`도 안정성을 명세로 보장한다.

기본 타입 배열은 사정이 다르다. `int[]`에서는 값이 같은 두 원소를 구분할 방법이 없다. 어느 3이 어느 3인지 알 수 없으니 순서가 바뀌어도 결과가 똑같다. 그래서 `int[]`처럼 안정성이 의미 없는 곳에는 더 빠른 불안정 정렬을 써도 된다. Java에서 `Arrays.sort(int[])`는 듀얼 피벗 퀵소트를, 객체 배열은 안정 정렬을 쓰는 이유가 여기에 있다.

## 3. 퀵소트: 빠르지만 두 가지를 내준다

### 동작

퀵소트(quicksort)의 핵심 아이디어는 한 문장이다. **피벗(pivot) 하나를 골라 작은 쪽과 큰 쪽으로 나눈 뒤, 양쪽을 재귀로 정렬한다.**

마지막 원소를 피벗으로 쓰는 간단한 분할을 `[5, 2, 8, 1, 9, 3]`에 적용해 보자. 피벗은 3이다.

```
[5, 2, 8, 1, 9, 3]   pivot = 3
 -> 3보다 작은 값(2, 1)을 앞으로 모으고, 피벗을 그 바로 뒤로 옮긴다
[2, 1, | 3 |, 5, 9, 8]
   small  p     large
```

피벗은 이 자리에서 최종 위치를 찾았다. 나머지 두 덩어리에 같은 작업을 반복한다. 나누는 과정에서 새 배열을 만들지 않아 제자리(in-place) 정렬이다. 값을 같은 배열 안에서 맞바꾸기 때문에 캐시 효율도 좋고 상수도 작다.

### 문제 1: 안정적이지 않다

위 분할은 멀리 있는 원소끼리 자리를 바꾼다. 같은 키가 둘 있으면 순서가 뒤집힐 수 있다. `[2a, 2b, 1]`을 마지막 원소 1을 피벗으로 분할하면 이렇게 된다.

```
[2a, 2b, 1]   pivot = 1
 -> 1을 맨 앞(첫 번째 큰 값 자리)과 맞바꾼다
[1, 2b, 2a]   2a and 2b swapped
```

값이 같은 2a와 2b의 순서가 바뀌었다. 퀵소트가 빠른 이유(멀리 있는 것끼리 바로 교환)와 불안정한 이유는 같은 뿌리다.

### 문제 2: 피벗이 나쁘면 O(n²)

피벗이 매번 한쪽으로 쏠리면 재귀가 균형 있게 나뉘지 않는다.

```
balanced pivot               skewed pivot
n                            n
n/2    n/2                   n-1
n/4 n/4 n/4 n/4              n-2
...                          ...
depth ~ log2 n               depth ~ n
```

고전적인 예가 이미 정렬된 입력에 첫 원소를 피벗으로 쓰는 경우다. 피벗이 항상 최솟값이라 한쪽은 비고 다른 쪽에 n-1개가 몰린다. 비교 횟수는 `(n-1) + (n-2) + ... + 1 = n(n-1)/2`다. n이 1,000이면 약 499,500번이다. 균형 잡힌 경우의 `n log₂ n`은 약 10,000번이니 50배 가까이 차이 난다. 재귀 깊이도 n까지 가서 스택 오버플로 위험이 생긴다.

더 나쁜 점은 이 쏠림을 일부러 만들 수 있다는 것이다. 피벗 선택 규칙이 예측 가능하면 공격자가 입력을 조작해 CPU를 `n²`로 태울 수 있다. 이를 알고리즘 복잡도 공격(algorithmic complexity attack)이라 한다. 외부 입력을 정렬하는 서비스는 피벗을 무작위로 고르거나 아래의 introsort 같은 방어가 있는지 확인해야 한다.

### 방어: Introsort

인트로소트(introsort)는 퀵소트로 시작하되, 재귀 깊이가 `2·log₂ n`을 넘으면 "쏠리고 있다"고 보고 힙소트로 갈아탄다. 힙소트(heapsort)는 원소를 [앞 글](/posts/cs/algorithm/heap-timing-wheel)의 힙에 모두 넣고 최솟값을 차례로 꺼내는 정렬로, 어떤 입력에서도 `n log n`이다. 작은 구간은 삽입 정렬로 마무리한다. 평균은 퀵소트만큼 빠르고, 최악도 `n log n`으로 막힌다. 안정성은 여전히 포기한 상태다.

## 4. 머지소트: 안정적이지만 메모리를 쓴다

머지소트(merge sort)의 핵심 아이디어도 한 문장이다. **반으로 나눠 각각 정렬한 뒤, 정렬된 두 덩어리를 앞에서부터 하나씩 비교하며 합친다.**

합치는 단계를 보자. 왼쪽 `[2, 5, 9]`와 오른쪽 `[1, 5, 7]`이다.

```
left   [2, 5, 9]     right [1, 5, 7]
step 1: 2 vs 1 -> 1      out: [1]
step 2: 2 vs 5 -> 2      out: [1, 2]
step 3: 5 vs 5 -> 5(L)   out: [1, 2, 5L]    tie: take left first
step 4: 9 vs 5 -> 5(R)   out: [1, 2, 5L, 5R]
...
```

세 번째 단계가 안정성의 핵심이다. 값이 같으면 항상 왼쪽을 먼저 꺼낸다. 왼쪽 원소는 원래 앞에 있었으므로 순서가 지켜진다. 멀리 있는 원소를 교환하지 않고 앞에서부터 차례로 옮기기 때문이다.

대가는 메모리다. 합치는 동안 결과를 담을 보조 공간이 필요해서 `O(n)`을 더 쓴다. 항상 `n log n`이고 안정적이지만, 퀵소트가 제자리로 해내는 일을 여분 메모리로 한다.

머지소트는 데이터를 순차로 읽고 쓰는 성질 덕분에 연결 리스트나 디스크 위의 정렬에 잘 맞는다. 메모리에 안 들어가는 데이터를 정렬하는 외부 정렬은 [외부 머지 소트](/posts/cs/algorithm/external-merge-sort)에서 따로 다룬다.

## 5. TimSort: 이미 있는 순서를 활용한다

### 왜 필요한가

현실의 데이터는 완전히 무작위인 경우가 드물다. 로그는 시간순으로 쌓이고, 어제 정렬해 둔 목록에 새 항목 몇 개가 붙는다. 이미 정렬된 구간이 많은데 퀵소트도 머지소트도 이를 모르는 척 처음부터 쪼갠다.

TimSort의 핵심 아이디어는 한 문장이다. **입력에서 이미 정렬된 구간(run)을 찾아 그대로 쓰고, 이 run들을 머지소트처럼 합친다.** Tim Peters가 Python용으로 만들었고, Java의 객체 정렬(`Arrays.sort(Object[])`)도 이를 가져다 쓴다. Java 문서는 이를 Python 리스트 정렬에서 가져온 안정적이고 적응형(adaptive)인 머지소트로 설명하고, 부분 정렬된 입력에서는 `n log n`보다 훨씬 적은 비교로 끝난다고 밝힌다.

### 단계별 동작

입력이 `[1, 2, 3, 4, 9, 8, 7, 5, 6, 10]`이라고 하자.

1. 앞에서부터 이미 정렬된 구간을 찾는다. `1 2 3 4 9`가 오름차순 run이다.
2. 다음 `8 7 5`는 내림차순이다. 내림차순 run은 뒤집어서 오름차순으로 만든다. 같은 값이 섞인 경우에는 안정성이 깨지지 않도록 엄격한 내림차순만 뒤집는다.
3. run이 너무 짧으면 합치는 비용 대비 이득이 없다. 정해둔 최소 길이(minrun)보다 짧으면 뒤의 원소를 삽입 정렬로 붙여 길이를 채운다. 짧은 구간에서는 삽입 정렬이 가장 빠르기 때문이다. CPython 문서는 minrun으로 32 안팎을 좋은 값으로 본다.
4. 만든 run을 스택(stack)에 쌓고, 규칙에 따라 인접한 run끼리 합친다.

완전히 정렬된 입력이면 run이 하나뿐이라 한 번 훑는 `O(n)`으로 끝난다. 최악은 `O(n log n)`이다. 합치기는 머지소트와 같은 방식이라 안정적이고, 최대 `O(n)`의 보조 메모리를 쓴다. 그래서 TimSort는 머지소트의 안정성을 가져오면서 "이미 정렬된 정도"에 따라 빨라진다.

### 왜 아무 run이나 합치지 않는가

run을 쌓는 순서대로 무조건 합치면 큰 run과 작은 run이 반복해서 합쳐진다. 크기 1,000짜리를 작은 run 하나와 합치는 데 1,000번 가까이 쓰고, 이를 계속 반복하면 비용이 커진다. 합칠 때는 크기가 비슷한 run끼리 합쳐야 머지소트의 균형 잡힌 트리와 비용이 같아진다.

그래서 원래 TimSort(지금의 Java 구현도 같다)는 스택에 쌓인 run 길이에 규칙을 건다. 이를 불변식(invariant)이라 부른다. 스택의 위쪽 세 run을 아래부터 A, B, C라 하면 다음 두 조건이다.

```
A > B + C
B > C
```

조건이 깨지면 이웃한 run을 합쳐 다시 맞춘다. 이 규칙이 지켜지면 각 run이 바로 위 두 run의 합보다 길어서, 아래로 갈수록 길이가 피보나치 수열처럼 불어난다. 따라서 스택 깊이는 입력 크기의 로그에 비례해 수십 단 이내로 묶인다. 구현은 이 사실을 믿고 스택 배열을 미리 고정 크기로 잡는다. 이 가정이 다음 절의 버그와 연결된다.

## 6. TimSort 불변식 버그

### 무슨 일이 있었나

2013년 CWI(네덜란드 국립 수학·컴퓨터과학 연구소)의 Stijn de Gouw와 Frank de Boer 등은 TimSort가 정말 올바른지 형식 증명(formal verification)을 시도했다. 증명 도구는 KeY였다. 그 과정에서 병합 스택의 불변식 검사가 불충분하다는 것을 발견했고, 2015년 2월 개선안과 함께 보고했다. 연구팀이 ERCIM News에 쓴 글은 Java의 `Collections.sort`, `Arrays.sort`, Android가 이 알고리즘을 쓰고, 같은 버그가 원조인 Python 구현에도 있었다고 밝힌다.

### 어디가 문제였나

Java 구현의 `mergeCollapse`는 불변식이 깨졌는지 스택 위쪽 세 run만 확인했다. 그런데 위쪽에서 병합이 일어나면 run 길이가 바뀌어 더 아래쪽 run 사이의 관계가 깨질 수 있다. 위쪽 세 개만 보는 검사는 이 위반을 보지 못한다.

아래는 이 상황을 보여 주는 예시용 상태다. 숫자는 설명을 위해 만들었고, 이 상태에 이르는 입력을 구성하는 방법은 논문의 몫이다.

```
bottom -> top
 Z=80   A=60   B=30   C=20

top three check (A, B, C):
  60 > 30 + 20 = 50   ok
  30 > 20             ok      -> "invariant holds"

one level down (Z, A, B), never checked:
  80 > 60 + 30 = 90   NO      -> violated, not detected
```

불변식이 조용히 깨진 채로 정렬이 계속되면 스택이 설계된 깊이보다 깊어질 수 있다. 앞서 본 것처럼 스택 배열의 크기는 "깊이는 로그 이내"라는 가정으로 정했기 때문이다. 가정이 깨진 입력, 즉 짧은 run이 많이 이어지는 특수한 입력에서는 run을 하나 더 쌓다가 배열 범위를 벗어난다.

### 실제 증상

결과는 `ArrayIndexOutOfBoundsException`이다. OpenJDK 이슈 JDK-8072909는 `mergeCollapse`가 불변식을 지키지 못해 `pushRun`에서 이 예외가 날 수 있다고 적는다. 제보자의 재현 코드는 원소 67,108,864개짜리 배열이다. 이 이슈는 JDK 9에서 고쳐졌고 8u60 등으로 백포트됐다. 이 이슈 이전에도 스택 배열을 키우는 식의 땜질이 있었으나 충분하지 않았다고 이슈에 적혀 있다.

### 수정과 교훈

논문팀의 제안은 위쪽 세 개 대신 네 개의 run까지 확인해 불변식을 복원하는 것이었다. 수정한 버전은 KeY로 다시 검증했다. 이 검증에는 200만 개가 넘는 추론 규칙이 쓰였다고 한다.

여기서 얻는 교훈은 구체적이다. 수년간 수많은 시스템에서 쓰이고 테스트된 알고리즘에도 "검사 범위가 충분한가"라는 논리 구멍이 있을 수 있다. 평범한 입력은 수없이 시험해도 이 구멍을 건드리지 않는다. 구멍은 특수한 입력에서만 드러나고, 그 입력을 찾아낸 것은 테스트가 아니라 증명을 시도하던 과정이었다.

참고로 최근 CPython의 정렬 문서(listsort.txt)는 병합 순서를 정하는 방식으로 파워소트(powersort)를 설명하고, 원래 불변식이 실제로는 유지되지 않는다는 사실이 컴퓨터가 만든 정확성 증명을 완성하려던 중 발견됐다고 적고 있다. 병합 정책은 계속 다듬어지는 중이다.

## 7. 실무에서 만나는 함정

### 일관되지 않은 Comparator

TimSort와 머지 기반 정렬은 비교 함수가 일관되다고 가정한다. 즉 a가 b보다 작고 b가 c보다 작으면 a는 c보다 작아야 하고(전이성), a와 b의 비교 결과와 b와 a의 비교 결과가 반대여야 한다(대칭성). 이를 어기면 정렬이 틀린 순서를 내거나 예외가 난다. Java 문서는 `Comparable`이나 `Comparator` 계약을 어긴 것이 발견되면 `IllegalArgumentException`을 던질 수 있다고 적는다. 던지는 것이 필수는 아니라서 어떤 경우엔 예외 없이 조용히 틀린 순서가 나온다.

흔한 실수는 비교 함수를 뺄셈으로 짜는 것이다.

```java
// a = 2_000_000_000, b = -2_000_000_000
comparator = (a, b) -> a - b;   // overflow: result is negative
// -> says a < b, but actually a > b
```

두 값의 차가 `int` 범위를 넘으면 부호가 뒤집힌다. 이 한 건의 모순이 정렬 중간에 다른 비교와 충돌하면서 계약 위반 예외나 잘못된 순서로 이어진다. 안전한 방법은 `Integer.compare(a, b)`를 쓰는 것이다. `double`의 NaN 비교도 같은 종류의 함정이다.

### 최악 입력에 노출되는 서비스

외부에서 들어온 데이터를 정렬하는 곳은 퀵소트 계열의 구현을 확인한다. 3절에서 본 대로 피벗이 예측 가능하면 공격 입력이 가능하다. introsort나 무작위 피벗이면 `n log n`이 보장된다. 안정 정렬이 필요하다면 TimSort 같은 머지 계열이 기본값이다.

## 8. 트레이드오프 정리

| 알고리즘 | 평균 | 최악 | 추가 메모리 | 안정 | 특징 |
|---|---|---|---|---|---|
| 퀵소트 | `n log n` | `n²` | `log n` 스택 | X | 캐시 친화적, 상수가 작다 |
| Introsort | `n log n` | `n log n` | `log n` | X | 퀵 + 힙 + 삽입 혼합 |
| 머지소트 | `n log n` | `n log n` | `n` | O | 연결 리스트, 외부 정렬에 적합 |
| 힙소트 | `n log n` | `n log n` | `1` | X | 캐시 비친화적이라 실제로는 느린 편 |
| TimSort | `n log n` | `n log n` | 최대 `n` | O | 부분 정렬 데이터에서 `n`에 가깝다 |

고르는 기준을 한 줄씩 줄이면 이렇다.

- 같은 키 순서를 지켜야 하는 객체 정렬이면 TimSort 같은 안정 정렬이다.
- 기본 타입이고 속도가 전부라면 퀵소트 계열이다.
- 메모리가 빠듯하고 최악 시간이 중요하면 힙소트나 introsort다.
- 데이터가 메모리를 넘으면 머지 기반 외부 정렬이다.

---

## 결론

- 비교 정렬은 `n log n` 아래로 내려갈 수 없다. 그래서 알고리즘 선택은 안정성, 메모리, 최악 입력, 부분 정렬 활용 같은 부가 성질로 갈린다.
- 안정성은 "이름순 후 나이순"처럼 여러 번 정렬해 복합 정렬을 만들 때 필요하다. 퀵소트는 멀리 있는 원소를 교환해서 이를 지키지 못하고, 머지소트는 앞에서부터 차례로 합쳐서 지킨다.
- 퀵소트는 피벗이 쏠리면 `n²`이 되고 이는 공격에도 쓰인다. introsort는 깊이가 깊어지면 힙소트로 바꿔 이를 막는다.
- TimSort는 이미 정렬된 run을 찾아 합치는 안정 정렬이다. run 스택의 불변식으로 깊이를 로그로 묶는다.
- 그 불변식을 위쪽 세 개만 검사한 탓에 `ArrayIndexOutOfBoundsException`이 가능했고, 형식 증명을 시도하던 연구팀이 이를 찾았다. 검사 범위를 네 개로 넓혀 고쳤다.
