## 개요

백엔드 코드에서 리스트에 `add`나 `append`를 부르는 일은 흔하다. 그런데 배열은 크기가 고정이다. 가득 찬 배열에 원소를 넣으려면 누군가 더 큰 배열을 만들고 원소를 전부 옮겨야 한다. 그럼에도 `append`는 "O(1)"이라고 배운다.

이 글이 답하는 질문은 두 가지다.

- 한 번에 O(n)이 드는 연산이 끼어 있는데도 왜 `append`는 O(1)이라고 말해도 되는가?
- 용량을 늘리는 비율(성장 계수)은 왜 2나 1.5처럼 배수여야 하고, 둘의 차이는 무엇인가?

이 글은 복사 횟수를 손으로 세는 데서 출발한다. 다음 글인 [해시 테이블](/posts/cs/algorithm/hash-table)의 리해시(rehash)도 같은 원리를 쓴다.

## 1. 왜 문제가 되는가: 가득 찬 배열

동적 배열(dynamic array)은 내부에 고정 크기 배열을 하나 들고 있다가, 가득 차면 더 큰 배열로 갈아타는 자료구조다. Java의 `ArrayList`, C++의 `std::vector`, Python의 `list`, Go의 슬라이스가 모두 이 구조다.

가득 찼을 때 일어나는 일은 이렇다.

1. 더 큰 배열을 새로 할당한다.
2. 기존 원소를 전부 새 배열로 복사한다.
3. 새 원소를 쓴다.

원소가 n개일 때 2번이 n번 일어나므로 이 `append` 한 번은 O(n)이다. 그러면 n번 `append`하면 O(n²)일까? 그렇지 않다. 대부분의 `append`는 빈 칸에 쓰기만 하면 되기 때문이다. 그 총합을 따져 보는 것이 상각 분석이다.

**핵심 아이디어**: 비싼 연산은 드물게 일어나고, 그 간격이 비용만큼 벌어지면 비용을 전체 연산에 나눠 낼 수 있다.

## 2. 직접 세기: 크기 1에서 16까지

용량 1짜리 배열에서 시작해, 가득 차면 용량을 2배로 늘린다고 하자. 비용은 "쓰기 1회 + 복사한 원소 수"로 센다.

`append`를 1번째부터 17번째까지 따라가 보자.

| append 번째 | 넣기 전 크기 | 용량 변화 | 복사 개수 | 이번 비용(쓰기 1 + 복사) |
| ---: | ---: | --- | ---: | ---: |
| 1 | 0 | 그대로 (1) | 0 | 1 |
| 2 | 1 | 1 -> 2 | 1 | 2 |
| 3 | 2 | 2 -> 4 | 2 | 3 |
| 4 | 3 | 그대로 (4) | 0 | 1 |
| 5 | 4 | 4 -> 8 | 4 | 5 |
| 6 | 5 | 그대로 | 0 | 1 |
| 7 | 6 | 그대로 | 0 | 1 |
| 8 | 7 | 그대로 (8) | 0 | 1 |
| 9 | 8 | 8 -> 16 | 8 | 9 |
| 10 ~ 16 | 9 ~ 15 | 그대로 (16) | 0 | 각 1 (7번) |
| 17 | 16 | 16 -> 32 | 16 | 17 |

복사 총합을 누적해 보면 이렇다.

| 지금까지 append 수 | 복사 누적 | 쓰기 누적 | 총비용 | append당 평균 |
| ---: | ---: | ---: | ---: | ---: |
| 16 | 1 + 2 + 4 + 8 = 15 | 16 | 31 | 31 / 16 = 약 1.94 |
| 17 | 15 + 16 = 31 | 17 | 48 | 48 / 17 = 약 2.82 |

비용이 큰 `append`는 2의 거듭제곱 + 1번째(2, 3, 5, 9, 17)에서 나온다. 그 크기는 점점 커지지만 간격도 두 배씩 벌어진다. 확장 직후인 17번째의 평균이 약 2.82로 높지만 3을 넘지 않는다. 이 값이 3에 머무는 이유는 4절에서 증명한다.

## 3. 왜 "배수"여야 하는가

용량을 2배가 아니라 10칸씩만 늘리면 어떻게 될까? `append` 1000번을 세어 보자. 초기 용량은 10이라고 하자.

- 크기가 10, 20, 30, ..., 990일 때 확장이 일어난다. 모두 99번이다.
- 복사 총합은 10 + 20 + ... + 990 = 10 x (1 + 2 + ... + 99) = 10 x 4950 = 49,500이다.
- 2배 방식(초기 용량 1)은 크기 1, 2, 4, ..., 512에서 확장하므로 1 + 2 + ... + 512 = 1023이다.

같은 1000번인데 복사량이 약 48배 차이 난다. 게다가 n이 커질수록 벌어진다. +k씩 늘리면 확장이 n/k번 일어나고 평균 복사량이 n/2에 비례하므로 총합이 n²/(2k) 수준이 된다. `append` 하나당 O(n)이다.

배수로 늘리면 확장 간격도 같은 비율로 벌어진다. 복사 비용이 커지는 속도와 확장이 드물어지는 속도가 맞물려 총합이 n에 비례한다. 이것이 상각 O(1)의 핵심 조건이다.

## 4. 증명 두 가지: 집계법과 회계법

상각(amortized) 비용은 "연산 시퀀스 전체의 최악 총비용을 연산 수로 나눈 값"이다. 평균 케이스(average case) 분석과는 다르다. 평균 케이스는 입력 분포를 가정하지만, 상각 분석은 확률을 쓰지 않고 어떤 순서로 연산이 와도 성립한다.

### 집계법(aggregate method)

전체 총비용을 한 번에 계산해 n으로 나눈다. 성장 계수를 g(1보다 크다), 최종 용량을 C라 하자.

- 복사 총량은 `C/g + C/g² + C/g³ + ...` 이다. 마지막 확장은 C/g개를 복사하고, 그 전은 C/g²개를 복사하는 식이다.
- 이 등비급수의 합은 `C/(g-1)`이다.
- 최종 용량은 원소 수의 g배를 넘지 않으므로 `C <= g*n`이다. 따라서 복사 총량은 `g*n/(g-1)` 이하다.

g = 2를 넣으면 복사 총량은 2n 이하다. 쓰기 n번을 더해도 총비용은 3n 미만이고, `append` 한 번당 상각 비용은 O(1)이다. 2절에서 평균이 3을 넘지 않은 이유가 이것이다.

### 회계법(accounting method)

연산마다 요금을 미리 걷어 두었다가 비싼 연산에서 꺼내 쓰는 방식이다. `append` 한 번에 3코인을 청구한다고 하자.

- 1코인은 자기 자신을 쓰는 데 쓴다.
- 1코인은 나중에 자기 자신이 복사될 때 쓸 몫으로 저축한다.
- 1코인은 나중에 복사될 기존 원소(앞쪽 절반) 하나의 몫으로 저축한다.

용량이 m에서 2m으로 늘어난 직후를 보자. 새로 들어오는 m개 원소가 각각 2코인씩 저축하면 2m코인이 쌓인다. 다음 확장 때 복사할 원소는 2m개다. 비용이 정확히 미리 적립되어 있으므로, 확장 연산이 와도 추가로 낼 돈이 없다. 모든 `append`의 청구액이 3으로 고정이므로 상각 O(1)이다.

## 5. 성장 계수 2와 1.5: Java ArrayList

성장 계수는 2여야 할 이유가 없다. 1보다 큰 상수이기만 하면 상각 O(1)이다. 그렇다면 무엇을 얻고 무엇을 잃는지가 선택 기준이 된다.

Java `ArrayList`는 1.5배다. JDK 소스에서 확장은 이렇게 요청한다.

```java
// java.util.ArrayList#grow (OpenJDK)
int newCapacity = ArraysSupport.newLength(
    oldCapacity,
    minCapacity - oldCapacity,   // 최소 증가량
    oldCapacity >> 1);           // 선호 증가량: 현재 용량의 절반
```

새 용량은 `oldCapacity + (oldCapacity >> 1)`, 즉 약 1.5배다. 기본 첫 용량이 10이므로 10 -> 15 -> 22 -> 33 -> 49 -> 73 -> 109로 자란다(정수 나눗셈으로 내림한다).

Kotlin으로 두 정책의 복사량을 세는 코드는 이렇다.

```kotlin
class DynamicArray(private var cap: Int, private val grow: (Int) -> Int) {
    var size = 0
        private set
    var copies = 0L
        private set
    private var buf = IntArray(cap)

    fun append(x: Int) {
        if (size == cap) {
            cap = maxOf(grow(cap), cap + 1)
            buf = buf.copyOf(cap)   // 옛 배열을 새 배열로 복사
            copies += size
        }
        buf[size++] = x
    }
}

// 2배: DynamicArray(1) { it * 2 }
// 1.5배: DynamicArray(10) { it + (it shr 1) }
```

같은 시퀀스를 돌렸을 때 이론 한계와 실제 측정을 비교한다. 여기서 n은 `append` 횟수다.

| 성장 계수 | 복사 총량 상한 (`g*n/(g-1)`) | 낭비 공간 상한 (`(g-1)*n`) | 확장 순간 필요 메모리 |
| --- | --- | --- | --- |
| g = 2 | 2n | 약 n | 옛 용량 + 새 용량 = 약 3배 |
| g = 1.5 | 3n | 약 0.5n | 약 2.5배 |

직접 돌려 본 값도 상한 안에 있다. n = 1000이면 2배 방식은 복사 1023번(약 1.02n), 1.5배 방식(초기 용량 10)은 2456번(약 2.46n)이다. 2배 방식의 최악은 용량이 막 두 배가 된 직후라서, n = 1025라면 복사가 2047번으로 2n에 가깝다.

정리하면 g가 작을수록 복사는 늘고 낭비 공간은 준다. 즉 CPU와 메모리의 교환이다.

### 1.5를 고르는 이론적 논거

2배 방식에는 메모리 재사용에 불리하다는 논거가 있다. 해제된 블록이 연속된 빈 영역으로 합쳐진다고 가정해 보자. 확장하는 순간에는 지금 쓰는 블록에서 원소를 복사해야 하므로, 그 블록은 아직 해제되지 않았다.

```text
g = 2   : 해제됨 1 + 2 + 4 = 7               쓰는 중 8      새 요청 16    -> 못 들어감
g = 1.5 : 해제됨 4 + 6 + 9 + 13.5 = 32.5     쓰는 중 20.25  새 요청 약 30.4 -> 들어감
```

g = 2에서는 `1 + 2 + ... + 2^(k-1) = 2^k - 1`이다. 지금 쓰는 블록까지 합쳐도 다음 요청(`2^k`)에 1이 모자라므로, 이전 블록 자리를 영영 재사용하지 못한다. g가 황금비(약 1.618)보다 작으면 몇 번 확장한 뒤에는 합쳐진 빈 영역이 다음 요청을 담을 수 있다.

이 논거는 해제된 인접 블록이 합쳐진다는 가정에서만 성립한다. 실제 메모리 할당자는 크기 등급(size class)이나 `mmap`을 쓰므로 효과가 제한적일 수 있다. "1.5가 정답"이라기보다 "복사 몇 번을 더 쓰는 대신 낭비를 줄이는 합리적 선택" 정도로 이해하는 편이 안전하다.

### 다른 구현들의 선택

| 구현 | 성장 방식 | 비고 |
| --- | --- | --- |
| libstdc++ `std::vector` | 크기를 2배로 (`_M_check_len`) | 소스 주석에 "Grow by (at least) doubling" |
| MSVC `std::vector` | 현재 용량 + 절반 (1.5배) | `_Calculate_growth` |
| Java `ArrayList` | 현재 용량 + 절반 (1.5배) | 기본 첫 용량 10 |
| CPython `list` | 약 1.125배 + 상수, 4의 배수로 올림 | 0, 4, 8, 16, 24, 32, 40, 52, 64, 76 순서 |
| Go 슬라이스 | 용량에 따라 계수가 변함 | 아래 설명 |

Go는 한때 "1024개 미만이면 2배, 이상이면 1.25배"였다. 이 방식은 임계점에서 계수가 갑자기 꺾이고, 시작 용량이 클수록 최종 용량이 작아질 수 있었다. 2021년 Keith Randall의 커밋이 256개부터 계수를 서서히 줄이는 식으로 바꿨다.

| 시작 용량 | 256 | 512 | 1024 | 2048 | 4096 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 성장 계수 | 2.0 | 1.63 | 1.44 | 1.35 | 1.30 |

이 변경은 Go 1.18 릴리스 노트에 "급격한 전환이 덜한 새 공식"으로 기록되었다. 성장 계수는 상수일 필요가 없고, 크기에 따라 조절해도 된다는 사례다.

## 6. 상각 O(1)이 보장하지 않는 것: 꼬리 지연

상각 O(1)은 총합에 대한 보장이다. 개별 연산의 지연 상한(worst-case latency)은 보장하지 않는다.

인메모리 리스트에 계속 쌓는 서비스를 생각해 보자. p50은 요청 지연을 줄 세웠을 때 가운데 값이고, p99.9는 상위 0.1% 경계 값이다. 평소 p50이 2ms로 평온한데, 가끔 `append` 하나가 수백 ms에 걸린다. 배열이 `Int` 1억 개(약 400MB)라면 복사만으로도 메모리 대역폭 때문에 수십 ms 이상이 든다. 여기에 대용량 할당과 GC(garbage collection, 쓰지 않는 객체를 회수하는 작업) 비용이 붙는다. 이 수치는 크기 감각을 잡기 위한 대략적 추정이다.

결정적 단서는 간격이다. 2배 성장이라면 확장은 2의 거듭제곱 지점에서 일어나므로, 지연이 튀는 간격이 점점 두 배씩 벌어진다. 이런 패턴이 보이면 동적 배열의 리사이즈를 의심해 볼 수 있다.

메모리 피크도 있다. 복사하는 순간에는 옛 배열과 새 배열이 동시에 존재하므로 `(1 + g)` 배의 메모리가 필요하다. 평소 사용량만 보고 한도를 잡으면 이 순간에 OOM(out of memory, 메모리 부족으로 할당이 실패하거나 프로세스가 종료되는 상황)이 날 수 있다.

## 7. 대응 방법과 대가

| 방법 | 효과 | 대가 |
| --- | --- | --- |
| 크기를 알면 미리 예약 (`ArrayList(n)`, `ensureCapacity`, Go의 `make([]T, 0, n)`) | 확장 자체를 없앰 | 크기를 미리 알아야 함 |
| 고정 크기 청크의 리스트(deque 같은 구조) | 복사 spike 없음, 최악도 O(1) | 임의 접근이 느리고 캐시 지역성이 떨어짐 |
| 증분 리사이즈(incremental resize) | 복사를 여러 연산에 나눠 spike를 분산 | 두 구조를 동시에 유지해 메모리가 늘고 구현이 복잡함 |
| 링 버퍼, 풀 사전 할당 | 최악 O(1) 보장 (실시간 시스템) | 크기 상한이 필요함 |

증분 리사이즈는 복사 비용을 이후 연산에 "분할 상환"하는 방식이다. 회계법에서 저축한 코인을 미리 조금씩 쓰는 셈이다. 다음 글의 해시 테이블 리해시에서 같은 문제가 다시 나온다.

## 8. 재할당이 남기는 부작용: 참조 무효화

복사가 일어나면 데이터가 새 주소로 옮겨진다. C++에서는 `push_back` 뒤에 기존 포인터와 이터레이터가 옛 버퍼를 가리키게 된다(iterator invalidation).

Go 슬라이스에서는 더 미묘하다. 슬라이스 두 개가 같은 백킹 배열을 공유하다가, `append`로 용량이 넘치는 순간 서로 분리된다.

```go
a := make([]int, 3, 4)   // 길이 3, 용량 4
b := append(a, 10)       // 용량이 남아 같은 배열에 씀
a = a[:4]
a[3] = 99
fmt.Println(b[3])        // 99, 공유 중

c := append(b, 20)       // 용량 초과: 새 배열로 복사
b[0] = 7
fmt.Println(c[0])        // 0, 이제 분리됨
```

원본이 바뀌기도 하고 안 바뀌기도 하는 이유는 용량이 남았느냐에 있다. 안전하게 쓰려면 명시적으로 복사하거나 `a[:len(a):len(a)]`처럼 용량을 제한한다.

---

## 결론

- `append` 하나는 최악 O(n)이지만, 확장은 드물게 일어나고 간격이 비용만큼 벌어지므로 n번의 총비용은 O(n)이다. 평균 O(1)이 아니라 상각 O(1)이라 부르는 이유는 확률 가정 없이 어떤 순서에서도 성립하기 때문이다.
- 핵심 조건은 배수 성장이다. +k씩 늘리면 총비용이 n²/(2k)로 무너진다.
- 성장 계수는 CPU와 메모리의 교환이다. 2배는 복사 상한 2n에 낭비가 크고, 1.5배(Java `ArrayList`)는 복사 상한 3n에 낭비가 작다.
- 상각 O(1)은 총합의 보장이다. 개별 `append`의 지연은 보장하지 않으므로, p99.9가 두 배씩 벌어지는 간격으로 튄다면 리사이즈를 의심하고 예약이나 분산으로 대응한다.
