## 개요

[앞 글](/posts/cs/algorithm/probabilistic-data-structures)에서는 정확도를 조금 내주고 메모리를 아끼는 자료구조를 봤다. 이번 글은 "가장 급한 것부터 꺼내기"라는 단순한 요구에서 출발한다.

이 글이 답하는 질문은 두 가지다.

- 이진 힙은 어떻게 배열 하나로 "가장 작은 값 꺼내기"를 O(log n)에 해내는가?
- 서버의 타임아웃 타이머처럼 수십만 개가 생기고 대부분 취소되는 경우, 힙 대신 타이밍 휠을 쓰는 이유는 무엇인가?

앞의 세 섹션은 힙 자체를, 뒤의 네 섹션은 타이머라는 실제 문제를 다룬다.

---

## 1. 우선순위 큐가 필요한 순간

작업 목록이 있고, 매번 "가장 우선순위가 높은 것"을 하나씩 꺼내야 한다고 하자. 응급실 대기열, 다익스트라 알고리즘의 "가장 가까운 정점", 타이머의 "가장 먼저 만료될 일"이 모두 이 모양이다.

이 요구를 담는 추상 자료형을 **우선순위 큐**(priority queue)라고 한다. 원소를 넣고(insert), 가장 작은(또는 큰) 원소를 꺼내는(extract-min) 두 연산이 핵심이다.

가장 먼저 떠오르는 구현은 배열이다. 그런데 배열로는 두 연산 중 하나가 반드시 느려진다.

| 구현 | 넣기 | 최소값 꺼내기 | n = 1,000,000일 때 최악 |
|---|---|---|---|
| 정렬 안 한 배열 | O(1), 끝에 붙임 | O(n), 전체를 훑음 | 꺼낼 때마다 100만 번 비교 |
| 정렬한 배열 | O(n), 자리를 비키려 원소를 밀어냄 | O(1), 끝에서 꺼냄 | 넣을 때마다 최대 100만 칸 이동 |
| 이진 힙 | O(log n) | O(log n) | 둘 다 트리 높이인 약 20단계 |

핵심 아이디어는 한 문장이다. **전체를 정렬하지 않고 "부모가 자식보다 작다"는 느슨한 순서만 지키면, 최소값은 항상 맨 위에 있고 고치는 비용은 트리 높이만큼만 든다.**

이 성질 덕분에 힙은 여러 곳에 쓰인다. [외부 정렬](/posts/cs/algorithm/external-merge-sort)의 k-way 병합은 k개 런의 머리 중 최소값을 힙으로 고르고, [다익스트라](/posts/cs/algorithm/shortest-path-dijkstra-bellman-ford)는 아직 확정하지 않은 정점 중 거리가 가장 짧은 것을 힙으로 꺼낸다.

## 2. 이진 힙의 배열 표현: 부모 i의 자식은 2i+1과 2i+2

**이진 힙**(binary heap)은 두 가지 조건을 지키는 이진 트리다.

1. **모양 조건**: 완전 이진 트리(complete binary tree)다. 위 레벨부터 채우고, 마지막 레벨은 왼쪽부터 빈칸 없이 채운다.
2. **힙 조건**: 모든 노드는 자기 자식보다 작거나 같다. 이 글은 최소 힙(min-heap) 기준으로 설명한다.

힙 조건은 형제 사이의 순서는 따지지 않는다. 그래서 "정렬"보다 훨씬 느슨하고, 그만큼 유지하기 싸다.

모양 조건 덕분에 포인터 없이 배열 하나로 트리를 표현할 수 있다. 레벨 순서대로 왼쪽부터 번호를 매겨 배열에 넣으면 된다. 원소 7개짜리 예시를 보자.

```
array : [ 3,  5,  8, 10,  7, 12,  9 ]
index :   0   1   2   3   4   5   6

tree  :              3 (0)
                  /        \
             5 (1)          8 (2)
            /     \        /     \
        10 (3)   7 (4)  12 (5)   9 (6)
```

인덱스 사이의 관계는 공식 세 개로 정리된다(0부터 셀 때).

| 관계 | 공식 | 예시 (i = 1) |
|---|---|---|
| 왼쪽 자식 | 2i + 1 | 3번 칸, 값 10 |
| 오른쪽 자식 | 2i + 2 | 4번 칸, 값 7 |
| 부모 | (i - 1) / 2, 소수점 버림 | 0번 칸, 값 3 |

힙 조건이 지켜지는지 확인해 보자. 0번(3)은 자식 5, 8보다 작다. 1번(5)은 자식 10, 7보다 작다. 2번(8)은 자식 12, 9보다 작다. 그런데 형제인 10과 7은 순서가 뒤집혀 있어도 상관없다.

완전 이진 트리이므로 원소가 n개면 높이는 `floor(log2 n)`이다. 원소 7개면 높이 2, 100만 개여도 높이 19(레벨 20개)다. 2^20이 1,048,576이기 때문이다. 아래 두 연산이 이 높이만큼만 움직이므로 O(log n)이 된다.

## 3. sift-up과 sift-down을 숫자 예시로, O(log n)

힙 연산은 결국 "일단 모양 조건을 맞춰 놓고, 깨진 힙 조건을 한 경로를 따라 고친다"는 한 가지 패턴이다. 위로 고치면 **sift-up**, 아래로 고치면 **sift-down**이라고 한다.

### 넣기: 끝에 붙이고 sift-up

**sift-up**(bubble-up)은 새 원소가 부모보다 작으면 부모와 자리를 바꾸는 일을 멈출 때까지 반복하는 과정이다.

앞의 힙 `[3, 5, 8, 10, 7, 12, 9]`에 4를 넣어 보자.

1. 모양 조건부터 맞춘다. 배열 끝인 7번 칸에 4를 붙인다. `[3, 5, 8, 10, 7, 12, 9, 4]`
2. 7번의 부모는 (7 - 1) / 2 = 3번, 값은 10이다. 4가 더 작으므로 바꾼다. `[3, 5, 8, 4, 7, 12, 9, 10]`
3. 3번의 부모는 (3 - 1) / 2 = 1번, 값은 5다. 4가 더 작으므로 바꾼다. `[3, 4, 8, 5, 7, 12, 9, 10]`
4. 1번의 부모는 0번, 값은 3이다. 4가 더 크므로 멈춘다.

```
before:          3                  after:           3
              /     \                             /     \
             5       8                           4       8
            / \     / \                         / \     / \
          10   7  12   9                       5   7  12   9
          /                                   /
         4   <- new                          10
```

결과를 검증하자. 0번(3)의 자식은 4, 8이다. 1번(4)의 자식은 5, 7이다. 2번(8)의 자식은 12, 9다. 3번(5)의 자식은 10이다. 모든 부모가 자식보다 작으니 힙 조건이 지켜졌다.

비교는 3번, 교환은 2번 했다. 경로가 아무리 길어도 리프에서 루트까지의 거리, 즉 트리 높이를 넘지 않는다.

### 꺼내기: 루트를 빼고 sift-down

**sift-down**(bubble-down)은 원소가 자식보다 크면 두 자식 중 더 작은 쪽과 자리를 바꾸는 일을 멈출 때까지 반복하는 과정이다.

방금 만든 힙 `[3, 4, 8, 5, 7, 12, 9, 10]`에서 최소값을 꺼내 보자.

1. 답은 루트의 3이다. 3을 꺼낸다.
2. 빈 루트에 배열의 마지막 원소 10을 옮긴다. 원소는 7개가 된다. `[10, 4, 8, 5, 7, 12, 9]`
3. 0번(10)의 자식은 1번(4)과 2번(8)이다. 더 작은 4와 비교하면 10이 크므로 바꾼다. `[4, 10, 8, 5, 7, 12, 9]`
4. 1번(10)의 자식은 3번(5)과 4번(7)이다. 더 작은 5와 비교하면 10이 크므로 바꾼다. `[4, 5, 8, 10, 7, 12, 9]`
5. 3번의 자식은 7번, 8번인데 원소가 7개(0~6번)이므로 자식이 없다. 멈춘다.

결과를 검증하자. 0번(4)의 자식은 5, 8이다. 1번(5)의 자식은 10, 7이다. 2번(8)의 자식은 12, 9다. 힙 조건이 지켜졌고, 새 최소값 4가 루트에 있다.

3단계에서 "더 작은 자식"과 바꾸는 이유가 중요하다. 만약 8과 바꿨다면 8이 루트로 올라가 자식 4를 거느리게 된다. 부모 8이 자식 4보다 커서 힙 조건이 즉시 깨진다. 더 작은 자식을 올려야 그 자리가 남은 형제보다도 작다는 것이 보장된다.

### 비용 정리

| 연산 | 방법 | 비용 |
|---|---|---|
| 최소값 보기 (peek) | 0번 칸 읽기 | O(1) |
| 넣기 (insert) | 끝에 붙이고 sift-up | O(log n) |
| 최소값 꺼내기 (extract-min) | 마지막 원소를 루트로, sift-down | O(log n) |
| 임의 원소 삭제 | 먼저 원소의 위치를 찾아야 함 | 찾기 O(n) + 고치기 O(log n) |

마지막 줄이 이 글 후반의 주제다. 힙은 "가장 작은 것"만 빨리 찾는다. 중간에 있는 특정 원소가 어디 있는지는 모른다. Java `PriorityQueue`의 공식 문서도 넣기와 꺼내기는 O(log(n))이지만 `remove(Object)`와 `contains(Object)`는 선형 시간이라고 밝힌다.

원소마다 자기 배열 인덱스를 기록해 두는 **인덱스 힙**(indexed heap)을 쓰면 임의 삭제도 O(log n)이 된다. 다만 교환할 때마다 인덱스를 갱신하는 코드가 붙고, 표준 라이브러리 힙은 대개 이 기능을 주지 않는다.

## 4. 타이머의 요구사항: 추가, 취소, 만료

서버에는 "N ms 뒤에도 이 일이 안 끝났으면 이걸 하라"는 **타이머**(timer)가 끊임없이 생긴다. 요청 타임아웃, TCP 재전송 타이머, 세션 TTL, 지연 작업(delayed operation)이 모두 그렇다.

타이머 자료구조가 지원해야 하는 연산은 세 가지다. Varghese와 Lauck의 논문은 타이머 모듈을 루틴 네 개로 모델링한다. 사용자가 부르는 StartTimer와 StopTimer, 그리고 tick마다 도는 PerTickBookkeeping과 ExpiryProcessing이다. 아래 표는 tick에서 도는 두 루틴을 "만료" 하나로 묶었다.

| 연산 | 언제 일어나나 | 예시 |
|---|---|---|
| 추가 (start timer) | 요청이 들어올 때 | 30초 타임아웃 등록 |
| 취소 (stop timer) | 요청이 제시간에 끝났을 때 | 응답을 보냈으니 타임아웃 해제 |
| 만료 (expiry, per-tick) | 시계가 움직일 때 | 만료 시각이 지난 타이머 실행 |

핵심 관찰은 한 문장이다. **타임아웃 타이머는 대부분 만료되지 않고 취소된다.** 타임아웃은 "만약을 위한 보험"이라서, 정상 요청은 끝나는 순간 타이머가 필요 없어진다.

숫자로 보자. 초당 10,000건의 요청이 들어오고, 타임아웃은 30초, 요청은 보통 50ms 만에 끝난다고 하자.

- 취소가 즉시 반영되면 살아 있는 타이머는 약 10,000 x 0.05 = 500개다.
- 취소가 반영되지 않고 만료 시각까지 남는다면 10,000 x 30 = 300,000개가 쌓인다.

같은 트래픽인데 600배 차이다. 그래서 좋은 타이머 자료구조의 조건은 정렬 성능보다 이쪽에 있다.

- 추가와 취소가 싸야 한다. 둘 다 요청마다 한 번씩 일어난다.
- 취소된 타이머가 메모리에서 즉시 빠져야 한다.
- 타이머가 수십만 개여도 시계를 한 칸 움직이는 비용이 폭증하지 않아야 한다.

## 5. 힙으로 만든 타이머의 한계: 취소 비용, 대량 타이머

가장 자연스러운 구현은 만료 시각을 키로 하는 최소 힙이다. 루트가 곧 "다음에 만료될 타이머"이므로, 루트의 만료 시각까지 잠들었다가 깨어나 꺼내면 된다. Java의 `DelayQueue`가 이 방식이다. OpenJDK 소스를 보면 내부에 `PriorityQueue` 하나를 두고 락으로 감싼다.

힙 타이머의 장점은 분명하다. 만료 시각이 정확하고, 다음 만료까지 얼마나 남았는지 O(1)로 안다. 타이머가 적고 취소가 드물면 이것으로 충분하다.

문제는 4절의 "대부분 취소된다"와 만날 때 생긴다.

### 문제 1: 취소가 선형 시간이다

3절에서 봤듯 힙은 특정 원소의 위치를 모른다. `DelayQueue.remove(Object)`는 내부 `PriorityQueue.remove(Object)`를 그대로 부르고, 이것은 선형 시간이다. 타이머가 300,000개면 요청 하나가 끝날 때마다 최악 300,000칸을 훑는다. 그것도 큐 전체를 잠근 채로 한다.

### 문제 2: 취소를 미루면 메모리가 샌다

선형 삭제를 피하려고 "취소 표시만 하고, 나중에 루트로 올라오면 버린다"는 지연 삭제(lazy deletion)를 쓸 수 있다. 그러면 취소된 타이머가 원래 만료 시각까지 힙에 남는다. 4절의 계산대로 진짜 대기 중인 타이머는 500개인데 힙에는 300,000개가 들어 있다.

증상은 이렇다. 요청은 거의 다 정상 완료되는데도 JVM 힙 사용량이 서서히 늘고 GC가 잦아진다. 심하면 OutOfMemoryError가 난다. 힙 덤프를 떠 보면 이미 끝난 요청 객체를 타이머 엔트리가 붙잡고 있다.

### 문제 3: 청소하는 쪽도 비싸다

죽은 엔트리를 치우는 별도 스레드(reaper)를 둘 수 있다. 이번엔 딜레마가 생긴다. 자주 전체를 훑으면 CPU를 쓰고, 드물게 훑으면 메모리가 찬다.

Kafka의 옛 purgatory가 정확히 이 상황이었다. Confluent 블로그에 따르면 옛 구현은 `DelayQueue` 기반 타이머를 썼다. 완료된 요청은 조건 검사 중에 우연히 발견되거나, 전체 개수가 설정한 임계치를 넘어 reaper 스레드가 타이머 큐와 모든 감시 리스트를 훑을 때에야 제거됐다. 원문은 삭제가 따라가지 못하면 JVM 힙이 바닥나 OutOfMemoryError가 날 수 있고, 임계치를 낮춰 자주 훑으면 성능 비용이 크다고 설명한다.

### 문제 4: 추가도 O(log n)이다

추가 자체도 요청마다 O(log n)이다. 300,000개면 약 18단계다. 여기에 모든 스레드가 한 락을 두고 경쟁한다. 타이머 수와 요청률이 함께 올라가면 이 비용이 처리량의 상한이 된다.

정리하면 힙은 "다음 만료가 언제인가"에 최적화된 구조다. 타임아웃 워크로드에서 정작 자주 일어나는 연산은 추가와 취소인데, 힙은 그쪽이 약하다.

## 6. 단일 타이밍 휠에서 계층형 타이밍 휠로

타이밍 휠의 핵심 아이디어는 한 문장이다. **만료 시각으로 정렬하지 말고, 만료 시각을 시간 칸(버킷) 번호로 바꿔 해당 칸의 리스트에 붙인다.** 정렬이 없으니 추가가 O(1)이고, 각 타이머가 자기 리스트 노드를 들고 있으니 취소도 O(1)이다.

비유하자면 시계의 문자판이다. 바늘이 한 칸 갈 때마다 그 칸에 꽂힌 쪽지를 모두 처리한다. 다만 실제 시계와 달리 칸 수가 정해져 있어서, 한 바퀴를 넘는 시간은 그대로 표현할 수 없다. 이 한계를 푸는 방법이 이 절의 후반부다.

### 단일 타이밍 휠

**타이밍 휠**(timing wheel)은 버킷 n개짜리 원형 배열이다. 각 버킷은 tick 하나(시간 u)를 맡고, 버킷 안에는 그 시간에 만료될 타이머들이 이중 연결 리스트(doubly linked list)로 매달려 있다. 휠 하나가 덮는 범위는 n x u다.

u = 1ms, n = 20인 휠을 예로 들자. 범위는 20ms다. 현재 시각은 0ms다.

```
tick u = 1ms, n = 20 buckets, range = 20ms

 bucket:  [0] [1] [2] ... [7] ... [13] ... [19]
           ^                |       |
         now=0              v       v
                         task B   task A
                         (7ms)    (13ms)
```

1. **추가**: task A가 13ms 뒤 만료라면 13 mod 20 = 13번 버킷 리스트 끝에 붙인다. 비교도 이동도 없다. O(1)이다.
2. **취소**: task A는 자기 리스트 노드를 알고 있다. 앞뒤 노드의 포인터만 바꿔 리스트에서 떼어낸다(unlink). O(1)이다. 떼어낸 순간 메모리에서도 빠진다.
3. **만료**: 시계가 1ms 갈 때마다 포인터를 한 칸 옮기고, 그 버킷의 리스트를 통째로 실행한다.

5절의 문제와 비교해 보자. 300,000개의 타이머가 있어도 추가와 취소는 포인터 몇 개만 바꾼다. 취소가 즉시 반영되므로 4절의 계산처럼 살아 있는 타이머는 500개 수준으로 유지된다.

### 단일 휠의 한계

대가는 두 가지다.

첫째, **범위**다. 1ms 해상도로 30초 타임아웃을 담으려면 버킷이 30,000개 필요하다. 하루짜리 타이머라면 86,400,000개다. 대부분 비어 있는 버킷을 위해 메모리를 쓰고, 빈 버킷도 tick마다 지나가야 한다.

둘째, **정밀도**다. 같은 버킷의 타이머는 같은 tick에 만료된다. tick보다 짧은 차이는 구분하지 못한다.

범위 문제를 푸는 방법은 두 갈래다. 버킷 번호를 n으로 나눈 나머지로 정하고 "몇 바퀴 더 돌아야 하는지"를 따로 세는 **해시 휠**(hashed wheel)이 있고, 해상도가 다른 휠을 여러 층 쌓는 **계층형 휠**(hierarchical wheel)이 있다. Varghese와 Lauck의 논문 제목 "Hashed and Hierarchical Timing Wheels"가 바로 이 두 확장을 가리킨다. 해시 휠은 7절의 Netty에서 보고, 여기서는 계층형을 따라간다.

### 계층형 타이밍 휠

**계층형 타이밍 휠**(hierarchical timing wheel)은 위층으로 갈수록 tick이 굵어지는 휠을 쌓은 구조다. 위층 휠의 tick은 아래층 휠 전체 범위와 같다. 시계의 초침, 분침, 시침과 같은 원리다.

Confluent 글의 벤치마크 설정처럼 u = 1ms, n = 20으로 3층을 쌓으면 이렇게 된다.

| 레벨 | tick | 버킷 수 | 덮는 범위 |
|---|---|---|---|
| 1 | 1ms | 20 | 20ms |
| 2 | 20ms | 20 | 400ms |
| 3 | 400ms | 20 | 8,000ms |

버킷은 모두 60개인데 8초를 덮는다. 단일 휠로 1ms 해상도에 8초를 덮으려면 8,000개가 필요하다.

논문에 실린 예시는 차이를 더 극적으로 보여준다. 100일을 1초 단위로 다루려면 단일 휠은 8,640,000개 버킷이 필요하다. 일(100칸), 시(24칸), 분(60칸), 초(60칸) 휠 4개를 쌓으면 244칸이면 된다.

### task 하나를 따라가 보자

현재 시각 0ms에 205ms 뒤 만료되는 task A를 넣는다.

1. **레벨 1 검사**: 205ms는 레벨 1 범위(0~19ms)를 넘는다. 위층으로 보낸다.
2. **레벨 2에 삽입**: 레벨 2의 tick은 20ms다. 205 / 20 = 10.25이므로 소수점을 버린 10번 버킷에 넣는다. 이 버킷은 200~219ms 구간을 맡는다.
3. **t = 200ms**: 레벨 2의 10번 버킷이 만료된다. 하지만 task A의 실제 만료까지는 5ms가 남았다. 그래서 실행하지 않고 다시 삽입한다. 이 과정을 **cascade**(재삽입, 아래층으로 내려보내기)라고 한다.
4. **레벨 1에 재삽입**: 남은 시간 5ms는 레벨 1 범위 안이다. 205 mod 20 = 5번 버킷에 넣는다.
5. **t = 205ms**: 레벨 1의 5번 버킷이 만료되고 task A가 실행된다.

```
level 2 (tick 20ms, range 400ms)
  [0] [1] ... [9] [10] [11] ... [19]
                    |
                    v  task A (expires 205ms) -> bucket 10 = [200, 220)
                    |
                    |  t = 200ms: bucket 10 expires, cascade down
                    v
level 1 (tick 1ms, range 20ms)
  [0] [1] [2] [3] [4] [5] [6] ... [19]
                        |
                        v  task A -> bucket 205 mod 20 = 5
                           t = 205ms: run
```

Confluent 글이 설명하는 삽입 규칙을 의사코드로 줄이면 다음과 같다.

```
add(task):
  if task.expiry < now + tick:            run(task)               # already due
  elif task.expiry < now + tick * n:      bucket[(task.expiry / tick) % n].append(task)
  else:                                   overflowWheel().add(task) # tick = tick * n, created on demand

onBucketExpired(bucket):
  for task in bucket.drainAll(): add(task)   # less time left -> lower level, or run now
```

### 비용과 남는 문제

- **추가**는 위층으로 올라가는 횟수만큼 든다. 휠 개수를 m이라 하면 O(m)이다. 레벨이 하나 늘 때마다 범위가 n배가 되므로 m은 아주 작다. 위 예시에서 3층이면 8초, 4층이면 160초를 덮는다.
- **취소**는 여전히 O(1)이다. 어느 층에 있든 자기 리스트 노드를 떼어내면 된다.
- **cascade 비용**은 task 하나당 많아야 레벨 수만큼이다. 위층 버킷이 만료될 때마다 한 층씩 내려오기 때문이다. 이 비용은 시간에 걸쳐 나눠서 치러진다. 게다가 대부분의 타이머는 cascade 전에 취소되므로 이 비용조차 내지 않는다.
- **정밀도 손실**은 그대로다. 실행 시각은 레벨 1의 tick 단위로 맞춰진다. 마이크로초 단위 정밀도가 필요하다고 tick을 그만큼 줄이면 버킷 수와 tick 빈도가 폭증한다. 정밀한 시각이 중요하면 힙이 맞는 도구다.

빈 버킷을 tick마다 확인하는 비용도 남는다. 1ms마다 깨어나 대부분 빈 버킷을 확인하는 것은 낭비다. 다음 절의 Kafka는 이 부분을 힙과 섞어서 푼다.

## 7. 실제 사용처: Kafka purgatory, Netty `HashedWheelTimer`

### Kafka purgatory: 계층형 휠 + 버킷만 담은 힙

Kafka 브로커는 바로 응답할 수 없는 요청을 **purgatory**(대기실)에 보류한다. 예를 들어 `acks=all`인 produce 요청은 모든 in-sync 복제본(리더를 충분히 따라잡은 복제본)이 쓰기를 확인할 때까지, fetch 요청은 소비자에게 돌려줄 새 데이터가 생길 때까지 기다린다. 각 요청에는 타임아웃이 붙는다. 대부분은 조건이 채워져 타임아웃 전에 완료된다. 4절의 워크로드 그대로다.

Confluent 블로그 "Apache Kafka, Purgatory, and Hierarchical Timing Wheels"(2015)가 설명하는 새 설계는 다음과 같다.

- tick u = 1ms인 계층형 타이밍 휠을 쓴다. 범위를 넘는 타이머를 위한 상위 휠은 필요할 때 만든다.
- 버킷은 이중 연결 리스트이고, task가 자기 노드를 들고 있어서 완료되거나 취소되면 O(1)로 떼어낸다. 완료된 요청이 타이머에 남지 않는다.
- 추가는 O(m), 삭제는 O(1)이다.

빈 버킷 문제는 영리하게 푼다. 시계를 움직이는 데 `DelayQueue`를 쓰되, 그 안에 task가 아니라 **비어 있지 않은 버킷**만 넣는다. 스레드는 다음 버킷의 만료 시각까지 잠들었다가 깨어난다. 1ms마다 깨어날 필요가 없다.

이 조합이 좋은 이유는 힙의 크기 때문이다. 힙에 들어가는 것은 버킷이므로 개수가 많아야 전체 버킷 수 정도다. 타이머가 300,000개여도 힙은 수십 개 원소만 다룬다. 힙의 장점(다음 만료 시각을 바로 앎)은 살리고 약점(원소 수에 비례하는 비용, 선형 취소)은 피한 셈이다.

원문은 enqueue만 하는 마이크로벤치마크 결과도 싣는다. 조건은 tick 1ms, 휠 크기 20, 타임아웃 200ms, 요청 100만 건, JVM 힙 200MB, 아무 일도 하지 않는 가짜 요청이다.

| 시나리오 | 옛 구현 (`DelayQueue`) | 새 구현 (계층형 휠) |
|---|---|---|
| 타임아웃 비율이 낮음 | 약 40,000 RPS에서 포화 | 눈에 띄는 저하 없음 |
| 타임아웃 비율이 높음 | 약 25,000 RPS에서 포화 | 약 105,000 RPS에서 포화 |

원문도 purgatory만 떼어 낸 실험이라 실제 시스템의 처리량은 더 낮을 수 있다고 밝힌다. 이 숫자는 "몇 배 빨라진다"는 약속이 아니라 병목이 어디 있었는지를 보여주는 자료로 읽는 것이 맞다.

### Netty `HashedWheelTimer`: 단일 해시 휠

Netty의 `HashedWheelTimer`는 이름 그대로 해시 휠이다. Javadoc은 이 클래스를 "approximated I/O timeout scheduling"(근사적인 I/O 타임아웃 스케줄링)에 최적화된 타이머로 소개하고, 예약한 작업을 정시에 실행하지 않는다고 명시한다. 알고리즘은 Varghese와 Lauck의 논문에 기반한다고 밝힌다.

기본값은 tick 100ms, 휠 크기(ticksPerWheel) 512다. 한 바퀴가 51.2초를 덮는다. 그보다 긴 타임아웃은 층을 쌓지 않고 바퀴 수로 처리한다. 소스를 보면 각 타이머가 `remainingRounds`(남은 바퀴 수)를 가진다.

현재 tick이 0일 때 120초 타임아웃을 넣는 경우를 따라가 보자.

1. 만료까지 tick 수는 120,000ms / 100ms = 1,200이다.
2. 버킷은 1,200 mod 512 = 176번이다. 남은 바퀴는 1,200 / 512 = 2(소수점 버림)다.
3. tick 176: 워커가 176번 버킷을 지나가며 남은 바퀴를 2에서 1로 줄인다.
4. tick 688(176 + 512): 남은 바퀴를 1에서 0으로 줄인다.
5. tick 1,200(688 + 512): 남은 바퀴가 0이므로 실행한다.

구현 세부도 몇 가지 눈여겨볼 만하다.

- 휠 크기는 2의 거듭제곱으로 올림한다. 그래서 나머지 연산을 `tick & mask` 비트 연산으로 계산한다.
- 버킷은 `prev`와 `next`를 가진 이중 연결 리스트다.
- `cancel()`은 상태를 바꾸고 취소 큐에 넣는다. 워커 스레드가 다음 tick에 리스트에서 떼어낸다. 소스 주석은 GC까지 최대 1 tick의 지연이 있다고 적는다.
- 인스턴스를 만들 때마다 전용 스레드가 하나 생긴다. Javadoc은 인스턴스 하나를 만들어 공유하라고 권하고, 연결마다 새로 만드는 것을 흔한 실수로 꼽는다. 소스에는 인스턴스가 64개를 넘으면 에러 로그를 한 번 남기는 검사가 있다.

해시 휠의 약점은 per-tick 비용이다. 한 버킷에 여러 바퀴짜리 타이머가 섞여 있으면 tick마다 아직 만료되지 않은 타이머까지 훑으며 바퀴 수를 줄인다. Javadoc이 타이머를 많이 예약한다면 휠 크기를 키우라고 권하는 이유다. 버킷이 많을수록 한 버킷에 섞이는 타이머가 줄어든다.

### 어떤 것을 고를까

| 방식 | 추가 | 취소 | 얻는 것 | 잃는 것 |
|---|---|---|---|---|
| 이진 힙 (`DelayQueue`) | O(log n) | O(n), 또는 지연 삭제로 메모리 누적 | 정확한 만료 시각, 단순한 구현 | 타이머가 많고 취소가 잦으면 느리고 메모리가 샘 |
| 단일 휠 | O(1) | O(1) | 대량 타이머에도 일정한 비용 | 범위가 n x u로 제한, tick 이하 정밀도 없음 |
| 해시 휠 (Netty) | O(1) | O(1), 다음 tick에 반영 | 범위 제한 없음, 구조 단순 | 긴 타이머가 섞이면 tick마다 훑는 비용 |
| 계층형 휠 (Kafka) | O(m) | O(1) | 적은 버킷으로 넓은 범위 | cascade 재삽입, tick 단위로 만료가 뭉침 |

휠이 힙보다 항상 빠른 것은 아니다. 타이머가 수백 개 수준이고 취소가 드물거나, 만료 시각이 정확해야 하는 스케줄러라면 힙이 더 단순하고 정확하다. 휠은 "수 ms 오차는 괜찮지만 개수가 매우 많고 대부분 취소되는" 타임아웃에 맞는 도구다.

## 결론

- 이진 힙은 "부모가 자식보다 작다"는 느슨한 순서만 지켜서, 배열 하나로 넣기와 최소값 꺼내기를 트리 높이인 O(log n)에 해낸다. 고치는 일은 sift-up과 sift-down이 한 경로만 따라가며 한다.
- 힙의 약점은 중간 원소를 모른다는 것이다. 임의 삭제가 선형 시간이 되거나, 지연 삭제로 죽은 엔트리가 쌓인다.
- 타임아웃 타이머는 대부분 취소되므로, 타이머 자료구조는 만료보다 추가와 취소가 싸야 한다.
- 타이밍 휠은 정렬 대신 시간 칸에 리스트로 매달아 추가와 취소를 O(1)로 만든다. 범위 문제는 해시 휠(바퀴 수 세기)이나 계층형 휠(층 쌓기와 cascade)로 풀고, 대가로 tick 단위 정밀도를 받아들인다.
- Kafka는 계층형 휠에 "버킷만 담은 힙"을 섞어 두 구조의 장점을 함께 얻었다.
