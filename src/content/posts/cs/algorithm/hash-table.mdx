## 개요

[앞 글](/posts/cs/algorithm/amortized-analysis-dynamic-array)에서는 배열을 2배씩 키우면 한 번의 확장이 비싸도 평균은 O(1)이 되는 이유를 봤다. 해시 테이블(hash table)도 같은 원리로 커진다. 이번 글은 해시 테이블의 나머지 절반, 즉 서로 다른 키가 같은 칸에 떨어졌을 때의 처리를 다룬다.

이 글이 답하는 질문은 두 가지다.

- 충돌은 어떻게 처리하고, 처리 방식마다 무엇이 달라지는가?
- 평균 O(1)인 구조가 어떻게 O(n²)으로 무너지고, Java `HashMap`은 이를 어떻게 막는가?

해시 테이블은 키를 해시 함수(hash function)로 정수로 바꾸고, 그 값으로 배열의 칸(버킷, bucket)을 골라 값을 저장하는 자료구조다. 해시 함수는 키를 받아 고정된 범위의 정수를 돌려주는 함수다.

---

## 1. 왜 해시 테이블인가

회원 10만 명이 있고 이메일로 회원을 찾는다고 하자. 배열을 처음부터 훑으면 O(n)이다. 이메일 순으로 정렬해 두면 이진 탐색으로 O(log n)이지만, 새 회원을 넣을 때마다 정렬을 유지해야 한다.

핵심 아이디어는 한 문장이다. **키에서 위치를 계산하면, 찾을 때 훑지 않고 바로 그 칸으로 간다.**

```
index = hash(key) mod m        (m: 버킷 수)
```

`m`이 2의 거듭제곱이면 나머지 연산 대신 비트 마스크 `hash & (m - 1)`을 쓸 수 있다. 더 빠르다. Java `HashMap`이 용량을 항상 2의 거듭제곱으로 유지하는 이유 중 하나다.

여기서 생기는 문제는 단순하다. 키가 될 수 있는 값은 사실상 무한하고 버킷은 유한하다. 그래서 서로 다른 두 키가 같은 칸에 떨어지는 충돌(collision)은 피할 수 없다. 해시 테이블의 구현은 대부분 충돌을 어떻게 다루느냐의 문제다.

## 2. 충돌 처리 방식 1: 체이닝

버킷 7개(`m = 7`)에 키 네 개를 넣어 보자. 해시 값은 다음과 같다고 하자.

| 키 | 해시 값 | hash mod 7 |
|----|---------|------------|
| A | 2 | 2 |
| D | 9 | 2 |
| F | 16 | 2 |
| B | 11 | 4 |

A, D, F가 모두 2번 칸으로 간다. 체이닝(separate chaining)은 버킷마다 리스트를 두고 충돌한 원소를 뒤에 이어 붙이는 방식이다.

```
index   bucket
  0     (empty)
  1     (empty)
  2     [A] -> [D] -> [F]
  3     (empty)
  4     [B]
  5     (empty)
  6     (empty)
```

조회는 두 단계다. 버킷을 계산하고(O(1)), 그 버킷의 리스트를 훑으며 키를 비교한다. F를 찾으면 2번 칸에서 A, D, F를 차례로 비교한다. 리스트 길이만큼 걸린다.

리스트가 얼마나 긴지는 적재율(load factor)로 정해진다. 적재율은 `α = n / m`, 즉 원소 수를 버킷 수로 나눈 값이다. 해시가 고르게 퍼진다면 버킷당 평균 길이가 α이므로 조회 기대 비용은 대략 `1 + α`다. α가 작게 유지되는 한 O(1)이다.

체이닝의 장점은 단순함이다.

- α가 1을 넘어도 동작한다. 리스트가 길어질 뿐이다.
- 삭제는 노드 하나를 리스트에서 빼면 끝이다.

단점은 노드마다 포인터와 별도 메모리 할당이 든다는 점이다. 노드가 힙 메모리(동적 할당 영역) 여기저기에 흩어져 있어 CPU 캐시에도 불리하다.

## 3. 충돌 처리 방식 2: 개방 주소법

같은 키 집합을 개방 주소법(open addressing)으로 넣어 보자. 이 방식은 리스트 없이, 충돌하면 배열 안에서 다른 빈 칸을 찾는다. 가장 단순한 선형 탐사(linear probing)는 바로 다음 칸을 본다.

- A: 2번이 비어 있다. 2번에 넣는다.
- D: 2번이 찼다. 3번이 비어 있다. 3번에 넣는다.
- F: 2번, 3번이 찼다. 4번에 넣는다.
- B: 해시는 4번인데 이미 F가 있다. 5번에 넣는다.

```
index:     0     1     2     3     4     5     6
        +-----+-----+-----+-----+-----+-----+-----+
        |     |     |  A  |  D  |  F  |  B  |     |
        +-----+-----+-----+-----+-----+-----+-----+
                       ^           ^
                       |           +-- B hashes to 4 (taken by F) -> slot 5
                       +-- A, D, F hash to 2
```

B는 A, D, F와 해시가 다른데도 그들이 만든 연속 구간 때문에 밀려났다. 이렇게 채워진 구간이 길어질수록 새 키가 그 구간에 걸릴 확률이 커지고 구간은 더 길어진다. 이 현상을 군집(clustering)이라 한다. α가 1에 가까워지면 탐사 길이가 급격히 늘어난다. 또 모든 원소가 배열 안에 있으므로 α는 반드시 1보다 작아야 한다.

장점은 포인터가 없고 연속된 배열이라 캐시 친화적이고 칸당 메모리가 작다는 점이다.

### 삭제가 까다로운 이유

D를 삭제한다고 하자. 3번 칸을 그냥 비우면 어떻게 될까?

```
before:  | . | . | A | D | F | B | . |
after :  | . | . | A |   | F | B | . |     <- slot 3 emptied
```

이제 F를 찾는다. 해시가 2번이니 2번(A, 불일치)을 보고 3번으로 간다. 3번이 비어 있다. 탐사는 "빈 칸을 만나면 이 키는 없다"고 판단하고 멈춘다. F는 4번에 있는데도 없는 키로 오판한다. 탐사 체인이 끊긴 것이다.

해결책은 칸을 비우는 대신 삭제 표시(tombstone)를 남기는 것이다. 조회는 tombstone을 건너뛰고 계속 탐사하고, 삽입은 tombstone 칸을 재사용할 수 있다. 대신 tombstone이 쌓이면 실제로는 빈 칸인데도 탐사가 길어진다. 그래서 주기적으로 테이블을 다시 만들어(rehash) 정리해야 한다.

## 4. 체이닝과 개방 주소법 비교

| 항목 | 체이닝 | 개방 주소법 |
|------|--------|-------------|
| α가 1을 넘을 수 있는가 | 가능. 체인이 길어질 뿐 | 불가능. 반드시 1 미만 |
| 캐시 지역성 | 포인터를 따라가서 불리 | 연속 배열이라 유리 |
| 삭제 | 노드 제거로 단순 | tombstone 필요, 쌓이면 rehash |
| 메모리 | 노드마다 포인터와 할당 오버헤드 | 빈 칸을 남겨 두는 낭비 |
| 부하가 높을 때 | 완만하게 느려짐 | 군집 때문에 급격히 느려짐 |

고르는 기준은 이렇다. α를 낮게 유지할 수 있고 메모리와 캐시 효율이 중요하면 개방 주소법이 낫다. 삭제가 잦거나 α가 크게 출렁이면 체이닝이 안전하다. Java `HashMap`은 체이닝을 쓴다. 체이닝은 한 버킷을 리스트 대신 다른 구조로 바꿀 여지가 있기 때문인데, 이 점은 6절에서 다시 나온다.

## 5. 리사이즈: 적재율을 낮게 유지하는 방법

원소가 늘수록 α가 커지고 충돌이 늘어난다. 그래서 α가 임계치를 넘으면 버킷 수를 늘리고 모든 원소를 새 배열에 다시 배치한다. 이를 리사이즈(resize) 또는 rehash라고 한다. 해시 값은 그대로지만 `m`이 바뀌면 `mod m` 결과가 달라지므로 위치를 다시 계산해야 한다.

Java `HashMap`의 기본 적재율은 0.75다(소스의 `DEFAULT_LOAD_FACTOR = 0.75f`). 기본 용량 16이면 원소가 12개를 넘을 때 용량을 32로 2배 늘린다.

한 번의 리사이즈는 O(n)이다. 그런데 2배씩 키우면 n개를 넣는 동안 rehash 비용의 합이 `n + n/2 + n/4 + ...`로 약 2n에 수렴해 삽입당 평균 O(1)이 된다. 고정량씩 늘리면 이 성질이 깨진다. 계산은 [동적 배열의 상각 분석](/posts/cs/algorithm/amortized-analysis-dynamic-array)과 같으니 이 글에서는 반복하지 않는다.

### 평균은 O(1)이지만 순간은 O(n)이다

상각 O(1)은 평균이다. 원소가 수천만 개인 테이블이 한 번에 rehash되면 그 스레드는 그동안 멈춘다. 평균 처리량에는 보이지 않고 p99, p999 지연이 주기적으로 튀는 형태로 나타난다. 대응은 둘이다.

- 미리 크기를 정한다(pre-size). 예상 원소 수를 알면 `new HashMap<>((int) (expected / 0.75f) + 1)`처럼 처음부터 넉넉히 잡아 리사이즈를 없앤다. Java 19부터는 이 계산을 대신해 주는 `HashMap.newHashMap(expected)`가 있다.
- 점진적 rehash(incremental rehashing)를 쓰는 구현을 쓴다. Redis의 `dict`는 새 테이블을 하나 더 만들고, 조회나 삽입이 올 때마다 버킷 몇 개씩만 옮긴다. 지연은 평탄해지지만 이행 중에는 두 테이블을 모두 조회해야 하고 구현이 복잡하다.

Redis의 해시 자료구조를 캐시에 쓰는 관점은 [Redis String vs Hash 캐싱 전략](/posts/dev/cache/redis-string-vs-hash-caching)에서 다룬다.

## 6. 최악의 경우: 모든 키가 한 칸에 몰리면

체이닝에서 키 n개가 모두 한 버킷에 들어가면 리스트 길이가 n이다. 조회 한 번이 O(n)이고, n개를 차례로 넣으면 삽입마다 기존 키와 비교하므로 합계가 O(n²)이다. 10만 개라면 비교가 약 50억 번이다.

이것이 우연이 아니라 공격으로 일어나면 해시 플러딩(hash flooding, HashDoS)이다. 2011년 28C3에서 Klink와 Wälde가 PHP, Ruby, Python, Java, ASP.NET, V8 등 주요 웹 플랫폼이 이 공격에 취약하다고 시연했다. 방법은 다음과 같다.

1. 공격자가 해시가 같은 키를 오프라인에서 미리 계산한다.
2. 그 키들을 HTTP POST 파라미터 이름으로 담아 보낸다. 약 1MB면 수만에서 수십만 개의 충돌을 만들 수 있다.
3. 서버는 파라미터를 해시 테이블에 넣는다. 삽입마다 O(n)이므로 전체가 O(n²)이 되어 CPU가 포화된다.

Java에서는 충돌 키를 만들기가 어렵지 않다. `"Aa"`와 `"BB"`는 `hashCode()`가 둘 다 2112로 같다(`65*31+97`과 `66*31+66`). 이 두 블록을 이어 붙인 문자열도 해시가 같아서, 블록 수를 늘리면 충돌 문자열이 지수적으로 늘어난다.

서버 CPU가 갑자기 100%가 되고 프로파일 상위에 `HashMap.put`이 보이면 이 가능성을 의심해야 한다. 쿼리 파라미터, JSON 키, 헤더처럼 사용자가 제어하는 입력이 해시 테이블의 키로 들어가는 곳이 후보다. 확인할 것은 요청의 크기와 파라미터 수, 버킷별 체인 길이 분포, 그리고 `hashCode` 구현이다. 해시가 상수에 가깝게 구현된 사용자 정의 클래스는 공격이 없어도 같은 증상을 낸다.

## 7. 방어: 트리화, 무작위화, 입력 제한

방어는 세 겹으로 쌓는다.

### Java HashMap의 treeify

Java 8부터 `HashMap`은 한 버킷의 리스트가 길어지면 그 버킷을 레드-블랙 트리로 바꾼다. 소스의 주석은 "Bins are converted to trees when adding an element to a bin with at least this many nodes"라고 설명한다(`TREEIFY_THRESHOLD = 8`). 즉 이미 8개가 있는 버킷에 하나가 더 들어올 때 변환이 시작된다. 트리 안에서는 탐색이 O(log n)이므로 한 버킷에 n개가 몰려도 최악이 O(n)에서 O(log n)으로 줄어든다.

변환에는 조건이 하나 더 있다. 테이블 용량이 `MIN_TREEIFY_CAPACITY = 64` 미만이면 트리로 바꾸지 않고 테이블을 리사이즈한다. 소스 주석대로 "Otherwise the table is resized if too many nodes in a bin"이다. 작은 테이블에서 한 버킷이 길어진 것은 테이블이 좁아서일 가능성이 높으므로, 구조를 바꾸기 전에 넓혀 보는 쪽이 싸다.

| 상수 | 값 | 의미 |
|------|-----|------|
| `DEFAULT_LOAD_FACTOR` | 0.75 | 기본 적재율 |
| `TREEIFY_THRESHOLD` | 8 | 버킷이 이만큼 찬 상태에서 추가하면 트리화 시도 |
| `MIN_TREEIFY_CAPACITY` | 64 | 용량이 이보다 작으면 트리화 대신 리사이즈 |
| `UNTREEIFY_THRESHOLD` | 6 | 리사이즈로 버킷이 갈라진 뒤 6개 이하면 다시 리스트로 |

되돌리는 기준(6)을 트리화 기준(8)보다 낮게 둔 덕분에, 원소 수가 경계 근처에서 오르내려도 리스트와 트리 사이를 매번 오가지 않는다. 참고로 `UNTREEIFY_THRESHOLD`는 리사이즈로 버킷이 나뉠 때 쓰이고, 삭제로 트리가 작아질 때는 트리 모양을 보는 별도 조건으로 되돌린다.

트리는 만능이 아니다. 키가 `Comparable`이면 크기 비교로 효율적으로 탐색하지만, 그렇지 않으면 탐색 비용이 늘 수 있다. 그리고 트리 노드는 일반 노드보다 메모리를 더 쓴다. 정상 데이터에서 8개 이상 몰리는 일은 드물기 때문에 평소 비용은 거의 없다.

### 키 입력형 해시와 무작위화

트리화는 최악을 O(log n)으로 낮출 뿐 충돌 자체를 없애지는 않는다. 근본 대응은 공격자가 충돌을 미리 계산하지 못하게 하는 것이다. 처음에는 프로세스마다 비밀 seed를 넣는 방법이 쓰였다. 그러나 Aumasson과 Bernstein이 seed를 복구하는 공격을 보였고, 이에 CPython은 3.4의 PEP 456에서 키 입력형 해시인 SipHash를 기본 문자열 해시로 채택했다.

### 입력 제한

해시 테이블에 들어가는 사용자 입력의 개수와 크기에 상한을 둔다. 파라미터가 최대 1000개라면 O(n²)의 n 자체가 작다. 가장 값싸고 어느 언어에서나 통한다.

## 결론

- 해시 테이블은 키에서 위치를 계산해 훑지 않고 바로 간다. 충돌은 피할 수 없고, 구현의 본질은 충돌 처리다.
- 체이닝은 단순하고 α가 1을 넘어도 되지만 캐시에 불리하다. 개방 주소법은 캐시에 유리하지만 군집과 tombstone을 관리해야 한다.
- 적재율이 임계치를 넘으면 용량을 2배로 키워 다시 배치한다. 평균은 O(1)이지만 리사이즈 순간은 O(n)이라 p99가 튈 수 있고, 미리 크기를 잡으면 줄일 수 있다.
- 충돌이 한 칸에 몰리면 O(n²)이 되고, 공격자가 이를 의도하면 hash flooding이다. Java `HashMap`은 버킷을 트리로 바꿔 O(log n)으로 제한하고, 근본 대응은 SipHash 같은 무작위화와 입력 상한이다.
