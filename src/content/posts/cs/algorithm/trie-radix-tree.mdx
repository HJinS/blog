## 개요

[해시 테이블](/posts/cs/algorithm/hash-table)은 키 하나를 정확히 찾는 데 가장 빠르다. 하지만 "`ca`로 시작하는 키를 전부 달라"거나 "이 IP 주소를 포함하는 가장 구체적인 라우트가 무엇인가"는 해시로 풀 수 없다. 이 글이 답하는 질문은 두 가지다.

- 접두사(prefix)를 기준으로 찾는 질의는 어떤 구조로 푸는가?
- 그 구조가 메모리를 많이 쓰는 문제는 어떻게 줄이는가?

접두사는 문자열의 앞부분이다. `cart`의 접두사는 `c`, `ca`, `car`, `cart`다.

---

## 1. 왜 해시로는 안 되는가

키가 `car`, `cart`, `cat`, `dog` 네 개라고 하자. 해시 테이블에서 `cart`를 찾는 일은 빠르다. 키 전체를 해시해서 버킷 하나를 보면 된다.

그런데 `ca`로 시작하는 키를 모두 찾으려면 어떻게 해야 할까. `ca`의 해시값은 `car`나 `cat`의 해시값과 아무 관계가 없다. 해시는 비슷한 키를 일부러 흩어 놓는 함수이기 때문이다. 결국 모든 키를 하나씩 꺼내 앞부분을 비교해야 하고, 비용은 키 개수 n에 비례한다.

정렬된 배열이나 B-tree는 접두사 범위를 찾을 수는 있다. 비용은 O(log n)번의 키 비교이고, 비교 한 번도 문자열이면 길이 L만큼 걸린다.

핵심 아이디어는 한 문장이다. **키를 한 글자씩 쪼개 트리의 간선(edge)으로 만들고, 같은 접두사를 가진 키들이 같은 경로를 공유하게 한다.** 이 트리가 트라이(trie, prefix tree)다.

---

## 2. Trie: 글자 하나가 간선 하나

루트(root)에서 시작해 키의 글자를 하나씩 따라 내려간다. 없는 간선은 새로 만들고, 키가 끝나는 노드에는 "여기서 키가 끝난다"는 표시(terminal, 아래 그림의 `*`)를 한다.

`car`, `cart`, `cat`, `dog`를 넣으면 다음 모양이 된다. 각 노드에 적힌 글자는 부모에서 그 노드로 오는 간선의 글자다.

```
              (root)
              /    \
             c      d
             |      |
             a      o
            / \     |
           r*  t*   g*
           |
           t*
```

루트를 빼고 노드는 8개다. `car`, `cart`, `cat`이 `c -> a`를 공유하는 점을 보자. 접두사가 겹칠수록 저장 공간이 줄어든다.

### 삽입과 탐색

두 연산은 같은 길을 따라간다.

| 연산 | 동작 | 비용 |
| --- | --- | --- |
| 삽입 | 글자를 따라가며 없는 간선을 만들고, 마지막 노드에 terminal 표시 | O(L) |
| 정확 탐색 | 끝까지 따라가서 terminal이면 성공, 중간에 간선이 없으면 실패 | O(L) |
| 접두사 탐색 | 접두사 끝 노드까지 내려간 뒤 그 서브트리를 순회 | O(L + 결과 크기) |

여기서 L은 키의 길이다. 중요한 점은 비용이 저장된 키 개수 n과 무관하다는 것이다. 키가 천만 개여도 `cat`을 찾는 일은 3단계다.

예를 들어 `ca`로 시작하는 키를 찾는다고 하자. `c`, `a`를 따라 내려가 `a` 노드에 도착하면 그 아래 서브트리를 훑는다. `car`, `cart`, `cat`이 나온다. 아래에서 가지가 사전순으로 정렬되어 있다면 결과도 사전순으로 나온다.

삭제는 terminal 표시를 지우고, 자식이 없어진 노드를 위로 올라가며 정리한다.

---

## 3. 순진한 trie의 문제: 메모리

trie의 약점은 노드 하나가 가질 수 있는 자식 수다. 바이트 단위 키라면 자식이 최대 256개이므로 가장 쉬운 구현은 노드마다 `child[256]` 배열을 두는 것이다.

64비트 환경에서 포인터 하나가 8바이트이니 노드 하나가 8 x 256 = 2KB다. 위 예의 노드 8개만 해도 16KB지만, 실제로 쓰이는 자식 포인터는 몇 개 되지 않는다. 나머지는 모두 빈 슬롯이다.

배열 대신 해시맵이나 정렬된 리스트로 자식을 들면 빈 슬롯은 줄어든다. 대신 노드마다 객체 오버헤드가 붙고, 자식을 찾는 일이 포인터 추적으로 바뀐다.

또 하나 있다. `car`처럼 자식이 하나뿐인 체인도 글자마다 노드를 만든다. 키가 길고 다른 키와 겹치지 않을수록 이런 체인이 길어진다. 다음 절의 압축은 이 체인을 겨냥한다.

---

## 4. Radix tree: 한 줄 체인을 간선 하나로

라딕스 트리(radix tree, Patricia trie라고도 부른다)는 자식이 하나뿐인 체인을 간선 하나로 합친다. 간선에 글자 하나가 아니라 문자열이 붙는다.

같은 키 집합을 radix tree로 그리면 이렇다. 이번에는 간선의 문자열을 노드 위에 적었다.

```
                 (root)
                 /    \
             "ca"      "dog"*
             /   \
          "r"*    "t"*
           |
          "t"*
```

루트를 빼고 노드는 5개로 줄었다. `c -> a`는 `"ca"` 한 간선이 되었고, `d -> o -> g`는 `"dog"` 한 간선이 되었다. 분기점(`"ca"` 아래에서 `r`과 `t`로 갈라지는 곳)과 terminal만 노드로 남는다. terminal이 아닌 노드는 자식이 2개 이상이므로 그 수는 키 개수보다 적다. 따라서 노드 수는 키 개수 n의 2배를 넘지 않고, 전체 글자 수에 비례하던 trie보다 훨씬 작다. 키가 길고 겹침이 적을수록 효과가 크다.

### 간선 쪼개기(edge split)

압축한 대가는 삽입이 복잡해진다는 점이다. 이미 `"car"` 한 간선만 있는 radix tree에 `cat`을 넣는 상황을 따라가 보자.

```
before                      after
                                
(root)                      (root)
  |                           |
"car"*                      "ca"
                            /   \
                         "r"*    "t"*
```

`cat`은 `car`와 `ca`까지만 같고 세 번째 글자에서 갈라진다. 그래서 간선 `"car"`를 `"ca"`와 `"r"`로 쪼개고, 쪼개진 지점에 새 노드를 만든다. 거기에 `"t"` 간선을 새로 붙인다. 이 작업이 edge split이다. 삭제는 반대로, 자식이 하나만 남은 노드를 부모 간선과 다시 합친다.

## 5. 최장 접두사 매칭: IP 라우팅

접두사를 쓰는 대표적인 곳이 IP 라우팅이다. 라우팅 테이블에는 "이 접두사로 시작하는 주소는 이쪽으로 보낸다"는 규칙이 들어 있다. 규칙 세 개가 있다고 하자.

| 접두사 | 다음 홉 |
| --- | --- |
| `10.0.0.0/8` | A |
| `10.1.0.0/16` | B |
| `10.1.2.0/24` | C |

`/8`은 앞 8비트가 일치한다는 뜻이다. 목적지 `10.1.2.7`은 세 규칙에 모두 맞는다. 이럴 때는 가장 긴, 즉 가장 구체적인 규칙이 이긴다. 이것이 최장 접두사 매칭(longest prefix match, LPM)이다.

주소를 비트 단위 trie에 넣으면 이 규칙이 거의 공짜로 나온다. 목적지의 비트를 따라 내려가면서, 접두사 규칙이 달린 노드를 만날 때마다 그 규칙을 기억해 둔다. 더 내려갈 간선이 없으면 마지막에 기억한 규칙을 쓴다. 아래 그림은 비트 trie를 8비트(한 옥텟) 단위로 묶어 그린 것이다.

```
(root) --- 10 ---> [/8  -> A] --- 1 ---> [/16 -> B] --- 2 ---> [/24 -> C]
```

목적지 `10.1.2.7`은 이렇게 진행된다.

1. `10`을 따라가 `/8` 노드에서 A를 기억한다.
2. `1`을 따라가 `/16` 노드에서 B로 바꿔 기억한다.
3. `2`를 따라가 `/24` 노드에서 C로 바꿔 기억한다.
4. 더 내려갈 간선이 없다. 마지막에 기억한 C로 보낸다.

목적지가 `10.1.9.5`라면 `/8`에서 A, `/16`에서 B를 기억한 뒤 `9` 간선이 없어 멈춘다. 마지막에 기억한 B로 보낸다. 같은 방식으로, `192.168.0.1`처럼 루트에서 곧바로 간선이 없으면 기억한 규칙이 없으므로 일치하는 라우트가 없다.

의사코드로 쓰면 짧다.

```python
def lookup(dst):
    node, best = root, None
    for bit in bits(dst):          # IPv4면 최대 32단계, IPv6면 128단계
        if node.route:
            best = node.route      # 지금까지 본 가장 긴 접두사
        node = node.child[bit]
        if node is None:
            break
    else:
        if node.route:
            best = node.route
    return best
```

깊이가 주소 비트 수로 고정되니 비용은 O(주소 비트 수)다. 라우트가 몇 개든 상관없다. 해시 테이블로 같은 일을 하려면 접두사 길이마다 따로 조회해야 한다. 정렬 배열은 범위 검색은 되지만 "가장 긴 것"을 찾는 일이 번거롭다.

## 6. 다른 자료구조와 비교

| 자료구조 | 정확 일치 | 접두사 질의 / LPM | 정렬 순회 | 특징 |
| --- | --- | --- | --- | --- |
| 해시 테이블 | 평균 O(1) (키 해싱은 O(L)) | 불가 (키 전체를 해싱) | 불가 | 가장 간결하고 캐시 친화적 |
| 정렬 배열 / B-tree | O(log n)번 비교 (비교마다 O(L)) | 범위 탐색으로 가능, LPM은 번거로움 | 가능 | 디스크와 캐시에 유리 |
| Trie | O(L) | 자연스러움 | 가능 (사전순 DFS) | 노드와 포인터가 폭증, 캐시에 불리 |
| Radix tree | O(L) | 자연스러움 | 가능 | 압축으로 메모리 절감, 삽입 시 edge split 비용 |

정확 일치만 필요하다면 해시 테이블이 낫다. 접두사, 사전순 순회, 최장 접두사가 필요할 때 trie 계열을 고른다.

## 7. 실제로 생기는 문제

### 메모리 폭증과 캐시 미스

키 수백만 개를 `child[256]` trie에 넣으면 힙이 수 GB까지 커지고 GC 부담도 커진다. 한글을 코드포인트 단위로 쪼개면 한 노드의 분기 수가 크게 늘어난다. 그래서 보통 바이트 단위로 쪼개고 압축한 노드를 쓴다.

탐색이 모두 포인터를 따라가는 일이다. 다음 노드가 CPU 캐시에 없으면 메모리에서 읽어 오느라 기다리는데, 이를 캐시 미스(cache miss)라 한다. 트리가 깊으면 이 대기 시간이 전체 시간을 지배한다. 이를 줄이려는 변형도 있다.

- multibit trie: 한 노드에서 여러 비트를 한꺼번에 소비해 깊이를 줄인다. LC-trie(level-compressed trie)는 여기에 radix tree식 경로 압축을 더한 구조다.
- ART(adaptive radix tree): 자식 수에 따라 노드 크기를 4, 16, 48, 256칸 중에서 바꿔 빈 슬롯을 줄인다. 대신 자식 수가 경계를 넘을 때 노드를 옮겨 담는 비용이 든다.

### 접두사 질의의 결과 폭발

자동완성에서 한 글자 접두사로 서브트리 전체를 순회하면 응답 시간이 키 수에 비례한다. 접두사가 짧을수록 서브트리가 크다. 노드마다 인기 있는 상위 K개를 미리 저장해 두거나, 결과 개수를 제한해야 한다.

### 라우터의 우선순위 충돌

HTTP 경로 라우터 중에도 radix tree를 쓰는 구현이 있다. 이때 `/users/:id`와 `/users/new`처럼 정적 세그먼트와 와일드카드가 같은 위치에서 겹치면 어느 쪽이 이기는지를 라우터 구현이 정한다. 규칙을 모르고 쓰면 의도와 다른 핸들러가 선택된다.

### 실제 사용처

- Redis는 radix tree 구현인 rax를 자체 라이브러리로 두고 쓴다.
- 리눅스 커널의 FIB(forwarding information base, 커널 라우팅 테이블)는 LC-trie로 IPv4 최장 접두사 매칭을 한다.
- 리눅스 커널 문서는 XArray의 가장 중요한 사용처로 페이지 캐시를 꼽는다. 커널 소스의 `radix-tree.h`는 `radix_tree_root`를 `xarray`의 별칭으로 정의한다. 예전 radix tree 인터페이스가 이제 XArray 위에서 동작한다는 뜻이다.

## 결론

- trie는 키를 글자(비트) 단위로 쪼개 접두사를 공유한다. 탐색 비용이 키 개수가 아니라 키 길이 L에만 달린다.
- 순진한 구현은 빈 자식 슬롯 때문에 메모리가 많이 든다. radix tree는 자식이 하나인 체인을 간선 하나로 압축해 노드 수를 키 개수에 비례하게 만든다. 대신 삽입 때 edge split이 필요하다.
- 최장 접두사 매칭은 비트 trie를 내려가며 "마지막으로 본 규칙"을 기억하면 풀린다. 비용은 주소 비트 수로 고정된다.
- 정확 일치만 필요하면 해시 테이블이 낫고, 접두사나 사전순 순회가 필요하면 trie 계열이 맞다.
