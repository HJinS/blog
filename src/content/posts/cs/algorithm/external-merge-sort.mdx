## 개요

[앞 글](/posts/cs/algorithm/heap-timing-wheel)에서 힙(heap)이 "여러 후보 중 최솟값을 빠르게 꺼내는 구조"라는 것을 봤다. 이번 글은 그 힙을 디스크 위의 정렬에 쓴다.

이 글이 답하는 질문은 두 가지다.

- 메모리보다 큰 데이터를 어떻게 정렬하고, 비용은 무엇으로 결정되는가?
- 데이터가 메모리를 넘는 순간 쿼리가 갑자기 느려지는 이유는 무엇인가?

DB의 `ORDER BY`, `GROUP BY`, 정렬 병합 조인, 인덱스 빌드가 모두 이 구조를 쓴다. 정렬 병합 조인에서 정렬이 메모리를 넘으면 어떻게 하느냐는 [조인 알고리즘 글](/posts/cs/database/join-algorithms-cardinality)에서 남겨 둔 질문이다.

---

## 1. 왜 일반 정렬로는 안 되는가

퀵소트나 힙소트는 데이터가 전부 메모리에 있다고 가정한다. 데이터가 메모리보다 크면 이 가정이 깨진다.

메모리를 넘는 데이터를 디스크에 두고 퀵소트를 그대로 돌리면 어떻게 될까. 퀵소트는 배열의 이곳저곳을 오가며 원소를 교환한다. 이 접근이 디스크에서는 임의 접근(random access)이 되어 매우 느리다. 비교 횟수는 같아도 비용의 단위가 달라진다.

디스크가 관련되면 CPU 비교 횟수보다 디스크를 몇 번 오가는가가 비용을 지배한다. 그래서 외부 정렬(external sort)은 비교 횟수가 아니라 pass 수를 줄이는 방향으로 설계한다. 여기서 pass는 전체 데이터를 처음부터 끝까지 한 번 읽고 쓰는 일을 말한다.

---

## 2. 핵심 아이디어

> 메모리에 들어가는 만큼씩 잘라 정렬해 두고(run 생성), 정렬된 조각들을 순차적으로 합친다(k-way 병합).

정렬된 조각을 run이라고 부른다. 합치는 단계는 디스크를 앞에서부터 순서대로만 읽고 쓰기 때문에 순차 I/O(sequential I/O)만 쓴다.

```text
입력 10GB (정렬 안 됨)
   |
   |  Phase 1: 100MB씩 읽기 -> 메모리에서 정렬 -> 디스크에 쓰기
   v
run 1 | run 2 | run 3 | ... | run 100      (각 100MB, 각각 정렬됨)
   |
   |  Phase 2: 여러 run의 맨 앞 원소를 비교하며 합치기
   v
정렬된 출력 10GB
```

---

## 3. Phase 1: run 만들기

메모리 M이 100MB이고 데이터 N이 10GB라고 하자. 편의상 1GB = 1,000MB로 계산한다.

1. 입력에서 100MB를 읽는다.
2. 메모리에서 퀵소트 같은 일반 정렬로 정렬한다.
3. 결과를 임시 파일(run)로 쓴다.
4. 입력이 끝날 때까지 반복한다.

run의 개수는 `R = ceil(N / M) = ceil(10,000MB / 100MB) = 100`개다. 이 단계에서 데이터 전체를 한 번 읽고 한 번 쓴다. 즉 I/O는 읽기 10GB와 쓰기 10GB, 합계 20GB다.

이제 100개의 정렬된 조각이 있다. 남은 일은 이것을 하나로 합치는 것이다.

---

## 4. Phase 2: k-way 병합과 최소 힙

### 두 개를 합치는 법

정렬된 run 두 개를 합치는 법은 정렬 병합 조인에서 본 투 포인터와 같다. 두 run의 맨 앞 원소를 비교해 작은 쪽을 출력하고 그 run의 포인터를 한 칸 옮긴다. 이것이 2-way 병합이다.

### k개를 동시에 합치는 법

run이 k개면 맨 앞 원소 k개 중 최솟값을 매번 찾아야 한다. 매번 k개를 전부 훑으면 원소 하나에 k번 비교한다. 여기서 최소 힙(min-heap)을 쓴다.

1. 각 run에서 맨 앞 원소를 하나씩 꺼내 힙에 넣는다. 힙에는 항상 k개가 들어 있다.
2. 힙에서 최솟값을 꺼내 출력한다. 비용은 `O(log k)`다.
3. 꺼낸 원소가 속한 run에서 다음 원소를 읽어 힙에 넣는다.
4. 힙이 빌 때까지 반복한다.

작은 예로 따라가 보자. run 세 개(k=3)가 있다.

```text
run A: 1  4  9
run B: 2  3  8
run C: 5  6  7

힙(각 run의 맨 앞)    꺼냄    다음에 넣는 것
{1(A), 2(B), 5(C)}    1(A)    A의 4
{4(A), 2(B), 5(C)}    2(B)    B의 3
{4(A), 3(B), 5(C)}    3(B)    B의 8
{4(A), 8(B), 5(C)}    4(A)    A의 9
...                   ...     ...
출력: 1 2 3 4 5 6 7 8 9
```

힙의 크기는 run 개수 k뿐이므로 원소 하나당 비교는 `log2 k`번이다. 전체 CPU 비용은 `O(N log k)`이고, 병합 pass 수와 곱하면 `O(N log N)`으로 메모리 정렬과 같은 차수다. 병목은 CPU가 아니라 디스크다.

### 한 번에 몇 개까지 합칠 수 있나 (fan-in)

k를 아무리 키워도 되는 것은 아니다. 각 run에서 읽어 온 블록을 담는 입력 버퍼가 k개, 출력 버퍼가 1개 필요하고, 이 모두가 메모리 M에 들어가야 한다. 버퍼 크기를 B라고 하면 다음 관계가 성립한다.

```text
(k + 1) x B <= M     ->     k <= M / B - 1
```

버퍼를 1MB로 잡으면 `k <= 100 / 1 - 1 = 99`다. 한 번에 최대 99개를 합칠 수 있다. 이 한계를 fan-in이라고 부른다.

버퍼를 왜 한 원소가 아니라 블록으로 잡는가. 디스크는 한 번에 큰 덩어리를 읽을수록 효율이 좋고, 매번 원소 하나씩 run을 오가면 임의 접근이 되기 때문이다. 버퍼가 작아질수록 k는 커지지만 읽기 하나가 작아져서 시크가 늘어난다. 이것이 5절 트레이드오프의 핵심이다.

## 5. 숫자로 계산해 보기

run이 100개, 한 번에 합칠 수 있는 run 수가 k일 때 병합 pass 수는 `ceil(log_k 100)`이다. 병합이 끝나면 한 run이 되어야 하므로 한 pass마다 run 수가 k분의 1로 줄어든다고 생각하면 된다.

한 pass는 10GB를 읽고 10GB를 쓴다. 즉 pass 하나의 I/O는 20GB다. 마지막 pass의 출력 쓰기도 포함한다. 전체 pass 수는 run 생성 1번에 병합 pass를 더한 값이다.

| fan-in k | 병합 pass 수 | 전체 pass 수 | 총 I/O |
|---|---|---|---|
| 2 | 7 (2^7 = 128 >= 100) | 8 | 160GB |
| 8 | 3 (`8^2 = 64 < 100 <= 512`) | 4 | 80GB |
| 10 | 2 (10^2 = 100) | 3 | 60GB |
| 99 | 2 (`99 < 100`) | 3 | 60GB |

k를 2에서 8로 올리면 I/O가 160GB에서 80GB로 절반이 된다. pass 수가 `log_k`로 줄기 때문이다. 이것이 "병합은 많이 묶을수록 좋다"의 정량적 의미다.

### 100개인데 99개밖에 못 합친다

마지막 줄이 흥미롭다. run이 100개인데 fan-in이 99라 한 pass로 끝나지 않는다. 그렇다고 pass를 통째로 한 번 더 돌릴 필요는 없다. 첫 pass에서 run 두 개만 합쳐 99개로 만들고, 마지막 pass에서 99개를 합치면 된다.

```text
run 생성          읽기 10GB   쓰기 10GB    = 20GB
부분 병합(2개)     읽기 200MB  쓰기 200MB   = 0.4GB
최종 99-way 병합   읽기 10GB   쓰기 10GB    = 20GB
------------------------------------------------
합계 약 40.4GB
```

통째로 두 pass를 도는 60GB보다 3분의 1쯤 줄어든다. 요점은 첫 병합에서 run 수를 fan-in 이하로 맞출 만큼만 합치는 것이다. 데이터 전체를 한 번 더 읽고 쓰는 대신 일부만 읽고 쓰면 된다.

### 2 pass로 끝낼 수 있는 한계

run 생성 뒤 한 번의 병합으로 끝내려면 `R <= k`여야 한다. `R = N / M`, `k = M / B`이므로 `N <= M^2 / B`다. M=100MB, B=1MB이면 `100 x 100 / 1 = 10,000MB`, 즉 10GB다. 이 예시의 10GB는 정확히 2 pass로 끝낼 수 있는 한계선에 걸쳐 있다.

그 한계를 넘으면 병합 pass가 하나 늘어난다. 데이터가 커지면 pass가 로그로 늘어나므로 비용은 완만하게 느는 것이 아니라 한계선마다 계단처럼 오른다. 메모리를 넘는 순간 성능이 계단식으로 나빠지는 현상의 정체가 이것이다.

| 단계 | 처리 가능한 크기 (M=100MB, B=1MB) | 읽기·쓰기 횟수 |
|---|---|---|
| 메모리 내 정렬 | 100MB 이하 | 입력 1번 읽기 |
| 외부 정렬 2 pass | 약 10GB 이하 | 데이터당 읽기 2번, 쓰기 2번 |
| 외부 정렬 3 pass | 약 1TB 이하 | 데이터당 읽기 3번, 쓰기 3번 |

3 pass의 한계는 `M^3 / B^2 = 100^3 / 1 = 1,000,000MB`, 약 1TB다.

## 6. 구현에서 생기는 문제와 선택지

### 버퍼 크기와 fan-in의 균형

fan-in을 키우려고 버퍼를 줄이면 run마다 읽는 조각이 작아져 디스크 시크가 늘어난다. 반대로 버퍼를 키우면 fan-in이 줄어 pass가 늘어난다. 둘 사이의 균형점을 찾는 것이 외부 정렬 구현의 핵심 튜닝이다. 앞의 10GB 예시에서 B=1MB 대신 B=0.5MB를 쓰면 k=199가 되어 run 100개를 한 pass로 합칠 수 있다. 대신 읽기 요청 하나가 반으로 작아진다.

### run을 더 길게 만들기, replacement selection

run의 길이가 M으로 고정되는 것은 아니다. 대체 선택(replacement selection)은 메모리에 힙을 두고, 힙에서 가장 작은 값을 출력한 뒤 새 입력을 그 자리에 넣는다. 새 값이 방금 출력한 값보다 크거나 같으면 같은 run에 이어 붙일 수 있고, 작으면 다음 run 몫으로 표시해 둔다. 입력이 무작위이면 평균 run 길이가 메모리 크기의 약 2배가 된다(Knuth의 "snowplow" 논증). run 수가 절반으로 준다.

다만 실제 DB가 늘 이 방식을 쓰지는 않는다. PostgreSQL은 9.6에서 run을 만들 때 replacement selection 대신 퀵소트를 쓰도록 바꿨다. 릴리스 노트는 그 이유로 CPU 캐시를 더 잘 활용한다는 점을 든다. 11에서는 남아 있던 설정(`replacement_sort_tuples`)마저 지웠다.

### 정렬 자체를 피하는 방법

외부 정렬은 비싸므로 가능하면 피한다.

| 방식 | 조건 | 특징 |
|---|---|---|
| 메모리 내 정렬 | N이 M 이하 | I/O가 없다 |
| 외부 병합 정렬 | N이 M 초과 | 임시 파일을 순차 I/O로 처리한다 |
| Top-N 힙 | `ORDER BY ... LIMIT n` | n개만 힙에 유지하므로 N이 커도 디스크를 쓰지 않을 수 있다 |
| 인덱스 순서 스캔 | 정렬 키에 B-tree 인덱스가 있다 | 정렬 단계 자체가 사라진다. 대신 쓰기 때마다 인덱스를 유지하는 비용을 낸다 |

`LIMIT` 쿼리는 힙에 n개만 두는 방식이라 N 전체를 정렬하지 않는다. 오름차순 상위 n개를 구한다면 최대 힙을 쓴다. 지금까지 고른 n개 중 가장 큰 값(현재 n등)이 루트에 있으므로, 그보다 작은 값이 오면 루트만 갈아치우면 된다.

## 7. 실제 DB에서는 어떻게 보이나

PostgreSQL에서 정렬이 쓸 수 있는 메모리는 `work_mem`이 정한다. 기본값은 4MB다. 정렬 결과가 이 값을 넘으면 위에서 본 외부 정렬이 일어난다. `EXPLAIN ANALYZE`에서는 이를 `Sort Method: quicksort Memory`(메모리 내)와 `Sort Method: external merge Disk`(디스크 사용)의 차이로 볼 수 있다.

AWS Database Blog의 실험이 이를 잘 보여 준다. 행 폭이 약 354바이트이고 약 1,300만 행인 테이블을 기본 `work_mem`(4MB)으로 정렬했다. 병렬 쿼리라 프로세스 3개(리더와 워커 2개)가 각자 정렬했고, 임시 파일이 합쳐서 약 1.9GB 생겼으며 각 프로세스의 정렬은 약 53초 걸렸다. 로그에는 16개 tape(PostgreSQL이 run을 담는 임시 파일 단위)로 run을 만들고 15-way 병합을 하는 모습이 찍혀 있다. 앞에서 계산한 `k = M/B - 1`과 같은 구조다. 4MB로 15-way 병합을 하려면 버퍼 하나가 수백 KB 수준으로 작다.

여기서 "그럼 `work_mem`을 크게 올리면 되겠다"는 결론은 위험하다. PostgreSQL 문서에 따르면 `work_mem`은 정렬이나 해시 연산 하나가 쓸 수 있는 양이다. 복잡한 쿼리는 이런 연산을 여러 개 동시에 수행하고, 세션도 여러 개가 동시에 돌 수 있다. 전체 메모리는 `work_mem`의 여러 배가 될 수 있다. 전역값을 올리기보다 정렬이 큰 쿼리가 도는 세션에서만 올리는 쪽이 안전하다.

## 8. 정렬 병합 조인과의 연결

[조인 알고리즘 글](/posts/cs/database/join-algorithms-cardinality)의 정렬 병합 조인은 양쪽을 조인 키로 정렬한 뒤 투 포인터로 합친다. 입력이 메모리보다 크면 앞 단계의 정렬이 이 글의 외부 정렬이다. 이때 비용은 비교 횟수보다 pass 수가 지배한다.

- 정렬된 입력이 이미 있으면(인덱스 순서, 앞 단계의 `ORDER BY`) 외부 정렬을 건너뛴다.
- 해시 조인도 build 쪽이 메모리를 넘으면 데이터를 여러 조각(batch)으로 나눠 디스크에 내렸다가 다시 읽는다. 방식은 다르지만 데이터를 한 번 더 읽고 쓰는 비용이 생긴다는 점은 같다.

MapReduce나 Spark의 셔플 정렬도 비슷한 원리를 쓴다. 노드마다 메모리 안에서 정렬한 조각을 만들고, 이를 병합한다.

## 결론

- 외부 정렬은 메모리 크기 M으로 자른 정렬된 조각(run)을 만든 뒤 k-way 병합으로 합친다. 비용은 CPU 비교가 아니라 디스크를 몇 번 오가는지(pass 수)가 결정한다.
- k-way 병합은 최소 힙으로 k개 run의 맨 앞 원소 중 최솟값을 `O(log k)`에 뽑는다. fan-in은 `M / B - 1`로 제한되고, 병합 pass 수는 `ceil(log_k R)`이다.
- 100MB 메모리로 10GB를 정렬하면 run이 100개이고, 2-way 병합은 총 160GB, 8-way는 80GB, 99-way는 60GB(부분 병합 최적화로 약 40.4GB)를 읽고 쓴다.
- 데이터가 `M^2 / B`를 넘으면 pass가 하나 늘어나기 때문에 성능은 완만하지 않고 계단식으로 나빠진다.
- 가능하면 정렬 자체를 피한다. 인덱스 순서 스캔이나 `LIMIT`용 Top-N 힙으로 피할 수 있고, 메모리를 늘리는 것은 `work_mem`처럼 동시성이 곱해지는 값이면 신중해야 한다.
