## 개요

같은 B+tree 인덱스인데도 DB마다 읽기와 쓰기 비용이 다르다. 차이는 인덱스 리프(leaf)가 무엇을 담느냐에서 나온다.

이 글은 두 가지 질문에 답한다.

- InnoDB의 세컨더리 인덱스는 왜 행의 위치 대신 PK를 저장할까?
- 그래서 PK를 UUID로 잡으면 무엇이 느려질까?

B+tree의 구조(리프끼리 연결되고, 페이지 단위로 읽고, 가득 차면 split하는 것)는 [B+tree vs LSM-tree](/posts/cs/database/b-tree-vs-lsm-tree)에서 다뤘다. 이 글은 그 내용을 알고 있다고 가정한다.

## 1. 인덱스 리프에 무엇을 넣을 것인가

### 왜 필요한가

`users` 테이블에서 `WHERE id = 7`로 한 행을 찾는다고 하자. B+tree로 `id`를 찾았다면 다음 질문이 남는다. 찾은 자리에 행 데이터가 있을까, 행이 있는 곳의 주소만 있을까?

이 선택에 따라 읽기 경로와 쓰기 비용이 모두 달라진다.

### 핵심 아이디어

리프에 행 전체를 넣으면 클러스터드 인덱스, 위치만 넣으면 힙 방식이다.

### 두 가지 방식

먼저 용어를 정리한다.

- 클러스터드 인덱스(clustered index): 행 자체가 인덱스 리프에 키 순서대로 저장되는 구조다. 테이블당 하나뿐이다.
- 세컨더리 인덱스(secondary index): PK 외 컬럼으로 만든 보조 인덱스다.
- 힙(heap): 행을 순서 없이 쌓아 두는 저장 공간이다.
- ctid: PostgreSQL에서 행의 물리 위치다. (페이지 번호, 페이지 안 슬롯 번호)로 이루어진다.

두 DB는 이렇게 다르다.

| 구분 | InnoDB (MySQL) | PostgreSQL |
|---|---|---|
| 행 저장 | PK 순서로 정렬된 B+tree 리프 안 | 힙이라는 별도 파일 |
| PK 인덱스 리프 | 행 전체 | 행의 위치(ctid) |
| 세컨더리 인덱스 리프 | (인덱스 컬럼, PK) | (인덱스 컬럼, ctid) |

InnoDB에서는 PK 인덱스가 곧 테이블이다. 그래서 InnoDB에서 PK를 고르는 일은 행이 디스크에 놓이는 순서를 정하는 일이다.

## 2. 세컨더리 인덱스로 조회하면 일어나는 일

### 왜 필요한가

`WHERE last_name = 'Kim'`처럼 PK가 아닌 컬럼으로 찾는 일은 흔하다. 이때 세컨더리 인덱스가 어떻게 행까지 길을 안내하는지 알아야 읽기 비용을 계산할 수 있다.

### 핵심 아이디어

InnoDB의 세컨더리 인덱스는 행의 위치가 아니라 PK 값을 알려 주고, 그 PK로 클러스터드 인덱스를 한 번 더 탐색한다.

### 단계별 동작

```text
SELECT * FROM users WHERE last_name = 'Kim';

[세컨더리 인덱스 B+tree]            [클러스터드 인덱스 B+tree = 테이블]
 리프: (last_name, PK)               리프: (PK, 행 전체)

 1) 'Kim' 탐색  ----------------+
    리프에서 ('Kim', 42) 발견    |
                                 | 2) PK=42 로 다시 탐색
                                 +----------------->  (42, Kim, 서울, ...)
                                                      3) 행 반환
```

MySQL 문서도 같은 설명이다. 세컨더리 인덱스의 각 레코드는 인덱스 컬럼과 그 행의 PK 컬럼을 담고, InnoDB는 이 PK 값으로 클러스터드 인덱스에서 행을 찾는다.

탐색이 B+tree 두 개에서 일어나므로 비용은 대략 $O(\log n)$을 두 번 낸 만큼이다. 이 두 번째 탐색을 흔히 북마크 룩업(bookmark lookup)이라 부른다.

### 생기는 문제와 해결: 커버링 인덱스

`Kim`이 1만 명이면 두 번째 탐색을 1만 번 한다. 각각이 서로 다른 페이지를 건드리면 랜덤 I/O가 된다.

필요한 컬럼이 전부 세컨더리 인덱스 안에 있으면 두 번째 탐색을 생략할 수 있다. 이를 커버링 인덱스(covering index)라 한다.

```sql
-- INDEX (last_name) 하나만 있어도 PK 컬럼은 이미 리프에 들어 있다
SELECT id, last_name FROM users WHERE last_name = 'Kim';
```

세컨더리 리프에는 PK가 자동으로 포함되므로, 위 쿼리는 `id`를 읽으려고 테이블까지 갈 필요가 없다. `EXPLAIN`의 `Extra`에 `Using index`로 나타난다.

대가도 있다. 컬럼을 더 넣을수록 인덱스가 커지고, 쓰기 때 갱신할 양도 늘어난다.

## 3. 왜 위치가 아니라 PK를 저장할까

### 왜 필요한가

위치(주소)를 저장하면 조회는 한 번에 끝난다. 그런데 InnoDB는 일부러 한 번 더 도는 설계를 택했다. 이유는 클러스터드 인덱스 안에서 행이 자주 움직이기 때문이다.

### 핵심 아이디어

행의 위치는 바뀌지만 PK는 바뀌지 않으므로, 세컨더리 인덱스가 PK를 가리키면 행이 이동해도 고칠 필요가 없다.

### 단계별 동작

클러스터드 B+tree는 페이지가 가득 차면 쪼개진다(split, 5절에서 자세히 설명). 쪼개질 때 행 절반이 새 페이지로 이동한다.

세컨더리 인덱스가 물리 위치를 갖고 있다고 가정해 보자. 테이블에 세컨더리 인덱스가 5개 있다면, 이동한 행 하나마다 인덱스 5개의 엔트리를 모두 고쳐야 한다. 페이지 하나에 행이 수십~수백 개이니 split 한 번이 수백~수천 번의 인덱스 수정으로 번진다.

PK를 저장하면 이 비용이 사라진다. 행이 어디로 가든 PK는 그대로이기 때문이다.

### 생기는 문제

- 조회가 항상 두 번 탐색한다(커버링으로 완화).
- PK가 길면 모든 세컨더리 인덱스가 같이 커진다.

두 번째 문제는 다음 절의 주제다.

## 4. 긴 PK는 모든 세컨더리 인덱스를 키운다

### 왜 필요한가

PK를 고를 때 "어차피 PK는 한 번만 저장되는 것 아닌가" 하고 생각하기 쉽다. InnoDB에서는 그렇지 않다.

### 핵심 아이디어

PK 값은 세컨더리 인덱스 엔트리마다 복사되어 저장되므로, PK 크기는 인덱스 수만큼 곱해진다.

### 구체적인 숫자

행이 1억 개이고 세컨더리 인덱스가 5개인 테이블로 비교한다.

| PK 타입 | PK 크기 | 인덱스 5개 x 1억 행의 PK 복사본 |
|---|---|---|
| BIGINT | 8바이트 | 약 4GB |
| UUID 문자열 (CHAR(36)) | 36바이트 | 약 18GB |
| UUID 바이너리 (BINARY(16)) | 16바이트 | 약 8GB |

숫자는 "PK 크기 x 5 x 1억"으로 PK 복사본만 센 단순 계산이다. 실제 인덱스는 페이지 여유 공간과 내부 노드까지 있어 이보다 크다.

인덱스가 커지면 한 페이지(InnoDB 기본 16KB)에 들어가는 엔트리가 준다. 같은 메모리(버퍼 풀, buffer pool: 디스크 페이지를 캐시하는 InnoDB의 메모리 영역)에 올릴 수 있는 인덱스 양도 줄어 캐시 적중률이 떨어진다. MySQL 문서도 PK가 길면 세컨더리 인덱스가 더 많은 공간을 쓰므로 짧은 PK가 유리하다고 설명한다.

UUID를 꼭 써야 한다면 문자열 대신 `BINARY(16)`으로 저장하면 크기가 절반 이하로 준다.

## 5. 랜덤 PK와 순차 PK의 페이지 분할

### 왜 필요한가

PK 크기 말고도 PK의 순서가 문제를 일으킨다. 클러스터드 인덱스에서는 PK 순서가 곧 행의 저장 순서이기 때문이다.

### 핵심 아이디어

새 행이 항상 맨 끝에 붙으면 페이지가 꽉 차게 채워지고, 아무 데나 끼어들면 페이지가 쪼개지며 반쯤 비게 된다.

### 단계별 동작: 순차 PK

`AUTO_INCREMENT`처럼 계속 커지는 PK를 보자. 리프 페이지 하나에 행 100개가 들어간다고 가정한다.

```text
리프1(100/100)  리프2(100/100)  리프3(100/100)  리프4(37/100)
                                                  ^ 새 행은 항상 여기
```

- 새 행은 마지막 리프에만 들어간다.
- 마지막 리프가 차면 빈 새 페이지를 하나 붙인다.
- 앞 페이지는 가득 찬 채로 남는다.

MySQL 문서에 따르면 순차 삽입일 때 페이지는 약 15/16(약 94%)까지 찬다. 나머지 1/16은 나중의 갱신을 위해 비워 둔다.

### 단계별 동작: 랜덤 PK (UUID v4)

UUID v4는 무작위 값이라 새 행이 어느 리프에 들어갈지 알 수 없다.

```text
삽입 전:  리프1(100/100)  리프2(100/100)  리프3(100/100)

'리프2 범위'에 새 행 삽입 -> 리프2가 가득 참 -> 분할

삽입 후:  리프1(100/100)  리프2(50/100)  리프2'(51/100)  리프3(100/100)
                          ^ 절반씩 나뉘어 둘 다 반쯤 빔
```

이때 세 가지 비용이 생긴다.

- 분할: 새 페이지를 할당하고 행 절반을 옮기고 부모 노드도 고친다.
- 낮은 채움률: MySQL 문서는 랜덤 삽입 시 페이지가 1/2에서 15/16 사이로 찬다고 한다. 같은 데이터를 담는 데 더 많은 페이지가 필요하다.
- 캐시 미스: 삽입할 때마다 임의의 리프가 필요하다. 테이블이 버퍼 풀보다 커지면 그 페이지를 디스크에서 읽어 와야 한다.

초반에는 모든 페이지가 메모리에 있어서 티가 나지 않는다. 데이터가 메모리를 넘어서는 시점부터 INSERT가 급격히 느려지고, 버퍼 풀 적중률이 떨어지는 형태로 나타난다.

### 순차 PK의 반대편 문제

순차 키가 항상 이기는 것은 아니다. 모든 쓰기가 맨 오른쪽 한 페이지에 몰린다(핫스팟, hotspot). 동시 INSERT가 매우 많으면 그 페이지에서 경합이 생길 수 있다.

| 구분 | 순차 PK | 랜덤 PK |
|---|---|---|
| 삽입 위치 | 마지막 리프 | 임의 리프 |
| 페이지 채움 | 약 94% | 50~94% |
| 페이지 분할 | 드묾 | 잦음 |
| 캐시 | 최근 페이지만 필요 | 전체 인덱스가 필요 |
| 약점 | 한 지점에 쓰기 집중 | 분할, 캐시 미스, 인덱스 비대 |

### 절충안

시간 순서를 앞에 두고 뒤에 무작위 값을 붙이는 키(UUIDv7, ULID)가 있다. 값이 대체로 증가하므로 삽입이 끝 쪽에 모이고, 뒤쪽 무작위 부분 덕에 여러 서버가 충돌 없이 ID를 만든다.

외부에 노출할 ID가 필요하다면 내부 PK는 `AUTO_INCREMENT`로 두고 UUID는 별도 유니크 컬럼으로 두는 방법도 있다. 이렇게 의미 없는 내부 키를 PK로 쓰는 것을 대리키(surrogate key)라 한다. 이 경우 UUID 인덱스가 세컨더리 인덱스가 된다는 점은 감수해야 한다.

## 6. 쓰기 증폭: PostgreSQL과 InnoDB의 갱신 방식

### 왜 필요한가

지금까지는 읽기와 삽입을 봤다. 갱신(UPDATE)에서는 두 구조의 차이가 더 크게 드러난다.

### 핵심 아이디어

행 하나를 바꿨는데 디스크에 쓰는 양이 그보다 훨씬 많아지는 현상을 쓰기 증폭(write amplification)이라 한다. 인덱스가 위치를 가리키는지 PK를 가리키는지에 따라 증폭되는 정도가 달라진다.

### 단계별 동작

`birth_year` 컬럼 하나를 바꾸는 UPDATE를 생각한다. 인덱스는 PK, (first, last), `birth_year` 세 개다.

PostgreSQL은 기존 행을 고치지 않고 새 버전(튜플)을 만든다. 새 튜플은 새 위치(새 ctid)를 갖는다. 인덱스가 ctid를 가리키므로 모든 인덱스에 새 위치를 써야 한다. 옛 버전을 남기는 이유는 [MVCC 글](/posts/cs/database/mvcc-snapshot-isolation-write-skew)에서 다룬다.

```text
PostgreSQL:  새 튜플 1 + 인덱스 3개 = 최소 4번의 쓰기 (+ 각각 WAL 기록)
InnoDB:      행을 제자리 갱신 + birth_year 인덱스만 갱신
             PK, (first, last) 인덱스는 건드리지 않음
```

InnoDB는 행을 제자리에서 고치고 이전 버전을 undo 로그에 보관한다. 세컨더리 인덱스는 PK를 담고 있고 PK는 안 바뀌었으니, `birth_year`가 들어 있는 인덱스만 갱신하면 된다.

### 생기는 문제

인덱스를 "일단 많이" 만들어 두면 쓰기마다 고칠 B+tree가 는다. 인덱스가 12개인 PostgreSQL 테이블이라면, 인덱스 컬럼 하나만 바꿔도 12개 모두에 새 위치를 써야 한다.

반대로 InnoDB의 약점도 있다. PK 값을 바꾸면 행이 클러스터드 B+tree 안에서 다른 자리로 옮겨 가고, 모든 세컨더리 인덱스의 PK 복사본도 고쳐야 한다. PK는 바뀌지 않는 값으로 설계하는 것이 원칙이다.

### PostgreSQL의 완화책: HOT 업데이트

PostgreSQL이 항상 불리한 것은 아니다. 바뀐 컬럼에 인덱스가 걸려 있지 않고 같은 페이지에 새 튜플을 둘 공간이 있으면, HOT(Heap-Only Tuple) 업데이트로 인덱스 갱신을 건너뛴다.

정확히 말하면 PostgreSQL은 "인덱스 컬럼을 자주 바꾸고 인덱스가 많은" 워크로드에서 불리하다. 반대로 InnoDB는 PK 갱신이나 랜덤 PK 삽입에서 불리하다. 워크로드의 갱신 패턴을 먼저 봐야 한다.

## 7. 사례: Uber가 Postgres에서 MySQL로 옮긴 이유

Uber Engineering은 2016년 7월 26일 글에서 위 구조 차이를 이유로 들어 Postgres에서 MySQL로 옮긴 경험을 설명했다. 글에서 확인되는 내용은 다음과 같다.

- 위 `birth_year` 예시와 같은 상황에서 Postgres는 새 튜플과 인덱스 갱신으로 최소 4번의 물리 업데이트가 필요하다고 설명한다. 각각이 WAL에도 기록되어 실제 디스크 쓰기는 더 많다.
- 인덱스가 12개인 테이블에서는, 인덱스 하나에만 걸린 필드의 변경도 12개 인덱스 모두에 전파된다고 적었다.
- Postgres의 물리 복제는 이 WAL을 그대로 전송한다. 데이터센터 사이 대역폭이 부담이 되었고, 피크 때 WAL 아카이브가 뒤처졌다고 한다.
- 9.2 버전의 버그로 복제본이 타임라인 전환을 잘못 따라가 일부 WAL 레코드를 잘못 적용했고, 그 결과 한 사용자 ID에 행이 두 개 조회되는 문제가 있었다고 한다.

이 글에는 PostgreSQL 쪽 응답도 나왔다. Markus Winand는 Uber의 불만이 갱신 위주의 특정 워크로드에서 나온 것이므로 PostgreSQL 일반에 대한 평가로 읽으면 안 된다고 정리했다.

EnterpriseDB의 Robert Haas는 인덱스 컬럼을 갱신할 때의 쓰기 증폭과 내장 논리 복제의 부재를 실제 약점으로 인정하고, 다른 저장 형식을 붙일 수 있는 구조가 필요하다고 썼다.

따라서 이 사례는 "어느 쪽이 낫다"가 아니라, 구조 차이가 쓰기 패턴에 따라 비용을 어떻게 바꾸는지 보여 주는 사례로 읽는 것이 좋다. 복제 쪽 이야기는 [WAL과 크래시 복구](/posts/cs/database/wal-aries-crash-recovery)에서 다시 짚는다.

## 8. 트레이드오프 정리

| 항목 | InnoDB (클러스터드, 세컨더리는 PK 참조) | PostgreSQL (힙, 인덱스는 ctid 참조) |
|---|---|---|
| PK 조회 | 탐색 1회로 행까지 도달 | 인덱스 탐색 + 힙 접근 |
| 세컨더리 조회 | 세컨더리 탐색 + PK 재탐색 (커버링이면 생략) | 인덱스 탐색 + 힙 접근 |
| 인덱스 컬럼이 아닌 값 갱신 | 행만 제자리 갱신 | 새 튜플 생성, HOT가 아니면 모든 인덱스 갱신 |
| 인덱스 컬럼 갱신 | 해당 인덱스만 갱신 | 모든 인덱스 갱신 |
| PK 갱신 | 행 이동 + 모든 세컨더리 갱신 (비쌈) | 일반 갱신과 비슷 |
| PK 길이의 영향 | 모든 세컨더리 인덱스가 커짐 | 인덱스는 ctid(고정 길이)를 가리킴 |
| 구조적 약점 | 랜덤 PK 삽입, 긴 PK | 갱신이 잦으면 죽은 튜플(bloat)과 vacuum 부담 |

InnoDB에서 PK를 고르는 실용적 기준을 정리하면 다음과 같다.

- 짧고, 바뀌지 않고, 대체로 증가하는 값을 쓴다.
- UUID가 필요하면 UUIDv7 같은 시간 정렬 키나 `BINARY(16)` 저장을 고려한다.
- 세컨더리 인덱스는 필요한 만큼만 만든다. 인덱스 하나는 쓰기마다 갱신할 B+tree 하나다.
- 느린 조회는 `EXPLAIN`으로 `Using index`(커버링) 여부를 먼저 확인한다.

## 결론

- InnoDB는 PK 순서로 행을 저장하는 클러스터드 인덱스를 쓰고, 세컨더리 인덱스는 PK 값을 가진다. 그래서 세컨더리 조회는 B+tree를 두 번 탐색한다.
- 위치 대신 PK를 저장하는 이유는 행이 이동해도 세컨더리 인덱스를 고치지 않기 위해서다. 대가는 재탐색과 인덱스 크기다.
- PK는 모든 세컨더리 인덱스에 복사되므로 짧을수록 좋고, 랜덤 PK는 페이지 분할과 캐시 미스를 늘린다.
- 쓰기 증폭의 정도는 인덱스 개수와 구조(힙인지 클러스터드인지)에 달려 있고, 어느 쪽이 항상 낫지는 않다.

인덱스는 "키로 행을 빨리 찾는 구조"다. 이어지는 글 [조인 알고리즘과 카디널리티 추정](/posts/cs/database/join-algorithms-cardinality)에서는 인덱스가 있느냐 없느냐가 두 테이블을 합치는 방법을 어떻게 바꾸는지 본다.
