## 개요

`SELECT ... WHERE id = 7 FOR UPDATE`가 0행을 돌려줬다. 잠글 행이 없는데 무엇이 잠긴 걸까?

InnoDB는 행이 없어도 "그 행이 들어갈 자리"를 잠근다. 이 글은 두 가지를 답한다.

- 왜 존재하지 않는 구간까지 잠가야 하는가
- 그 잠금 때문에 왜 두 세션의 INSERT가 서로를 기다리는 데드락이 나는가

팬텀(phantom)의 정의와 격리 수준별 차이는 [격리 수준과 이상 현상](/posts/cs/database/isolation-levels-anomalies/)에서 다뤘다. 여기서는 InnoDB가 팬텀을 락으로 막는 방법에 집중한다. 데드락 자체의 일반론은 [데드락과 우선순위 역전](/posts/cs/os/deadlock-priority-inversion/)을 참고하면 된다.

## 1. 왜 빈 구간까지 잠가야 하는가

### 레코드만 잠그면 생기는 구멍

`orders` 테이블의 `amount` 컬럼에 인덱스가 있고 값이 10, 20, 30인 행이 있다고 하자.

트랜잭션 T1이 이렇게 실행한다.

```sql
SELECT * FROM orders WHERE amount BETWEEN 10 AND 30 FOR UPDATE;
```

결과는 3행이다. 행 3개만 잠갔다면, 그 사이 T2가 `amount = 15`인 행을 INSERT할 수 있다.

T1이 같은 쿼리를 다시 실행하면 4행이 나온다. 없던 행이 "유령"처럼 나타난 것이다. 이것이 팬텀이다.

### 핵심 아이디어

> 범위를 잠근다는 것은 지금 있는 행뿐 아니라, 그 범위에 앞으로 들어올 수 있는 자리까지 잠그는 것이다.

InnoDB의 기본 격리 수준은 REPEATABLE READ다. 일반 `SELECT`는 MVCC 스냅샷으로 읽기 때문에 락이 필요 없다. 하지만 `SELECT ... FOR UPDATE`, `UPDATE`, `DELETE`는 스냅샷이 아니라 가장 최근에 커밋된 데이터를 읽고 락을 잡는다. 이런 읽기를 잠금 읽기(locking read)라 한다. 이때 팬텀을 막으려고 레코드 사이의 빈 구간(gap)까지 잠근다.

## 2. 락의 종류: 레코드 락, 갭 락, 넥스트 키 락

세 가지 락이 있다. 모두 **인덱스 레코드**에 대해 건다. 인덱스 레코드는 B+tree 리프에 들어 있는 항목 하나다. InnoDB에서는 테이블 자체가 PK로 정렬된 클러스터드 인덱스이므로([클러스터드 vs 세컨더리 인덱스](/posts/cs/database/clustered-vs-secondary-index/)), "행을 잠근다"는 말도 실제로는 인덱스 레코드를 잠근다는 뜻이다.

| 락 | 영어 | 잠그는 대상 |
| --- | --- | --- |
| 레코드 락 | record lock | 인덱스 레코드 하나 |
| 갭 락 | gap lock | 인덱스 레코드 사이의 빈 구간 |
| 넥스트 키 락 | next-key lock | 레코드 락 + 그 레코드 앞의 갭 락 |

### 인덱스 값이 10, 20, 30일 때의 지도

인덱스 위의 키 공간을 수직선으로 그리면 이렇다.

```
  -inf          10          20          30        +inf
   |-----------[10]--------[20]--------[30]--------|
     gap A            gap B       gap C       gap D
```

레코드는 3개고 갭은 4개다. 처음 레코드 앞(gap A)과 마지막 레코드 뒤(gap D)도 갭이다.

각 락이 덮는 범위는 괄호로 표시한다. `(` 는 그 값을 포함하지 않고, `]` 는 포함한다.

```
  레코드 락 [20]   : 20 하나
  갭 락 (10, 20)   : 10과 20 사이 빈 구간. 10, 20은 제외
  넥스트 키 락 (10, 20] : 갭 (10, 20) + 레코드 20
```

위 그림과 같은 값이면 넥스트 키 락 후보는 다음 네 구간이다.

```
  (-inf, 10]    (10, 20]    (20, 30]    (30, +inf)
```

마지막 구간 (30, +inf)는 레코드가 없어서 갭 락만 걸린다. 이 모양은 MySQL 문서가 값 10, 11, 13, 20으로 보여주는 예시와 같은 구조다.

### 넥스트 키 락이 기본값인 이유

REPEATABLE READ에서 InnoDB는 검색과 인덱스 스캔에 넥스트 키 락을 쓴다. 레코드만 잠그면 앞 절의 구멍이 생기고, 갭만 잠그면 레코드 자체의 수정을 못 막기 때문이다. 둘을 묶으면 구멍 없이 구간을 덮을 수 있다.

## 3. 쿼리마다 락 범위가 어떻게 달라지는가

락 범위는 쿼리 조건과 **인덱스가 유니크한지**에 따라 달라진다.

### 경우 1: 유니크 인덱스로 존재하는 행 하나를 정확히 찾을 때

`id`에 유니크 인덱스가 있고 값이 10, 20, 30이다.

```sql
SELECT * FROM t WHERE id = 20 FOR UPDATE;
```

MySQL 8.4 문서("Locks Set by Different SQL Statements in InnoDB")는 유니크 인덱스와 유일한 검색 조건을 쓰는 잠금 읽기가 찾은 인덱스 레코드만 잠그고 그 앞의 갭은 잠그지 않는다고 설명한다. 레코드 락만 건다는 뜻이다.

```
  -inf          10          20          30        +inf
   |-----------[10]--------[20]--------[30]--------|
                           ^^^^
                       레코드 락만
```

(10, 20) 사이에 다른 세션이 INSERT해도 상관없다. 한 행만 찾는 쿼리는 새 행이 끼어들어도 결과가 안 바뀌기 때문이다.

예외도 있다. 멀티 컬럼 유니크 인덱스에서 일부 컬럼만 조건에 쓰면 갭 락이 걸린다.

### 경우 2: 논유니크 인덱스로 찾을 때

`amount`의 인덱스는 유니크가 아니다. 값은 10, 20, 30이다.

```sql
SELECT * FROM orders WHERE amount = 20 FOR UPDATE;
```

`amount = 20`인 행이 또 들어올 수 있으니 그 자리를 막아야 한다. InnoDB는 이렇게 건다.

- 20에 대한 넥스트 키 락 (10, 20]
- 다음 레코드 30 앞의 갭 락 (20, 30)

```
  -inf          10          20          30        +inf
   |-----------[10]--------[20]--------[30]--------|
                  (===========]  next-key 락 (10, 20]
                              (========)   갭 락 (20, 30)
```

그래서 `amount = 15`와 `amount = 25`의 INSERT는 막힌다. 10이나 30의 바깥쪽 갭 (-inf, 10)과 (30, +inf)는 열려 있다.

"행 하나를 잠갔는데 왜 INSERT가 막히지?" 하는 현상은 대부분 이 경우다.

### 경우 3: 존재하지 않는 값을 찾을 때

경우 1의 예외는 "유일한 행을 찾았을 때"의 이야기다. 유니크 인덱스라도 찾는 행이 **없으면** 잠글 레코드가 없다. 대신 그 값이 들어갈 갭을 잠가, 다른 세션이 그 값을 끼워 넣지 못하게 한다.

다만 이 동작을 문서가 직접 적어 둔 것은 아니다. 위 문서의 규칙은 "찾은 레코드만 잠근다"는 것이고, 찾는 행이 없는 경우는 따로 설명하지 않는다. 그래서 이 절의 설명은 그 규칙과 InnoDB의 갭 락 동작에서 따라 나오는 결과다. 직접 확인하려면 한 세션에서 트랜잭션을 열고 아래 쿼리를 실행한 채로 두고, 다른 세션에서 `INSERT`로 15를 넣어 대기하는지 본다. 걸린 락은 `performance_schema.data_locks`의 `lock_mode`와 `lock_data` 컬럼으로 볼 수 있다.

```sql
SELECT * FROM t WHERE id = 15 FOR UPDATE;   -- id는 유니크, 15는 없음
```

```
  -inf          10          20          30        +inf
   |-----------[10]--------[20]--------[30]--------|
                  (=========)  갭 락 (10, 20)
```

이 동작이 5절 데드락의 원인이다.

### 경우 4: 인덱스를 못 쓰는 조건

조건에 쓸 인덱스가 없으면 테이블 전체를 스캔한다. 스캔한 모든 행에 락이 걸리므로 사실상 테이블 락처럼 동작한다. 갭 락 문제를 줄이는 첫걸음은 쿼리가 인덱스를 타게 만드는 것이다.

| 조건 | 거는 락 |
| --- | --- |
| 유니크 인덱스, 존재하는 행 하나 | 레코드 락 |
| 논유니크 인덱스 등치 | 넥스트 키 락 + 다음 갭 락 |
| 유니크 인덱스, 존재하지 않는 값 | 해당 갭 락 |
| 범위 조건 | 범위 안의 넥스트 키 락들 |
| 인덱스 없음 | 스캔한 모든 행과 갭 |

## 4. 갭 락끼리는 충돌하지 않는다

### 왜 이게 중요한가

락이라고 하면 보통 "하나가 잡으면 다른 하나는 기다린다"를 떠올린다. 갭 락은 다르다.

MySQL 문서는 갭 락을 "purely inhibitive", 즉 순수하게 막는 역할만 한다고 설명한다. 목적은 오직 "이 구간에 INSERT하지 못하게 하기"다. 그래서 여러 트랜잭션이 같은 갭에 동시에 갭 락을 가질 수 있다. 공유(S) 갭 락과 배타(X) 갭 락의 차이도 없다.

### 충돌하는 것은 INSERT다

갭 락은 "다른 트랜잭션이 이 구간에 새 행을 넣지 못하게 해 달라"는 표시일 뿐이다. 두 트랜잭션이 같은 갭에 이 표시를 해도 서로 방해하지 않는다. 막히는 쪽은 그 갭에 실제로 행을 넣으려는 INSERT다.

충돌은 INSERT가 갭에 들어오려 할 때 생긴다. INSERT는 삽입 직전에 **삽입 의도 락(insert intention lock)** 을 건다. 이것은 갭 락의 한 종류이고, 이런 특성이 있다.

- 같은 갭에 다른 트랜잭션의 갭 락이 있으면 기다린다
- 같은 갭의 서로 다른 위치에 INSERT하는 트랜잭션끼리는 기다리지 않는다

예를 들어 갭 (10, 20)에 한 세션이 12를, 다른 세션이 18을 INSERT하면 둘 다 진행된다. 같은 갭에 갭 락이 없을 때의 이야기다.

정리하면 이렇다.

| 이미 가진 락 | 새로 요청 | 결과 |
| --- | --- | --- |
| 갭 락 | 갭 락 | 호환 (둘 다 가능) |
| 갭 락 | 삽입 의도 락 | 대기 |
| 삽입 의도 락 | 삽입 의도 락 (다른 위치) | 호환 |

MySQL 문서의 예시를 보면 이렇다. 행 ID가 90과 102뿐일 때 클라이언트 A가 `SELECT * FROM child WHERE id > 100 FOR UPDATE`로 102 앞의 갭을 잠근다. 클라이언트 B가 id 101을 INSERT하려 하면 삽입 의도 락을 걸려다 대기한다.

## 5. INSERT 데드락: "없으면 넣기" 패턴

### 흔한 코드

중복 방지를 위해 많이 쓰는 패턴이다.

```sql
BEGIN;
SELECT * FROM t WHERE id = 7 FOR UPDATE;   -- 있나 확인
-- 없으면
INSERT INTO t(id) VALUES (7);
COMMIT;
```

단일 세션에서는 문제가 없다. 이 코드가 동시에 두 세션에서 돌면 데드락이 난다.

### 타임라인

`t` 테이블의 `id` 인덱스에 3과 10이 있고, 7은 없다. 갭 (3, 10)이 비어 있다.

| 시점 | T1 | T2 | 락 상태 |
| --- | --- | --- | --- |
| t1 | `BEGIN; SELECT ... WHERE id=7 FOR UPDATE;` (0행) | | T1이 갭 (3, 10)에 갭 락 |
| t2 | | `BEGIN; SELECT ... WHERE id=7 FOR UPDATE;` (0행) | T2도 같은 갭에 갭 락 (호환이라 대기 없음) |
| t3 | `INSERT INTO t(id) VALUES (7);` | | 삽입 의도 락 요청. T2의 갭 락 때문에 대기 |
| t4 | (대기 중) | `INSERT INTO t(id) VALUES (7);` | 삽입 의도 락 요청. T1의 갭 락 때문에 대기 |
| t5 | | | 사이클 감지. 한쪽이 롤백 |

### 왜 이렇게 되는가

- T1은 T2의 갭 락이 풀리기를 기다린다
- T2는 T1의 갭 락이 풀리기를 기다린다

둘 다 상대가 COMMIT 또는 ROLLBACK 하기 전에는 갭 락을 놓지 않으므로 영원히 풀리지 않는다. 일반적인 순환 대기(circular wait)다. 이 조건이 왜 데드락인지는 [데드락과 우선순위 역전](/posts/cs/os/deadlock-priority-inversion/)에서 다룬 데드락 조건 중 순환 대기에 해당한다.

InnoDB는 락 대기 그래프에서 사이클을 찾아내 한쪽 트랜잭션을 희생자(victim)로 골라 롤백한다. 롤백된 쪽에는 이 에러가 나간다.

```
ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction
```

### 이 데드락을 피하는 방법

원인은 "갭 락을 먼저 잡고, 그 위에 INSERT하려 한다"는 구조다. 선택지가 몇 가지 있다.

- **확인 없이 바로 INSERT.** 유니크 인덱스에 맡기고 중복 키 에러를 잡는다. `INSERT ... ON DUPLICATE KEY UPDATE`나 `INSERT IGNORE`도 같은 방향이다. 갭 락을 먼저 잡는 단계가 없어 위 데드락은 피한다. 다만 MySQL 문서는 세 세션이 같은 키를 동시에 INSERT할 때도 중복 키 검사의 공유 락 때문에 데드락이 날 수 있다고 설명한다. 그래서 다음 항목의 재시도는 여전히 필요하다.
- **재시도 로직.** 에러 1213을 받으면 트랜잭션 전체를 다시 실행한다. 데드락 감지는 정상 동작이므로 재시도는 필수다.
- **트랜잭션을 짧게.** 갭 락을 오래 쥘수록 충돌 확률이 커진다.

## 6. 격리 수준에 따른 차이

갭 락은 팬텀을 막는 대신 동시성을 깎는다. 이 비용을 받아들일지는 격리 수준 선택의 문제다.

| | REPEATABLE READ (InnoDB 기본) | READ COMMITTED |
| --- | --- | --- |
| 범위 잠금 읽기 | 넥스트 키 락 (레코드+갭) | 레코드 락 위주, 갭 락 없음 |
| 팬텀 | 잠금 읽기 기준으로 막힘 | 허용 |
| 동시성 | 갭 때문에 불필요한 대기와 데드락이 늘 수 있음 | 락 범위가 좁아 높음 |

READ COMMITTED에서는 검색과 인덱스 스캔의 갭 락이 꺼진다. 외래 키 검사와 중복 키 검사에서만 갭 락을 쓴다. 앞 절의 데드락이 READ COMMITTED에서는 사라지는 경우가 많은 이유다.

대신 팬텀을 직접 감당해야 한다. 같은 트랜잭션 안에서 같은 범위를 두 번 읽을 때 결과가 다를 수 있다는 뜻이다.

일반 `SELECT`는 두 수준 모두 락을 안 잡지만 스냅샷 시점이 다르다. REPEATABLE READ는 트랜잭션 첫 읽기 시점의 스냅샷을 유지하고, READ COMMITTED는 문장마다 새 스냅샷을 쓴다. 자세한 이상 현상은 [격리 수준과 이상 현상](/posts/cs/database/isolation-levels-anomalies/)을 참고한다.

## 7. 트레이드오프 정리

| 선택 | 얻는 것 | 잃는 것 |
| --- | --- | --- |
| REPEATABLE READ의 갭 락 | 잠금 읽기에서 팬텀 방지 | 넓은 락 범위, 대기와 데드락 증가 |
| READ COMMITTED로 변경 | 락 범위 축소, 동시성 향상 | 팬텀 허용, 같은 쿼리 재실행 시 결과 변동 |
| 유니크 인덱스 + 정확한 등치 조건 | 레코드 락만으로 좁은 범위 | 존재하지 않는 값이면 여전히 갭 락 |
| 확인 없이 바로 INSERT | 갭 락 데드락 회피 | 중복 키 에러 처리 코드 필요 |

실무에서 갭 락을 의심하는 신호는 "행이 없는데 INSERT가 대기한다", "서로 다른 값을 넣는데 데드락이 난다" 같은 현상이다.

---

## 결론

- InnoDB는 REPEATABLE READ에서 팬텀을 막기 위해 레코드뿐 아니라 레코드 사이의 빈 구간(갭)까지 잠근다.
- 넥스트 키 락은 레코드 락과 그 앞 갭 락의 합이다. 범위 스캔의 기본값이다.
- 유니크 인덱스로 존재하는 행 하나를 찾으면 레코드 락만 걸리고, 논유니크이거나 행이 없으면 갭이 잠긴다.
- 갭 락끼리는 충돌하지 않고 삽입 의도 락과만 충돌한다. 그래서 "둘 다 확인하고 둘 다 INSERT"하면 서로를 막는 데드락이 된다.
- READ COMMITTED는 갭 락을 꺼서 이 문제를 줄이지만 팬텀을 허용한다.
