## 개요

데이터베이스는 결국 디스크에 데이터를 저장한다. 그 저장 방식은 크게 두 갈래로 나뉜다.

- **B+tree**: MySQL InnoDB, PostgreSQL 인덱스 같은 전통적 RDBMS가 쓴다.
- **LSM-tree**: Cassandra, RocksDB, LevelDB, HBase, ScyllaDB가 쓴다.

이 글은 두 가지 질문에 답한다.

1. 두 구조는 왜 이렇게 다르게 만들어졌는가?
2. 읽기, 쓰기, 공간 중 무엇을 내주고 무엇을 얻는가?

한 줄로 줄이면 이렇다. 둘의 차이는 "작은 랜덤 쓰기를 어디서 감당하느냐"다.

---

## 1. 출발점: 디스크는 작은 쓰기를 싫어한다

디스크는 바이트가 아니라 **페이지(page)** 단위로 읽고 쓴다. 보통 4~16KB다.

그래서 100바이트짜리 행 하나를 고쳐도 페이지 하나(16KB)를 통째로 쓴다.

또 하나, 디스크는 순차 접근이 랜덤 접근보다 훨씬 효율적이다. HDD는 헤드가 움직이는 시간 때문이고, SSD도 큰 단위로 이어서 쓰는 편이 유리하다.

이 두 사실에서 두 가지 설계가 나온다.

| | B+tree | LSM-tree |
|---|---|---|
| 철학 | 데이터가 있어야 할 자리를 정해 두고, 그 자리를 고친다 | 일단 순서대로 이어 붙이고, 정리는 나중에 한다 |
| 쓰기 방식 | 제자리 갱신(update-in-place) | 추가 전용(append-only) |

---

## 2. B+tree: 제자리에서 고친다

### 왜 필요한가

키로 데이터를 찾을 때 디스크를 처음부터 훑으면 너무 느리다. 몇 번의 디스크 접근으로 찾을 수 있는 정렬된 구조가 필요하다.

### 핵심 아이디어

페이지 하나를 노드 하나로 쓰는, 넓고 낮은 균형 트리를 만든다.

### 동작

노드 하나에 자식 포인터를 수백 개 담는다. 이 자식 수를 **팬아웃**(fan-out)이라 한다. 팬아웃이 500이고, 리프 페이지 하나에도 키가 500개 들어간다고 하자.

- 깊이 3: 루트 1개 -> 내부 노드 500개 -> 리프 25만 개. 키는 25만 x 500 = 1억 2500만 개
- 깊이 4: 키 약 625억 개

그래서 수억 건이어도 키 하나를 찾는 데 페이지 3~4개만 읽으면 된다. 루트와 위쪽 노드는 메모리에 캐시되므로 실제 디스크 읽기는 더 적다.

```
          [ 루트 ]
         /   |    \
    [내부]  [내부]  [내부]
     / | \
 [리프]<->[리프]<->[리프]<->[리프]
   모든 키/값이 리프에 있고, 리프끼리 연결되어 있다
```

리프끼리 연결 리스트로 이어져 있어서 범위 조회(range scan)도 빠르다. 시작 키를 찾은 뒤 옆 리프로 따라가기만 하면 된다.

쓰기는 이렇게 진행한다.

1. 키가 속한 리프 페이지를 찾는다.
2. 그 페이지를 메모리에서 고치고 디스크에 다시 쓴다.
3. 페이지가 가득 차 있으면 둘로 쪼갠다(split). 부모 노드도 고쳐야 한다.
4. 크래시에 대비해 **WAL**(Write-Ahead Log)을 먼저 쓴다. 변경 내용을 순차 로그에 먼저 남기는 방식이다. 자세한 동작은 [WAL과 크래시 복구](/posts/cs/database/wal-aries-crash-recovery)에서 다룬다.

### 생기는 문제

- 변경 위치가 디스크에 흩어져 있어, 작은 랜덤 쓰기가 발생한다.
- 100바이트를 고치려고 16KB 페이지를 다시 쓴다. WAL까지 합하면 같은 데이터가 두 번 쓰인다.
- split 직후 두 페이지는 반씩만 차 있다. MySQL 문서에 따르면 InnoDB 페이지는 키가 순서대로 들어오면 약 15/16까지 차지만, 무작위 순서로 들어오면 1/2에서 15/16 사이로 찬다. 그만큼 빈 공간이 생긴다.

## 3. LSM-tree: 이어 붙이고 나중에 정리한다

### 왜 필요한가

쓰기가 아주 많은 서비스(메시지 저장, 로그, 시계열)에서는 랜덤 쓰기가 병목이 된다. 쓰기를 순차 I/O로 바꿀 수 있다면 처리량이 크게 오른다.

### 핵심 아이디어

쓰기는 메모리와 순차 로그에만 하고, 정렬과 병합은 백그라운드로 미룬다.

LSM-tree는 Log-Structured Merge-tree의 약자다.

### 동작: 쓰기 경로

```
쓰기 -> WAL (순차 append) -> MemTable (메모리, 정렬된 구조)
                                 |  가득 차면 디스크로 flush
                                 v
   L0 : SSTable 여러 개 (키 범위가 서로 겹칠 수 있음)
   L1 : 정렬된 SSTable들 (겹치지 않음)   <- compaction
   L2 ... Ln : 레벨마다 크기가 약 10배
```

용어를 하나씩 짚자.

- **MemTable**: 메모리에 있는 정렬된 쓰기 버퍼. 새 쓰기는 일단 여기에 들어간다.
- **SSTable(Sorted String Table)**: MemTable이 가득 차면 디스크에 쓰는 정렬된 불변 파일. 한번 쓰면 고치지 않는다.
- **컴팩션(compaction)**: 여러 SSTable을 병합 정렬해서 새 파일로 만드는 백그라운드 작업.

수정과 삭제도 제자리에서 하지 않는다. 새 값을 또 하나 쓰고, 삭제는 **톰스톤**(tombstone)이라는 삭제 표시를 쓴다. 오래된 값과 톰스톤은 컴팩션 때 정리된다.

### 동작: 읽기 경로

같은 키의 값이 여러 파일에 있을 수 있다. 그래서 최신 쪽부터 뒤진다.

1. MemTable을 본다.
2. L0의 모든 파일을 본다. 범위가 겹칠 수 있기 때문이다.
3. L1부터는 레벨마다 파일 하나만 본다. 레벨 컴팩션(5절)에서는 한 레벨 안의 파일끼리 키 범위가 겹치지 않기 때문이다.

없는 키를 찾으면 모든 레벨을 헛되이 뒤지게 된다. 이를 줄이려고 **블룸 필터**(Bloom filter)를 쓴다. 파일마다 "이 키는 확실히 없다"를 메모리에서 빠르게 알려 주는 구조다. "없다"는 대답은 항상 맞고, "있다"는 대답은 가끔 틀린다(false positive). 대신 메모리를 쓴다.

블룸 필터는 한 키를 찾는 포인트 읽기를 줄여 준다. 범위 조회는 여러 레벨을 병합해 읽어야 해서 도움이 크지 않다.

### 생기는 문제

- 컴팩션이 같은 데이터를 계속 다시 쓴다.
- 컴팩션이 쓰기 유입을 못 따라가면 쓰기를 멈춘다. 이는 6절에서 다룬다.
- 톰스톤이 많은 삭제 위주 워크로드는 컴팩션 전까지 읽기를 느리게 한다.

## 4. 세 가지 증폭으로 비교하기

두 구조를 공정하게 비교하려면 같은 잣대가 필요하다. 업계에서는 세 가지 증폭(amplification)을 쓴다. RocksDB 튜닝 가이드의 정의는 이렇다.

| 증폭 | 정의 | 직관 |
|---|---|---|
| 쓰기 증폭(write amplification) | 디스크에 쓴 바이트 / 사용자가 쓴 바이트 | 한 번 쓰면 실제로 몇 번 쓰이나 |
| 읽기 증폭(read amplification) | 질의 하나당 디스크 읽기 횟수 | 하나 찾으려고 몇 군데 보나 |
| 공간 증폭(space amplification) | 디스크 파일 크기 / 실제 데이터 크기 | 데이터 대비 얼마나 더 차지하나 |

### 쓰기 증폭

B+tree는 앞에서 봤듯이 100바이트 변경에 16KB 페이지를 쓴다. 이론상 160배다. 다만 같은 페이지에 변경이 모이면 한 번의 쓰기로 합쳐지니 실제로는 더 낮다.

LSM-tree는 쓰기가 로그와 flush로 순차적이라 처음엔 가볍다. 하지만 레벨을 내려갈 때마다 다시 쓴다. 레벨 컴팩션(leveled compaction)에서 레벨 크기가 10배씩 커지면, RocksDB 가이드의 예시는 대략 `1 + 2 + 10 + 10 + 10 = 33`배의 쓰기 증폭을 든다.

그러니 "LSM은 쓰기 증폭이 항상 작다"고 단정할 수 없다. 쓰기가 순차라서 빠를 뿐, 같은 데이터를 여러 번 다시 쓴다. 어느 쪽 증폭이 더 큰지는 행 크기, 갱신 패턴, 컴팩션 설정에 따라 달라진다.

쓰기 증폭은 저장 장치의 수명과도 연결된다. 플래시 셀은 지우고 다시 쓸 수 있는 횟수가 정해져 있다. RocksDB 튜닝 가이드도 높은 쓰기 증폭이 플래시 수명을 줄인다고 적는다.

### 읽기 증폭

B+tree는 깊이만큼, 즉 보통 3~4개 페이지다. 안정적이다.

LSM-tree는 MemTable, L0의 모든 파일, 그 아래 레벨마다 파일 하나를 본다. 블룸 필터와 블록 캐시가 없으면 훨씬 불리하다.

### 공간 증폭

B+tree는 split으로 반쯤 빈 페이지가 생긴다. 무작위 삽입이 많을수록 빈 공간이 늘어난다.

LSM-tree는 같은 키의 옛 값과 톰스톤이 컴팩션 전까지 남는다. 컴팩션 중에는 원본과 결과 파일이 동시에 있어 일시적으로 공간이 더 필요하다.

## 5. 컴팩션 전략: 증폭을 서로 맞바꾼다

LSM-tree 안에서도 컴팩션 방식에 따라 증폭이 이동한다.

| 전략 | 쓰기 증폭 | 읽기 증폭 | 공간 증폭 |
|---|---|---|---|
| 레벨(leveled) | 큼 | 작음 | 작음 |
| 사이즈 티어드(size-tiered) | 작음 | 큼 | 큼 |

- **레벨 방식**: 레벨 안의 파일이 겹치지 않아 읽기가 쉽고 중복도 빨리 사라진다. 대신 자주 다시 쓴다.
- **사이즈 티어드 방식**: 비슷한 크기의 파일이 모이면 그때 합친다. 덜 다시 쓰지만, 겹치는 파일이 많이 남는다.

세 증폭을 모두 낮추는 설정은 없다. 워크로드에 맞춰 무엇을 포기할지 고르는 것이다.

## 6. LSM이 잘못되면: 컴팩션 부채와 쓰기 멈춤

### 왜 문제가 되는가

컴팩션은 백그라운드 작업이지만 디스크 대역폭과 CPU를 쓴다. 쓰기가 몰려 들어오는 속도가 컴팩션 속도보다 빠르면 정리하지 못한 파일이 쌓인다.

### 동작: 쓰기 멈춤(write stall)

RocksDB는 쌓인 양이 임계치를 넘으면 일부러 쓰기를 늦추거나 멈춘다. 공식 문서가 꼽는 조건은 세 가지다.

- flush를 기다리는 MemTable 수 (`max_write_buffer_number`)
- L0 파일 수 (`level0_slowdown_writes_trigger`, `level0_stop_writes_trigger`)
- 처리 대기 중인 컴팩션 바이트 추정치 (`soft_pending_compaction_bytes`, `hard_pending_compaction_bytes`)

L0 파일이 늘면 읽기도 느려진다. L0의 모든 파일을 봐야 하기 때문이다. 쌓이는 파일이 읽기 증폭도 키운다는 뜻이다.

증상은 평균 처리량이 아니라 **p99 지연이 주기적으로 튀는 모양**으로 나타난다. 평균은 멀쩡한데 가끔 쓰기가 멈춘다면 컴팩션을 의심한다. 컴팩션 스레드 수, 디스크 대역폭, 컴팩션 전략, 쓰기 속도 제한을 확인한다.

### 사례: Discord

Discord는 메시지 저장소를 Cassandra에서 ScyllaDB로 옮긴 경험을 블로그에 적었다. 글에 따르면 Cassandra 클러스터는 2017년 12노드에서 2022년 초 177노드까지 커졌다. 컴팩션이 뒤처지는 일이 잦았고, 노드를 트래픽에서 빼고 컴팩션을 돌린 뒤 다시 넣는 "gossip dance"라는 작업을 반복해야 했다.

ScyllaDB로 옮긴 뒤 177노드가 72노드가 되었다. 이력 메시지 조회 p99는 40~125ms에서 15ms가 되었고, 메시지 삽입 p99는 5~70ms에서 5ms가 되었다.

이 사례는 LSM 자체의 문제만으로 볼 수는 없다. 원문은 핫 파티션과 JVM 가비지 컬렉션 문제도 함께 다룬다. 컴팩션 부채는 LSM이 치르는 대가의 한 예로 읽는 것이 적절하다.

## 7. 트레이드오프 정리: 언제 무엇을 고르나

| 항목 | B+tree | LSM-tree |
|---|---|---|
| 쓰기 패턴 | 랜덤 제자리 갱신 | 순차 append + 백그라운드 병합 |
| 쓰기 처리량 | 상대적으로 낮음 | 높음 (컴팩션이 따라간다면) |
| 포인트 읽기 | 안정적, 깊이 3~4 | 레벨 수와 블룸 필터에 따라 변동 |
| 범위 조회 | 매우 좋음 (리프 연결) | 여러 레벨 병합 필요 |
| 공간 효율 | 페이지 빈 공간 | 옛 값, 톰스톤, 컴팩션 중 임시 공간 |
| 지연 특성 | 예측 가능 | 컴팩션과 쓰기 멈춤 때 p99 변동 |
| 대표 사용처 | OLTP RDBMS | 쓰기 많은 NoSQL, 로그, 시계열, 메시지 |

OLTP(Online Transaction Processing)는 주문, 결제처럼 짧은 트랜잭션을 많이 처리하는 워크로드다. 범위 조회가 많고 쓰기가 적당한 OLTP라면 B+tree가 일반적인 선택이다. 쓰기가 압도적으로 많고 순간적인 지연 변동을 받아들일 수 있다면 LSM-tree가 맞는다.

---

## 결론

- 두 구조의 뿌리는 "작은 랜덤 쓰기를 어디서 감당하느냐"다. B+tree는 쓰는 순간에, LSM-tree는 나중에 컴팩션으로 감당한다.
- B+tree는 읽기가 안정적이고 범위 조회에 강하다. 대신 작은 쓰기에도 페이지 단위로 쓰고 빈 공간이 생긴다.
- LSM-tree는 쓰기가 순차라 빠르다. 대신 읽기에서 여러 파일을 뒤지고, 컴팩션이 데이터를 반복해서 다시 쓴다.
- 컴팩션이 뒤처지면 쓰기 멈춤과 p99 변동이 생긴다. LSM 운영의 핵심은 컴팩션 관리다.

| | B+tree | LSM-tree |
|---|---|---|
| 읽기 증폭 | 낮고 안정적 | 높을 수 있음, 블룸 필터로 완화 |
| 쓰기 증폭 | 페이지 단위 + WAL | 컴팩션으로 반복 재작성 |
| 공간 증폭 | 페이지 빈 공간 | 옛 값과 톰스톤, 전략에 따라 다름 |

B+tree로 인덱스를 만든다고 해서 그 인덱스가 데이터 자체를 담는지, 데이터 위치만 가리키는지는 별개의 문제다. 이어지는 글 [클러스터드 인덱스 vs 세컨더리 인덱스](/posts/cs/database/clustered-vs-secondary-index)에서 B+tree가 실제 인덱스로 쓰일 때의 차이를 살펴본다.
