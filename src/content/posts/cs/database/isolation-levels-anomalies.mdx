## 개요

[앞 글](/posts/cs/database/wal-aries-crash-recovery)에서는 트랜잭션이 장애가 나도 사라지지 않게 만드는 방법을 봤다. 이번 글은 ACID의 I, 즉 격리(isolation)를 다룬다. 장애가 없어도 트랜잭션 두 개가 동시에 돌면 데이터가 틀어질 수 있다.

이 글이 답하는 질문은 두 가지다.

- 격리 수준(isolation level)마다 정확히 어떤 이상 현상을 막고, 무엇을 막지 못하는가?
- MySQL과 PostgreSQL의 기본 격리 수준에서 내 코드는 안전한가?

여기서 격리 수준은 "동시에 도는 트랜잭션이 서로의 중간 상태를 얼마나 볼 수 있는가"를 정한 약속이다. 이상 현상(anomaly)은 트랜잭션을 하나씩 순서대로 돌렸다면 나올 수 없는 결과를 말한다.

---

## 1. 왜 격리가 필요한가: 재고 차감 타임라인

쇼핑몰에 상품 A의 재고가 10개 있다. 주문이 들어오면 애플리케이션은 이렇게 처리한다.

```sql
-- 1) 재고를 읽는다
SELECT stock FROM product WHERE id = 1;      -- 10
-- 2) 애플리케이션에서 1을 뺀다                  -- 10 - 1 = 9
-- 3) 계산한 값을 쓴다
UPDATE product SET stock = 9 WHERE id = 1;
```

주문이 하나씩 오면 아무 문제가 없다. 문제는 두 주문이 거의 동시에 올 때다.

```
time   T1 (order #1)              T2 (order #2)              stock in DB
----   -----------------------    -----------------------    -----------
 t1    BEGIN                                                  10
 t2    SELECT stock -> 10                                     10
 t3                               BEGIN                       10
 t4                               SELECT stock -> 10          10
 t5    UPDATE stock = 9                                       9
 t6    COMMIT                                                 9
 t7                               UPDATE stock = 9            9
 t8                               COMMIT                      9
```

두 개가 팔렸으니 재고는 8이어야 한다. 그런데 DB에는 9가 남았다. T1이 쓴 값을 T2가 덮어쓰면서 T1의 차감이 사라졌다.

이 현상을 갱신 손실(lost update)이라고 한다. 두 트랜잭션이 같은 값을 읽고, 각자 계산한 값을 쓰면서 먼저 쓴 쪽의 결과가 없어지는 현상이다.

재고가 1개였다면 더 심각하다. 두 주문 모두 재고 1을 보고 "살 수 있다"고 판단한다. 결과는 재고 0, 판매 2건이다. 없는 물건을 판 것이다.

핵심 아이디어는 한 문장이다. **격리는 동시에 도는 트랜잭션들이 마치 하나씩 차례로 돈 것처럼 보이게 만드는 장치다.** 다만 완벽한 격리는 비싸다. 그래서 DB는 "어디까지 허용할지"를 단계로 나눠 고르게 한다. 그 단계가 격리 수준이다.

## 2. ANSI 4단계와 3가지 현상

SQL 표준(ANSI SQL-92)은 격리 수준을 "어떤 현상이 일어나면 안 되는가"로 정의했다. 현상(phenomenon)은 세 가지다. 재고 예시로 하나씩 보자.

### 더티 리드(dirty read)

아직 커밋되지 않은 다른 트랜잭션의 값을 읽는 현상이다.

```
time   T1                          T2
----   -------------------------   -------------------------
 t1    UPDATE stock = 9  (10->9)
 t2                                SELECT stock -> 9   (dirty)
 t3    ROLLBACK          (9->10)
 t4                                stock 9 기준으로 계속 진행
```

T2가 본 9는 한 번도 확정된 적이 없는 값이다. T1이 롤백했으니 그런 값은 존재하지 않았던 셈이다.

### 반복 불가능한 읽기(non-repeatable read)

같은 행을 두 번 읽었는데, 그 사이 다른 트랜잭션이 값을 바꾸고 커밋해서 결과가 달라지는 현상이다. 퍼지 리드(fuzzy read)라고도 부른다.

```
time   T1                          T2
----   -------------------------   -------------------------
 t1    SELECT stock -> 10
 t2                                UPDATE stock = 9
 t3                                COMMIT
 t4    SELECT stock -> 9   (changed)
```

T2는 커밋까지 했으니 더티 리드는 아니다. 하지만 T1 입장에서는 한 트랜잭션 안에서 같은 질문에 다른 답을 받았다.

### 팬텀(phantom)

같은 조건으로 행 집합을 두 번 조회했는데, 그 사이 조건에 맞는 행이 새로 생겨서 결과 집합이 달라지는 현상이다.

```
time   T1                                     T2
----   ------------------------------------   ---------------------------
 t1    SELECT COUNT(*) FROM orders
       WHERE product_id = 1   -> 3
 t2                                           INSERT INTO orders (...)
                                              VALUES (product_id = 1)
 t3                                           COMMIT
 t4    SELECT COUNT(*) ... -> 4   (phantom)
```

반복 불가능한 읽기는 "이미 있던 행의 값"이 바뀌는 것이고, 팬텀은 "조건에 맞는 행의 개수"가 바뀌는 것이다. 이 차이가 뒤에서 구현 방식을 가른다. 기존 행은 그 행만 잠그면 되지만, 아직 없는 행은 잠글 대상이 없기 때문이다.

### 4단계 표

표준은 이 세 현상을 몇 개까지 막느냐로 네 단계를 나눈다.

| 격리 수준 | 더티 리드 | 반복 불가능한 읽기 | 팬텀 |
|---|---|---|---|
| READ UNCOMMITTED | 가능 | 가능 | 가능 |
| READ COMMITTED | 불가능 | 가능 | 가능 |
| REPEATABLE READ | 불가능 | 불가능 | 가능 |
| SERIALIZABLE | 불가능 | 불가능 | 불가능 |

아래로 갈수록 안전하지만 동시에 처리할 수 있는 양이 줄어든다. 더 많이 막으려면 더 오래 잠그거나, 더 자주 트랜잭션을 실패시켜야 하기 때문이다.

그런데 이 표를 보고 1절의 재고 문제를 찾아보면 이상한 점이 있다. **갱신 손실은 표에 없다.** 1절의 타임라인에는 더티 리드도, 같은 행을 두 번 읽는 일도, 새 행도 없다. 그런데 데이터는 틀어졌다.

## 3. ANSI 정의에 없는 현상: lost update, write skew

1995년 Berenson, Bernstein, Gray 등은 "A Critique of ANSI SQL Isolation Levels"에서 이 표의 빈틈을 정리했다. 요점은 세 가지다.

- 표준의 영어 문장은 해석이 두 가지로 갈린다. 좁게 읽으면 막아야 할 비직렬 실행이 빠져나간다.
- 세 현상만으로는 실제 제품의 격리 수준을 구분하지 못한다.
- 그래서 새로운 현상을 추가로 정의해야 한다.

논문은 먼저 더티 라이트(dirty write, P0)를 짚는다. 커밋되지 않은 값을 다른 트랜잭션이 다시 덮어쓰는 현상이다. 이게 허용되면 롤백할 때 어느 값으로 되돌려야 할지 정할 수 없다. 논문은 모든 격리 수준에서 P0를 막아야 한다고 제안했다. 논문에 따르면 가장 약한 락 기반 시스템도 쓰기 락은 커밋까지 잡는다. 그러지 않으면 롤백 자체가 불가능하기 때문이다.

### 갱신 손실(P4, lost update)

논문의 정의는 1절 타임라인과 같다. 기호로 쓰면 다음과 같다. `r1[x]`는 T1이 x를 읽음, `w2[x]`는 T2가 x를 씀, `c1`은 T1 커밋이다.

```
P4:  r1[x] ... w2[x] ... w1[x] ... c1
H4:  r1[x=100] r2[x=100] w2[x=120] c2 w1[x=130] c1
```

H4에서 T2는 20을 더했고 T1은 30을 더했다. 정답은 150이다. 하지만 최종 값은 130이라서 T2의 +20이 사라졌다.

논문은 이 현상이 READ COMMITTED에서 가능하다고 지적한다. T1이 읽은 값도, T2가 쓴 값도 모두 커밋된 값이라 더티 리드 규칙에 걸리지 않기 때문이다. 반대로 반복 불가능한 읽기를 막는 수준(REPEATABLE READ)에서는 P4도 막힌다. T1이 읽은 x를 T1이 끝나기 전에 T2가 바꾸는 순간이 반복 불가능한 읽기의 조건이기 때문이다.

### 쓰기 스큐(A5B, write skew)

갱신 손실은 같은 행을 두고 다툰다. 쓰기 스큐는 **서로 다른 행**을 쓰는데도 규칙이 깨지는 현상이다. 두 트랜잭션이 같은 데이터를 읽고, 각자 다른 행을 고쳐서, 둘이 함께 지키던 제약이 깨진다.

```
A5B: r1[x] ... r2[y] ... w1[y] ... w2[x] ... (c1 and c2 occur)
H5:  r1[x=50] r1[y=50] r2[x=50] r2[y=50] w1[y=-40] w2[x=-40] c1 c2
```

논문의 예는 은행 계좌다. 공동 명의 계좌 x와 y는 각각 마이너스가 되어도 되지만, 합계 `x + y`는 0 이상이어야 한다.

1. 시작할 때 x = 50, y = 50, 합계 100이다.
2. T1은 둘을 읽고 "합계 100이니 y에서 90을 빼도 된다"고 판단한다. y = -40을 쓴다.
3. T2도 같은 시점의 값을 읽고 "x에서 90을 빼도 된다"고 판단한다. x = -40을 쓴다.
4. 둘 다 커밋된다. 합계는 -80이다.

각 트랜잭션은 혼자 돌았다면 규칙을 지켰다. 두 트랜잭션이 쓴 행이 서로 다르니 같은 행을 두고 충돌한 적도 없다. 이 성질 때문에 쓰기 스큐는 같은 행의 충돌만 감지하는 방식으로는 잡히지 않는다. 당직 의사 예시로 보는 쓰기 스큐는 [MVCC와 스냅샷 격리 글](/posts/cs/database/mvcc-snapshot-isolation-write-skew)에서 자세히 다룬다.

### 논문이 내린 결론

논문은 이런 현상을 기준으로 격리 수준을 다시 줄 세웠다. 아래는 그중 이 글에 필요한 부분만 옮긴 것이다.

| 격리 수준 | 더티 라이트 | 더티 리드 | 갱신 손실 | 반복 불가능한 읽기 | 팬텀 | 쓰기 스큐 |
|---|---|---|---|---|---|---|
| READ COMMITTED | 불가능 | 불가능 | 가능 | 가능 | 가능 | 가능 |
| REPEATABLE READ (락 기반) | 불가능 | 불가능 | 불가능 | 불가능 | 가능 | 불가능 |
| Snapshot Isolation | 불가능 | 불가능 | 불가능 | 불가능 | 경우에 따라 가능 | 가능 |
| SERIALIZABLE | 불가능 | 불가능 | 불가능 | 불가능 | 불가능 | 불가능 |

여기서 스냅샷 격리(Snapshot Isolation, SI)가 새로 등장한다. 트랜잭션이 시작 시점에 커밋된 데이터의 사진(스냅샷)을 보고 일하는 방식이다. 논문의 평가는 이렇다.

- SI는 READ COMMITTED보다 강하다.
- SI는 REPEATABLE READ와 **비교할 수 없다.** REPEATABLE READ가 허용하는 팬텀을 SI는 대부분 막고, SI가 허용하는 쓰기 스큐를 REPEATABLE READ는 막는다.
- SI는 직렬화 가능(serializable)하지 않다.

논문은 REPEATABLE READ라는 이름 자체도 비판한다. 팬텀을 허용하니 읽기가 실제로는 반복 가능하지 않다는 것이다. 이 혼란은 4절과 5절에서 다시 만난다. 이름은 같은데 DB마다 실제로 하는 일이 다르다.

## 4. 구현 두 갈래: 락 기반 vs 스냅샷 기반

격리 수준은 "무엇을 막는가"라는 약속이다. 그 약속을 지키는 방법은 크게 두 갈래로 나뉜다.

**락 기반(lock-based)** 은 남이 쓰는 중인 데이터에는 손대지 못하게 기다리게 한다. Berenson 논문의 표 2는 각 격리 수준을 락을 얼마나 오래 잡는지로 설명한다.

| 수준 | 읽기 락 | 쓰기 락 |
|---|---|---|
| READ UNCOMMITTED | 잡지 않음 | 커밋까지 |
| READ COMMITTED | 읽는 순간만 잠깐 | 커밋까지 |
| REPEATABLE READ | 행 락은 커밋까지, 조건(predicate) 락은 잠깐 | 커밋까지 |
| SERIALIZABLE | 행 락과 조건 락 모두 커밋까지 | 커밋까지 |

표를 보면 격리 수준이 올라갈수록 읽기 락을 더 오래 잡는다. 팬텀을 막으려면 "아직 없는 행"까지 막아야 하므로, 행이 아니라 조건 범위를 잠가야 한다. 이게 락 방식에서 가장 비싼 부분이다.

읽기 락과 쓰기 락을 모두 커밋까지 잡으면 SERIALIZABLE이 된다. 이 방식은 2단계 락킹(two-phase locking, 2PL)의 한 형태다. 왜 이렇게 하면 직렬 실행과 같은 결과가 보장되는지는 [직렬 가능성 글](/posts/cs/database/serializability-2pl-ssi)에서 다룬다.

**스냅샷 기반(snapshot-based)** 은 기다리게 하는 대신 데이터의 여러 버전을 남긴다. 이 방식을 다중 버전 동시성 제어(Multi-Version Concurrency Control, MVCC)라고 한다.

1. 트랜잭션 T1이 시작하면 그 시점의 스냅샷을 받는다.
2. T1이 읽을 때는 스냅샷 기준의 버전을 본다. 다른 트랜잭션이 그 사이 커밋한 새 버전은 보이지 않는다.
3. 그래서 읽기가 쓰기를 기다리지 않고, 쓰기도 읽기를 기다리지 않는다.
4. 두 트랜잭션이 같은 행을 쓰면, 먼저 커밋한 쪽이 이기고 나중 쪽은 중단된다. 논문은 이 규칙을 first-committer-wins라고 부른다. 이 규칙이 갱신 손실을 막는다.

두 방식의 트레이드오프는 분명하다.

| | 락 기반 | 스냅샷 기반 |
|---|---|---|
| 읽기와 쓰기가 만나면 | 한쪽이 기다린다 | 둘 다 진행한다 |
| 충돌을 처리하는 방식 | 대기, 그리고 데드락 | 나중 트랜잭션을 중단하고 재시도 |
| 약한 부분 | 대기 시간과 처리량 | 쓰기 스큐, 버전 정리 비용 |

실제 DB는 둘을 섞는다. 이 시리즈의 다음 세 글이 각각 한 조각씩을 맡는다.

- [MVCC와 스냅샷 격리, 쓰기 스큐](/posts/cs/database/mvcc-snapshot-isolation-write-skew): 스냅샷이 어떻게 만들어지고 왜 쓰기 스큐를 막지 못하는지
- [InnoDB 갭 락과 넥스트 키 락](/posts/cs/database/innodb-gap-next-key-lock): 아직 없는 행을 락으로 막는 방법
- [직렬화 가능성, 2PL과 SSI](/posts/cs/database/serializability-2pl-ssi): 진짜 SERIALIZABLE을 만드는 두 방법

## 5. MySQL InnoDB vs PostgreSQL

같은 이름의 격리 수준이라도 두 DB가 하는 일은 다르다. 먼저 기본값부터 다르다.

- MySQL InnoDB의 기본값은 **REPEATABLE READ**다.
- PostgreSQL의 기본값은 **READ COMMITTED**다.

공식 문서로 확인한 동작을 표로 정리하면 다음과 같다.

| 수준 | MySQL InnoDB | PostgreSQL |
|---|---|---|
| READ UNCOMMITTED | 더티 리드가 일어날 수 있다 | READ COMMITTED와 똑같이 동작한다 |
| READ COMMITTED | 읽을 때마다 새 스냅샷을 쓴다. 갭 락을 쓰지 않아 팬텀이 생길 수 있다 | 문장마다 새 스냅샷을 쓴다 (기본값) |
| REPEATABLE READ | 첫 읽기에서 만든 스냅샷을 계속 쓴다. 락을 잡는 읽기와 UPDATE, DELETE는 범위에 갭 락, 넥스트 키 락을 건다 (기본값) | Snapshot Isolation으로 구현한다. 팬텀을 허용하지 않는다. 동시 수정을 만나면 에러로 중단한다 |
| SERIALIZABLE | REPEATABLE READ와 같지만, autocommit이 꺼져 있으면 일반 SELECT를 `SELECT ... FOR SHARE`로 바꾼다 (락 기반) | Serializable Snapshot Isolation(SSI)으로 구현한다. 위험한 패턴을 감지하면 SQLSTATE `40001`로 중단한다 |

이름이 같은 REPEATABLE READ를 1절의 재고 시나리오에 넣어 보면 차이가 잘 보인다. 두 트랜잭션 모두 `SELECT`로 10을 읽고, 애플리케이션에서 9를 계산해 `UPDATE ... SET stock = 9`를 보낸다고 하자.

**PostgreSQL REPEATABLE READ에서는** T1이 먼저 커밋한 뒤 T2의 `UPDATE`가 에러를 받는다.

```
ERROR:  could not serialize access due to concurrent update
```

T2는 스냅샷 이후에 바뀐 행을 고치려 했기 때문에 중단된다. 문서는 이 경우 트랜잭션 전체를 처음부터 다시 실행하라고 안내한다. 재시도하면 T2는 새 스냅샷에서 9를 읽고 8을 쓴다. 갱신 손실이 막힌다.

**MySQL REPEATABLE READ에서는** 사정이 다르다. 문서에 따르면 스냅샷은 `SELECT`에 적용되며 DML에는 꼭 적용되지 않는다. `UPDATE`와 `DELETE`는 다른 트랜잭션이 방금 커밋한 행에도 작용한다. 타임라인에서 T1은 이미 커밋했으므로 T2의 `UPDATE`는 에러 없이 실행된다. T1이 아직 커밋 전이었다면 행 락을 기다렸다가 역시 에러 없이 실행된다. T2가 보낸 값은 이미 계산된 9이므로 결과는 9가 된다. 이름은 REPEATABLE READ지만 "읽고 계산해서 쓰는" 코드의 갱신 손실은 막아 주지 않는다.

PostgreSQL READ COMMITTED도 마찬가지로 이 코드를 지켜 주지 않는다. 다만 `UPDATE`가 잠긴 행을 만나면 상대가 커밋한 뒤 **최신 버전으로 WHERE 조건을 다시 평가**한다. 그래서 `SET stock = stock - 1`처럼 DB 안에서 계산하면 안전하다. 다음 절에서 이 점을 쓴다.

정리하면, 기본값만 믿고 있으면 두 DB 모두 1절의 코드에서 재고가 틀어진다. 격리 수준을 올리는 것만이 답은 아니다. 애플리케이션 쪽에서 막는 방법이 따로 있다.

## 6. 애플리케이션에서의 선택

1절의 문제는 "읽은 값을 기준으로 계산해서 쓴다"는 데서 나왔다. 읽기와 쓰기 사이에 다른 트랜잭션이 끼어들지 못하게 하면 된다. 방법은 세 가지다.

### 방법 1: DB 안에서 계산하기 (원자적 UPDATE)

가장 간단하다. 읽고 계산하는 단계를 없애고 한 문장으로 끝낸다.

```sql
UPDATE product
SET stock = stock - 1
WHERE id = 1 AND stock > 0;
-- 영향받은 행이 0이면 재고 부족
```

같은 행을 쓰는 두 `UPDATE`는 행 락 때문에 차례로 실행된다. 두 번째 `UPDATE`는 첫 번째가 커밋한 9를 기준으로 8을 만든다. 재고가 0이면 `stock > 0` 조건에 걸려 아무 행도 바뀌지 않는다. 이 동작은 MySQL 기본값과 PostgreSQL READ COMMITTED 기준이다. PostgreSQL REPEATABLE READ 이상에서는 두 번째 `UPDATE`가 5절의 에러로 중단되므로 재시도 코드가 필요하다.

다만 로직이 한 문장에 담길 만큼 단순해야 쓸 수 있다.

### 방법 2: 비관적 락 `SELECT ... FOR UPDATE`

읽을 때부터 쓰기 락을 잡는다. "어차피 충돌할 것"이라고 보고 미리 막는 방식이라 비관적 락(pessimistic lock)이라고 부른다.

```sql
BEGIN;
SELECT stock FROM product WHERE id = 1 FOR UPDATE;   -- 10, 행 락 획득
-- 애플리케이션에서 검증과 계산
UPDATE product SET stock = 9 WHERE id = 1;
COMMIT;                                              -- 락 해제
```

```
time   T1                               T2
----   ------------------------------   ------------------------------
 t1    SELECT ... FOR UPDATE -> 10
 t2                                     SELECT ... FOR UPDATE  (wait)
 t3    UPDATE stock = 9
 t4    COMMIT
 t5                                     -> 9  (wait ends)
 t6                                     UPDATE stock = 8
 t7                                     COMMIT
```

MySQL 문서는 `FOR UPDATE`가 `UPDATE`를 실행한 것처럼 행과 인덱스 항목을 잠그고, 락은 커밋이나 롤백할 때 풀린다고 설명한다. 문서의 카운터 증가 예시도 바로 이 패턴이다. PostgreSQL READ COMMITTED에서도 기다린 쪽은 갱신된 최신 행을 잠그고 받는다. 단, PostgreSQL REPEATABLE READ에서는 t5에서 기다림이 끝날 때 값 대신 에러를 받는다.

대가는 대기다. 인기 상품 하나에 주문이 몰리면 모두 한 줄로 선다. 여러 행을 서로 다른 순서로 잠그면 데드락도 생긴다.

### 방법 3: 낙관적 락 (version 컬럼)

락을 잡지 않고, 쓸 때 "내가 읽은 뒤로 바뀌었는지"를 확인한다. 충돌이 드물 것이라고 보는 방식이라 낙관적 락(optimistic lock)이라고 부른다.

```sql
-- 읽기: stock = 10, version = 3
SELECT stock, version FROM product WHERE id = 1;

-- 쓰기: 읽었을 때의 version이 그대로일 때만 성공
UPDATE product
SET stock = 9, version = 4
WHERE id = 1 AND version = 3;
-- 영향받은 행이 0이면 누군가 먼저 바꿨다 -> 다시 읽고 재시도
```

1절의 타임라인에 대입해 보자.

1. T1과 T2가 모두 `stock = 10, version = 3`을 읽는다.
2. T1이 `WHERE version = 3`으로 쓴다. 성공하고 version은 4가 된다.
3. T2도 `WHERE version = 3`으로 쓴다. 이제 version은 4라서 바뀐 행이 0개다.
4. T2는 다시 읽어 `stock = 9, version = 4`를 받고, 8과 version 5로 쓴다.

락 대기가 없으니 충돌이 드물 때 빠르다. 충돌이 잦으면 재시도가 계속 쌓여 오히려 느려진다. 재시도 로직도 애플리케이션이 직접 짜야 한다.

### 무엇을 고를까

| 방법 | 잘 맞는 경우 | 대가 |
|---|---|---|
| 원자적 UPDATE | 계산이 한 문장으로 끝날 때 | 복잡한 검증을 넣기 어렵다 |
| `SELECT ... FOR UPDATE` | 충돌이 잦고, 읽은 뒤 검증이 필요할 때 | 대기, 데드락 가능성 |
| 낙관적 락 (version) | 충돌이 드물고, 사용자 편집처럼 읽기와 쓰기 사이가 길 때 | 재시도 로직, 충돌이 잦으면 낭비 |
| 격리 수준 올리기 (PostgreSQL RR, SERIALIZABLE) | 여러 행에 걸친 규칙을 지켜야 할 때 | 에러 `40001` 재시도 처리, 처리량 감소 |

마지막 줄이 중요하다. 세 방법은 같은 행에 대한 갱신 손실을 막는다. 3절의 쓰기 스큐처럼 **서로 다른 행**에 걸친 규칙은 한 행의 version이나 행 락으로 막히지 않는다. 그때는 규칙에 관련된 행을 모두 잠그거나 SERIALIZABLE을 써야 한다. 그 이야기는 [직렬화 가능성 글](/posts/cs/database/serializability-2pl-ssi)에서 이어진다.

## 결론

- 격리 수준은 동시에 도는 트랜잭션이 서로를 얼마나 볼 수 있는지 정한 약속이다. ANSI 표준은 더티 리드, 반복 불가능한 읽기, 팬텀 세 현상으로 네 단계를 나눴다.
- 이 표에는 갱신 손실과 쓰기 스큐가 없다. Berenson 등(1995)은 이 빈틈을 정리하고, 스냅샷 격리가 READ COMMITTED보다 강하지만 직렬화 가능하지 않다는 것을 보였다.
- 구현은 락 기반(기다리게 한다)과 스냅샷 기반(버전을 남기고 충돌하면 중단한다)으로 나뉜다.
- 같은 REPEATABLE READ라도 PostgreSQL은 동시 수정을 에러로 막고, MySQL InnoDB는 최신 값에 그대로 쓴다. 기본값도 다르다(MySQL은 REPEATABLE READ, PostgreSQL은 READ COMMITTED).
- 재고 차감 같은 "읽고 계산해서 쓰기"는 격리 수준만 믿지 말고, 원자적 UPDATE, `SELECT ... FOR UPDATE`, version 컬럼 중 하나로 직접 막는다.
