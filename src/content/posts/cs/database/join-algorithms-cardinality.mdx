## 개요

이 글은 두 가지 질문에 답한다.

- 같은 JOIN 문장을 DB는 어떤 방법으로 실행하고, 방법마다 비용은 얼마나 다른가?
- 어제까지 빠르던 쿼리가 오늘 수십 배 느려지는 일은 왜 생기는가?

앞 글 [클러스터드 vs 세컨더리 인덱스](/posts/cs/database/clustered-vs-secondary-index/)에서 인덱스가 "키로 행을 빨리 찾는 구조"라는 것을 봤다. 이 글에서는 그 인덱스를 쓰느냐 마느냐가 조인 알고리즘 선택을 어떻게 바꾸는지 본다.

글 전체에서 같은 예시를 쓴다.

```sql
SELECT o.id, u.name
FROM orders o
JOIN users u ON o.user_id = u.id;
```

- `orders`: 1,000,000행 (주문)
- `users`: 10,000행 (사용자). `id`가 기본 키다.
- 주문 하나는 사용자 한 명을 가리키므로, 결과는 1,000,000행이다.

## 1. 조인은 "어떻게"를 DB가 고른다

SQL은 선언적(declarative) 언어다. "무엇을 원하는지"만 적고, "어떻게 구할지"는 적지 않는다.

그 "어떻게"를 정하는 부품이 옵티마이저(optimizer)다. 옵티마이저는 가능한 실행 방법을 여러 개 만들고, 비용(cost)을 계산해서 가장 싼 것을 고른다.

여기서 왜 실제로 돌려 보지 않고 추정할까? 후보가 너무 많기 때문이다. 테이블 10개를 한 줄로 늘어놓는 조인 순서만 세어도 10! = 3,628,800가지다. 거기에 조인마다 알고리즘 3가지를 곱하면 모두 실행해 볼 수 없다.

그래서 옵티마이저는 통계(statistics)로 비용을 싸게 근사한다. 통계는 테이블 행 수, 컬럼별 distinct 값 개수, 값 분포 히스토그램 같은 요약 정보다.

이 구조에서 핵심 입력은 각 단계가 몇 행을 내놓을지에 대한 예측이다. 이 예측을 카디널리티 추정(cardinality estimation)이라고 부른다. 이 예측이 틀리면 비용 계산 전체가 틀어진다. 7절에서 자세히 본다.

먼저 DB가 쓰는 세 가지 알고리즘을 같은 예시로 계산해 보자.

## 2. Nested Loop Join: 하나씩 찾아간다

### 왜 필요한가

조인의 가장 단순한 정의는 "orders의 각 행에 맞는 users 행을 찾는 것"이다. 이 정의를 그대로 코드로 옮기면 중첩 반복문이 된다.

### 핵심 아이디어

바깥 테이블의 행마다 안쪽 테이블에서 짝을 찾는다. 이름이 Nested Loop Join(NLJ)이다.

### 동작: 인덱스가 없을 때

```text
for o in orders:          # 바깥 1,000,000번
    for u in users:       # 안쪽 10,000번
        if o.user_id == u.id: emit(o, u)
```

비교 횟수는 1,000,000 x 10,000 = 100억 번이다. 비교 한 번을 10ns로 잡아도 100초다. 쓸 수 없는 방법이다.

### 동작: 안쪽에 인덱스가 있을 때

`users.id`는 기본 키라서 B+tree 인덱스가 이미 있다. 안쪽을 "전부 훑기"에서 "인덱스로 찾기"로 바꿀 수 있다.

```text
for o in orders:                     # 1,000,000번
    u = users_pk_index.lookup(o.user_id)   # 트리 깊이 약 2~3
    emit(o, u)
```

사용자 10,000건이면 B+tree 깊이는 2~3단이면 충분하다. 조회 한 번에 페이지 2~3개를 읽으므로 총 약 200만~300만 번의 페이지 접근이다. 100억에 비하면 3,000배 이상 줄었다.

### 생기는 문제

NLJ의 비용은 바깥 행 수에 비례한다.

- 바깥이 10행이면 인덱스 조회 10번이다. 가장 빠르다.
- 바깥이 100만 행이면 인덱스 조회 100만 번이다. 느리다.

그래서 NLJ는 "바깥 행이 적고 안쪽에 인덱스가 있는" 경우에 최고이고, 그렇지 않으면 재앙이다. 주문 한 건을 `WHERE o.id = 42`로 찾아서 사용자를 붙이는 OLTP 점 조회가 전형적인 좋은 경우다.

## 3. Hash Join: 해시 테이블을 한 번 만든다

### 왜 필요한가

100만 번의 인덱스 조회는 사실 같은 사용자를 계속 다시 찾는 일이다. 사용자는 1만 명뿐인데, 조회는 100만 번 한다. 1만 명을 메모리에 한 번 올려두면 조회마다 트리를 타지 않아도 된다.

### 핵심 아이디어

작은 쪽으로 해시 테이블을 만들고(build), 큰 쪽을 한 번 훑으면서 조회한다(probe).

### 동작

```text
# 1) build: users 10,000행을 읽어 해시 테이블 생성
for u in users:
    H[hash(u.id)].append(u)

# 2) probe: orders 1,000,000행을 한 번만 훑음
for o in orders:
    for u in H[hash(o.user_id)]:
        if u.id == o.user_id: emit(o, u)
```

작은 예로 따라가 보자. users의 id가 3, 7, 9이고 orders의 user_id가 7, 4, 3 순서로 온다고 하자.

| 단계 | 읽은 값 | 결과 |
|---|---|---|
| build | id=3, 7, 9 | 해시 테이블에 3개 저장 |
| probe | user_id=7 | 해시 테이블에 있음 -> 결과 (7, 7) |
| probe | user_id=4 | 해시 테이블에 없음 -> 버림 |
| probe | user_id=3 | 해시 테이블에 있음 -> 결과 (3, 3) |

비용은 users 10,000 + orders 1,000,000 = 약 101만 번의 해시 연산이다. 인덱스 NLJ의 200만~300만 번 페이지 접근보다 적다. 게다가 인덱스가 필요 없다.

두 숫자의 단위는 엄밀히 같지 않다. 해시 연산 한 번은 메모리 안에서 끝나지만, 인덱스 조회 한 번은 B+tree를 루트부터 내려가야 한다. 그래서 실제 차이는 숫자보다 더 벌어지는 경우가 많다.

### 왜 작은 쪽이 build인가

probe가 $O(1)$으로 빠른 이유는 해시 테이블이 메모리에 있어서다. build 쪽이 크면 메모리에 안 들어간다. 그래서 둘 중 작은 쪽을 build로 쓴다.

users 10,000행을 행당 100바이트로 잡으면 약 1MB다. PostgreSQL의 `work_mem` 기본값이 4MB이고, 해시 테이블은 `hash_mem_multiplier` 기본값 2.0을 곱해서 8MB까지 쓸 수 있다. 이 정도면 메모리에 들어간다.

### 생기는 문제

- **메모리를 넘으면 디스크로 흘린다.** build 쪽이 한도를 넘으면 해시 값으로 양쪽을 파티션(partition)으로 나눠 디스크에 쓴다. 그다음 파티션 쌍을 하나씩 다시 읽어서 조인한다. 이 방식을 Grace/hybrid hash join이라고 부른다. 양쪽을 한 번씩 더 쓰고 읽으므로 I/O가 최소 한 번 더 생긴다.
- **등가 조건(`=`)만 가능하다.** 해시는 "같은 값은 같은 칸"만 보장한다. `o.created_at > u.joined_at` 같은 부등 조건은 해시로 찾을 수 없다.
- **build가 끝나야 첫 결과가 나온다.** 해시 테이블을 다 만들기 전에는 probe를 시작할 수 없다.

## 4. Sort-Merge Join: 정렬해서 나란히 훑는다

### 왜 필요한가

해시로는 부등 조건을 못 푼다. 그리고 인덱스를 타고 들어가면 데이터가 이미 정렬되어 있을 수 있는데, 해시는 그 정렬을 활용하지 못한다. 양쪽이 같은 키로 정렬되어 있다면 훨씬 싸게 조인할 수 있다.

### 핵심 아이디어

양쪽을 조인 키로 정렬한 뒤, 투 포인터(two pointers)로 한 번씩만 훑으며 합친다.

### 동작

users의 id가 1, 3, 5, 7이고 orders의 user_id가 1, 1, 3, 7, 7이라고 하자. 이미 정렬된 상태다.

```text
users:  1  3  5  7
orders: 1  1  3  7  7

u=1, o=1 -> 일치, o 다음으로
u=1, o=1 -> 일치, o 다음으로
u=1, o=3 -> u가 작다, u 다음으로
u=3, o=3 -> 일치, o 다음으로
u=3, o=7 -> u가 작다, u 다음으로
u=5, o=7 -> u가 작다, u 다음으로
u=7, o=7 -> 일치, o 다음으로
u=7, o=7 -> 일치, 끝
```

어느 쪽도 뒤로 가지 않는다. 병합 단계 비용은 두 입력 크기의 합, 즉 약 101만이다.

### 정렬 비용

정렬이 안 되어 있다면 정렬 비용이 든다.

| 입력 | 정렬 비교 횟수 ($n \log_2 n$) |
|---|---|
| orders 1,000,000행 | 약 1,000,000 x 20 = 2,000만 |
| users 10,000행 | 약 10,000 x 13 = 13만 |
| 병합 | 약 101만 |
| 합계 | 약 2,100만 |

해시(약 101만)보다 20배쯤 비싸다. 정렬 결과가 메모리를 넘으면 디스크를 쓰는 외부 정렬이 필요하다. 그 방법은 [외부 정렬과 k-way 병합](/posts/cs/algorithm/external-merge-sort/)에서 다룬다.

반대로 `orders.user_id`에 인덱스가 있어서 인덱스 순서로 읽을 수 있다면 정렬 단계가 사라진다. 이때는 병합 비용만 든다.

### 언제 유리한가

- 입력이 이미 정렬되어 있을 때 (인덱스 순서, 앞 단계의 `ORDER BY`)
- 범위 조인이나 부등 조인이 필요할 때
- 결과가 조인 키로 정렬되어 나와야 할 때 (뒤에 `ORDER BY o.user_id`가 있으면 정렬을 한 번에 해결)

정렬되지 않은 대용량 입력에서 정렬 비용이 크다는 점이 약점이다.

## 5. 세 알고리즘 비교

같은 예시(orders 100만, users 1만)의 비용을 모아 보자.

| 알고리즘 | 대략 비용 | 메모리 | 유리한 경우 | 불리한 경우 |
|---|---|---|---|---|
| NLJ (인덱스 없음) | 100억 비교 | 거의 없음 | 거의 없음 | 거의 항상 |
| NLJ (안쪽 인덱스) | 200만~300만 페이지 접근 | 거의 없음 | 바깥 행이 적을 때, OLTP 점 조회 | 바깥 행이 많을 때 |
| Hash | 약 101만 해시 연산 | build 크기 | 대량 등가 조인, 인덱스 없음 | build가 메모리 초과, 부등 조인 |
| Sort-Merge | 약 2,100만 (정렬 포함) / 약 101만 (정렬됨) | 정렬 버퍼 | 이미 정렬됨, 범위 조인, 정렬 결과 필요 | 정렬 안 된 대용량 |

이 표에서 읽을 점은 두 가지다.

- 정답 알고리즘은 없다. 바깥 행이 몇 개인지, 인덱스가 있는지, 메모리가 얼마인지에 따라 달라진다.
- 같은 쿼리여도 `WHERE` 조건이 바깥 행을 10행으로 줄이면 NLJ가 가장 싸다. 100만 행이면 Hash가 가장 싸다.

즉 알고리즘 선택은 "바깥에서 몇 행이 올라오는가"라는 추정값에 크게 의존한다.

## 6. EXPLAIN ANALYZE로 계획 읽기

PostgreSQL에서는 `EXPLAIN ANALYZE`로 옵티마이저가 고른 계획과 실제 실행 결과를 함께 볼 수 있다. 아래는 위 쿼리의 계획 예시다. 수치는 설명용이다.

```text
Hash Join  (cost=290.00..30540.00 rows=1000000 width=40)
           (actual time=2.1..380.5 rows=1000000 loops=1)
  Hash Cond: (o.user_id = u.id)
  ->  Seq Scan on orders o
        (cost=0.00..18334.00 rows=1000000 width=16)
        (actual time=0.02..95.3 rows=1000000 loops=1)
  ->  Hash  (cost=165.00..165.00 rows=10000 width=28)
            (actual time=2.0..2.0 rows=10000 loops=1)
        Buckets: 16384  Batches: 1  Memory Usage: 700kB
        ->  Seq Scan on users u
              (cost=0.00..165.00 rows=10000 width=28)
              (actual time=0.01..0.9 rows=10000 loops=1)
```

읽는 요령은 다음과 같다.

- 노드 이름(`Hash Join`)이 알고리즘이다. 들여쓰기가 깊은 쪽이 먼저 실행되는 자식이다.
- `Hash` 노드가 build 쪽이고, 그 형제 `Seq Scan on orders`가 probe 쪽이다.
- `rows=`는 두 번 나온다. 앞쪽 `cost=...` 괄호의 `rows`는 옵티마이저의 추정이고, `actual ... rows`는 실제 값이다.
- `Batches: 1`은 해시 테이블이 한 번에 메모리에 들어갔다는 뜻이다. 이 값이 2 이상이면 디스크로 흘렸다는 신호다.
- `loops`는 그 노드가 몇 번 실행됐는지다. Nested Loop의 안쪽 노드에서는 바깥 행 수만큼 커진다.

여기서 가장 중요한 습관은 추정 `rows`와 실제 `rows`를 나란히 보는 것이다. 둘이 크게 다른 노드가 문제의 출발점이다.

## 7. 카디널리티 추정이 틀리면

### 왜 문제인가

옵티마이저는 5절의 표처럼 "바깥 행이 몇 개냐"에 따라 알고리즘을 바꾼다. 그런데 그 행 수는 통계로 계산한 추정값이다. 추정이 틀리면 알고리즘 선택이 틀린다.

### 핵심 아이디어

계획의 품질은 비용 공식보다 행 수 추정의 정확도에 더 크게 좌우된다.

### 동작: 잘못된 선택 예

`WHERE` 조건이 붙은 쿼리를 생각해 보자.

```sql
SELECT o.id, u.name
FROM orders o
JOIN users u ON o.user_id = u.id
WHERE o.status = 'PAID' AND o.coupon = 'WELCOME';
```

옵티마이저가 "조건을 만족하는 주문은 약 10행"이라고 추정했다고 하자. 그러면 NLJ(인덱스)가 가장 싸다. 10번만 찾으면 되기 때문이다.

그런데 실제로는 1,000,000행이 나왔다면 어떻게 될까?

| | 추정 | 실제 |
|---|---|---|
| 바깥 행 수 | 약 10 | 약 1,000,000 |
| 선택된 계획 | Nested Loop | Nested Loop (이미 고름) |
| 인덱스 조회 횟수 | 10 | 1,000,000 |

계획은 실행 전에 정해지므로, 틀린 선택이 그대로 실행된다. 이 쿼리는 Hash를 골랐을 때(약 101만 연산)보다 훨씬 오래 걸릴 수 있다. `EXPLAIN ANALYZE`에서는 이렇게 보인다.

```text
Nested Loop  (cost=0.30..95.00 rows=10 width=40)
             (actual time=0.05..4200.0 rows=1000000 loops=1)
  ->  Seq Scan on orders o  (rows=10)  (actual rows=1000000 loops=1)
  ->  Index Scan using users_pkey on users u
        (rows=1)  (actual rows=1 loops=1000000)
```

`rows=10`인데 `actual rows=1000000`이다. 그리고 안쪽 노드의 `loops=1000000`이 눈에 띈다.

### 오차는 왜 생기나

| 원인 | 설명 |
|---|---|
| 낡은 통계 | 데이터가 많이 바뀌었는데 통계는 예전 것이다 |
| 컬럼 독립성 가정 | `status`와 `coupon`이 서로 무관하다고 보고 선택도를 곱한다. 실제로는 상관된 컬럼이면 곱한 값이 크게 틀린다 |
| 균등 분포 가정 | 값이 고르게 퍼져 있다고 보지만, 특정 고객이 전체의 90%를 차지하는 식의 쏠림이 있다 |
| 조인 단계의 누적 | 단계마다 작은 오차가 곱해져 조인이 깊을수록 커진다 |

조건을 통과하는 행의 비율을 선택도(selectivity)라 한다. 독립성 가정을 숫자로 보자. `status = 'PAID'`가 10%, `coupon = 'WELCOME'`이 10%라면 독립일 때 결과는 1%다. 그런데 WELCOME 쿠폰이 쓰인 주문은 대부분 PAID라면 실제는 약 10%다. 이미 10배 틀렸다. 조인이 두 단계 더 있고 단계마다 10배씩 틀리면 1,000배가 된다.

### 연구로 확인된 사실

Leis 등의 "How Good Are Query Optimizers, Really?"(PVLDB, 2015) 논문은 실제 IMDB 데이터와 복잡한 쿼리 113개로 만든 JOB 벤치마크로 옵티마이저를 비교했다. 결론은 계획 품질에서 카디널리티 추정이 가장 중요한 요소라는 것이다. 비용 모델을 손보는 것보다 정확한 행 수를 쓰는 쪽의 효과가 훨씬 컸다.

이 논문에 따르면 PostgreSQL에서 조인 1개짜리 추정의 16%가 10배 이상 틀렸다. 그 비율은 조인 2개에서 32%, 조인 3개에서 52%로 올랐다. 조인이 깊어질수록 오차가 쌓인다는 점을 보여주는 수치다.

## 8. 쿼리가 갑자기 느려졌을 때

### 플랜 회귀

같은 쿼리인데 어느 날 갑자기 느려지는 일을 플랜 회귀(plan regression)라고 부른다. 흔한 계기는 다음과 같다.

- 데이터가 늘어서 행 수 추정이 임계값을 넘었다.
- 통계가 갱신되면서 알고리즘이 바뀌었다.
- DB 버전을 올리면서 비용 모델이 달라졌다.

대표적인 모양은 Hash Join이 Nested Loop로 바뀌거나 조인 순서가 바뀌는 것이다.

### 파라미터에 따라 계획이 다르다

값이 쏠린 컬럼에서는 같은 쿼리라도 파라미터에 따라 최적 계획이 다르다. 예를 들어 `WHERE user_id = ?`에서 한 고객이 주문의 90%를 가지고 있다고 하자.

| 파라미터 | 결과 행 수 | 좋은 계획 |
|---|---|---|
| 평범한 사용자 | 약 100 | 인덱스 + Nested Loop |
| 그 고객 | 약 900,000 | Hash Join + 순차 스캔 |

계획을 캐시해서 재사용하면 한쪽 값에 최적인 계획이 다른 값에는 최악이 된다.

### 접근 순서

느려진 쿼리는 이 순서로 본다.

1. `EXPLAIN (ANALYZE)`로 계획이 바뀌었는지 확인한다.
2. 추정 `rows`와 `actual rows`가 크게 다른 노드를 찾는다. 가장 아래쪽(먼저 실행된) 노드의 오차가 위로 퍼진다.
3. 원인 후보를 확인한다: 낡은 통계, 데이터 분포 변화, 인덱스 변경, 파라미터 의존, 업그레이드.
4. 대응은 약한 것부터 쓴다. 통계 재수집(`ANALYZE`), 상관된 컬럼의 확장 통계(extended statistics, 다중 컬럼 통계), 쿼리 재작성 순서다. 힌트나 계획 고정은 최후 수단이다.

### 참고: OUTER JOIN은 재배치가 제한된다

INNER JOIN은 `A JOIN B JOIN C`의 순서를 옵티마이저가 자유롭게 바꿀 수 있다. 결과가 같기 때문이다.

LEFT JOIN은 NULL을 보존해야 해서 순서를 마음대로 바꿀 수 없다. 대신 `WHERE`가 NULL 쪽 컬럼을 걸러내는 조건이면 사실상 INNER JOIN이므로, 옵티마이저가 변환해서 재배치 폭을 넓힐 수 있다. 의도와 달리 LEFT JOIN을 쓰면 후보 계획이 줄어든다는 뜻이다.

## 결론

- 조인 알고리즘 세 가지는 비용이 "무엇에 비례하는가"가 다르다. NLJ는 바깥 행 수, Hash는 두 입력 크기의 합과 build 메모리, Sort-Merge는 정렬 비용(입력이 정렬돼 있으면 거의 없음)이다.
- 100만 행과 1만 행을 조인하는 같은 쿼리에서, 인덱스 없는 NLJ는 100억, 인덱스 NLJ는 200만~300만, Hash는 약 101만, 정렬이 필요한 Sort-Merge는 약 2,100만 정도의 일을 한다.
- 옵티마이저는 후보를 전부 실행할 수 없어서 통계로 행 수를 추정해 알고리즘을 고른다. 그래서 계획 품질은 추정 정확도에 달려 있다.
- 쿼리가 갑자기 느려지면 `EXPLAIN ANALYZE`에서 추정 `rows`와 `actual rows`의 차이가 큰 노드부터 찾는다.
