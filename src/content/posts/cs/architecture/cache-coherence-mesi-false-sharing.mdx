## 개요

[앞 글](/posts/cs/architecture/memory-hierarchy-cache-mapping/)에서는 캐시가 메모리를 캐시 라인(cache line, 보통 64바이트) 단위로 옮긴다는 것을 봤다. 이번 글은 코어가 여러 개일 때 생기는 문제를 다룬다. 코어마다 자기 L1 캐시가 있으니, 같은 라인의 사본이 여러 곳에 생길 수 있다.

이 글이 답하는 질문은 두 가지다.

- 한 코어가 값을 쓰면, 다른 코어의 캐시에 있는 옛날 사본은 어떻게 처리되는가?
- 락도 없고 서로 다른 변수만 쓰는데, 스레드를 늘릴수록 왜 느려지는가?

---

## 1. 왜 일관성 프로토콜이 필요한가

코어 0과 코어 1이 둘 다 변수 `x`가 들어 있는 라인을 읽었다고 하자. 두 코어의 L1에 `x = 5`가 한 부씩 있다.

이때 코어 0이 `x = 6`으로 쓴다. 아무 조치가 없으면 코어 1은 계속 `x = 5`를 읽는다. 같은 주소인데 코어마다 다른 값을 보게 된다.

이 문제를 막는 규칙이 캐시 일관성(cache coherence) 프로토콜이다. 핵심 아이디어는 한 문장이다. **"쓰기 전에 다른 코어의 사본을 먼저 없앤다."**

사본을 없애는 일을 무효화(invalidation)라고 한다. 값을 새 값으로 갱신해서 뿌리는 방식도 가능하지만, 쓰기마다 데이터를 전부 보내야 해서 비싸다. 일반적인 구현은 "무효 표시만 보내는" 방식을 쓴다.

---

## 2. MESI: 라인마다 네 가지 상태

가장 널리 알려진 프로토콜이 MESI다. 캐시는 라인마다 상태 비트를 붙여 두고, 라인이 다음 네 상태 중 하나에 있다고 기록한다.

| 상태 | 이름 | 뜻 |
| --- | --- | --- |
| M | Modified | 이 캐시에만 있고, 메모리 값과 다르다(더럽다). |
| E | Exclusive | 이 캐시에만 있고, 메모리 값과 같다. |
| S | Shared | 여러 캐시가 읽기용 사본을 갖고 있다. 메모리 값과 같다. |
| I | Invalid | 쓸 수 없는 사본이다. 없는 것과 같다. |

규칙은 단순하다.

- 읽기는 M, E, S 어느 상태든 그냥 된다.
- 쓰기는 M 또는 E 상태일 때만 된다. 즉 라인을 혼자 갖고 있어야 한다.
- S 상태에서 쓰려면 먼저 다른 코어의 사본을 모두 I로 만들어야 한다.

"혼자 갖는다"는 요청을 RFO(Read For Ownership)라고 부른다. 소유권을 얻으며 읽어 오는 요청이고, 이걸 받은 다른 코어는 자기 사본을 I로 바꾼다.

### 읽기가 끼어들 때

코어 A가 라인을 M 상태로 갖고 있는데 코어 B가 같은 라인을 읽으려 한다고 하자.

1. B의 읽기 요청을 A가 알아챈다.
2. A는 더러운 데이터를 B에게 넘기거나 메모리에 써 넣는다(write-back).
3. 두 코어 모두 S 상태가 된다.

이후 A가 다시 쓰려면 S에서 M으로 올라가야 하고, 그러려면 B의 사본을 I로 만들어야 한다. 읽기만 하는 코어가 끼어도 쓰는 코어는 매번 비용을 낸다.

일부 CPU는 여기에 Owned 상태를 더한 MOESI를 쓴다. 더러운 라인을 메모리에 쓰지 않고 한 코어가 책임지고 나눠 주는 변형이다. 큰 흐름은 같다.

## 3. 두 코어가 같은 라인을 번갈아 쓰면

이제 문제의 상황이다. 변수 `a`와 `b`가 서로 다른 변수지만 같은 64바이트 라인에 붙어 있다. 스레드 0은 `a`만, 스레드 1은 `b`만 쓴다. 코드상 공유하는 데이터는 없다.

```
        메모리의 한 캐시 라인 (64B)
  +-----------+-----------+------------------+
  |     a     |     b     |      (기타)      |
  +-----------+-----------+------------------+
     ^ 코어 0이 씀  ^ 코어 1이 씀
```

하지만 캐시는 라인 단위로 상태를 관리한다. `a`와 `b`는 같은 상태를 공유한다. 상태 전이를 따라가 보자. 처음에는 라인이 두 코어 모두에 없다(I).

| 단계 | 동작 | 코어 0 상태 | 코어 1 상태 | 일어나는 일 |
| --- | --- | --- | --- | --- |
| 0 | 시작 | I | I | 라인은 메모리에만 있다. |
| 1 | 코어 0이 `a`를 씀 | M | I | RFO로 라인을 가져와 독점한다. |
| 2 | 코어 1이 `b`를 씀 | I | M | 코어 0의 더러운 라인을 넘겨받고 코어 0은 무효화된다. |
| 3 | 코어 0이 `a`를 씀 | M | I | 이번엔 코어 1에서 라인을 뺏어 온다. |
| 4 | 코어 1이 `b`를 씀 | I | M | 다시 뺏긴다. |

단계 2부터는 쓰기 한 번마다 라인이 다른 코어로 넘어간다. 라인이 공 튀기듯 왕복한다고 해서 핑퐁(ping-pong)이라고 부른다.

이 상황을 false sharing이라고 한다. 논리적으로는 무관한 변수인데 물리적으로 같은 라인에 있어서 서로의 쓰기를 방해하는 현상이다.

### 얼마나 느려지는가

L1 캐시 적중은 수 사이클이면 끝난다. 반면 코어 사이에 라인을 옮기는 비용은 CPU 구조에 따라 수십~100ns 이상까지 늘어날 수 있다. 이 값은 소켓 구성에 따라 크게 달라서 정확한 숫자를 하나로 말하기 어렵다.

가정을 하나 해 보자. 증가 연산 하나가 L1 적중이면 약 1ns, 매번 라인을 뺏겨야 하면 약 50ns라고 하자. 스레드마다 1억 번 증가시킨다면 이상적으로는 0.1초지만, false sharing이 있으면 5초 정도로 늘어난다. 숫자는 설명을 위한 가정이고, 핵심은 쓰기마다 코어 간 전송이 낀다는 점이다.

실제 측정 사례도 있다.

- cppreference의 `hardware_destructive_interference_size` 문서는 두 카운터를 같은 라인에 둘 때와 다른 라인에 둘 때 약 6배 차이가 나는 벤치마크를 싣고 있다.
- 한 개발자는 스레드가 나눠 쓰는 배열의 경계가 같은 캐시 라인에 걸리던 문제를 정렬로 고쳐 실행 시간을 10.92초에서 0.06초로 줄였다고 기록했다(출처 참고). 이 수치는 그 프로그램의 데이터에 한정된 결과다.

### 증상으로 알아채기

- 코어를 더 쓰는데 처리량이 오르지 않거나 떨어진다.
- CPU 사용률은 높은데 락 대기 같은 뚜렷한 원인이 없다.
- 프로파일러에서 특정 필드 접근이 핫스팟으로 나온다.
- 변수 사이에 상관없는 필드를 끼워 넣었더니 갑자기 빨라진다.

전형적인 위치는 스레드별 통계 카운터, `sum[tid]++`처럼 배열 원소를 스레드마다 하나씩 나눠 쓰는 병렬 루프, 링 버퍼의 head와 tail 인덱스다.

## 4. 진짜 공유와 가짜 공유 구분하기

두 스레드가 같은 변수를 쓴다면 true sharing이다. 이건 알고리즘 차원의 경합이어서 락이나 원자 연산을 어떻게 설계하느냐의 문제다. 라인을 옮기지 않으면 아예 올바르게 동작하지 못한다.

false sharing은 다른 변수가 같은 라인에 있을 뿐이라, 배치만 바꾸면 사라진다. 구분은 간단하다. 두 스레드가 쓰는 필드의 주소가 같은지 오프셋을 본다. 주소는 다르지만 같은 64바이트 구간 안에 있으면 false sharing이다.

Linux에서는 `perf c2c`로 확인할 수 있다. 같은 라인을 두고 코어 사이에서 오가는 접근(HITM, 다른 코어의 수정된 라인에 적중)을 보여 준다.

---

## 5. 해결 1: 패딩과 정렬

핵심 아이디어는 "코어마다 쓰는 데이터를 서로 다른 라인에 넣는다"이다. 변수 사이에 빈 공간을 채워 라인을 나눈다.

```
 false sharing:   [ a | b |   ...   ]     한 라인, 쓰기마다 왕복

 패딩/정렬 후:    [ a | 패딩 ......  ]    코어 0이 M 상태로 독점
                  [ b | 패딩 ......  ]    코어 1이 M 상태로 독점
```

각 코어가 자기 라인을 M 상태로 계속 쥐고 있으니 전이가 일어나지 않는다. 쓰기는 L1 적중으로 끝난다.

### C++의 경우

```cpp
struct alignas(64) Padded {
    long v;
};
Padded c[2];   // c[0]은 스레드 0, c[1]은 스레드 1
```

`alignas(64)`로 구조체를 64바이트 경계에 맞추면 크기도 64바이트가 되어, 배열의 원소가 각자 한 라인씩 차지한다.

64를 직접 쓰기보다 C++17의 `std::hardware_destructive_interference_size`를 쓰는 편이 이식성이 좋다. 거짓 공유를 피하려면 이만큼 떨어뜨리라는 표준 상수다.

### Java의 경우: @Contended

Java는 필드 배치를 JVM이 정하므로 코드에서 `long p1, p2, ...` 같은 필드를 끼워 넣어도 순서가 바뀔 수 있다. 그래서 JVM이 직접 패딩을 넣도록 하는 `@Contended` 어노테이션이 있다.

```java
import jdk.internal.vm.annotation.Contended;

class Counters {
    @Contended volatile long a;   // 스레드 0 전용
    @Contended volatile long b;   // 스레드 1 전용
}
```

JDK 소스의 javadoc은 이 어노테이션을 "false sharing 같은 메모리 경합이 예상되는 필드"에 붙이며, 해당 필드를 다른 필드와 떨어진 위치에 두고, 그 결과 객체 크기가 상당히 늘어난다고 설명한다. `@Contended("그룹")`처럼 그룹 이름을 주면 같은 그룹의 필드끼리는 붙여 두고 그룹 사이만 떼어 놓는다.

이 어노테이션은 `jdk.internal` 패키지에 있는 JDK 내부용이다. HotSpot은 기본값으로 `@Contended`를 JDK 자신의 클래스에만 적용한다(`RestrictContended` 플래그의 기본값이 `true`). 일반 애플리케이션 클래스에 효과를 내려면 컴파일과 실행 때 `--add-exports java.base/jdk.internal.vm.annotation=ALL-UNNAMED`로 패키지를 열고, 실행 때 `-XX:-RestrictContended`를 함께 줘야 한다.

표준 API가 아니고 JVM 옵션에 기대므로, 애플리케이션 코드에서는 보통 배열 인덱스 사이에 간격을 둬서 직접 라인을 나눈다.

```java
// 스레드 i는 counters[i * 16]만 쓴다 (long 16개 = 128B 간격)
long[] counters = new long[nThreads * 16];
counters[tid * 16]++;
```

long 하나가 8바이트라서 16칸이면 128바이트 간격이다. 어느 쪽 이웃과도 같은 라인에 놓이지 않는다.

### 패딩의 대가

- **메모리가 늘어난다.** 카운터 하나에 라인 하나(64바이트)를 쓰는 셈이다.
- **라인 크기를 가정한다.** Apple Silicon 같은 CPU는 128바이트 라인을 쓰기도 한다. 일부 Intel CPU는 인접 라인 프리페처가 128바이트 단위로 동작해 64바이트 패딩만으로 부족할 수 있다는 주장도 있으니, 타깃 환경에서 측정해야 한다.

## 6. 해결 2: 스레드 로컬 누적 후 합산

패딩은 "한 라인을 한 스레드가 독점"하게 만든다. 더 근본적인 방법은 아예 공유 변수를 쓰지 않는 것이다. 스레드마다 로컬 변수에 누적하고, 나중에 합친다.

대표 예가 Java의 `LongAdder`다. 공식 문서에 따르면 경합이 있을 때 내부 변수 집합을 동적으로 늘려 경합을 줄이며, 경합이 심한 상황에서 `AtomicLong`보다 처리량이 크게 높은 대신 공간을 더 쓴다. Linux 커널의 per-CPU 카운터도 같은 발상이다.

대가가 있다. `LongAdder.sum()`은 원자적 스냅샷이 아니다. 합산하는 동안 들어온 갱신은 반영되지 않을 수 있다. 통계 수집에는 충분하지만 정밀한 동기화 제어용으로는 맞지 않는다는 것이 문서의 설명이다.

## 7. 트레이드오프 정리

| 해결책 | 얻는 것 | 잃는 것 |
| --- | --- | --- |
| 패딩 / 라인 정렬(`alignas(64)`, `@Contended`) | 쓰기 경합 제거 | 메모리 증가, 라인 크기 가정(128B 환경 등) |
| 스레드 로컬 누적 후 합산(`LongAdder`, per-CPU) | 쓰기가 로컬이라 확장성이 가장 좋다 | 읽을 때 합산 비용, 읽은 값이 순간 스냅샷이 아니다 |
| 자주 쓰는 필드와 드문 필드 분리(hot/cold) | 캐시 적중률도 함께 좋아진다 | 코드 구조 변경 |
| 락/원자 연산으로 직접 공유 | 구현이 단순하다 | 진짜 공유라 경합 자체는 남는다 |

캐시가 바이트가 아닌 라인 단위로 동작하는 것은 결함이 아니라 설계 선택이다. 한 바이트를 읽으면 이웃 바이트도 곧 쓸 가능성이 높고(공간 지역성), DRAM은 연속 구간을 한 번에 전송하는 편이 효율적이다. 태그와 상태 비트를 라인당 한 벌만 두면 메타데이터 비용도 줄어든다. false sharing은 이 선택의 부작용이다.

---

## 결론

- 캐시는 라인 단위로 상태(MESI)를 관리하고, 쓰려면 먼저 그 라인을 혼자 가져야(M 또는 E) 한다.
- 다른 코어가 같은 라인을 쓰면 소유권이 코어 사이를 오간다. 이 전송은 L1 적중보다 훨씬 비싸다.
- false sharing은 무관한 변수가 같은 라인에 있어서 생긴다. 락이나 공유 변수가 없는데 스레드를 늘릴수록 느려지면 의심한다.
- 해결은 라인을 나누는 패딩과 정렬, 또는 공유를 없애는 스레드 로컬 누적이다. 둘 다 메모리나 읽기 비용을 대가로 낸다.
- 확인은 `perf c2c`로 하고, 64바이트를 하드코딩하기 전에 대상 CPU의 라인 크기를 확인한다.

여기까지는 코어 사이의 거리를 모두 같다고 봤다. 소켓이 여러 개인 서버에서는 메모리 자체가 코어에서 가까운 것과 먼 것으로 나뉜다. [NUMA](/posts/cs/architecture/numa/) 글에서 이어 간다.
