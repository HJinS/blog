## 개요

앞선 글들에서는 [메모리 계층과 캐시](/posts/cs/architecture/memory-hierarchy-cache-mapping/), [NUMA](/posts/cs/architecture/numa/)처럼 데이터가 코어까지 오는 길을 봤다. 이번 글은 CPU 내부로 들어가, 명령어를 빠르게 처리하려고 CPU가 어떤 도박을 하는지 본다.

이 글이 답하는 질문은 두 가지다.

- 알고리즘 복잡도가 같은데 입력을 정렬하기만 해도 반복문이 몇 배 빨라지는 이유는 무엇인가?
- 분기 예측이 틀리면 결과를 버리는데, 어떻게 비밀이 새는가?

---

## 1. 왜 파이프라인인가: 명령어를 겹쳐 처리한다

명령어 하나를 처리하는 일은 여러 단계로 나뉜다. 대표적인 5단계는 다음과 같다.

| 단계 | 약자 | 하는 일 |
|---|---|---|
| 인출(Instruction Fetch) | IF | 메모리에서 명령어를 가져온다 |
| 해독(Instruction Decode) | ID | 무슨 명령인지 해석하고 레지스터를 읽는다 |
| 실행(Execute) | EX | 계산하거나 분기 조건을 판단한다 |
| 메모리 접근(Memory) | MEM | 필요하면 메모리를 읽고 쓴다 |
| 쓰기(Write Back) | WB | 결과를 레지스터에 기록한다 |

단계마다 쓰는 하드웨어가 다르다. 그런데 명령어 하나가 끝날 때까지 다음 명령어를 기다리면, 한 시점에는 5개 장치 중 하나만 일하고 나머지 넷은 논다.

**핵심 아이디어는 한 문장이다. 앞 명령어가 다음 단계로 넘어가면, 그 자리에 다음 명령어를 바로 넣는다.** 이것이 파이프라이닝(pipelining)이다. 세탁기, 건조기, 다림질을 각각 다른 빨래가 동시에 쓰는 것과 같다. 이 비유는 한 가지가 틀린다. 빨래와 달리 명령어는 앞 명령어의 결과에 의존할 수 있다.

명령어 4개를 처리하는 데 걸리는 사이클(cycle, 클록 한 주기)을 비교해 보자.

- 겹치지 않을 때: 4개 x 5단계 = 20 사이클
- 파이프라인: 5 + (4 - 1) = 8 사이클

파이프라인이 가득 차면 사이클마다 명령어 하나가 끝난다. 명령어 하나에 드는 평균 사이클 수(CPI, Cycles Per Instruction)가 이상적으로 1에 가까워진다. 단계를 더 잘게 나눌수록 한 단계가 짧아져 클록을 올릴 수 있다. 현대 CPU는 파이프라인이 깊고, 한 사이클에 여러 명령어를 동시에 내보내기까지 한다(슈퍼스칼라, superscalar).

대가는 이렇다. 파이프라인이 깊고 넓을수록, 중간에 흐름이 끊길 때 날아가는 일의 양이 커진다.

## 2. 해저드: 파이프라인이 막히는 세 가지 이유

겹쳐 처리하다 보면 다음 명령어를 그대로 흘려보낼 수 없는 경우가 생긴다. 이를 해저드(hazard)라고 한다.

| 종류 | 원인 | 완화 방법 |
|---|---|---|
| 구조적 | 두 명령어가 같은 자원을 동시에 쓰려 한다 | 자원을 복제한다 |
| 데이터 | 앞 명령어의 결과가 있어야 다음 명령어를 실행할 수 있다 | 포워딩(forwarding, 결과를 WB 전에 바로 전달), 부족하면 스톨(stall, 한 사이클 쉼) |
| 제어 | 분기 결과가 나와야 다음에 인출할 명령어를 안다 | 분기 예측 |

앞의 둘은 몇 사이클 쉬거나 결과를 바로 넘겨 주면 해결된다. 문제는 제어 해저드다. 이 글의 나머지는 제어 해저드를 다룬다.

## 3. 분기 앞에서 CPU는 찍는다

`if (x >= 128)` 같은 조건 분기(branch)를 만나면, 조건이 계산되는 EX 단계가 끝나기 전에는 다음에 인출할 명령어가 둘 중 무엇인지 모른다. 기다리면 파이프라인이 비고, 분기는 코드에 흔하다. 보통 명령어 5~6개에 하나쯤 분기다.

**핵심 아이디어는 한 문장이다. 결과를 예측해서 그 경로를 일단 실행하고, 틀리면 버린다.** 이것이 투기적 실행(speculative execution)이다. 맞으면 공짜로 시간을 번다. 틀리면 투기적으로 인출·실행한 명령어를 모두 폐기(flush)하고 올바른 경로에서 다시 시작한다.

5단계 파이프라인에서 I2가 분기(`beq`)이고, 예측은 "분기하지 않음"이었는데 실제로는 분기했다고 하자. `✕`가 폐기된 칸이다.

| 명령어 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 | 9 |
|---|---|---|---|---|---|---|---|---|---|
| I1 | IF | ID | EX | MEM | WB | | | | |
| I2 (`beq`) | | IF | ID | **EX (분기 확정)** | MEM | WB | | | |
| I3 (예측 경로) | | | IF | ID | ✕ | | | | |
| I4 (예측 경로) | | | | IF | ✕ | | | | |
| T (올바른 경로) | | | | | IF | ID | EX | MEM | WB |

4번 사이클 끝에 I2의 EX가 끝나고서야 예측이 틀렸음을 안다. 그때 파이프라인에 들어 있던 I3, I4가 버려지고, 5번 사이클에야 올바른 경로 T를 인출한다. 예측이 맞았다면 I3, I4가 그대로 진행되어 이 두 칸은 낭비되지 않았을 것이다. 이 그림은 단순화한 5단계 기준이다. 실제 코어는 분기가 훨씬 뒤에서 확정되므로 버려지는 칸이 더 많다.

손실을 숫자로 보자. 명령어 5개당 분기가 1개, 실패 한 번의 손실이 15사이클이라고 가정한다(마이크로아키텍처마다 다르며, 깊은 파이프라인에서는 십수 사이클 이상이다).

| 예측 실패율 | 분기당 평균 손실 | 명령어당 추가 사이클 | CPI |
|---|---|---|---|
| 0% | 0 | 0 | 1.00 |
| 5% | 0.75 | 0.15 | 1.15 |
| 50% | 7.5 | 1.5 | 2.50 |

실패율 5%면 15% 느려지고, 50%면 2.5배 느려진다. 예측 정확도가 성능을 좌우하는 이유다.

## 4. 분기 예측기는 어떻게 맞히는가

가장 단순한 예측은 "이 분기는 지난번과 같은 방향"이다. 분기 주소마다 1비트로 마지막 결과를 기억한다. 그런데 반복문에서 문제가 생긴다. 반복 10번짜리 루프의 끝 분기는 "돌아감"이 9번, "빠져나감"이 1번이다.

- 1비트: 빠져나갈 때 한 번 틀리고, 다음 루프 첫 반복에서 "빠져나감"을 기억하고 있어 또 틀린다. 루프당 2번 실패한다.
- 2비트 포화 카운터(saturating counter): 상태가 4개다. 강한 taken, 약한 taken, 약한 not-taken, 강한 not-taken. 한 번 반대 결과가 나와도 "강한 taken"이 "약한 taken"으로 내려갈 뿐 예측 방향은 그대로다. 루프당 1번만 실패한다.

현대 예측기는 여기서 더 나아가 최근 여러 분기의 결과 이력(global history)을 함께 본다. "직전 세 분기가 참, 거짓, 참이었다면 이번 분기는 거짓" 같은 패턴을 학습한다. 규칙적인 코드에서는 대부분의 분기를 맞힌다.

예측기가 맞히지 못하는 것은 규칙이 없는 분기, 즉 무작위 데이터에 의존하는 분기다.

## 5. 정렬된 배열이 더 빠른 이유

유명한 예시다. 0~255 사이 값이 든 큰 배열에서 128 이상인 값만 더한다.

```c
for (int i = 0; i < n; i++) {
    if (data[i] >= 128)   // 데이터 의존 분기
        sum += data[i];
}
```

복잡도는 둘 다 $O(n)$이다. 그런데 배열의 상태에 따라 분기 패턴이 달라진다.

| 배열 상태 | 분기 결과 나열 | 예측기가 하는 일 | 예측 실패 |
|---|---|---|---|
| 무작위 | 참, 거짓, 거짓, 참, 참, 거짓 ... | 규칙이 없어 사실상 동전 던지기 | 약 50% |
| 정렬 | 거짓 x 절반, 참 x 절반 | 긴 구간 동안 같은 방향을 맞힘 | 경계에서 1번 남짓 |

정렬하면 앞쪽 절반은 전부 128 미만이라 계속 거짓이고, 뒤쪽 절반은 전부 참이다. 앞 절의 표대로 실패율 50%와 0%의 차이가 CPI를 크게 벌린다. 같은 코드가 입력 분포만 달라졌는데 몇 배 느려질 수 있다.

확인은 `perf stat -e branch-misses`로 한다. 알고리즘은 같은데 입력에 따라 시간이 크게 달라지고 branch-misses가 높다면 이 현상을 의심한다.

대응은 세 가지다.

| 방법 | 얻는 것 | 잃는 것 |
|---|---|---|
| 입력을 정렬한다 | 분기가 한쪽으로 몰린다 | 정렬 비용($O(n \log n)$)이 더 클 수 있다 |
| 분기를 없앤다(`sum += (x >= 128) ? x : 0`을 조건부 이동 `cmov`로 컴파일) | 예측 실패 자체가 없다 | 두 경로를 모두 계산한다. 컴파일러가 항상 이 코드를 내 주지는 않는다 |
| 분기 수를 줄인다 | 실패할 기회가 줄어든다 | 코드를 바꿔야 한다 |

## 6. 투기 실행의 부작용: 되돌릴 수 없는 것

앞 절들은 "틀리면 버린다"를 전제했다. 그런데 무엇을 버리는가가 문제다.

비순차(out-of-order) 코어는 명령어를 재정렬 버퍼(ROB, ReOrder Buffer)에 넣어 준비된 것부터 순서 없이 실행하되, 결과를 확정(commit, retire)하는 것은 프로그램 순서로 한다. 예측이 틀리면 아직 확정되지 않은 결과를 버린다. 버려지는 것은 **아키텍처 상태**, 즉 프로그램이 볼 수 있는 레지스터와 메모리 값이다.

그러나 투기 실행 중에 메모리 로드가 일어났다면, 그 데이터가 올라간 **캐시 라인**은 그대로 남는다. 캐시는 프로그램이 직접 보는 상태가 아니라 속도를 위한 마이크로아키텍처 상태이기 때문이다. 이 틈이 Spectre의 뿌리다. 캐시 접근 시간이 라인마다 다르다는 점은 [메모리 계층 글](/posts/cs/architecture/memory-hierarchy-cache-mapping/)에서 봤다.

## 7. Spectre v1: 버려진 실행이 캐시에 남긴 흔적

Spectre는 2018년 1월 초에 공개된 취약점 계열이다. 분기 예측과 투기 실행을 이용해 원래 실행되지 않을 연산을 투기적으로 실행시키고, 그 부수 효과를 사이드 채널(side channel, 설계 의도 밖의 정보 경로)로 읽는다. 그중 경계 검사 우회(CVE-2017-5753) 변종이 이해하기 쉽다.

피해 코드는 이런 모양이다.

```c
if (x < array1_size)               // 경계 검사
    y = array2[array1[x] * 256];   // array1[x]가 비밀이 되도록 x를 조작
```

공격은 여섯 단계로 진행된다.

| 단계 | 공격자가 하는 일 | CPU 안에서 일어나는 일 |
|---|---|---|
| 1. 예측기 훈련 | 범위 안의 x로 이 코드를 여러 번 호출한다 | 예측기가 "분기는 참"이라고 학습한다 |
| 2. 캐시 준비 | `array2`의 캐시 라인을 비우고 `array1_size`도 캐시에서 쫓아낸다 | `array1_size` 로드가 메모리까지 가야 해 느려진다 |
| 3. 공격 | 범위 밖의 x를 넣는다 | 크기 로드를 기다리는 동안 예측대로 분기 안쪽을 투기 실행한다 |
| 4. 투기 | | `array1[x]`의 비밀 바이트 s를 읽고 `array2[s * 256]` 라인을 캐시에 올린다 |
| 5. 롤백 | | 검사 결과가 나와 예측 실패를 알고 레지스터는 폐기하지만, 캐시 라인은 남는다 |
| 6. 측정 | `array2`의 라인 256개를 접근하며 시간을 잰다 | 하나만 빠르고 나머지는 느리다. 빠른 라인의 번호가 s다 |

그림으로 보면 이렇다. 비밀 값이 77이라면 77번 라인만 빠르게 읽힌다.

| array2 라인 | 0 | ... | 76 | 77 | 78 | ... | 255 |
|---|---|---|---|---|---|---|---|
| 접근 시간 | 느림 | 느림 | 느림 | **빠름** | 느림 | 느림 | 느림 |

비밀 값은 레지스터에서 지워졌지만, "어느 라인이 빠른가"라는 부수 효과가 값을 알려 준다. 이 측정 기법을 Flush+Reload라고 부른다(캐시를 비우고, 접근해서 시간을 잰다). 정리하면 이 공격이 성립하는 이유는 세 가지다. 예측기를 훈련시킬 수 있고, 검사 결과를 기다리는 시간 창이 있고, 투기 중에도 로드가 캐시를 바꾼다는 것이다.

같은 시기에 공개된 Meltdown(CVE-2017-5754)은 다른 메커니즘이다. 예측이 아니라 권한 검사보다 먼저 일어나는 비순차 로드를 이용해 커널 메모리를 읽는다. 이 글에서는 다루지 않으며, 대응책인 KPTI는 [가상 메모리, 페이지 테이블, TLB](/posts/cs/os/virtual-memory-page-table-tlb/) 글에서 설명한다.

## 8. 완화와 트레이드오프

Spectre는 한 번에 막히지 않았고, 여러 층의 완화가 이어졌다. 모두 성능이나 기능을 맞바꾼다.

| 층 | 방법 | 막는 방식 | 대가 |
|---|---|---|---|
| 코드 | 경계 검사 뒤 투기를 막는 직렬화 명령(`lfence` 등) | 검사 결과가 나올 때까지 뒤 명령의 실행을 멈춘다 | 위험한 지점마다 넣어야 하고, 넣은 곳은 느려진다 |
| 코드 | 인덱스 마스킹 | 투기 중에도 인덱스가 범위를 벗어나지 못하게 계산한다 | 코드 크기와 연산이 늘어난다 |
| 브라우저 | 고해상도 타이머 정밀도 축소, SharedArrayBuffer 제한, 사이트 격리 | 캐시 접근 시간을 재는 수단을 약화시킨다 | 정당한 고정밀 타이머 기능을 희생한다 |
| 커널·마이크로코드 | 분기 예측기 관련 완화(간접 분기를 노리는 Spectre v2 대응인 IBRS, IBPB, retpoline 등) | 다른 프로세스나 권한 수준이 예측기를 훈련시키는 경로를 좁힌다 | 환경과 버전에 따라 성능이 떨어진다 |

여기서 얻는 교훈은 "투기 실행은 공짜 성능"이라는 가정이 깨졌다는 점이다. 분기 예측과 투기 실행을 빼면 현대 CPU의 속도를 낼 수 없지만, 그 부작용이 보안 경계를 넘을 수 있다는 것을 보여 줬다. 완화마다 비용이 다르고 수치는 환경에 따라 달라서 이 글에서는 저하율을 적지 않는다.

## 결론

- 파이프라인은 명령어를 단계별로 겹쳐 처리량을 높인다. 대신 깊을수록 흐름이 끊길 때의 손실이 크다.
- 분기 결과를 기다리지 않으려고 CPU는 예측해서 투기적으로 실행한다. 예측이 틀리면 파이프라인을 flush하고, 비용은 파이프라인 깊이에 비례한다.
- 데이터 의존 분기가 무작위이면 예측이 실패해, 복잡도가 같아도 정렬된 입력보다 몇 배 느려질 수 있다. `branch-misses`로 확인한다.
- 롤백은 레지스터와 메모리에만 적용되고 캐시에는 적용되지 않는다. 그래서 투기 실행 중 캐시에 남은 흔적을 시간으로 재면 비밀을 복원할 수 있다(Spectre).
- 완화는 직렬화, 마스킹, 타이머 약화 등 여러 층이며 모두 성능이나 기능을 맞바꾼다.

한 코어 안에서는 이런 재배치가 결과를 바꾸지 않는다. 코어가 여럿이면 이야기가 다르다. [메모리 모델과 배리어](/posts/cs/architecture/memory-model-barriers/)에서 다른 코어에 보이는 순서 문제를 다룬다.
