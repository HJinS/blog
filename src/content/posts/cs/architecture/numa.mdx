## 개요

[앞 글](/posts/cs/architecture/cache-coherence-mesi-false-sharing/)에서는 코어마다 있는 캐시가 같은 라인을 주고받는 비용을 봤다. 이번 글은 한 단계 바깥, 메모리 자체가 소켓마다 나뉜 서버를 다룬다.

서버에서 `free -m`을 찍으면 여유 메모리가 20GB 넘게 남아 있다. 그런데 스왑 사용량은 계속 늘고, DB 쿼리 지연은 간헐적으로 튄다. 프로세스의 RSS(실제 점유 메모리)는 평소와 같다. 메모리 누수도 아니고 일반적인 메모리 부족도 아니다. 무슨 일일까?

이 글이 답하는 질문은 두 가지다.

- 멀티 소켓 서버에서 "메모리는 하나의 균일한 풀"이라는 가정은 어떻게 깨지는가?
- 그 가정이 깨지면 왜 전체 여유가 충분한데도 스왑이 발생하는가?

일반적인 메모리 부족 경로(오버커밋, 스래싱, OOM Killer)는 [메모리 부족의 경로: 오버커밋, 스래싱, OOM Killer](/posts/cs/os/overcommit-thrashing-oom-killer/)에서 다뤘다. 이 글은 그 경로와 겉모습은 비슷하지만 원인이 다른 경우, 즉 노드 하나만 모자란 경우를 다룬다.

## 1. 왜 메모리가 노드로 나뉘는가

CPU 코어가 늘어나면 모든 코어가 하나의 메모리 컨트롤러를 공유하는 구조가 병목이 된다. 코어가 아무리 많아도 메모리로 가는 통로가 하나면 그 통로에서 줄을 서야 한다.

그래서 서버는 CPU 소켓마다 메모리 컨트롤러와 DIMM(메모리 모듈)을 따로 붙인다. 소켓끼리는 별도의 인터커넥트(소켓 사이를 잇는 고속 링크)로 연결한다. 최근에는 소켓 하나 안에서도 칩렛(chiplet) 단위로 메모리 컨트롤러가 나뉘는 구성이 있다.

핵심 아이디어는 한 문장이다. **메모리를 CPU 곁에 분산 배치해 대역폭을 늘리는 대신, 어느 메모리인지에 따라 접근 시간이 달라지는 것을 받아들인다.** 이 구조를 NUMA(Non-Uniform Memory Access, 비균일 메모리 접근)라고 부른다. 모든 접근 시간이 같은 구조는 UMA 또는 SMP라고 한다.

```text
        Node 0                              Node 1
  +----------------+                  +----------------+
  | CPU 0 (core x4)|<---interconnect-->| CPU 1 (core x4)|
  +-------+--------+                  +--------+-------+
          |                                    |
   memory controller                    memory controller
          |                                    |
  +-------+--------+                  +--------+-------+
  |  local memory  |                  |  local memory  |
  |     32GB       |                  |     32GB       |
  +----------------+                  +----------------+

  CPU 0 -> Node 0 memory : 빠름 (local)
  CPU 0 -> Node 1 memory : 인터커넥트를 거쳐 느림 (remote)
```

어느 CPU에서든 모든 메모리에 접근은 할 수 있다. 다만 자기 소켓에 붙은 메모리(로컬)는 빠르고, 남의 소켓에 붙은 메모리(원격)는 인터커넥트를 한 번 더 건너야 해서 느리다. 그림에서 보듯 이 구조에서는 운영체제가 "이 페이지를 어느 노드에 놓을까"를 정해야 하고, 그 선택이 성능을 좌우한다.

## 2. 거리 표 읽기: `numactl --hardware`

Linux에서 NUMA 구성은 `numactl --hardware`로 본다. 아래는 Jeremy Cole가 MySQL swap insanity 글에서 보여준 2소켓 서버의 출력이다(64GB, 노드 2개).

```text
available: 2 nodes (0-1)
node 0 size: 32276 MB
node 0 free: 26856 MB
node 1 size: 32320 MB
node 1 free: 26897 MB
node distances:
node   0   1
  0:  10  21
  1:  21  10
```

읽는 법은 이렇다.

| 줄 | 의미 |
|---|---|
| `available: 2 nodes (0-1)` | 노드가 2개다. 각 노드가 소켓 하나에 대응한다 |
| `node 0 size / free` | 노드마다 크기와 여유 메모리가 따로 관리된다 |
| `node distances` | 노드 사이의 상대적 거리. 자기 자신은 10, 원격은 그보다 큰 값이다 |

여기서 눈여겨볼 점이 두 가지 있다.

첫째, 여유 메모리(`free`)가 전체 하나가 아니라 노드마다 따로 있다. 노드마다 자체 free 리스트와 워터마크(여유가 이 아래로 내려가면 회수를 시작하는 기준선)를 가진다. 전체 합이 충분해도 한 노드의 값이 바닥일 수 있다.

둘째, 거리 값 10과 21은 절대 시간(ns)이 아니라 상대 비율이다. 이 표는 펌웨어가 ACPI의 SLIT(System Locality Information Table)라는 표로 OS에 알려주는 값이다. 대략 "원격이 로컬보다 2배 남짓 멀다"로 읽으면 된다. 실제 지연은 하드웨어마다 다르므로 직접 재야 한다.

## 3. 기본 정책: 내가 있는 노드에 놓는다

그러면 OS는 페이지를 어느 노드에 놓을까? 기본값은 단순하다. **페이지를 처음 만지는 순간(page fault) 그 스레드가 실행 중인 노드에서 할당하려 한다.** 이를 로컬 할당(local allocation) 또는 first-touch 정책이라고 한다. 리눅스 커널 문서도 시스템이 부팅된 뒤의 기본 정책이 로컬 할당이라고 설명한다.

이 기본값이 합리적인 이유는 두 가지다.

- 원격 접근이 느리므로, 쓰는 스레드와 데이터를 같은 노드에 두는 것이 평균적으로 유리하다.
- 할당 시점에 OS가 확실히 아는 정보가 "누가 이 페이지를 처음 쓰는가" 하나뿐이다. 앞으로 누가 쓸지는 모른다.

작은 예시로 따라가 보자. 노드당 32GB인 서버에서 mysqld의 스레드 하나가 Node 0 코어에서 돌며 버퍼 풀을 초기화한다고 하자.

| 단계 | 일어나는 일 |
|---|---|
| 1 | 스레드가 버퍼 풀의 첫 페이지를 만진다 (page fault) |
| 2 | 스레드가 Node 0에 있으므로 Node 0 free 리스트에서 페이지를 준다 |
| 3 | 20GB를 초기화하면 Node 0 안에서 20GB가 채워진다 |
| 4 | Node 1은 거의 비어 있다. 이 페이지들은 이후에도 Node 0에 머문다 |

마지막 줄이 중요하다. 별도의 NUMA balancing 기능이 없으면 **한 번 놓인 페이지는 다른 노드로 옮겨지지 않는다.** 정책을 나중에 바꿔도 이미 놓인 페이지에는 적용되지 않고, 바꾼 뒤에 새로 할당되는 페이지부터 적용된다(`mbind()`의 페이지 이동 옵션을 쓰면 기존 페이지를 옮길 수는 있다).

그래서 한 스레드, 또는 소수의 스레드가 큰 메모리를 한꺼번에 초기화하면 메모리가 한 노드에 쏠린다. 이것이 로컬 우선 정책의 약점이다.

## 4. 노드 단위로 압박이 생긴다

메모리 부족은 시스템 전체가 아니라 노드 단위로 판단된다. 노드마다 free 리스트와 워터마크가 따로 있기 때문이다.

```text
  Node 0                         Node 1
  +--------------------+        +--------------------+
  | buffer pool ###### |        | (idle)             |
  | node 0 FULL ###### |        | free: plenty       |
  | free: ~0           |        |                    |
  +--------------------+        +--------------------+
        |
        v
  Node 0 위의 스레드가 새 페이지를 요청
  -> Node 0 에는 free 가 없다
  -> Node 0 의 페이지 캐시를 비우거나, Node 0 의 페이지를 swap-out
  (Node 1 에 free 가 많아도 그렇게 될 수 있다)
```

Node 0에서 도는 스레드가 새 페이지를 달라고 하면, 커널은 우선 Node 0 안에서 공간을 만들려 한다. 같은 노드의 페이지 캐시를 비우거나, 쓰는 중인 익명 메모리(anonymous memory, 파일과 연결되지 않은 힙이나 스택 같은 메모리)를 스왑으로 내보낸다. 그 사이 Node 1에는 free가 가득 있어도 말이다.

결과는 이렇다. `free -m`의 전체 합계로는 여유가 충분한데 스왑이 발생한다. 시스템 전체가 아니라 노드 하나가 모자란 것이므로, 일반적인 메모리 부족 경로와는 원인이 다르다.

## 5. 사례: MySQL swap insanity

이 현상을 정리한 고전적인 사례가 Jeremy Cole의 "The MySQL swap insanity problem and the effects of the NUMA architecture"다. 글에 나온 사실만 정리하면 다음과 같다.

**환경.** RAM 64GB의 2소켓(쿼드코어 2개) 서버에서 InnoDB 버퍼 풀을 48GB로 설정했다. NUMA 노드는 소켓마다 하나, 각각 약 32GB다.

**증상.**

- 시스템이 실제로 메모리가 모자라지 않은데도 리눅스가 대량으로 스왑했다.
- `free`에는 페이지 캐시가 넉넉히 보였고, 프로세스들의 resident set도 RAM에 들어갔다.
- 스왑된 것은 버퍼 풀처럼 실제로 쓰이는 메모리였다. 나중에 그 메모리가 필요해지면 swap-in 때문에 무작위 쿼리가 무작위로 느려졌다. 심하면 성능이 급락하는 "죽음의 소용돌이"로 빠졌다.
- mysqld의 RSS는 정상이고 안정적이었다. 누수가 아니었다.

**원인.** 기본 정책은 요청한 스레드가 있는 노드에서 할당하는 것이다. 버퍼 풀은 노드 하나(32GB)에 들어가지 않을 만큼 크다. `/proc/<pid>/numa_maps`로 보니 Node 0에 약 30.45GB, Node 1에 약 20.75GB가 놓여 있었다. Node 0이 거의 다 찼고 캐시를 둘 여유도 없었다. Node 0에서 도는 프로세스가 로컬 메모리를 필요로 하자, 커널은 여유가 많은 Node 1의 캐시를 버리는 대신 Node 0의 버퍼 풀 페이지를 스왑으로 내보냈다. 글쓴이도 커널이 왜 그렇게 선택하는지는 완전히 이해하지 못했다고 밝힌다. `zone_reclaim_mode`를 조정해 봤지만 이 경우에는 도움이 되지 않았다.

**해결.** mysqld를 interleave 정책으로 실행했다.

```bash
numactl --interleave all <command>
```

글쓴이는 `mysqld_safe`에서 명령을 만드는 줄에 `numactl --interleave all`을 앞에 붙이는 한 줄 수정으로 적용했다. 그 뒤 버퍼 풀은 노드마다 약 26GB로 거의 균등하게 놓였고(Node 0 약 6,679,535 페이지, Node 1 약 6,679,532 페이지), 재현되던 모든 스왑 시나리오에서 스왑이 멈췄다. DBT2 벤치마크에서는 평상시 성능 차이가 없었다고 보고한다.

같은 시리즈를 이어간 Percona의 후속 글(Swap insanity tome III)도 NUMA 불균형이 스왑을 부를 수 있다고 정리한다. 이 글은 `numactl`로 interleave하는 것 외에, 그래도 남는 원인으로 백업 중 쌓이는 dirty page를 따로 다룬다. 즉 이 증상의 원인이 NUMA 하나만은 아니다.

## 6. 정책을 바꾸는 방법

핵심 아이디어는 "페이지가 놓이는 노드를 기본값에 맡기지 않고 직접 정한다"이다. 도구는 크게 네 가지다.

```text
  기본(local)           interleave=all
  -----------           --------------
  Node 0  Node 1        Node 0  Node 1
  [####]  [    ]        [##  ]  [##  ]
  [####]  [    ]        [##  ]  [##  ]
   가득    비어 있음       절반씩 번갈아 배치
```

interleave는 페이지를 노드에 라운드 로빈으로 번갈아 놓는다. 커널 문서에 따르면 익명 메모리는 주소 기준으로 노드를 고르고, 페이지 캐시는 태스크별 카운터로 고른다. 어느 쪽이든 한 노드에 쏠리지 않는다.

| 정책 | 얻는 것 | 잃는 것 | 적합한 경우 |
|---|---|---|---|
| 기본 (local, first-touch) | 스레드와 메모리가 가까워 지연이 최소 | 메모리가 한 노드에 쏠리면 그 노드만 압박받아 스왑이 날 수 있다 | 작업 집합(working set)이 노드 하나에 들어가는 서비스 |
| `--interleave=all` | 용량과 대역폭이 노드 전체에 균등하고 한 노드가 먼저 소진되지 않는다 | 접근의 일부가 항상 원격이라 평균 지연과 인터커넥트 부하가 늘어난다 | 노드 하나보다 큰 단일 프로세스 힙(대형 DB 버퍼 풀) |
| `--membind`, `--cpunodebind` | 어디에 놓일지 예측할 수 있다 | 그 노드 용량이 한계다. 넘치면 스왑이나 OOM이고 운영도 복잡하다 | 노드 단위로 인스턴스를 나눠 운영할 때 |
| 자동 NUMA balancing | 워크로드가 바뀌어도 자동으로 적응한다 | 샘플링용 page fault와 페이지 이동 오버헤드, 지연 변동이 있다(아래 설명) | 접근 패턴이 안정적인 장기 실행 프로세스 |

`--membind`는 지정한 노드 집합에서만 할당하게 강제한다. `--preferred`는 한 노드를 우선하되 모자라면 가까운 노드부터 다른 노드로 넘어간다. `--cpunodebind`는 스레드가 돌 CPU 노드를 고정한다.

자동 NUMA balancing(`/proc/sys/kernel/numa_balancing`)은 동작이 독특하다. 커널이 주기적으로 페이지의 매핑을 일부러 해제해 두고, 다음 접근 때 나는 page fault를 보고 "이 페이지를 접근하는 태스크가 어느 노드에 있는가"를 판단해 페이지나 태스크를 옮긴다. 이 과정 자체가 비용이다. 커널 문서는 이 비용이 지역성 개선으로 상쇄되기를 기대할 뿐 항상 이득이라고 보장하지 않으며, 워크로드가 이미 특정 노드에 묶여 있다면 끄기를 권한다.

## 7. interleave는 왜 평소 성능을 별로 안 깎는가

interleave는 접근의 일부를 항상 원격으로 만든다. 그런데도 앞의 사례에서 DBT2 벤치마크 성능은 그대로였다. 왜일까?

DB 워크로드의 병목은 대개 메모리 접근 지연이 아니다. 디스크 I/O, 락 대기, CPU 연산이 훨씬 크다. 원격 접근으로 늘어난 지연은 그 아래에 묻혀 잘 드러나지 않는다.

반대로 메모리 지연이 곧 성능인 워크로드에서는 사정이 다르다. 고속 캐시나 인메모리 분석처럼 메모리를 쉴 새 없이 읽는 서비스에서는 원격 비율이 늘어난 만큼이 그대로 드러난다. 그래서 interleave는 만능이 아니다. 어떤 서비스에는 스왑 폭주를 막는 보험이고, 어떤 서비스에는 지연을 늘리는 비용이다.

그리고 한 노드에 몰려서 스왑이 나는 것과 평균 지연이 조금 느는 것을 비교하면, 대용량 단일 프로세스에서는 대체로 후자가 훨씬 싼 비용이다. 이것이 "작업 집합이 노드 하나보다 크면 interleave"라는 경험칙의 근거다.

## 8. 진단과 컨테이너에서의 함정

증상은 이렇다. 전체 free는 충분한데 스왑이 늘고, DB 지연이 간헐적으로 튀며, RSS는 정상이다. 이때 NUMA 불균형을 의심하고 다음 순서로 확인한다.

| 도구 | 보는 것 |
|---|---|
| `numactl --hardware` | 노드 수, 노드별 크기와 free, 거리 표 |
| `numastat -m` | 노드별 메모리 사용 현황. 한 노드만 free가 바닥인지 확인한다 |
| `/proc/<pid>/numa_maps` | 프로세스의 페이지가 노드마다 얼마나 놓였는지 |

주의할 점이 있다. `numa_maps`를 읽으면 커널이 결과를 만드는 동안 대상 프로세스가 잠시 멈춘다. Jeremy Cole의 글도 이 때문에 운영 중인 mysqld에서 연결과 쿼리가 멈출 수 있다고 경고한다. 운영 중인 DB에 분 단위로 폴링하는 용도로 쓰면 안 된다. 한 번씩 확인하는 데에만 쓴다.

원인이 노드 불균형이면 interleave, 노드별 인스턴스 분할, 버퍼 풀 크기 조정이 대응책이다. 노드 불균형이 아니라 진짜 전체 메모리 부족이라면 [앞서 다룬 메모리 부족 경로](/posts/cs/os/overcommit-thrashing-oom-killer/)로 가서 봐야 하므로 둘을 구분해야 한다.

컨테이너에서는 한 가지가 더 있다. CPU를 일부만 쓰도록 limit을 걸면 NUMA 문제가 사라질 것 같지만 그렇지 않다. CPU 사용량 제한(quota)은 "얼마나 쓰는가"를 제한할 뿐, 스레드가 어느 노드에서 돌지, 페이지가 어느 노드에 놓일지는 정하지 않는다. 노드 친화를 원하면 CPU와 메모리 노드를 함께 지정하는 cpuset을 쓰거나 노드 단위로 배치해야 한다.

## 결론

- NUMA 서버에서 메모리는 노드마다 따로 있고, 로컬은 빠르고 원격은 느리다. `numactl --hardware`의 거리 표가 그 구조를 보여준다.
- 기본 정책은 페이지를 처음 만진 스레드가 있는 노드에 할당하는 것이고, 한 번 놓인 페이지는 잘 옮겨지지 않는다.
- 메모리 압박은 노드 단위로 판단되므로, 전체 free가 충분해도 노드 하나가 가득 차면 스왑이 발생할 수 있다. swap insanity가 그 사례다.
- interleave는 이 쏠림을 막는 대신 평균 지연을 조금 올린다. 단일 프로세스가 노드 하나보다 클 때 효과가 크고, 메모리 지연이 지배적인 워크로드에서는 비용이 드러난다.
- 진단은 `numactl --hardware`, `numastat -m`, `numa_maps` 순서이고, `numa_maps`는 운영 서버에서 자주 읽지 않는다.
