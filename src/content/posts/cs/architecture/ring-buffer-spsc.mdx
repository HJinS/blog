## 개요

[앞 글](/posts/cs/architecture/cas-lock-free-aba)에서는 CAS로 락 없이 자료구조를 만들 때 생기는 ABA 문제를 봤다. 이번 글은 CAS조차 필요 없는 경우를 다룬다. 쓰는 쪽이 정확히 한 명이면 동기화가 놀랄 만큼 단순해진다.

이 글이 답하는 질문은 두 가지다.

- 링 버퍼(ring buffer)는 왜 크기를 2의 거듭제곱으로 잡고, 가득 참과 비어 있음은 어떻게 구분하는가?
- 생산자 하나, 소비자 하나(SPSC)라면 왜 락도 CAS도 없이 안전한가?

링 버퍼는 크기가 고정된 배열을 원형으로 되감아 쓰는 큐다. SPSC는 Single Producer Single Consumer의 약자로, 데이터를 넣는 스레드 하나와 꺼내는 스레드 하나만 있는 구성을 말한다.

## 1. 왜 링 버퍼인가

생산자가 데이터를 빠르게 쏟아내고 소비자가 따라가는 곳이 많다. 네트워크 카드의 수신 큐, 로그 파이프라인, 오디오 버퍼, 커널 로그가 그렇다. 여기에 흔한 큐를 쓰면 두 가지 비용이 생긴다.

| 구조 | 할당·GC | 동기화 | 캐시 지역성 | 가득 찼을 때 |
|---|---|---|---|---|
| 연결 리스트 큐 | 원소마다 노드 할당 | 락 또는 CAS(ABA 주의) | 나쁨(포인터를 따라감) | 메모리가 허락하는 만큼 계속 늘어남 |
| 락 기반 bounded 큐 | 배열이면 사전 할당 | 뮤텍스 경합, 컨텍스트 스위치 | 보통 | 생산자가 블로킹 |
| 링 버퍼 | 사전 할당, 이후 0회 | SPSC는 락 없음 | 좋음(연속 메모리) | 정책을 반드시 골라야 함 |

링 버퍼의 핵심 아이디어는 한 문장이다. **미리 만든 고정 배열의 끝에 닿으면 처음으로 되돌아가 같은 칸을 재사용한다.**

덕분에 push와 pop 모두 $O(1)$이고, 공간은 $O(N)$으로 고정되며, 힙 할당은 0회다. 원소가 연속 메모리에 있어서 CPU 캐시에도 잘 맞는다. 대신 용량이 고정이라는 대가가 있다. 가득 찼을 때 어떻게 할지는 설계에서 반드시 정해야 하고, 이는 5절에서 다룬다.

## 2. head와 tail: 계속 증가하는 시퀀스 번호

링 버퍼에는 두 개의 위치가 필요하다. 다음에 읽을 곳(head)과 다음에 쓸 곳(tail)이다.

가장 먼저 떠오르는 방식은 head와 tail을 0부터 N-1까지만 돌게 하는 것이다. 그런데 이러면 문제가 있다. head와 tail이 같은 칸을 가리킬 때 이것이 비어 있는 상태인지 가득 찬 상태인지 알 수 없다. 흔한 해법은 칸 하나를 항상 비워 두는 것인데, 그러면 슬롯을 하나 낭비한다.

더 깔끔한 방법이 있다. **head와 tail을 되감지 않고 계속 증가하는 번호(시퀀스 번호, sequence)로 둔다.** 슬롯 번호는 시퀀스에서 따로 계산한다.

- 비어 있음: `tail == head`
- 원소 개수: `tail - head`
- 가득 참: `tail - head == N`

크기 8짜리 버퍼에서 세 가지 상태를 따라가 보자.

```text
N = 8, slot = seq & 7

(1) 일반: head=2, tail=6 (원소 4개: seq 2,3,4,5)

 slot:  0    1    2    3    4    5    6    7
      +----+----+----+----+----+----+----+----+
      |    |    | s2 | s3 | s4 | s5 |    |    |
      +----+----+----+----+----+----+----+----+
                  ^                   ^
                 head                tail (6 & 7 = 6)

(2) 한 바퀴 돈 상태: head=6, tail=11 (원소 5개: seq 6,7,8,9,10)

 slot:  0    1    2    3    4    5    6    7
      +----+----+----+----+----+----+----+----+
      | s8 | s9 |s10 |    |    |    | s6 | s7 |
      +----+----+----+----+----+----+----+----+
                       ^              ^
                      tail (11 & 7 = 3)  head (6 & 7 = 6)

(3) 가득 참: head=3, tail=11 (tail - head = 8 = N)

      +----+----+----+----+----+----+----+----+
      | s8 | s9 |s10 | s3 | s4 | s5 | s6 | s7 |
      +----+----+----+----+----+----+----+----+
                       ^
                  head, tail 모두 slot 3 (3 & 7, 11 & 7)
```

(3)에서 head와 tail은 같은 슬롯을 가리킨다. 그래도 시퀀스 차이가 8이라서 가득 찬 상태임을 알 수 있다. 차이가 0이면 비어 있는 상태다. 슬롯을 낭비하지 않고 두 경우를 구분한다.

## 3. 2의 거듭제곱 마스킹

시퀀스를 슬롯 번호로 바꾸는 식은 `seq mod N`이다. 그런데 나머지 연산은 CPU에서 비싼 편이다. N이 2의 거듭제곱이면 비트 AND 한 번으로 같은 결과를 얻는다.

```text
N = 8 이므로 mask = N - 1 = 7 = 0b0111

seq =  5 = 0b0101   0101 & 0111 = 0101 = slot 5
seq =  8 = 0b1000   1000 & 0111 = 0000 = slot 0   <- 한 바퀴 돌아 처음으로
seq = 11 = 0b1011   1011 & 0111 = 0011 = slot 3
seq = 13 = 0b1101   1101 & 0111 = 0101 = slot 5   <- seq 5와 같은 칸 재사용
```

N이 8이면 마스크 `0b0111`은 아래 3비트만 남긴다. 아래 3비트가 0~7이므로 곧 슬롯 번호다. 위쪽 비트는 "몇 바퀴째인가"를 나타낼 뿐 버려도 된다.

이 마스킹에는 속도보다 더 중요한 이유가 하나 있다. 바로 카운터 오버플로다.

### 오버플로에서도 슬롯이 이어지는가

실제로는 head와 tail을 64비트 정수로 둔다. 64비트가 한 바퀴 도는 데는 수백 년이 걸려서 현실에서 문제가 되기 어렵지만, 개념을 보려고 8비트 카운터로 줄여서 생각해 보자. 8비트는 0~255이고, 255 다음은 0으로 되돌아간다.

| seq(8비트) | N=8일 때 `seq & 7` | N=6일 때 `seq % 6` |
|---|---|---|
| 254 | 6 | 2 |
| 255 | 7 | 3 |
| 0 (오버플로) | 0 | 0 |

- N=8이면 7 다음에 0으로, 슬롯이 끊김 없이 이어진다. 256이 8의 배수이기 때문이다.
- N=6이면 3 다음에 0으로 간다. 슬롯 4, 5를 건너뛴다. 256이 6의 배수가 아니기 때문이다.

건너뛴 슬롯에 있던 데이터는 읽히지 않고, 같은 칸이 엉뚱한 순서로 겹쳐 쓰이면 데이터가 깨진다. 64비트에서도 원리는 같다. 2의 64제곱이 N의 배수일 때만 오버플로 지점에서 슬롯 번호가 이어지고, 이는 N이 2의 거듭제곱일 때만 성립한다.

정리하면 N을 2의 거듭제곱으로 잡는 이유는 (1) 나눗셈을 AND로 바꿔 싸게 하려는 것, (2) 오버플로에서도 슬롯 번호가 이어지게 하려는 것이다. 두 번째가 더 본질적이다.

## 4. 락 없는 SPSC: 쓰는 주체가 하나뿐이다

이제 스레드 둘이 이 버퍼를 함께 쓸 때를 보자. 락이 필요할까?

핵심은 누가 무엇을 쓰는지다.

- `tail`은 생산자만 쓴다.
- `head`는 소비자만 쓴다.

같은 변수를 두 스레드가 동시에 바꾸는 일이 없다. 그래서 값을 읽고 바꾸는 사이에 끼어들 틈이 없고, [CAS](/posts/cs/architecture/cas-lock-free-aba)로 충돌을 감지할 필요가 없다. CAS가 풀던 문제 자체가 여기에는 없다.

그래도 한 가지가 남는다. 상대가 쓴 값이 **언제, 어떤 순서로 보이는가**다. 이것이 가시성 순서 문제다. 슬롯에 데이터를 쓴 다음 tail을 올렸는데, 소비자가 새 tail은 보고 데이터는 못 보면 쓰이지 않은 쓰레기를 읽는다. 컴파일러와 CPU는 성능을 위해 메모리 접근 순서를 바꿀 수 있기 때문에 이런 일이 실제로 가능하다. 자세한 내용은 [메모리 모델과 배리어](/posts/cs/architecture/memory-model-barriers) 글에서 다뤘다.

여기서는 필요한 만큼만 쓴다. `release` 저장은 "그 앞의 쓰기가 이 저장보다 먼저 보이게 한다"는 뜻이고, `acquire` 읽기는 "이 읽기가 값을 봤다면 그 앞에서 release한 쓰기도 보인다"는 뜻이다.

```text
// SPSC, N은 2의 거듭제곱, head/tail은 계속 증가하는 uint64
push(x):                              // 생산자 스레드만 호출
  t = tail.load(relaxed)
  if t - head.load(acquire) == N: return FULL
  buf[t & (N-1)] = x                  // (1) 데이터 쓰기
  tail.store(t + 1, release)          // (2) 공개: (1)이 먼저 보이도록

pop():                                // 소비자 스레드만 호출
  h = head.load(relaxed)
  if tail.load(acquire) == h: return EMPTY   // (3) 새 tail을 봤다면
  x = buf[h & (N-1)]                  // (4) (1)의 데이터도 반드시 보임
  head.store(h + 1, release)          // 슬롯을 다시 써도 된다는 신호
  return x
```

push에서 자기 `tail`은 `relaxed`로 읽어도 된다. 쓰는 주체가 자신뿐이라 최신 값이 항상 자기 것이기 때문이다. 상대 쪽 `head`를 읽을 때만 `acquire`가 필요하다.

(2)의 release와 (3)의 acquire가 짝을 이룬다.

```text
 생산자                                 소비자
   |                                      |
 (1) buf[t & mask] = x                    |
   |                                      |
 (2) tail.store(t+1, release) ---------> (3) tail.load(acquire) == t+1
   |                                      |
   |                                    (4) x = buf[h & mask]   <- (1)이 보장됨
```

반대 방향도 같다. 소비자가 `head`를 release로 올리면, 생산자는 acquire로 읽은 뒤에야 그 슬롯을 덮어쓴다. 소비자가 아직 읽는 중인 슬롯을 생산자가 덮어쓰는 일이 없다.

이 배리어가 빠지면 평소에는 멀쩡하다가 부하가 높을 때만 가끔 쓰레기 값이 읽힌다. 재현하기 어려운 버그다.

## 5. 가득 찼을 때: 대기, 버림, 덮어쓰기

링 버퍼는 용량이 고정이라 `tail - head == N`이 되면 push를 어떻게 할지 정해야 한다. 선택지는 세 가지다.

| 정책 | 지키는 것 | 잃는 것 | 어울리는 곳 |
|---|---|---|---|
| 대기(backpressure) | 데이터 | 생산자 지연이 소비자 속도에 묶임 | 유실이 안 되는 감사 로그 |
| 버림(drop) | 생산자 지연 | 새 데이터 | 일부가 빠져도 되는 일반 로그 |
| 덮어쓰기(overwrite) | 최신 데이터 | 가장 오래된 데이터 | 최근 N개만 중요한 커널 로그, 비행 기록기 |

덮어쓰기는 소비자가 느릴 때 오래된 데이터가 조용히 사라진다. 손실 횟수를 세는 카운터가 없으면 데이터가 빠진 줄도 모른다.

## 6. 사례: Log4j 2 비동기 로거와 LMAX Disruptor

링 버퍼를 실무에서 가장 쉽게 만나는 곳은 Apache Log4j 2의 비동기 로거다. 공식 문서가 설명하는 동작은 다음과 같다.

- 비동기 로거는 LMAX Disruptor를 쓴다. Disruptor는 스레드 간 통신용 락 프리(lock-free) 라이브러리다.
- 이벤트는 사전 할당된 링 버퍼에 들어간다. 기본 크기는 256 x 1024 슬롯이고, 한 번 만든 뒤에는 크기가 바뀌지 않는다.
- 애플리케이션이 지속적으로 appender(디스크나 네트워크로 내보내는 쪽)보다 빠르게 로그를 남기면 버퍼가 가득 찬다. 기본 정책(`Default`)에서는 호출한 스레드가 자리가 날 때까지 블로킹된다. 문서의 표현대로 가장 느린 appender의 속도로 로깅하게 된다.

Disruptor 사용자 가이드도 같은 설계를 확인해 준다. 링 버퍼 크기는 2의 거듭제곱이어야 한다고 예제 주석에 적혀 있다. 이벤트 객체는 `EventFactory`로 미리 만들어 두고 생산자는 새로 할당하는 대신 그 객체를 채운다. 가이드는 그 목적을 가비지 컬렉션으로 인한 멈춤을 줄이는 것이라고 설명한다. 각 소비자와 Disruptor가 가진 `Sequence`는 false sharing을 피하도록 설계되었다고 한다.

여기서 운영상의 교훈이 나온다. 링 버퍼는 무한한 완충이 아니다. 한계가 있는 완충이고, 가득 찼을 때의 정책이 함께 따라온다. 그래서 트래픽이 몰리는 시간에 API 응답 지연(p99)이 튀고, 스레드 덤프에 로거의 enqueue 대기가 보인다면 원인은 이런 상황이다.

- 소비자(appender) 처리량이 생산 속도보다 낮다. 디스크 fsync나 원격 전송 지연이 흔한 원인이다.
- 버퍼가 가득 차서 요청 스레드가 막혔다. 비동기 로깅이 사실상 동기 로깅으로 바뀐 셈이다.

대응은 네 방향이다. 버퍼를 늘리고, appender를 개선하고, 로그량을 줄이고, 정책을 `Discard`로 바꾼다. `Discard`는 임계 레벨 이하(기본 `INFO`)의 이벤트만 버리며, 버퍼 크기는 `log4j2.asyncLoggerRingBufferSize`로 조정한다. 문서는 버스트를 흡수할 만큼 충분히 크게 잡으라고 안내한다. 감사 로그처럼 잃으면 안 되는 로그는 버리는 쪽에 두지 말고 따로 분리한다.

## 7. 성능 세부: false sharing과 인덱스 캐싱

락이 없어도 두 코어가 같은 캐시 라인을 번갈아 쓰면 느려진다. `head`와 `tail`이 같은 캐시 라인(보통 64바이트)에 붙어 있으면, 생산자가 `tail`을 쓸 때마다 소비자 코어의 라인이 무효화되고 반대도 마찬가지다. [캐시 일관성 글](/posts/cs/architecture/cache-coherence-mesi-false-sharing)에서 본 false sharing이 링 버퍼에서도 그대로 생긴다.

해법은 두 가지다.

- `head`와 `tail`을 서로 다른 캐시 라인에 두도록 패딩(padding)을 넣는다.
- 상대 쪽 인덱스를 매번 읽지 않고 로컬에 캐시해 둔다. 생산자는 마지막으로 본 `head` 값을 들고 있다가, 가득 찬 것처럼 보일 때만 진짜 `head`를 다시 읽는다.

두 번째 방법은 상대 인덱스를 읽는 횟수를 크게 줄인다. 상대가 쓰는 변수를 읽는 일 자체가 그 캐시 라인을 내 코어로 끌어오는 비용이기 때문이다.

생산자나 소비자가 여럿이면 이 단순함이 깨진다. 같은 `tail`을 여러 생산자가 쓰므로 CAS로 슬롯을 선점하거나 슬롯마다 완료 플래그를 둬야 한다. Disruptor 가이드의 벤치마크도 이 차이를 보여 준다. 단일 생산자가 약 77~89M ops/sec, 복수 생산자가 약 26~30M ops/sec였다. 가이드 환경(i7 Sandy Bridge MacBook Air) 기준의 수치라서 절대값보다 비율을 참고하면 된다. 이처럼 쓰는 주체를 줄이는 것이 곧 성능이다.

## 8. 링 버퍼의 다른 모습: io_uring

이 구조는 커널과 사용자 공간 사이에서도 쓰인다. Linux의 io_uring은 이름 자체가 링 버퍼에서 왔다. 제출 큐(SQ)와 완료 큐(CQ)가 커널과 사용자 공간이 함께 매핑한 공유 메모리의 링 버퍼이고, 요청마다 시스템 콜을 부르지 않고도 둘이 통신한다.

역할 분담은 SPSC와 같은 모양이다.

- 제출 큐: 사용자 공간이 tail에 요청을 넣고, 커널이 head에서 꺼낸다.
- 완료 큐: 커널이 tail에 결과를 넣고, 사용자 공간이 head에서 꺼낸다.

man 페이지는 head나 tail 인덱스를 링 마스크로 마스킹해 항목을 찾는다고 설명하고, 양쪽이 공유 값을 갱신하므로 메모리 배리어로 일관성을 맞춰야 한다고 적고 있다. 3절의 마스킹과 4절의 release/acquire 짝이 그대로 쓰이는 셈이다. io_uring 전체 구조와 epoll과의 차이는 [I/O 멀티플렉싱과 io_uring](/posts/cs/os/io-multiplexing-epoll-io-uring) 글에서 다룬다.

네트워크 카드의 수신 큐(RX 링)도 같은 발상이다. NIC가 패킷을 링의 슬롯에 채우고 커널이 비워 간다. 이어지는 인터럽트와 DMA 이야기는 OS 시리즈의 [인터럽트, DMA, NAPI](/posts/cs/os/interrupt-dma-napi) 글에서 본다.

## 결론

- 링 버퍼는 미리 할당한 고정 배열을 원형으로 재사용한다. 할당·GC 비용이 없고 캐시 지역성이 좋다.
- head와 tail을 줄지 않는 시퀀스 번호로 두면 비어 있음(차이 0)과 가득 참(차이 N)을 슬롯 낭비 없이 구분한다.
- 크기를 2의 거듭제곱으로 잡으면 `seq & (N-1)`로 슬롯을 싸게 구하고, 카운터가 오버플로해도 슬롯 번호가 끊기지 않는다.
- SPSC는 tail은 생산자만, head는 소비자만 쓰므로 CAS가 필요 없다. 남은 문제는 가시성 순서뿐이고 release/acquire 짝이 해결한다.
- 용량이 고정이라 가득 찼을 때의 정책(대기, 버림, 덮어쓰기)을 반드시 정해야 한다. 이 선택이 운영에서 지연이나 유실로 드러난다.
