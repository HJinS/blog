## 개요

[앞 글](/posts/cs/distributed/distributed-lock-fencing-token)에서는 락을 쥔 노드가 멈춰 있다가 깨어나도 오래된 쓰기를 막는 방법을 봤다. 이번 글은 같은 뿌리에서 나온 다른 문제를 다룬다. 응답이 사라지면 클라이언트는 요청을 다시 보내야 하는데, 다시 보내면 같은 일이 두 번 일어날 수 있다.

이 글이 답하는 질문은 두 가지다.

- 네트워크 위에서 "정확히 한 번" 전달이 왜 불가능하고, 실무에서는 무엇으로 대신하는가?
- 멱등성 키(idempotency key)를 서버에 어떻게 구현해야 중복 결제도 유실도 생기지 않는가?

여기서 멱등(idempotent)하다는 것은 같은 요청을 한 번 보내든 여러 번 보내든 서버 상태에 남는 효과가 같다는 뜻이다. 이 글의 예시는 하나로 고정한다. 클라이언트가 결제 서버에 10,000원 결제를 요청했는데 타임아웃이 난 상황이다.

---

## 1. 타임아웃은 "실패"가 아니라 "모름"이다

결제 요청을 보내고 3초 안에 응답이 없다고 하자. 클라이언트가 아는 것은 "응답을 못 받았다"뿐이다. 그 원인은 세 가지 중 하나다.

```
케이스 A  요청이 서버에 도착하지 못함
Client --POST--> X          서버는 아무것도 못 봄. 결제 0회.

케이스 B  서버가 처리했지만 응답이 유실됨
Client --POST--> Server     결제 실행, DB에 커밋
Client <--200--- X          응답이 도중에 사라짐. 결제 1회.

케이스 C  서버가 느려서 아직 처리 중
Client --POST--> Server     아직 결제 진행 중. 곧 1회가 된다.
```

클라이언트 입장에서 A, B, C는 모두 "3초 동안 아무것도 안 왔다"로 똑같이 보인다. 구분할 방법이 없다.

여기서 선택지는 둘뿐이다.

- 재전송하지 않는다. A라면 결제가 영영 안 되고(유실), B라면 문제가 없다.
- 재전송한다. A라면 정상이지만, B라면 10,000원이 두 번 빠진다(중복).

이 선택은 구현을 잘하든 못하든 피할 수 없다. 송신자가 "수신자가 처리했는가"를 확신할 수 없다는 사실에서 나오기 때문이다.

## 2. 전달 보장 세 가지와 "정확히 한 번"의 실체

위의 선택을 이름 붙이면 전달 보장 의미론(delivery semantics) 세 가지가 된다.

| 의미론 | 방식 | 생기는 문제 |
|--------|------|-------------|
| at-most-once | 재전송하지 않는다 | 유실 가능 |
| at-least-once | 응답이 올 때까지 재전송한다 | 중복 가능 |
| exactly-once | 유실도 중복도 없다 | 전송 계층만으로는 얻을 수 없다 |

결제나 주문처럼 유실이 곤란한 일은 at-least-once를 고른다. 그러면 중복이 남는다. 그래서 실무의 "정확히 한 번"은 전달을 정확히 한 번 하는 것이 아니다. **전달은 여러 번 해도 효과가 한 번만 반영되게** 하는 것이다.

```
effectively-once = at-least-once 전달 + 멱등한 처리
```

이를 효과 기준 한 번(effectively-once)이라고도 부른다. 메시지가 서버에 두 번 도착하는 것은 막지 않는다. 두 번째 도착을 "이미 처리한 것"으로 알아보고 상태를 바꾸지 않는 것이다.

이 글의 나머지는 "알아보는 방법"에 관한 이야기다. 가장 쉬운 경우부터 보자.

## 3. 자연히 멱등한 연산과 그렇지 않은 연산

어떤 연산은 별도 장치 없이도 재시도해도 안전하다.

| 연산 | 두 번 실행하면 | 멱등한가 |
|------|----------------|----------|
| `UPDATE order SET status = 'PAID'` | 두 번째도 PAID | 멱등 |
| `PUT /users/1` (전체 덮어쓰기) | 같은 값으로 덮어씀 | 멱등 |
| upsert (있으면 갱신, 없으면 삽입) | 한 행만 남음 | 멱등 |
| `UPDATE account SET balance = balance - 10000` | 20,000원이 빠짐 | 멱등하지 않음 |
| `INSERT INTO orders ...` (키 없는 생성) | 주문이 두 개 | 멱등하지 않음 |
| `POST /payments` | 결제가 두 건 | 멱등하지 않음 |

차이는 연산이 "상태를 X로 설정"인지, "현재 상태에서 변화를 더함"인지에 있다. 설정은 몇 번을 해도 X가 되지만, 변화는 쌓인다.

HTTP는 이 구분을 메서드에 반영해 둔다. RFC 9110은 같은 요청을 여러 번 보냈을 때 서버에 미치는 의도된 효과가 한 번 보냈을 때와 같으면 멱등이라 정의하고, `PUT`, `DELETE`와 안전한 메서드(`GET` 등)를 멱등으로 분류한다. `POST`는 여기 없다. 그래서 같은 문서가 "클라이언트는 비멱등 메서드를 자동 재시도하지 말아야 한다(SHOULD NOT)"고 적어 두었다.

멱등의 기준에 관해 자주 나오는 오해가 하나 있다. 멱등은 응답이 같다는 뜻이 아니라 **서버 상태에 남는 효과가 같다**는 뜻이다. `DELETE /orders/7`을 두 번 보내면 첫 번째는 204, 두 번째는 404가 올 수 있다. 응답은 다르지만 두 경우 모두 주문 7이 없는 상태로 끝나므로 멱등이다. RFC 9110도 재시도해도 "응답은 다를 수 있다"고 명시한다. 다만 클라이언트가 404를 장애로 오해하지 않도록, 서버가 이미 삭제된 경우에도 204를 주는 설계를 택하기도 한다.

문제는 결제처럼 본질적으로 "변화를 더하는" 연산이다. 이 연산을 "상태 설정"으로 바꿀 수 없으면 다른 장치가 필요하다.

## 4. 핵심 아이디어: 요청에 이름표를 붙인다

비멱등 연산을 안전하게 재시도하려면 서버가 "이 요청은 아까 그 요청이다"를 알아볼 수 있어야 한다. 그래서 요청마다 이름표를 붙인다.

> 클라이언트가 작업 하나당 고유한 키를 만들어 요청에 싣고, 재시도할 때는 같은 키를 다시 보낸다. 서버는 키를 저장해 두고 본 적 있는 키면 부작용을 다시 실행하지 않는다.

이 키가 멱등성 키(idempotency key)다. 앞의 케이스 B를 키와 함께 다시 따라가 보자.

```
Client                       Server                       DB
  |                            |                           |
  |-- POST /payments --------->|                           |
  |   Idempotency-Key: K1      |-- K1 기록 + 결제 -------->|
  |                            |<-- COMMIT 성공 -----------|
  |<--- 200 (유실) -- X        |                           |
  |                            |                           |
  | 타임아웃. 처리됐는지 모름  |                           |
  | 잠시 대기 후 재시도        |                           |
  |                            |                           |
  |-- POST /payments --------->|                           |
  |   Idempotency-Key: K1      |-- K1 조회 --------------->|
  |                            |<-- 완료, 응답 200 --------|
  |<--- 200 (저장된 응답) -----|   결제는 다시 안 함       |
```

결제는 한 번만 일어났고, 클라이언트는 두 번째 요청으로 원래의 응답을 받는다. 케이스 A(첫 요청이 도착하지 못함)라면 서버가 K1을 처음 보므로 평소처럼 처리한다. 클라이언트는 어느 케이스인지 몰라도 같은 키로 재전송하면 된다.

이 방식을 API 수준에서 제공하는 대표 사례가 Stripe다. 클라이언트가 `Idempotency-Key` 헤더에 고유 값을 싣고, 서버는 첫 요청의 결과를 저장해 두었다가 같은 키의 재시도에 돌려준다. Stripe 문서의 요점은 다음과 같다.

| 항목 | Stripe API v1 문서의 설명 |
|------|---------------------------|
| 키 생성 | 클라이언트가 만든다. V4 UUID나 충분히 무작위인 문자열을 권장한다 |
| 길이 | 최대 255자. 이메일 같은 민감 정보를 키로 쓰지 말라고 한다 |
| 적용 대상 | 모든 `POST`. `GET`과 `DELETE`는 원래 멱등이므로 보내도 효과가 없다 |
| 저장 내용 | 엔드포인트 실행이 시작된 뒤 첫 요청의 상태 코드와 본문을 저장한다. 500 오류도 포함한다 |
| 보존 기간 | 24시간 이상 지난 키는 자동으로 제거될 수 있고, 제거된 뒤 같은 키가 오면 새 요청으로 처리한다 |
| 내용 불일치 | 같은 키에 파라미터가 원래 요청과 다르면 오류를 낸다 |
| 저장하지 않는 경우 | 파라미터 검증 실패, 동시에 실행 중인 다른 요청과의 충돌은 실행이 시작되지 않은 것이므로 저장하지 않고 재시도할 수 있다 |

IETF에도 이 헤더를 표준화하려는 `Idempotency-Key` HTTP 헤더 필드 초안(Internet-Draft)이 있다. 다만 이 글을 쓰는 시점에는 아직 표준(RFC)이 아니라 진행 중인 초안이므로, 세부 규칙은 바뀔 수 있다. 초안은 같은 키에 내용이 다르면 422, 원래 요청이 아직 처리 중이면 409를 권고한다. 아래 구현 설명에서 이 두 상황을 다룬다.

## 5. 서버 구현: 키 기록과 부작용은 한 덩어리여야 한다

키를 저장소에 넣고 결제를 실행하는 것은 간단해 보이지만, 순서를 잘못 잡으면 크래시 한 번에 결제가 두 번 되거나 사라진다.

### 5-1. 따로 커밋하면 크래시가 틈을 파고든다

서버가 "결제 실행"과 "키 기록"을 두 번에 나눠 커밋한다고 하자. 두 단계 사이에서 서버가 죽는 경우를 따져 본다.

| 순서 | 크래시 지점 | 재시도가 오면 | 결과 |
|------|-------------|---------------|------|
| 결제 실행 -> 키 기록 | 결제 후, 키 기록 전 | 키가 없으니 새 요청으로 보임 | 이중 결제 |
| 키 기록 -> 결제 실행 | 키 기록 후, 결제 전 | 키가 있으니 "이미 처리됨"으로 응답 | 결제 안 됐는데 성공 응답 (유실) |

어느 쪽 순서든 틈이 있다. 해법은 틈을 없애는 것이다. 키 기록과 결제를 **같은 트랜잭션**에 넣는다. 트랜잭션은 모두 반영되거나 모두 취소되므로 "키만 있고 결제는 없음"이나 "결제만 있고 키는 없음"이 생기지 않는다. 크래시 후 DB가 이를 어떻게 정리하는지는 [WAL과 크래시 복구](/posts/cs/database/wal-aries-crash-recovery) 글에서 다뤘다.

### 5-2. 한 트랜잭션 안의 처리

결제 기록이 같은 DB에 있다고 가정한 의사 코드다.

```sql
BEGIN;

-- 유니크 제약이 걸린 key 칼럼에 먼저 자리를 잡는다
INSERT INTO idempotency(key, req_hash, status)
VALUES (:k, :h, 'IN_PROGRESS')
ON CONFLICT (key) DO NOTHING;

-- 삽입된 행이 0개면 이미 본 키다.
--   저장된 행의 req_hash가 :h와 다르면 -> 거부 (422)
--   status가 COMPLETED이면            -> 저장된 응답을 그대로 반환
-- 삽입된 행이 1개면 처음 보는 키다. 아래를 계속 실행한다.

INSERT INTO payments(order_id, amount) VALUES (:order, 10000);   -- 부작용

UPDATE idempotency
   SET status = 'COMPLETED', response = :resp
 WHERE key = :k;

COMMIT;
```

여기에는 세 가지 방어가 들어 있다.

**1. 유니크 제약으로 동시 중복을 막는다.** 같은 키의 요청 두 개가 동시에 들어와도 유니크 제약 때문에 한쪽만 삽입에 성공한다. 이때 "조회해서 없으면 삽입"을 두 문장으로 나눠 쓰면 안 된다. 두 요청이 모두 "없음"을 보고 둘 다 삽입으로 가는 경쟁 상태(race condition)가 생긴다. [MVCC와 스냅샷 격리 글](/posts/cs/database/mvcc-snapshot-isolation-write-skew)에서 쓰기 스큐(write skew)의 예로 든 "아이디 선점"과 같은 구조다. 둘 다 "없음"을 확인한 뒤 각자 삽입한다. 중복 판단은 하나의 원자적 문장(유니크 제약 위의 삽입)으로 해야 한다.

**2. 지문(fingerprint)으로 내용 불일치를 잡는다.** 같은 키로 금액만 다른 요청이 오면 어느 쪽이 진짜인지 알 수 없다. 그래서 키와 함께 요청 본문의 해시(`req_hash`)를 저장해 두고, 같은 키에 해시가 다르면 거부한다. 클라이언트가 키를 재사용하는 버그를 조용히 넘기지 않고 눈에 보이게 만든다.

**3. 진행 중인 중복에는 기다리거나 충돌로 응답한다.** 첫 요청이 아직 커밋 전일 때 같은 키의 두 번째 요청이 오면, DB에 따라 첫 트랜잭션이 끝날 때까지 기다리거나 충돌 오류를 받는다. 어느 경우든 서버는 결제를 두 번 실행하지 않아야 하고, 클라이언트에는 잠시 후 다시 시도하라는 의미로 409를 돌려주는 설계가 흔하다.

### 5-3. 결제가 다른 시스템에 있다면

위 코드는 결제가 같은 DB 안의 한 행이라서 가능했다. 실제로는 결제가 외부 결제사(PG) API 호출인 경우가 많다. 외부 호출은 우리 DB의 트랜잭션에 넣을 수 없다. 이때는 두 가지로 보완한다.

- **외부 시스템에 같은 키를 전달한다.** 결제사가 멱등성 키를 지원하면 우리 서버도 결제사에 키를 넘긴다. 서버가 호출 직후 죽어 재시도하더라도 결제사가 중복을 걸러 준다. 멱등성이 우리 서버 한 곳이 아니라 호출 사슬 전체에 걸쳐 필요하다는 뜻이다.
- **아웃박스 패턴을 쓴다.** "결제를 요청해야 한다"는 사실을 우리 DB에 같은 트랜잭션으로 기록해 두고, 별도 프로세스가 그 기록을 읽어 외부로 보낸다. 외부 전달은 at-least-once가 되므로 받는 쪽의 멱등성이 다시 필요하다.

여러 시스템을 하나의 원자적 단위로 묶는 문제 자체는 [2단계 커밋](/posts/cs/distributed/two-phase-commit) 글에서 다룬다. 멱등성은 그 비용과 블로킹 없이 "여러 번 실행돼도 괜찮게" 만드는 대안으로 읽을 수 있다.

## 6. 재시도하는 쪽의 규칙

서버가 완벽해도 클라이언트가 재시도를 잘못 하면 효과가 없거나 장애를 키운다. 클라이언트 쪽 규칙은 두 가지다.

### 6-1. 키는 작업 단위로 만든다

가장 흔한 실수는 키를 재시도할 때마다 새로 만드는 것이다.

```
잘못된 예 (시도 단위)         올바른 예 (작업 단위)
try 1: key = uuid()  -> K1    작업 시작: key = uuid()  -> K1
try 2: key = uuid()  -> K2    try 1: K1
try 3: key = uuid()  -> K3    try 2: K1   <- 같은 키
                              try 3: K1
서버 눈에는 요청 3개 = 결제 3번   서버 눈에는 같은 요청의 반복
```

"결제 버튼을 누른 한 번의 의도"에 키 하나가 대응해야 한다. 키를 만드는 시점은 첫 요청을 보내기 전이고, 그 키는 재시도 동안 그대로 유지해야 한다.

### 6-2. 지수 백오프에 지터를 더한다

재시도 간격이 문제다. 서버 장애로 클라이언트 1,000개가 같은 시각에 실패했고, 모두 "1초 후 재시도, 실패하면 간격 2배"로 규칙이 같다고 하자.

```
간격만 2배 (지터 없음). 1,000개가 t=0에 함께 실패

t=0s      t=1s        t=3s        t=7s
실패      1000개      1000개      1000개   <- 매번 같은 순간에 몰린다

간격 2배 + 지터. 첫 재시도를 0 ~ 2초 사이 임의 시각에 보낸다

t=0s      t=0 ~ 2s 사이에 흩어짐
실패      초당 약 500개씩 두 구간으로 분산  <- 한 순간의 파도가 사라진다
```

지수 백오프(exponential backoff)는 실패할 때마다 대기 시간을 2배씩 늘리는 방식이다. 서버에 회복할 시간을 준다. 하지만 간격 규칙이 같으면 실패 시각이 같았던 클라이언트들은 계속 같은 시각에 다시 온다. 이렇게 한꺼번에 몰리는 현상을 thundering herd라 한다. 대기 시간에 무작위 값(지터, jitter)을 섞으면 재시도 시각이 흩어져 서버가 숨 돌릴 틈이 생긴다.

Stripe의 멱등성 글도 같은 맥락이다. 재시도는 간격을 늘리며(대기 시간이 2의 n제곱에 비례, n은 실패 횟수) 지터를 더하라고 권한다. 위 그림의 숫자는 이해를 돕는 가상의 예이며, 실제 분포와 대기 범위는 지터 구현에 따라 다르다.

## 7. 방식 비교와 흔한 실패 패턴

### 7-1. 어떤 방식을 고를까

| 방식 | 얻는 것 | 잃는 것 |
|------|---------|---------|
| at-most-once (재시도 없음) | 중복이 없고 단순하다 | 유실 가능. 결제와 주문에는 부적합 |
| at-least-once + 자연 멱등 연산 | 저장소 없이 안전하다 | 모든 연산을 "상태 설정"으로 모델링하기 어렵다 |
| at-least-once + 멱등성 키 저장 | 비멱등 연산도 안전하게 재시도 | 키 저장소(보존 기간, TTL), 쓰기 경로 추가, 동시 중복과 내용 불일치 처리 필요 |
| 비즈니스 키 유니크 제약 | 키 관리 없이 DB가 중복 차단 | 중복 시 원래 응답을 재현하기 어렵고, 유니크하게 쓸 도메인 키가 필요 |

비즈니스 키 유니크 제약은 예컨대 "주문 번호"에 유니크 제약을 거는 방식이다. 같은 주문이 두 번 들어오면 DB가 막아 주므로 단순하다. 대신 두 번째 요청은 오류로 끝나서 클라이언트가 원래 응답을 받지 못한다. 응답까지 그대로 돌려주려면 멱등성 키와 응답 저장이 필요하다.

### 7-2. 직접 구현할 때 자주 나는 문제

이 목록은 원리에서 도출한 일반적 위험이며 특정 사고를 가리키지 않는다. 배포 직후 "중복 결제 문의가 늘었다"면 아래 순서로 의심해 볼 만하다.

| 증상 | 원인 | 확인 방법 |
|------|------|-----------|
| 재시도마다 결제가 새로 생긴다 | 키를 시도마다 새로 생성 | 로그에서 재시도 요청의 키가 같은지 비교 |
| 가끔 동시에 두 건이 통과한다 | "조회 후 삽입"이 원자적이지 않음 | 중복 확인이 유니크 제약 위의 한 문장인지 확인 |
| 크래시 뒤 이중 처리 또는 유실 | 키 기록과 부작용이 별도 커밋 | 둘이 한 트랜잭션인지, 아니면 외부 키 전달이 있는지 확인 |
| 늦은 재시도가 새 요청으로 처리된다 | 키 TTL이 클라이언트 재시도 허용 기간보다 짧음 | 키 보존 기간 > 재시도 최대 기간인지 확인 |
| 서버 로그엔 한 번인데 결제는 두 번 | 게이트웨이나 프록시가 자체 재시도하는데 키가 전달되지 않음 | 중간 계층의 재시도 설정과 헤더 전달 확인 |

마지막 줄이 놓치기 쉽다. 앱이 키를 정확히 지켜도, 중간의 로드밸런서나 게이트웨이가 타임아웃 시 같은 요청을 자기 판단으로 다시 보내면 서버 입장에서는 같은 키가 두 번 오는 것과 같다. 키가 헤더로 그대로 전달되기만 하면 정상적으로 걸러지지만, 키를 붙이지 않고 재시도하는 계층이 있으면 중복이 새어 들어온다. RFC 9110도 프록시가 비멱등 요청을 자동 재시도해서는 안 된다고 규정한다.

### 7-3. 메시지 큐에서의 같은 문제

메시지를 소비하는 쪽도 똑같다. 소비자가 메시지를 처리하고 offset을 커밋하기 전에 죽으면 같은 메시지를 다시 받는다. 이것이 at-least-once이고, 처리 결과를 DB에 쓰는 쪽이 멱등해야 한다. 메시지 ID나 offset 같은 시퀀스 번호를 키로 삼아 이미 처리했는지 확인하는 것이 방법이다.

Kafka는 이 원리를 브로커 안의 트랜잭션과 멱등 프로듀서로 제공한다. 설정과 성능 비용은 [Kafka 파티셔닝 전략과 순서 보장](/posts/dev/messaging/kafka-partitioning-strategy) 글의 "Exactly-Once vs At-Least-Once" 절에서 다루므로 여기서는 반복하지 않는다. 핵심만 말하면, Kafka의 exactly-once도 전달을 한 번만 하는 마법이 아니다. 소비 위치(offset) 커밋과 결과를 Kafka 토픽에 쓰는 일을 한 트랜잭션으로 묶어 효과를 한 번만 반영하는 것이다. 결과를 외부 DB나 결제 API에 쓴다면 그 쓰기는 Kafka 트랜잭션 밖에 있으므로, 이 글의 멱등 처리가 여전히 필요하다.

## 결론

- 타임아웃은 "요청 유실"과 "응답 유실"을 구분하지 못한다. 그래서 재전송하면 중복, 안 하면 유실이다.
- 실무의 "정확히 한 번"은 전달을 한 번 하는 것이 아니라, at-least-once로 전달하고 처리를 멱등하게 만들어 효과를 한 번만 반영하는 것이다.
- 멱등하지 않은 연산(결제, 주문)에는 클라이언트가 작업 단위로 만든 멱등성 키를 붙이고, 서버는 본 키의 결과를 저장해 재시도에 돌려준다.
- 서버는 키 기록과 부작용을 같은 원자적 단위에 넣고, 유니크 제약으로 동시 중복을, 요청 지문으로 내용 불일치를 처리한다. 외부 시스템이 끼면 그쪽에도 키를 전달한다.
- 클라이언트는 키를 재시도 동안 유지하고, 지수 백오프에 지터를 섞어 서버가 회복할 틈을 준다.
