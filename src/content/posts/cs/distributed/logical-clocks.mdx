## 개요

분산 시스템 시리즈의 첫 글이다. 서버가 여러 대이면 "무엇이 먼저 일어났는가"라는 단순한 질문부터 어려워진다. 이 글이 답하는 질문은 두 가지다.

- 이벤트 순서를 서버의 물리 시각으로 정하면 왜 틀리는가?
- 시각 없이 순서를 정하는 Lamport 시계와 벡터 시계는 무엇을 보장하고 무엇을 보장하지 못하는가?

여기서 물리 시계(physical clock)는 서버가 가진 실제 시각(벽시계, wall clock)이다. 논리 시계(logical clock)는 시각이 아니라 이벤트 사이의 인과 관계를 세는 카운터다. 복제에서 이 문제가 어떻게 이어지는지는 [다음 글](/posts/cs/distributed/replication-cap-pacelc/)에서 다룬다.

---

## 1. 왜 물리 시각으로 순서를 정하면 안 되는가

노드 두 대에 쓰기가 들어온다. 노드 A가 값을 쓰고 1초 뒤에 노드 B가 같은 키를 덮어썼다. 사람이 보면 B의 값이 최신이다. 그런데 B의 시계가 A보다 2초 느리다면 어떻게 될까?

```
실제 순서        A: 쓰기 x=1 (A 시계 10:00:05)
                 B: 쓰기 x=2 (B 시계 10:00:04)   <- 1초 뒤에 썼지만 시각은 더 작다

시각이 큰 쪽이 이긴다고 하면 x=1이 남고, 나중에 쓴 x=2는 조용히 사라진다.
```

모든 노드가 공유하는 전역 시계는 없다. 노드마다 시계가 어긋나 있고(skew), 시간이 흐르는 속도도 조금씩 다르다(drift). NTP(Network Time Protocol)로 보정해도 완전히 일치시킬 수는 없다. 게다가 보정 중에 시계가 갑자기 점프하거나 거꾸로 갈 수도 있다.

핵심 문제는 "시각이 더 크다"가 "나중에 일어났다"를 보장하지 않는다는 것이다.

### 실제로 터진 사례

2017년 새해 0시(UTC)에 윤초(leap second)가 삽입되면서 Cloudflare의 DNS 소프트웨어(RRDNS)가 장애를 일으켰다. 업스트림 리졸버의 응답 시간을 `time.Now()`의 뺄셈으로 쟀는데, 당시 Go의 이 함수는 단조 증가를 보장하지 않았다. 시계가 거꾸로 가자 응답 시간이 음수로 나왔고, 이 값이 평균에 섞여 가중치가 음수가 되었다. 그 값을 `rand.Int63n()`에 넘기자 panic이 났다. 피크에는 DNS 질의의 약 0.2%가 영향을 받았고 전체 HTTP 요청의 1% 미만이 오류를 겪었다. 수정이 배포되면서 영향은 06:45 UTC에 끝났다.

이 사건은 논리 시계의 사례가 아니다. 물리 시계에 기대어 "시간은 앞으로만 간다"고 가정한 코드가 깨진 사례다. 교훈은 둘로 나뉜다.

- **간격**(타임아웃, 지연 측정)은 단조 시계(monotonic clock)로 잰다. 리눅스의 `CLOCK_MONOTONIC`, Java의 `System.nanoTime`, Python의 `time.monotonic`이 여기에 해당한다. Go는 1.9부터 `time.Now()`가 단조 시계 값을 함께 담아, 두 시각의 뺄셈에 그 값을 쓴다(Go 1.9 릴리스 노트의 "transparent monotonic time support"). 단조 시계는 벽시계 조정이나 윤초의 영향을 받지 않는다.
- **순서**(누가 먼저인가)는 시각이 아니라 인과 관계로 다룬다. 이것이 논리 시계의 출발점이다.

## 2. 시각 대신 인과를 쓴다: happens-before

핵심 아이디어는 한 문장이다. 순서를 시각이 아니라 "한 이벤트가 다른 이벤트의 원인이 될 수 있었는가"로 정의한다.

Lamport의 1978년 논문이 이 관계를 happens-before(기호 `->`)로 정의했다. 규칙은 세 가지다.

1. 같은 프로세스에서 a가 b보다 먼저 일어나면 `a -> b`다.
2. 메시지를 보낸 이벤트는 그 메시지를 받은 이벤트보다 먼저다.
3. 이행성: `a -> b`이고 `b -> c`이면 `a -> c`다.

세 규칙 어느 것으로도 연결되지 않는 두 이벤트는 동시(concurrent)라고 하고 `a || b`로 쓴다. 동시라는 말은 "같은 시각"이 아니라 "서로 영향을 줄 수 없었다"는 뜻이다. 한쪽의 소식이 다른 쪽에 닿기 전에 각자 일어난 일이기 때문이다.

이 관계는 부분 순서(partial order)다. 모든 쌍에 순서가 있는 것이 아니라, 인과로 이어진 쌍만 순서가 있다.

## 3. 예시: 프로세스 3개의 이벤트

이후 두 시계를 같은 예시 하나로 설명한다. 프로세스 P1, P2, P3가 있고 이벤트는 a부터 i까지 아홉 개다. 위에서 아래로 갈수록 프로세스가 다르고, 왼쪽에서 오른쪽으로 갈수록 실제 시간이 흐른다.

- P1: a(로컬), b(m1 송신), i(m3 수신)
- P2: c(로컬), d(m1 수신), e(m2 송신)
- P3: f(로컬), g(m2 수신), h(m3 송신)

각 칸의 윗줄은 Lamport 값(`L`), 아랫줄은 벡터 시계 값이다. 계산 방법은 다음 두 절에서 설명한다.

```
time ->
P1  a L=1                         b L=2                                             i L=7
    [1,0,0]                       [2,0,0]                                           [3,3,3]

P2            c L=1                         d L=3     e L=4
              [0,1,0]                       [2,2,0]   [2,3,0]

P3                      f L=1                                   g L=5     h L=6
                        [0,0,1]                                 [2,3,2]   [2,3,3]

m1: b -> d     m2: e -> g     m3: h -> i
```

## 4. Lamport 시계: 인과를 숫자 증가로 보존한다

프로세스마다 카운터 `C` 하나를 둔다. 규칙은 세 줄이다.

- 로컬 이벤트: `C = C + 1`
- 송신: `C = C + 1`을 한 뒤 그 값을 메시지에 실어 보낸다.
- 수신: `C = max(C, 메시지의 C) + 1`

논문의 수신 규칙은 "자기 현재 값 이상이면서 메시지 값보다 크게" 시계를 옮기라는 것이다. `max + 1`은 이 조건을 만족하는 가장 흔한 구현이다.

위 그림에서 따라가 보자.

1. P1에서 a는 `L=1`, 이어서 m1을 보내는 b는 `L=2`다. 메시지에 2가 실린다.
2. P2는 로컬 이벤트 c가 `L=1`이다. m1을 받는 d는 `max(1, 2) + 1 = 3`이다. 이어 m2를 보내는 e는 `L=4`다.
3. P3는 f가 `L=1`이다. m2를 받는 g는 `max(1, 4) + 1 = 5`, m3를 보내는 h는 `L=6`이다.
4. P1이 m3를 받는 i는 `max(2, 6) + 1 = 7`이다.

이 규칙은 `a -> b`이면 `C(a) < C(b)`를 항상 보장한다. 메시지를 받으면 보낸 쪽의 값보다 반드시 커지기 때문이다. 이 성질이 Lamport 시계가 인과 순서를 보존한다는 말의 정체다.

### 전체 순서 만들기

Lamport 값은 서로 다른 프로세스에서 같을 수 있다. 위에서 a, c, f는 모두 `L=1`이다. 모든 이벤트에 하나뿐인 순서가 필요하면 `(C, 프로세스 ID)` 쌍으로 비교해 동률을 깬다. 논문은 프로세스 사이에 임의의 고정 순서를 하나 정해 두라고 하는데, ID 순서가 그 예다. 이렇게 하면 인과와 모순되지 않는 전체 순서(total order)가 생긴다. 모든 노드가 같은 순서로 요청을 처리해야 하는 상호 배제 같은 문제에서 이 전체 순서를 쓴다.

### 한계: 역은 성립하지 않는다

`C(a) < C(b)`라고 해서 `a -> b`는 아니다. 그림에서 f는 `L=1`, d는 `L=3`이라 `C(f) < C(d)`다. 하지만 f와 d를 잇는 메시지 경로는 없다. 둘은 동시다. 반대 방향 예도 있다. b(`L=2`)와 c(`L=1`)는 동시인데 숫자만 보면 c가 앞선 것처럼 보인다.

즉 Lamport 값만으로는 "원인이다"와 "그냥 숫자가 작다"를 구분할 수 없다. 같은 키에 동시에 들어온 두 쓰기를 충돌로 잡아내려면 더 많은 정보가 필요하다.

## 5. 벡터 시계: 인과와 동시를 구분한다

카운터 하나로는 정보가 모자라니, 프로세스 수 N만큼의 카운터를 벡터로 들고 다닌다. 프로세스 i의 벡터를 `V`라 하면 규칙은 다음과 같다.

- 로컬 이벤트: `V[i]`를 1 올린다.
- 송신: `V[i]`를 1 올린 뒤 벡터 전체를 메시지에 싣는다.
- 수신: 자기 벡터와 메시지 벡터의 원소별 최댓값을 취하고, `V[i]`를 1 올린다.

벡터의 각 칸은 "그 프로세스의 이벤트를 내가 몇 개까지 알고 있는가"를 뜻한다. 같은 예시로 계산하면 이렇다.

| 이벤트 | 계산 | 결과 |
|---|---|---|
| a | P1 로컬 | `[1,0,0]` |
| b | P1 송신 | `[2,0,0]` |
| c | P2 로컬 | `[0,1,0]` |
| d | m1 수신: max(`[0,1,0]`, `[2,0,0]`) = `[2,1,0]`, P2 칸 +1 | `[2,2,0]` |
| e | P2 송신 | `[2,3,0]` |
| f | P3 로컬 | `[0,0,1]` |
| g | m2 수신: max(`[0,0,1]`, `[2,3,0]`) = `[2,3,1]`, P3 칸 +1 | `[2,3,2]` |
| h | P3 송신 | `[2,3,3]` |
| i | m3 수신: max(`[2,0,0]`, `[2,3,3]`) = `[2,3,3]`, P1 칸 +1 | `[3,3,3]` |

### 두 벡터를 비교하는 법

- 모든 칸에서 `V(a) <= V(b)`이고 두 벡터가 같지 않으면 `a -> b`다.
- `V(b) <= V(a)`이고 같지 않으면 `b -> a`다.
- 어느 쪽도 성립하지 않으면 `a || b`, 즉 동시다.

그림에서 확인해 보자.

- b `[2,0,0]`과 d `[2,2,0]`: 모든 칸이 `<=`이므로 `b -> d`다. m1이 실제로 둘을 이었다.
- f `[0,0,1]`과 d `[2,2,0]`: f는 P3 칸이 크고 d는 P1, P2 칸이 크다. 어느 쪽도 `<=`가 아니므로 동시다. Lamport 값으로는 구분하지 못했던 쌍이다.
- b `[2,0,0]`과 c `[0,1,0]`: 역시 서로 크고 작은 칸이 섞여 있어 동시다.
- a `[1,0,0]`과 g `[2,3,2]`: 모든 칸이 `<=`이므로 `a -> g`다. a와 g는 다른 프로세스에 있지만, a -> b(같은 P1), b -> d(m1), d -> e(같은 P2), e -> g(m2)로 이어지는 이행 경로가 있다.

벡터 시계는 `a -> b`와 `V(a) < V(b)`(모든 칸 `<=`이면서 같지 않음)가 서로 필요충분조건이다. Lamport가 한쪽 방향만 보장하던 것을 양방향으로 확장한 셈이다.

### 비용과 쓰임새

대가는 크기다. 메시지와 저장 데이터마다 N칸짜리 메타데이터가 붙는다. 노드나 클라이언트가 계속 늘고 줄면 벡터가 부풀어 오른다. 그래서 실제 시스템은 벡터 크기에 상한을 두고 오래된 항목을 잘라내기도 한다.

쓰임새는 충돌 감지다. 같은 키에 대한 두 쓰기의 벡터가 동시로 판정되면 "한쪽이 이겼다"고 단정하지 않고 충돌로 다뤄 병합하거나 클라이언트에게 맡길 수 있다. Amazon의 Dynamo 논문이 이 방식을 쓴다. 버전마다 벡터 시계를 붙이고, 인과 관계가 없는 버전들은 읽을 때 모두 돌려줘 애플리케이션이 합치게 한다. 벡터가 너무 길어지면 오래된 항목을 잘라낸다고도 밝힌다.

## 6. 물리 시계를 그대로 쓰는 경우: LWW의 위험

반대편 선택지가 LWW(Last Write Wins)다. 쓰기마다 물리 타임스탬프를 붙이고 큰 쪽을 남긴다. 메타데이터가 작고 단순해서 널리 쓰인다. Cassandra 공식 문서도 갱신 충돌을 last write wins로 해소하고, 타임스탬프를 클라이언트가 주지 않으면 코디네이터 노드의 시계로 채운다고 설명한다. 같은 문서가 올바른 동작이 이 시계들에 달려 있으므로 NTP 같은 시간 동기화를 쓰라고 권고한다.

1절의 예시가 바로 LWW의 실패 모습이다. 시계가 느린 노드에서 나중에 쓴 값은 타임스탬프가 작아 패배한다. 에러도 나지 않는다. 데이터가 조용히 사라진다.

멀티 리전 DB에서 "분명히 나중에 쓴 값이 예전 값으로 돌아가 있다"는 증상이 보이면 첫 번째 용의자는 이것이다. 확인은 노드 간 NTP나 chrony의 offset, 문제 키의 쓰기 타임스탬프와 요청 로그로 한다. 대응은 다음과 같다.

- 시계 동기 품질을 감시한다.
- 버전 기반 충돌 처리(벡터 시계)나 HLC를 쓴다.
- 조건부 쓰기(compare-and-set, CAS)로 낡은 값 위에 쓰는 것을 거부한다.
- 단일 리더로 쓰기 순서를 직렬화한다.

## 7. 트레이드오프 정리

| 방식 | 얻는 것 | 잃는 것 |
|---|---|---|
| 물리 시계 + LWW | 단순하고 메타데이터가 작다 | 시계 skew 때문에 나중 쓰기가 지고, 동시 쓰기를 구분하지 못한다 |
| Lamport 시계 | 메타데이터 $O(1)$, 인과 순서 보존, 전체 순서 가능 | 동시성을 감지하지 못한다. 실제 시각과 무관하다 |
| 벡터 시계 | 인과와 동시를 정확히 판별해 충돌을 감지한다 | 메타데이터 $O(N)$, 노드가 변하면 관리가 부담이다 |
| HLC (Hybrid Logical Clock) | 물리 시각에 가깝고 인과를 보존하며 메타데이터가 작다. CockroachDB가 쓴다 | 동시성의 정확한 판별은 별도 수단이 필요하다 |
| TrueTime (Spanner) | 시각의 불확실 구간을 알고 commit wait로 외부 일관성을 보장한다 | GPS나 원자시계 같은 전용 하드웨어와 대기 지연이 든다 |

HLC는 물리 시각 부분과 논리 카운터를 합친 시계다. TrueTime은 현재 시각을 한 점이 아니라 `[earliest, latest]` 구간으로 돌려주고, 커밋할 때 그 구간이 지나갈 때까지 기다린다(commit wait). 목표는 외부 일관성(external consistency)이다. 트랜잭션 T1이 끝난 뒤에 T2가 시작했다면 T2의 타임스탬프가 T1보다 반드시 크다는 성질이다.

고르는 기준은 단순하다. 충돌을 잃어도 되면 LWW, 인과 순서만 필요하면 Lamport, 동시 쓰기를 눈으로 잡아야 하면 벡터 시계를 쓴다.

## 결론

- 분산 시스템에는 전역 시계가 없고 노드 시계는 어긋난다. 그래서 물리 시각의 대소로 "누가 먼저인가"를 정하면 틀릴 수 있다.
- 간격은 단조 시계로 재고, 순서는 인과 관계(happens-before)로 다룬다.
- Lamport 시계는 `a -> b`이면 `C(a) < C(b)`를 보장하지만 역은 성립하지 않아 동시성을 감지하지 못한다.
- 벡터 시계는 원소별 비교로 인과와 동시를 정확히 구분한다. 비용은 노드 수에 비례하는 메타데이터다.
- 복제된 데이터에서 이 선택이 일관성과 어떻게 맞물리는지는 [다음 글](/posts/cs/distributed/replication-cap-pacelc/)에서 이어 본다.
