## 개요

여러 서버가 같은 자원을 동시에 고치면 데이터가 깨진다. 그래서 락(lock)을 잡고 일한다. 그런데 락 서비스가 멀쩡한데도 두 클라이언트가 동시에 쓰는 일이 생긴다. 이 글은 그 원인을 하나의 타임라인으로 따라가고, 같은 타임라인에 fencing token을 붙여 어떻게 막는지 본다.

이 글이 답하는 질문은 두 가지다.

- lease(만료 시간이 있는 락)를 쓰는데도 왜 상호배제(mutual exclusion, 한 번에 한 클라이언트만 자원을 쓰는 것)가 깨지는가?
- fencing token은 무엇을 더해서 그 쓰기를 막고, Redlock을 둘러싼 논쟁은 무엇을 두고 갈렸는가?

[논리 시계 글](/posts/cs/distributed/logical-clocks/)에서 "물리 시계 대신 번호로 순서를 잡는다"는 아이디어를 봤다. fencing token은 그 아이디어를 락에 적용한 것이다. 시계를 믿지 않고 번호의 대소로 오래된 요청을 가려낸다.

## 1. 왜 락에 만료 시간이 붙는가

서버 여러 대가 같은 파일이나 DB 행을 고친다고 하자. 한 번에 한 서버만 고치게 하려고 락 서비스(lock service)에 락을 요청한다. 락을 받은 서버만 쓴다. 이것이 분산 락(distributed lock)이다.

문제는 락을 쥔 서버(홀더, holder)가 죽을 때다. 락을 풀지 못하고 죽으면 락이 영원히 잠긴다. 그래서 락에 만료 시간을 붙인다. 만료 시간이 있는 락을 lease(임대)라고 부른다. "10초 동안 빌려준다. 그 안에 끝내라. 안 끝나면 회수한다"는 약속이다.

Redis로 가장 단순하게 쓰면 이렇다. Redis 공식 문서가 설명하는 방식이다.

```
SET resource_name my_random_value NX PX 30000
```

- `NX`: 키가 없을 때만 만든다. 이미 있으면 다른 홀더가 있다는 뜻이다.
- `PX 30000`: 30000ms 뒤에 키가 저절로 사라진다. 이것이 lease다.
- `my_random_value`: 모든 요청마다 다른 값이다. 풀 때 "내 값일 때만 지운다"를 검사하려고 쓴다. 그냥 `DEL`을 쓰면 늦게 깨어난 클라이언트가 이미 다른 클라이언트가 가져간 락을 지울 수 있다.

여기까지는 문제가 없어 보인다. 하지만 lease에는 빈틈이 하나 있다. lease는 락 서비스가 하는 약속이다. "시간이 지나면 락이 풀린다"는 사실을 홀더 본인이 항상 안다는 보장은 없다.

## 2. 타임라인: lease가 만료됐는데도 쓰는 클라이언트

홀더가 자기 lease가 끝난 걸 모르는 상황은 흔하다. 가장 대표적인 것이 GC 멈춤(GC pause)이다. 가비지 컬렉터가 프로세스 전체를 멈추는 동안(stop-the-world) 코드는 한 줄도 실행되지 않는다. 멈춘 프로세스는 시간이 흐른 것도 모른다.

숫자를 넣어 보자. lease는 10초다. Client 1이 파일 F를 읽고, 고쳐서, 다시 쓰는 작업을 한다.

```
time  Client 1                       Client 2                       Storage (file F)
----- -------------------------      -------------------------      ----------------
0s    acquire lock (lease 10s)
2s    read F (content v1)                                           F = v1
3s    GC pause starts ...
10s   (lease expires)                acquire lock (lease 10s)
11s                                  read F (v1)
12s                                  write v2                       F = v2
18s   GC pause ends
18s   write v1' (based on v1)                                       F = v1'   <- v2 lost
```

Client 1은 3초에 멈췄다가 18초에 깨어난다. 깨어난 Client 1의 코드에는 "나는 락을 쥐고 있다"는 상태가 그대로 남아 있다. 락 서비스는 10초에 락을 회수해 Client 2에게 줬지만, 그 소식은 Client 1에게 닿지 않았다. Client 1은 v1을 기준으로 계산한 값을 쓴다. Client 2가 쓴 v2는 사라진다.

락 서비스는 한 번도 잘못 동작하지 않았다. 10초에 락을 회수한 것도, Client 2에게 준 것도 규칙대로다. 그런데도 두 클라이언트가 동시에 "내가 홀더"라고 믿는 구간(10초에서 18초)이 생겼다.

### 쓰기 직전에 lease를 확인하면 안 되는가

"쓰기 직전에 내 lease가 남았는지 확인하면 되지 않나?"라고 생각하기 쉽다. 이 방법은 소용없다. 확인과 쓰기 사이에도 멈춤이 끼어들 수 있기 때문이다.

```
check: lease remaining 4s  ->  [ GC pause 15s ]  ->  write   (lease already expired)
```

멈춤은 GC에서만 오지 않는다. Martin Kleppmann은 이 문제를 다룬 글에서 페이지 폴트, 느린 디스크 읽기, CPU 경합, 심지어 실수로 보낸 SIGSTOP까지 원인으로 든다. HBase가 실제로 이 문제를 겪은 적이 있고, stop-the-world GC 멈춤이 몇 분씩 이어진 사례도 있다고 소개한다. 패킷이 늦게 도착하는 것도 같은 결과를 낳는다. 같은 글은 GitHub에서 패킷이 약 90초 지연된 사건을 사례로 든다. 쓰기 요청이 네트워크에 오래 떠 있다가 lease가 끝난 뒤에 저장소에 닿는 식이다.

이런 멈춤과 지연은 드문 버그가 아니라 분산 환경의 정상 범위다. 그러니 "락을 잡았으니 안전하다"는 가정을 홀더 쪽에서 지킬 방법은 없다.

시계 문제도 있다. 서버끼리 시계가 어긋나면 한쪽은 만료로, 다른 쪽은 유효로 본다. 단조 시계(monotonic clock)로 경과 시간만 재면 시계 점프는 피할 수 있다. 하지만 위 타임라인의 멈춤은 막지 못한다. 시계가 정확해도 프로세스가 멈춰 있는 동안에는 시계를 볼 수 없기 때문이다.

## 3. 같은 타임라인에 fencing token을 붙이면

해법은 락을 더 정교하게 만드는 것이 아니다. 쓰기를 받는 쪽(자원)이 "이 쓰기가 오래된 홀더에게서 온 것인가"를 직접 검사하게 하는 것이다. 이 검사에 쓰는 번호가 fencing token이다.

핵심 아이디어는 한 문장이다. **락을 줄 때마다 커지는 번호를 함께 주고, 자원은 이미 본 것보다 작은 번호의 쓰기를 거절한다.**

방금 타임라인에 그대로 얹어 보자.

```
time  Client 1                       Client 2                       Storage (maxSeen = 0)
----- -------------------------      -------------------------      ---------------------
0s    acquire -> token 33
2s    read F (v1)
3s    GC pause starts ...
10s   (lease expires)                acquire -> token 34
12s                                  write v2, token 34             34 >= 0: accept, maxSeen = 34
18s   GC pause ends
18s   write v1', token 33                                           33 < 34: REJECT
```

달라진 점은 세 가지다.

1. 락 서비스는 락을 줄 때마다 번호를 올려서 함께 준다. Client 1은 33, Client 2는 34를 받았다.
2. 클라이언트는 모든 쓰기에 자기 token을 붙여 보낸다.
3. 저장소는 지금까지 본 가장 큰 token(`maxSeen`)을 기억한다. 그보다 작은 token의 쓰기는 거절한다.

18초에 깨어난 Client 1은 여전히 자신이 홀더라고 믿는다. 하지만 33이 34보다 작으므로 저장소가 쓰기를 거절한다. 이제 Client 1이 락이 끝난 걸 몰라도 데이터는 안전하다. 안전을 지키는 주체가 "홀더의 자각"에서 "자원의 검사"로 옮겨 갔기 때문이다.

저장소 쪽 의사코드는 짧다.

```
write(key, value, token):
    atomically {
        if token < maxSeen[key]: reject
        maxSeen[key] = token
        apply(value)
    }
```

검사와 반영이 한 덩어리(원자적)여야 한다. 검사 뒤에 다른 쓰기가 끼어들면 같은 문제가 되돌아온다.

### 이 방법이 하는 일과 하지 않는 일

fencing token은 두 홀더가 겹치는 구간을 없애지 않는다. 저장소가 이미 더 큰 token을 본 뒤에 도착한 옛 token의 쓰기를 거절할 뿐이다.

그래서 빈틈이 하나 남는다. Client 1의 쓰기(token 33)가 Client 2의 첫 쓰기(token 34)보다 먼저 저장소에 도착하면 그대로 받아들여진다. 저장소는 아직 34를 본 적이 없으니 33을 거절할 이유가 없다. 이때 Client 2가 그 전에 읽은 v1을 바탕으로 v2를 쓰면 Client 1의 쓰기가 덮인다. 이 경우까지 막으려면 Client 2가 읽을 때도 token 34를 보내 저장소의 `maxSeen`을 먼저 올리거나, 4절의 버전 CAS를 함께 쓰는 식으로 보완해야 한다. 이 보완책은 이 글의 추론이며 Kleppmann의 글이 직접 다루지는 않는다.

token은 어디서 얻는가. 합의 시스템(consensus system)은 이미 순서 있는 번호를 갖고 있다.

- ZooKeeper: 모든 변경에 전체 순서를 나타내는 `zxid`가 붙는다. 공식 문서는 zxid1이 zxid2보다 작으면 zxid1이 먼저 일어났다고 설명한다. znode의 변경 횟수인 `version`도 쓸 수 있다.
- etcd: 저장소를 바꾸는 연산마다 하나씩 증가하는 revision이 붙고, 공식 문서는 revision으로 전체 순서가 정해진다고 설명한다.

두 시스템 모두 내부에서 합의 알고리즘으로 순서를 정한다. 합의가 어떻게 순서를 만드는지는 [Raft 글](/posts/cs/distributed/raft-consensus/)에서 다룬다. 번호를 만드는 쪽이 단일 서버면 그 서버가 죽을 때 번호가 끊기거나 되돌아갈 수 있으니, 이 번호 발급 자체를 합의 위에 올리는 것이다.

## 4. 저장소가 token을 검사할 수 없다면

fencing token에는 전제가 있다. 저장소가 token을 받아서 비교하고 기억해야 한다. 그래서 생기는 한계가 있다.

- 이메일 발송이나 외부 결제 API처럼 token을 모르는 시스템에는 적용할 수 없다.
- 이미 쓰고 있는 DB나 파일 시스템은 token 칸이 없다.

이런 경우에는 방법이 달라진다. 가장 단순한 것은 락 자체를 버리고 조건부 쓰기(conditional write)를 쓰는 것이다. 버전 컬럼을 두고 "내가 읽은 버전일 때만 갱신한다"고 쓴다.

```sql
-- 읽었을 때 version = 7 이었다
UPDATE product
   SET stock = 9, version = version + 1
 WHERE id = 1 AND version = 7;   -- 영향받은 행이 0이면 누가 먼저 바꿨다
```

영향받은 행이 0이면 다른 쓰기가 먼저 들어온 것이니 다시 읽고 재시도한다. 락이 만료됐는지는 아예 상관없다. 실제로 이 방식은 fencing token과 같은 일을 한다. "오래된 정보에 근거한 쓰기"를 저장소가 거절한다는 점이 같다. 다만 범위가 한 DB 행이나 한 자원으로 한정된다.

그 밖의 대안은 다음과 같다.

| 방법 | 어떻게 중복·충돌을 막나 | 한계 |
|---|---|---|
| fencing token | 저장소가 작은 token의 쓰기를 거절 | 저장소가 token을 검사해야 한다 |
| 버전 컬럼 CAS | `WHERE version = 읽은 값`으로 갱신 | 한 자원 범위, 충돌 시 재시도 |
| 유니크 제약 | 같은 키의 두 번째 삽입이 실패 | 삽입형 작업에 한정 |
| 멱등 키(idempotency key) | 같은 요청이 두 번 와도 한 번만 반영 | 키를 저장하고 확인하는 곳이 필요 |
| 키 단위 순차 처리 | 큐를 키로 나눠 한 키는 한 소비자가 처리 | 파티션 이동 중에는 짧게 겹칠 수 있다 |

토큰을 검사할 수 없는 외부 효과는 [멱등성 글](/posts/cs/distributed/idempotency-exactly-once/)에서 다룬 멱등 키로 막는 것이 보통이다. 락은 "중복 실행을 줄이는 최적화"로 쓰고, 최종 방어선은 멱등 키가 맡는 식이다.

## 5. 구현 선택지: 단일 Redis, Redlock, ZooKeeper와 etcd

### 단일 Redis 락의 약점

1절의 `SET NX PX`는 단순하고 빠르다. 하지만 Redis 한 대가 단일 장애점이다. 복제본(replica)을 붙이면 되지 않냐고 하겠지만, Redis 복제는 비동기라서 다음 경쟁 상태가 생긴다. Redis 공식 문서가 직접 설명하는 시나리오다.

1. Client A가 마스터에서 락을 얻는다.
2. 마스터가 그 쓰기를 복제본에 보내기 전에 죽는다.
3. 복제본이 마스터로 승격된다.
4. Client B가 같은 자원의 락을 얻는다. 두 홀더가 생겼다.

### Redlock

Redlock은 이 문제를 풀려고 Redis 작성자가 제안한 알고리즘이다. 서로 복제하지 않는 독립 Redis 마스터 N대(문서의 예시는 5대)를 쓴다.

1. 현재 시각을 기록한다.
2. 5대 모두에 같은 키와 같은 랜덤 값으로 락을 요청한다. 대기 시간은 짧게 잡는다.
3. 걸린 시간을 계산한다. 과반수(3대 이상)에서 얻었고 걸린 시간이 lease 시간보다 짧으면 락을 얻은 것이다.
4. 유효 시간은 처음 lease 시간에서 걸린 시간을 뺀 값이다.
5. 실패하면 모든 노드에서 락을 풀고, 랜덤 시간을 쉬고 다시 시도한다.

예를 들어 lease가 10초이고 락을 얻는 데 0.2초 걸렸다면 유효 시간은 9.8초다(실제로는 시계 오차분을 조금 더 뺀다).

Redlock은 서버 한두 대가 죽어도 락이 동작한다. 하지만 이 알고리즘은 번호를 발급하지 않는다. 각 노드에 저장하는 값은 매번 다른 랜덤 문자열일 뿐 대소를 비교할 수 없다. 이것이 다음 절 논쟁의 출발점이다.

### ZooKeeper와 etcd

합의 기반 시스템의 락은 락 서비스 자체가 순서 있는 번호를 갖고 있다. ZooKeeper는 임시 노드(ephemeral node)를 쓴다. 이 노드는 만든 세션이 살아 있는 동안만 존재하고, 서버가 세션 타임아웃 안에 클라이언트 소식을 듣지 못하면 지워진다. 순차 노드(sequential node)는 부모 노드마다 단조 증가하는 번호를 붙여 준다. 이 번호나 `zxid`를 fencing token으로 쓸 수 있다.

| 방식 | 장점 | 한계 |
|---|---|---|
| 단일 Redis | 단순하고 빠르다 | 장애 조치 때 두 홀더 가능, token 없음 |
| Redlock | 노드 일부 장애를 견딘다 | 단조 token이 없다, 시계 가정이 필요하다 |
| ZooKeeper, etcd | 합의 기반, 순서 있는 번호 제공 | 지연이 크다, 저장소가 token을 검사해야 안전하다 |
| DB 조건부 쓰기 | 락 없이도 이중 쓰기 방지 | 한 자원 범위, 재시도 필요 |

## 6. Redlock 논쟁: Kleppmann과 antirez

2016년 2월 Martin Kleppmann이 Redlock을 분석한 글을 냈고, Redis 작성자 antirez가 곧바로 반론을 썼다. 두 글은 지금도 Redis 공식 문서가 Redlock 설명 끝에 함께 링크하는 자료다. 양쪽 주장을 그대로 정리한다.

### Kleppmann의 주장

먼저 락을 쓰는 목적을 둘로 나눈다.

- 효율(efficiency): 락이 깨지면 같은 일을 두 번 하는 정도다. 같은 알림 메일이 두 번 가는 식이다.
- 정확성(correctness): 락이 깨지면 데이터가 영구히 틀어진다.

효율 목적이라면 Redlock의 노드 5대는 과하다. 단일 Redis로 충분하다. 정확성 목적이라면 Redlock은 부족하다고 본다. 이유는 두 가지다.

1. **fencing token이 없다.** Redlock이 주는 랜덤 값으로는 오래된 홀더를 저장소가 구분할 수 없다.
2. **타이밍 가정에 기댄다.** Redlock이 안전하려면 네트워크 지연, 프로세스 멈춤, 시계 오차가 모두 제한된 범위 안이어야 한다. 그는 "대부분의 경우"만으로는 정확성에 충분하지 않다고 본다.

그가 든 시나리오는 둘이다. 하나는 시계 점프다. 노드 A, B, C에서 Client 1이 락을 얻은 뒤 C의 시계가 앞으로 뛰어 키가 만료되고, Client 2가 C, D, E에서 락을 얻어 둘이 동시에 홀더가 된다. Redis가 만료 계산에 단조 시계가 아닌 `gettimeofday`를 쓴다는 점도 근거로 든다. 다른 하나는 락 요청을 보낸 뒤 Client 1이 멈추는 경우다. 그 사이 모든 노드에서 락이 만료되고 Client 2가 잡은 뒤, 깨어난 Client 1이 커널 버퍼에 남은 옛 성공 응답을 받는다.

권고는 이렇다. 효율 목적이면 단일 Redis, 정확성 목적이면 ZooKeeper 같은 합의 시스템과 fencing token이다.

### antirez의 반론

antirez는 결론에 동의하지 않지만, 일부는 받아들였다.

- **시계 점프.** 관리자가 시계를 손으로 바꾸지 않고, ntpd가 시계를 한 번에 점프시키지 않고 천천히 조정하게 설정하면 피할 수 있다고 한다. 다만 단조 시계 API를 쓰는 편이 좋다는 데는 동의하고 반영하겠다고 했다. Redlock이 필요로 하는 것은 절대 시각이 아니라 각 프로세스가 오차 범위 안에서 경과 시간을 재는 능력이라는 입장이다.
- **멈춤.** Redlock의 3단계에서 시각을 다시 재므로, 락을 얻는 과정(1~3단계)에서 생긴 지연은 그 자리에서 걸러진다고 한다. 따라서 Kleppmann이 든 두 번째 시나리오는 일어날 수 없다는 주장이다. 락을 얻은 뒤에 생기는 멈춤은 인정하지만, 그것은 자동 해제되는 모든 분산 락의 문제이지 Redlock만의 문제가 아니라고 답한다.
- **fencing token.** 세 가지를 지적한다. 첫째, 단조 증가 token을 검사하는 저장소는 이미 [선형화 가능](/posts/cs/distributed/consistency-models-quorum/)(linearizable)한 저장소이니 락 없이 증가 ID를 직접 쓰면 된다. 둘째, 랜덤 값을 락과 함께 저장소에 기록하고 그 값이 안 바뀌었을 때만 읽고-고쳐-쓰는 check-and-set 방식이 저장소에 더 적게 요구한다. 셋째, 물건을 옮기거나 외부 API를 부르는 일처럼 저장소가 token을 검사할 수 없는 자원이 많다.
- **시스템 모델.** Redlock은 프로세스들의 시계 속도가 비슷하다는 가정만 쓰고, 메시지 지연이 제한되어 있다고 가정하지 않는다고 말한다. 그 지연은 3단계 시각 검사로 처리한다는 설명이다.

### 어디서 갈렸나

| 쟁점 | Kleppmann | antirez |
|---|---|---|
| 락을 얻는 중의 멈춤 | 응답이 늦게 도착하면 옛 락을 쥔 줄 안다 | 3단계 시각 검사가 걸러낸다 |
| 락을 얻은 뒤의 멈춤 | 이것이 핵심 문제이며 fencing token으로 막아야 한다 | 모든 자동 해제 락의 공통 문제다 |
| 시계 | 점프하면 Redlock이 깨진다 | 점프는 설정으로 피할 수 있고 단조 시계를 쓰겠다 |
| 순서 있는 token | 필요하다 | 랜덤 값과 CAS로 충분하다 |
| 정확성 목적의 사용 | 권하지 않는다 | 가능하다고 본다 |

두 사람이 겹치는 부분도 있다. 락을 얻은 뒤의 멈춤은 락만으로 막을 수 없고, 자원 쪽에서 오래된 쓰기를 가려내야 한다는 점이다. 다만 가려내는 수단이 순서 있는 token이냐, 랜덤 값과 조건부 쓰기냐가 갈린다. 참고로 현재 Redis 공식 문서는 정확성이 중요하면 fencing token을 구현하라고 안내하고, Redis가 TTL 만료에 단조 시계를 쓰지 않는다는 점을 직접 경고한다.

## 7. 그래서 무엇을 고르는가

락을 고르기 전에 먼저 목적을 묻는다. 락이 깨졌을 때 무엇이 일어나는가?

| 목적 | 락이 깨지면 | 선택 |
|---|---|---|
| 효율: 중복 작업 줄이기 | 같은 일을 한 번 더 한다 | 단일 Redis `SET NX PX`로 충분하다. 약한 락임을 알고 쓴다 |
| 정확성, 저장소가 token을 검사할 수 있음 | 데이터가 틀어진다 | ZooKeeper나 etcd 락과 fencing token |
| 정확성, 한 DB 안 | 데이터가 틀어진다 | 락 없이 버전 CAS나 유니크 제약 |
| 정확성, 외부 효과(메일, 결제) | 효과가 두 번 일어난다 | 멱등 키 |

운영에서 "락이 정상인데 같은 레코드가 두 번 갱신된다"는 증상을 만나면 이 글의 타임라인을 의심한다. 로그에서 락 획득 시각과 쓰기 시각의 간격이 TTL보다 큰지 본다. 크다면 홀더가 멈춰 있었거나 요청이 늦게 도착한 것이다. lease를 늘리는 것은 임시방편일 뿐이고, 쓰기 쪽에 token 검증이나 버전 CAS를 넣어야 한다.

## 결론

- lease는 홀더가 죽었을 때 락이 영원히 잠기지 않게 하는 장치다. 하지만 홀더가 자기 lease 만료를 알게 해 주지는 않는다.
- GC 멈춤, 페이지 폴트, 패킷 지연은 정상 범위의 일이다. 쓰기 직전에 lease를 확인해도 확인과 쓰기 사이의 멈춤은 막지 못한다.
- fencing token은 락을 줄 때마다 커지는 번호를 붙이고, 저장소가 작은 번호의 쓰기를 거절하게 한다. 안전을 지키는 주체가 홀더에서 자원으로 옮겨 간다.
- 저장소가 token을 검사할 수 없으면 버전 CAS, 유니크 제약, 멱등 키로 같은 효과를 낸다. 락이 정말 필요한지부터 따져 본다.
- Redlock 논쟁은 락 뒤의 멈춤에 자원 쪽 검사가 필요하다는 데서는 겹치고, 그 수단과 Redlock을 정확성 목적에 쓸 수 있는지에서 갈렸다. 쓰기 전에 목적이 효율인지 정확성인지부터 정한다.
