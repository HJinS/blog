## 개요

[앞 글](/posts/cs/distributed/replication-cap-pacelc/)에서 데이터를 여러 복제본(replica)에 두는 방법과, 리더 없이 N개 중 W개에 쓰고 R개에서 읽는 쿼럼(quorum) 방식을 봤다. 흔히 $R + W > N$이면 "항상 최신 값을 읽는다", 곧 강한 일관성이라고 말한다.

이 글은 그 말이 어디까지 맞는지 따진다. 답할 질문은 두 가지다.

- 일관성 모델은 무엇을 약속하고, 가장 강한 모델인 선형화 가능성은 정확히 무엇을 요구하는가?
- $R + W > N$을 지켜도 선형화가 깨지는 이유는 무엇이고, 어떻게 고치는가?

본론은 N=3, W=2, R=2에서 선형화가 깨지는 타임라인 하나다. 장애 없이, 네트워크가 조금 느린 것만으로 깨진다.

## 1. 일관성 모델: 읽기가 어떤 쓰기를 볼 수 있는가

복제본이 하나뿐이면 질문이 없다. 마지막에 쓴 값을 읽는다. 복제본이 셋이 되면 쓰기가 세 곳에 닿는 시점이 제각각이다. 그 사이에 들어온 읽기는 새 값을 볼 수도, 옛 값을 볼 수도 있다.

그래서 시스템은 "읽기가 어떤 값을 돌려줄 수 있는가"를 미리 약속해야 한다. 이 약속을 **일관성 모델**(consistency model)이라고 한다. Jepsen은 일관성 모델을 시스템이 할 수 있는 일을 정하는 안전성 속성(safety property)이라고 정의한다. 허용되는 실행 기록(history)의 집합이라고 생각하면 된다.

모델은 강한 것부터 약한 것까지 사다리처럼 늘어선다. 아래는 이 글에 필요한 네 단계만 단순화한 그림이다.

```
  stronger
     |
     |   linearizable   one copy, ops happen at a single instant,
     |                  real-time order respected
     |        |
     |        v
     |   sequential     everyone sees the same total order,
     |                  but it may lag behind real time
     |        |
     |        v
     |   causal         cause-and-effect pairs are seen in order,
     |                  unrelated writes may be seen in any order
     |        |
     |        v
     |   eventual       stop writing and replicas converge, someday
     v
  weaker
```

위 모델을 만족하면 아래 모델도 자동으로 만족한다. 선형화 가능한 시스템은 순차 일관성도 지킨다.

표의 오른쪽 칸은 네트워크 분할(partition) 중에도 동작할 수 있는지를 Jepsen의 분류로 적은 것이다. 완전 가용(total availability)은 분할 중에도 고장 나지 않은 모든 노드가 요청을 처리할 수 있다는 뜻이다. 고정 가용(sticky availability)은 클라이언트가 늘 같은 서버에만 붙어 있다는 조건에서만 그렇다는 뜻이다.

| 모델 | 약속 | 분할 중 가용성 (Jepsen 기준) |
| --- | --- | --- |
| 선형화 가능성 | 실시간 순서를 지키는 단일 순서 | 완전 가용, 고정 가용 모두 불가 |
| 순차 일관성 | 모두가 같은 순서를 보되 실시간과 어긋나도 된다 | 완전 가용, 고정 가용 모두 불가 |
| 인과 일관성 | 원인과 결과의 순서만 지킨다 | 고정 가용(같은 서버에 붙어 있으면 진행) |
| 최종 일관성 | 쓰기가 멈추면 언젠가 수렴한다 | 수렴 시점 외에는 약속이 없어 분할 중에도 응답할 수 있다 |

**순차 일관성**(sequential consistency)은 모든 연산이 하나의 순서로 일어난 것처럼 보이고, 각 프로세스 안의 순서는 그대로 지켜지는 모델이다. 다만 실시간 순서는 요구하지 않는다. 이미 끝난 쓰기가 다른 클라이언트에게 아직 안 보여도 된다.

**인과 일관성**(causal consistency)은 인과 관계가 있는 연산만 모두에게 같은 순서로 보이게 한다. 댓글이 원글보다 먼저 보이는 일은 막지만, 서로 무관한 두 글의 순서는 사람마다 달라도 된다. 인과 관계를 추적하는 방법은 [논리 시계 글](/posts/cs/distributed/logical-clocks/)에서 다뤘다.

**최종 일관성**(eventual consistency)은 쓰기가 멈추면 언젠가 모든 복제본이 같은 값으로 수렴한다는 약속이다. 수렴하기 전까지 무엇이 보이는지는 약속하지 않는다.

사다리를 내려갈수록 조율이 줄어 빠르고 가용성이 높아진다. 대신 애플리케이션이 감당할 이상한 결과가 늘어난다.

## 2. 선형화 가능성: 복사본이 하나뿐인 것처럼

**선형화 가능성**(linearizability)은 복제본이 여럿이어도 데이터가 하나뿐인 것처럼 보이게 하는 모델이다. 핵심 아이디어는 한 문장이다. **모든 연산은 호출과 응답 사이의 어느 한 순간에 원자적으로 일어난 것처럼 보이고, 그 순서는 실제 시간 순서를 어기지 않는다.**

Jepsen은 실시간 조건을 이렇게 쓴다. 연산 A가 끝난 뒤에 연산 B가 시작했다면, B는 논리적으로 A 뒤에 일어나야 한다. 이 조건이 선형화를 순차 일관성과 가르는 지점이다.

규칙은 두 경우로 나뉜다.

**겹치지 않는 연산.** 쓰기가 끝난 뒤에 시작한 읽기는 반드시 그 쓰기의 값이나 더 새 값을 본다.

**겹치는 연산.** 읽기가 쓰기와 시간상 겹치면 어느 쪽이 먼저인지 정해지지 않는다. 옛 값을 돌려줘도, 새 값을 돌려줘도 된다. Kleppmann의 강의 노트도 겹치는 get과 set에서는 두 결과 모두 허용된다고 설명한다.

```
case 1: no overlap -> read MUST return 1

  C1  |--- write(x=1) ---|
  C2                        |--- read -> 1 ---|

case 2: overlap -> read may return 0 or 1

  C1  |-------- write(x=1) --------|
  C2         |--- read -> ? ---|
```

여기에 중요한 귀결이 하나 붙는다. **읽기끼리도 실시간 순서를 지켜야 한다.** 어떤 읽기가 새 값 1을 돌려줬다면, 그 쓰기는 이미 "일어난" 것이다. 그 읽기가 끝난 뒤에 시작한 읽기는 다시 0을 볼 수 없다. 값이 1이 됐다가 0으로 되돌아가면 하나뿐인 복사본에서는 일어날 수 없는 일이 된다. 4절의 타임라인이 정확히 이 규칙을 깬다.

선형화가 필요한 대표적인 경우는 사용자 이름 중복 검사, 리더 선출용 락, 재고 차감처럼 "지금 이 값"에 근거해 결정하는 곳이다. 두 클라이언트가 DB 밖의 경로(메시지 큐, 전화)로 서로 "방금 썼다"고 알려 주는 경우에도 필요하다. Jepsen이 순차 일관성 대신 선형화를 권하는 상황이 바로 이 경우다.

선형화와 이름이 비슷한 **직렬화 가능성**(serializability)은 다른 개념이다. 선형화는 객체 하나에 대한 연산 하나의 모델이고 실시간 순서를 지킨다. 직렬화 가능성은 여러 객체에 걸친 트랜잭션이 어떤 직렬 순서와 같은 결과를 내면 되고, 실시간 순서는 요구하지 않는다. 둘을 함께 만족하는 모델이 엄격한 직렬화 가능성(strict serializability)이다. 트랜잭션 쪽은 [직렬화 가능성 글](/posts/cs/database/serializability-2pl-ssi/)에서 다뤘다.

## 3. 쿼럼 `R + W > N`: 겹침이 보장하는 것

리더리스 복제에서 쓰기를 N개 모두에 기다리면 노드 하나만 죽어도 쓰기가 멈춘다. 하나에만 기다리면 읽기가 옛 값을 볼 수 있다. 쿼럼은 그 중간을 고르는 방법이다.

핵심 아이디어는 한 문장이다. **쓰기가 성공한 노드 집합과 읽기가 묻는 노드 집합이 반드시 겹치게 크기를 고른다.**

- N: 복제본 수
- W: 쓰기 성공으로 치는 확인(ack) 수
- R: 읽기가 응답을 모으는 노드 수

N=3, W=2, R=2라면 크기 2인 집합 둘을 3개 중에서 뽑는다. 2 + 2 = 4는 3보다 크므로 두 집합은 최소 한 노드에서 겹친다. 비둘기집 원리(pigeonhole principle)다.

```
N=3, W=2, R=2  ->  W + R = 4 > 3

  write set   { R1, R2 }      (both acked x=1)
  read set        { R2, R3 }
                    ^^
                    R2 is in both -> the read sees x=1
```

읽기는 응답 중 가장 새 값을 고른다. 그러려면 값마다 버전이 붙어 있어야 한다. 버전 번호나 타임스탬프가 그 역할을 한다. 위 그림에서 읽기는 R2의 `(x=1, ver 1)`과 R3의 `(x=0, ver 0)`을 받고 1을 돌려준다.

W와 R은 손잡이다.

| 설정 (N=3) | 겹침 | 얻는 것 | 잃는 것 |
| --- | --- | --- | --- |
| W=3, R=1 | 보장 | 읽기가 가장 가볍다 | 노드 하나만 죽어도 쓰기 불가 |
| W=1, R=3 | 보장 | 쓰기가 가장 가볍다 | 노드 하나만 죽어도 읽기 불가 |
| W=2, R=2 | 보장 | 노드 하나가 죽어도 읽기·쓰기 모두 된다 | 양쪽 모두 두 번째 응답을 기다린다 |
| W=1, R=1 | 없음 | 지연이 가장 짧다 | 옛 값 읽기, 최종 일관성 |

W=2, R=2가 흔한 이유가 표에 있다. 한 대 장애를 견디면서 겹침도 지킨다.

여기서 조심할 점이 있다. 겹침이 보장하는 것은 정확히 이것이다. **이미 완료된 쓰기는 그 뒤에 시작한 읽기가 본다.** 진행 중인 쓰기, 일부 노드에만 닿고 실패한 쓰기에 대해서는 아무것도 약속하지 않는다. 선형화는 바로 그 틈에서 깨진다.

## 4. N=3, W=2, R=2에서 선형화가 깨지는 타임라인

설정은 3절과 같다. x의 초기값은 0(버전 0)이다. 장애는 없다. 네트워크 경로 하나가 조금 느릴 뿐이다.

- C1이 x=1(버전 1)을 세 복제본 모두에 보낸다. R1에는 바로 닿고, R2와 R3로 가는 메시지는 늦어진다.
- C2는 R1, R2에서 읽는다.
- C3은 C2가 끝난 뒤에 R2, R3에서 읽는다.

```
x starts as 0 (ver 0).  N=3, W=2, R=2.

time  C1 (writer)            R1      R2      R3      readers
----  ---------------------  ------  ------  ------  -----------------------------
 t1   send x=1 to R1,R2,R3   x=1     x=0     x=0     (R2, R3 messages delayed)
 t2                          x=1     x=0     x=0     C2: read from {R1, R2}
 t3                          x=1     x=0     x=0     C2 gets 1@v1, 0@v0 -> returns 1
 t4                          x=1     x=0     x=0     C3: read from {R2, R3}
 t5                          x=1     x=0     x=0     C3 gets 0@v0, 0@v0 -> returns 0
 t6                          x=1     x=1     x=0     (x=1 finally reaches R2)
 t7   2 acks (W=2) -> ok     x=1     x=1     x=1
```

각 단계는 쿼럼 규칙을 하나도 어기지 않는다.

1. t1: C1은 쓰기를 세 곳에 보내고 확인 2개를 기다린다. 아직 R1 하나만 받았으므로 쓰기는 진행 중이다.
2. t2-t3: C2는 R1, R2에 묻는다. 버전 1과 버전 0을 받고 더 새 값 1을 돌려준다. 규칙대로다.
3. t4-t5: C2가 끝난 뒤 C3이 시작한다. R2, R3에 묻는다. 둘 다 버전 0이다. C3은 버전 1이 있다는 사실조차 모르고 0을 돌려준다. 역시 규칙대로다.
4. t6-t7: 늦은 메시지가 도착하고 C1이 성공 응답을 받는다.

이제 클라이언트 쪽에서만 보자. 선형화는 복제본 내부가 아니라 각 연산의 시작, 끝, 결과만 본다.

```
       t1   t2              t3  t4              t5  t7
C1     |---------------- write(x=1) ----------------|
C2          |-- read -> 1 --|
C3                              |-- read -> 0 --|
```

이 기록이 선형화 가능하려면 세 연산을 한 줄로 세울 수 있어야 한다. 세워 보면 모순이 나온다.

1. C2가 1을 읽었다. 따라서 줄 위에서 write는 C2의 read보다 앞에 있다.
2. C2는 t3에 끝났고 C3은 t4에 시작했다. 실시간 조건에 따라 C2의 read는 C3의 read보다 앞에 있다.
3. 1과 2를 이으면 write가 C3의 read보다 앞에 있다. 그렇다면 C3은 1을 읽어야 한다.
4. C3은 0을 읽었다. 어떤 순서로도 세울 수 없다. **선형화 위반이다.**

연산을 둘씩 떼어 보면 각각은 문제가 없다. C3의 read는 write와 겹치므로 혼자라면 0을 돌려줘도 된다. 문제는 C2와 C3의 조합이다. 값이 1이었다가 0으로 되돌아갔다. 복사본이 하나뿐인 시스템에서는 일어날 수 없는 결과다. Kleppmann의 Cambridge 강의 노트가 바로 이 형태(복제본 A, B, C, 읽기 쿼럼 `{A, B}`와 `{B, C}`)를 "쿼럼 읽기·쓰기를 쓰는데도 선형화 불가능한" 예로 든다.

현실에서 어떤 모습일지 보자. C2와 C3이 같은 사용자의 연속된 요청이라면, 방금 "주문 완료"를 본 사용자가 새로고침하자 "주문 없음"을 본다. C2가 C3에게 "x가 1로 바뀌었다"고 메시지를 보낸 경우라면, C3은 그 메시지를 받고 확인하러 가서 0을 본다.

## 5. 왜 깨지는가: 쿼럼이 놓치는 세 가지

타임라인의 원인은 한 문장으로 줄어든다. **C2는 새 값을 "봤지만", 그 값이 쿼럼에 자리 잡았는지는 확인하지 않고 돌려줬다.** C2가 1을 돌려준 시점에 1을 가진 노드는 R1 하나였다. 다음 읽기 쿼럼 `{R2, R3}`가 R1을 비켜 가면 1은 보이지 않는다.

쿼럼이 놓치는 경우는 이것 말고도 있다.

**진행 중이거나 모호하게 실패한 쓰기.** 쓰기가 R1에만 닿고 타임아웃이 나면 C1은 "실패"로 알고 있지만 R1에는 1이 남는다. 이런 쓰기는 성공도 실패도 아닌 모호한 상태다. 쿼럼 시스템은 보통 R1의 값을 되돌리지 않는다. 그러면 읽기 쿼럼이 R1을 포함하느냐에 따라 1과 0이 번갈아 보인다. Jepsen의 Kingsbury도 Cassandra 분석의 댓글에서, 쓰기 시도가 원자적으로 성공하거나 실패한다는 보장이 없어 나중에 되살아나 충돌하는 쓰기를 덮어쓸 수 있다고 설명한다.

여기서 흔한 오해 하나를 짚는다. "실패한 쓰기가 나중에 보였다"는 것만으로는 선형화 위반이 아니다. 타임아웃은 "결과를 모른다"는 뜻이다. 응답이 없는 연산은 끝나지 않은 연산이므로 이후 모든 연산과 겹친다. 선형화 가능한 시스템에서도 타임아웃된 쓰기가 나중에 반영될 수 있다. 0을 보고 나중에 1을 보는 것은 허용된다. 위반은 **1을 본 뒤에 다시 0을 보는** 순간에 생긴다. 4절의 타임라인이 그 순간이다.

**느슨한 쿼럼**(sloppy quorum)과 **힌트 핸드오프**(hinted handoff). Dynamo 논문에 나오는 두 기법이다. 느슨한 쿼럼은 원래 담당 노드에 닿지 못할 때 고리(ring)에서 다음으로 살아 있는 노드가 쓰기를 대신 받아 두는 방식이다. 힌트 핸드오프는 담당 노드가 돌아오면 대신 받아 둔 쓰기를 넘겨주는 과정이다. 

가용성은 오르지만 W개 확인이 담당 노드 N개 바깥에서 나올 수 있다. 그러면 읽기 집합과 쓰기 집합이 겹친다는 전제가 깨진다. Kleppmann은 느슨한 쿼럼과 읽기 수리(read repair, 읽기 중에 옛 값을 가진 복제본을 새 값으로 고쳐 쓰는 것) 같은 기능의 미묘한 조합이 선형화 불가능한 결과로 이어진다며, 쿼럼 읽기·쓰기가 선형화를 보장한다고 기대하지 말라고 쓴다.

**타임스탬프 기반 충돌 해소.** 버전을 물리 시계 타임스탬프로 매기면, 시계가 느린 노드에서 나중에 쓴 값이 "더 오래된" 값으로 판정된다. 이 문제는 [논리 시계 글](/posts/cs/distributed/logical-clocks/)의 LWW 절에서 다뤘다.

## 6. 쿼럼을 선형화로 만들기: 읽고 나서 다시 쓴다

고치는 방향은 원인에서 바로 나온다. 읽기가 값을 돌려주기 전에 그 값이 쿼럼에 자리 잡았음을 보장하면 된다.

핵심 아이디어는 한 문장이다. **읽기는 가장 새 값을 찾은 뒤, 그 값을 아직 갖지 않은 복제본에 다시 써서 쿼럼이 확인한 다음에야 돌려준다.** 저자 Attiya, Bar-Noy, Dolev의 이름을 따 ABD 알고리즘이라고 부른다. 5절의 읽기 수리를 응답 전에 동기적으로, 쿼럼이 확인할 때까지 하는 것과 같다.

4절의 타임라인에 적용하면 이렇다.

```
time  R1      R2      R3      readers
----  ------  ------  ------  ---------------------------------------
 t2   x=1     x=0     x=0     C2: read from {R1, R2}
 t3   x=1     x=0     x=0     C2 gets 1@v1, 0@v0 -> newest is 1@v1
 t3'  x=1     x=1     x=0     C2: write back 1@v1 to R2, R2 acks
                              -> 1@v1 is on {R1, R2}, a quorum
 t3"                          C2 returns 1
 t4   x=1     x=1     x=0     C3: read from {R2, R3}
 t5   x=1     x=1     x=0     C3 gets 1@v1, 0@v0 -> returns 1   (ok)
```

C2가 끝나는 순간 1은 이미 두 노드에 있다. 그 뒤의 어떤 읽기 쿼럼도 그중 하나를 반드시 포함한다. 그래서 C3은 1을 본다. 읽기든 쓰기든, 연산이 끝날 때 그 값이 쿼럼에 저장돼 있다는 불변식이 선형화를 만든다.

쓰는 사람이 여럿이면 한 단계가 더 필요하다. 쓰기 전에 쿼럼에 현재 최대 버전을 물어보고, 그보다 1 큰 버전으로 쓴다. 그래야 먼저 끝난 쓰기보다 나중에 시작한 쓰기의 버전이 커진다. 두 클라이언트가 같은 버전을 고르면 클라이언트 ID로 승자를 정한다.

대가와 한계는 분명하다.

- **왕복이 는다.** 응답이 엇갈린 읽기는 왕복이 두 번이다. 여러 클라이언트가 쓰는 경우에는 쓰기도 왕복이 두 번이다.
- **블라인드 쓰기만 된다.** ABD가 선형화하는 것은 이전 값과 상관없이 덮어쓰는 블라인드 쓰기(blind write)와 읽기다. 동시에 쓴 값 중 하나는 조용히 버려진다.
- **CAS는 안 된다.** 비교 후 교환(compare-and-swap, CAS)은 "현재 값이 A일 때만 B로 바꾼다"는 연산이다. 복제본마다 연산을 보는 순서가 다르면 같은 CAS가 어떤 곳에서는 성공하고 어떤 곳에서는 실패한다. Kleppmann의 노트는 ABD로는 CAS를 구현할 수 없고, 전체 순서 브로드캐스트(total order broadcast), 곧 합의가 필요하다고 정리한다.

합의 알고리즘은 [다음 글의 Raft](/posts/cs/distributed/raft-consensus/)에서 다룬다. Cassandra의 경량 트랜잭션(lightweight transaction)도 CAS를 위해 Paxos를 쓴다.

## 7. 충돌 해소 방법과 Jepsen의 Cassandra 실험

쿼럼은 동시 쓰기를 막지 않는다. 두 클라이언트가 같은 키를 동시에 쓰면 복제본마다 다른 값이 남고, 누군가 이를 정리해야 한다. [앞 글](/posts/cs/distributed/replication-cap-pacelc/)에서 예고한 충돌 해소 방법을 비교하면 이렇다.

| 방법 | 동작 | 얻는 것 | 잃는 것 |
| --- | --- | --- | --- |
| LWW (last-write-wins) | 타임스탬프가 큰 값만 남긴다 | 단순, 메타데이터가 작다 | 진 쪽 쓰기가 에러 없이 사라진다 |
| 형제 값 보관 + 버전 벡터 | 동시 쓰기를 모두 남기고 읽을 때 합친다 | 손실이 없다 | 애플리케이션이 병합 로직을 짜야 한다 |
| CRDT(Conflict-free Replicated Data Type) | 어떤 순서로 합쳐도 결과가 같은 자료구조. 예: 원소를 추가만 하는 집합 | 자동 병합, 손실 없음 | 표현할 수 있는 연산이 제한된다 |
| CAS (합의 기반) | 조건이 맞을 때만 쓴다 | 선형화 가능한 갱신 | 왕복 증가, 분할 시 소수 쪽 불가용 |

LWW가 실제로 얼마나 잃는지는 Kyle Kingsbury(aphyr)의 Jepsen Cassandra 분석이 숫자로 보여준다. 이 결과는 Cassandra 2.0 무렵 버전 기준이고, 현재 버전의 동작과는 다를 수 있다.

**한 셀을 반복 갱신하는 테스트.** 시계를 완벽히 맞추고, QUORUM 일관성과 외부 락 서비스까지 써서 LWW로 한 셀을 갱신했다. 2000건 중 1009건이 성공 응답을 받았지만 724건만 살아남았다. 확인된 쓰기 285건이 사라졌다. 저자는 댓글에서 이 실행이 분할된 클러스터에서 나왔다고 밝힌다. 원인으로 그는 LWW가 정보를 비결정적으로 버린다는 점을 든다. Cassandra는 쓰기 왕복을 줄이려고 벡터 시계 대신 LWW를 택했고, 그래서 한 셀을 안전하게 고쳐 쓸 방법이 없다는 것이다.

**CQL set에 원소를 추가하는 테스트.** 같은 셀을 덮어쓰지 않고 집합에 원소를 더하게 바꾸자 2000건이 모두 확인되고 모두 살아남았다. 읽고 고쳐 쓰는 모델은 위험하고, 추가만 하는 모델은 안전하다는 대비다.

**Paxos 기반 경량 트랜잭션(CAS) 테스트.** 829건이 확인됐고 그중 3건이 사라졌다. 저자는 이 문제를 보이는 데 네트워크 분할조차 필요 없다고 썼다. 합의를 쓴다는 설계와 구현이 맞다는 사실은 별개라는 점도 보여준다.

이 실험에서 나오는 실무 진단 순서는 이렇다. QUORUM으로 읽고 쓰는데 성공한 쓰기가 사라진다면 먼저 충돌 해소가 LWW인지 본다. 다음으로 읽기-수정-쓰기(read-modify-write)를 일반 쓰기로 구현했는지, 타임아웃된 쓰기를 재시도하면서 순서가 꼬였는지, 느슨한 쿼럼 설정이 켜져 있는지 확인한다.

## 8. 트레이드오프 정리

| 방식 | 보장 | 얻는 것 | 잃는 것 |
| --- | --- | --- | --- |
| 합의 기반 (Raft, Paxos) | 선형화, CAS 가능 | "쓴 값을 읽는다"는 직관적 의미 | 리더·다수결 왕복으로 지연 증가, 분할 시 소수 쪽 불가용 |
| 쿼럼 + ABD 읽기 write-back | 읽기·블라인드 쓰기의 선형화 | 리더 없이 선형화된 읽기·쓰기 | 왕복 증가, CAS 불가 |
| 단순 쿼럼 $R + W > N$ | 완료된 쓰기를 이후 읽기가 본다. 선형화는 아님 | 조절 가능한 지연과 가용성 | 4절의 값 역행, 모호한 실패, LWW 손실 |
| `R = W = 1` | 최종 일관성 | 가장 짧은 지연, 가장 높은 가용성 | 옛 값 읽기, 충돌 해소 부담 |

어느 줄을 고를지는 "지금 이 값"에 근거해 결정하는 코드가 있는지로 정한다. 사용자 이름 선점, 재고, 락처럼 그런 코드가 있으면 합의 기반이 필요하다. 조회수, 피드, 장바구니처럼 잠깐 어긋나도 되고 합칠 수 있는 데이터라면 쿼럼이나 최종 일관성이 지연과 가용성 면에서 낫다.

이 선택은 [앞 글](/posts/cs/distributed/replication-cap-pacelc/)의 PACELC와 같은 축 위에 있다. 분할 중에는 가용성과 일관성 사이에서, 분할이 없을 때는 지연과 일관성 사이에서 고른다. R과 W는 그 축 위의 위치를 정하는 손잡이다.

## 결론

- 일관성 모델은 읽기가 돌려줄 수 있는 값에 대한 약속이다. 선형화 가능성은 그중 가장 강한 단일 객체 모델로, 복사본이 하나뿐인 것처럼 보이고 실시간 순서를 지킨다.
- $R + W > N$이 보장하는 것은 "완료된 쓰기를 그 뒤의 읽기가 본다"까지다. 진행 중이거나 모호하게 실패한 쓰기에 대해서는 약속이 없다.
- N=3, W=2, R=2에서도 한 읽기가 1을 본 뒤 다음 읽기가 0을 보는 값 역행이 생긴다. 장애 없이 네트워크 지연만으로 생긴다.
- 읽기가 값을 돌려주기 전에 쿼럼에 다시 써 두면(ABD) 읽기와 블라인드 쓰기는 선형화된다. CAS까지 필요하면 합의가 있어야 한다.
