## 개요

[앞 글](/posts/cs/os/deadlock-priority-inversion)까지는 프로세스와 동기화를 다뤘다. 이번 글부터는 메모리로 넘어간다. 첫 주제는 모든 메모리 접근 밑에 깔려 있는 가상 메모리다.

이 글이 답하는 질문은 두 가지다.

- 프로그램이 쓰는 주소는 어떻게 실제 RAM 위치로 바뀌고, 그 변환은 왜 느리지 않은가?
- `malloc`으로 1GB를 받았는데 RSS가 거의 안 늘어나는 이유는 무엇이고, 보안 패치 뒤에 sys CPU가 오르는 이유는 무엇인가?

여기서 RSS(resident set size)는 프로세스가 지금 실제로 차지하고 있는 물리 메모리 크기다. 이 글은 x86-64와 Linux를 기준으로 설명한다.

---

## 1. 왜 가상 메모리인가

프로그램 두 개가 RAM을 직접 주소로 쓴다고 해 보자. A는 `0x1000` 번지에 계좌 잔액을 저장한다. B도 우연히 같은 `0x1000` 번지에 로그 버퍼를 둔다. B가 로그를 쓰는 순간 A의 잔액이 깨진다.

물리 주소를 직접 쓰면 문제가 세 가지 생긴다.

- **격리가 없다.** 다른 프로세스나 커널의 메모리를 그냥 읽고 쓸 수 있다.
- **배치가 어렵다.** 프로그램마다 겹치지 않는 주소를 미리 정해야 한다.
- **RAM보다 큰 공간을 못 쓴다.** 물리 메모리가 8GB면 주소도 8GB까지만 쓸 수 있다.

**가상 메모리**(virtual memory)는 프로세스마다 독립된 가짜 주소 공간을 주고, CPU가 그 주소를 실제 주소로 바꿔 주는 추상화다. 프로그램이 보는 주소를 가상 주소(virtual address), RAM의 실제 위치를 물리 주소(physical address)라고 부른다. 변환은 CPU 안의 하드웨어인 MMU(Memory Management Unit)가 한다.

핵심 아이디어는 한 문장이다. **모든 메모리 접근 사이에 "번역" 단계를 끼워 넣고, 그 번역표를 커널이 관리한다.**

이렇게 하면 앞의 세 문제가 풀린다.

| 문제 | 가상 메모리가 푸는 방법 |
| --- | --- |
| 격리 | A의 `0x1000`과 B의 `0x1000`이 서로 다른 물리 위치로 번역된다 |
| 배치 | 모든 프로세스가 같은 가상 주소 배치를 써도 된다 |
| 큰 주소 공간 | 아직 RAM에 없는 영역은 "없음"으로 표시해 두고, 필요할 때 채운다(5절) |

대가는 분명하다. 메모리를 한 번 읽을 때마다 번역이 필요하다. 이 글의 나머지는 이 번역을 어떻게 싸게 만드는가에 대한 이야기다.

## 2. 페이지와 페이지 테이블: 48비트 주소를 9/9/9/9/12로 나누기

번역표를 바이트마다 두면 표가 메모리보다 커진다. 그래서 메모리를 고정 크기 덩어리로 잘라 덩어리 단위로 번역한다.

- **페이지**(page): 가상 주소 공간을 자른 고정 크기 덩어리. x86-64의 기본 크기는 4KiB(4,096바이트)다.
- **프레임**(page frame): 물리 메모리를 같은 크기로 자른 덩어리.
- **페이지 테이블**(page table): "가상 페이지 몇 번이 물리 프레임 몇 번에 있는가"를 적은 표. 프로세스마다 하나씩 있다.

4KiB는 $2^{12}$바이트다. 그래서 주소의 아래 12비트는 페이지 안의 위치(오프셋)이고, 번역할 필요가 없다. 위쪽 비트만 페이지 번호로 번역하면 된다.

핵심 아이디어는 이것이다. **주소의 위쪽 비트는 "어느 페이지인가", 아래 12비트는 "페이지 안 어디인가"를 뜻한다.**

### 4단계 페이징의 주소 분할

x86-64의 4단계 페이징은 가상 주소 48비트를 쓴다. $2^{48}$바이트는 256TiB이고, 커널 문서도 4단계 페이징의 가상 주소 공간을 256TiB로 적고 있다. 64비트 레지스터 중 위 16비트는 47번 비트를 복사한 값(부호 확장)이라 번역에 쓰이지 않는다.

48비트는 이렇게 나뉜다.

```
 47      39 38      30 29      21 20      12 11           0
+----------+----------+----------+----------+--------------+
|   PML4   |   PDPT   |    PD    |    PT    |    offset    |
|  9 bits  |  9 bits  |  9 bits  |  9 bits  |   12 bits    |
+----------+----------+----------+----------+--------------+
```

왜 하필 9비트씩일까? 테이블 하나를 페이지 하나(4KiB)에 딱 맞추기 위해서다.

- 엔트리 하나는 8바이트다(64비트 주소와 플래그).
- 4,096 / 8 = 512개의 엔트리가 페이지 하나에 들어간다.
- $512 = 2^9$이므로 인덱스는 9비트면 된다.

Linux 커널 소스(`pgtable_64_types.h`)도 각 단계의 엔트리 수를 512로, 단계별 시프트를 12 -> 21 -> 30 -> 39로 정의한다. 12에 9씩 더해 가는 구조다.

### 주소 하나를 직접 쪼개 보기

가상 주소 `0x00007f1234567abc`를 예로 들자. 아래 48비트를 2진수로 쓰고 9/9/9/9/12로 자르면 다음과 같다.

```
binary : 011111110 001001000 110100010 101100111 101010111100
field  : PML4      PDPT      PD        PT        offset
value  : 254       72        418       359       0xabc
```

CPU는 이 숫자를 가지고 표를 네 번 따라간다. 이 과정을 **페이지 워크**(page walk)라고 한다.

```
CR3 register = physical address of the PML4 table
 |
 v
+----------------+
|  PML4 table    |   entry[254] -> address of a PDPT table   (read 1)
+----------------+
 |
 v
+----------------+
|  PDPT table    |   entry[72]  -> address of a PD table     (read 2)
+----------------+
 |
 v
+----------------+
|  PD table      |   entry[418] -> address of a PT table     (read 3)
+----------------+
 |
 v
+----------------+
|  PT table      |   entry[359] -> frame number (PFN)        (read 4)
+----------------+
 |
 v
physical address = PFN * 4096 + 0xabc
```

**CR3**는 지금 실행 중인 프로세스의 최상위 테이블 위치를 담는 CPU 레지스터다. 프로세스를 바꾸면 커널이 CR3 값을 바꾼다. 그러면 같은 가상 주소라도 다른 물리 주소로 번역된다. 1절의 격리가 이렇게 구현된다.

각 엔트리에는 주소 말고 플래그도 들어 있다. 대표적인 것이 present 비트(이 페이지가 지금 RAM에 있는가), 쓰기 허용 비트, 사용자 모드 접근 허용 비트다. 이 플래그가 5절의 페이지 폴트와 6절의 KPTI로 이어진다.

참고로 Intel 문서의 이름(PML4, PDPT, PD, PT)과 Linux 커널의 이름은 다르다. 커널은 5단계까지 표현할 수 있게 PGD, P4D, PUD, PMD, PTE라는 이름을 쓰고, 4단계 시스템에서는 P4D를 접어서(fold) 없는 것처럼 다룬다. 4단계 기준으로 PML4는 PGD, PDPT는 PUD, PD는 PMD, PT는 PTE 단계에 해당한다.

## 3. 멀티레벨인 이유: 단일 테이블의 메모리 계산

표를 네 번 따라가는 것은 느려 보인다. 표 하나에 모든 페이지를 적어 두면 한 번에 찾을 수 있다. 왜 그렇게 하지 않을까? 직접 계산해 보면 바로 답이 나온다.

### 단일 테이블로 만들면

- 48비트 주소 공간의 페이지 수: $2^{48} / 2^{12} = 2^{36}$ = 약 687억 개
- 엔트리 8바이트씩: $2^{36} \times 8 = 2^{39}$바이트 = **512GiB**

프로세스 하나의 번역표가 512GiB다. 그것도 프로세스마다 하나씩 필요하다. 엔트리 대부분이 "안 씀"이라도 배열이라서 자리는 다 차지한다.

### 멀티레벨로 만들면

핵심 아이디어는 한 문장이다. **쓰지 않는 영역은 하위 테이블을 아예 만들지 않는다.**

상위 엔트리가 "없음"이면 그 아래 512개, 그 아래 512 x 512개의 테이블이 통째로 생략된다. 실제 프로세스는 256TiB 중 아주 작은 조각만 쓰기 때문에 이 생략 효과가 크다.

작은 프로세스로 세어 보자. 아래 세 영역만 쓰고, 각 영역은 2MiB 이하라고 가정한다.

| 영역 | 가상 주소 근처 | PML4 인덱스 | PDPT 인덱스 | PD 인덱스 |
| --- | --- | --- | --- | --- |
| 코드 | `0x0000000000400000` | 0 | 0 | 2 |
| 힙 | `0x0000000002000000` | 0 | 0 | 16 |
| 스택 | `0x00007fffffff0000` | 255 | 511 | 511 |

필요한 테이블을 단계별로 센다.

- PML4: 항상 1개
- PDPT: PML4 인덱스가 0과 255 두 종류이므로 2개
- PD: 각 PDPT에서 쓰는 인덱스가 하나씩이므로 2개
- PT: PD 엔트리가 2, 16, 511 세 곳이므로 3개

합계 8개 x 4KiB = **32KiB**다. 512GiB와 비교하면 $2^{24}$분의 1, 약 1,680만 분의 1이다.

### 그래서 생기는 문제

공짜는 아니다. 트레이드오프를 표로 정리하면 이렇다.

| 방식 | 얻는 것 | 잃는 것 |
| --- | --- | --- |
| 단일 테이블 | 번역 한 번에 메모리 1회 참조 | 프로세스마다 512GiB. 현실적으로 불가능 |
| 4단계 테이블 | 쓰는 만큼만 테이블 메모리 사용 | 번역 한 번에 메모리 최대 4회 참조 |

메모리를 한 번 읽으려고 메모리를 네 번 더 읽어야 한다면 프로그램이 다섯 배 느려진다. 이 비용을 지우는 장치가 다음 장의 TLB다.

## 4. TLB

### 왜 필요한가

3절의 결론은 "번역 한 번에 메모리 4회"였다. 그런데 프로그램은 같은 페이지를 반복해서 쓴다. 배열을 순회하면 4KiB 안의 512개 `long` 값이 모두 같은 페이지에 있다. 같은 번역을 512번 다시 할 이유가 없다.

### 핵심 아이디어

**TLB**(Translation Lookaside Buffer)는 최근에 한 번역 결과를 저장하는 CPU 안의 작은 하드웨어 캐시다. 키는 가상 페이지 번호(VPN, virtual page number), 값은 물리 프레임 번호(PFN, page frame number)와 권한 플래그다.

### 단계별 동작

1. CPU가 가상 주소에서 오프셋을 뺀 페이지 번호로 TLB를 찾는다.
2. **TLB 적중**(hit)이면 바로 물리 주소를 만든다. 추가 메모리 참조는 없다.
3. **TLB 미스**(miss)면 2절의 페이지 워크를 한다. x86에서는 하드웨어가 직접 표를 따라간다.
4. 찾은 결과를 TLB에 넣고, 다음 접근부터는 적중한다.

미스가 나도 항상 DRAM을 네 번 읽는 것은 아니다. 페이지 테이블 엔트리도 일반 데이터처럼 CPU 캐시에 올라가 있을 수 있기 때문이다. 그래도 적중에 비하면 훨씬 비싸다.

### TLB가 덮는 범위: reach

TLB는 작다. 그래서 "TLB가 한꺼번에 기억할 수 있는 메모리 크기"가 중요하다. 이것을 **TLB reach**라고 부르고, 엔트리 수 x 페이지 크기로 계산한다.

설명을 위해 엔트리가 1,536개인 TLB를 가정해 보자(실제 개수는 CPU마다 다르다).

- 4KiB 페이지: 1,536 x 4KiB = 6MiB

작업 집합이 6MiB 안이면 거의 모든 접근이 적중한다. 하지만 10GiB짜리 해시 테이블을 무작위로 찌르는 서버라면 대부분의 접근이 TLB 밖으로 나간다. 데이터는 L3 캐시에 있어도 번역이 미스라 느려지는 상황이 생긴다. 이 문제는 7절의 huge page가 다룬다.

### 그래서 생기는 문제

**컨텍스트 스위치.** TLB 엔트리는 "지금 CR3가 가리키는 주소 공간"의 번역이다. 다른 프로세스로 바꾸면 이전 번역은 틀린 값이 된다. 태그가 없으면 TLB를 비워야 하고, 전환 직후 한동안 미스가 몰린다.

이를 줄이는 장치가 **PCID**(Process-Context Identifier)다. TLB 엔트리마다 주소 공간 번호를 붙여서, 현재 번호와 맞는 엔트리만 쓰게 한다. 그러면 전환할 때 TLB를 통째로 비우지 않아도 된다. 같은 프로세스의 스레드끼리 전환할 때는 주소 공간이 같아서 이 비용이 아예 없다. 스레드 전환이 프로세스 전환보다 싼 이유 중 하나다. 자세한 비교는 [프로세스 vs 스레드 글](/posts/cs/os/process-vs-thread-context-switching)에 있다.

**TLB shootdown.** 멀티코어에서는 같은 프로세스의 스레드가 여러 코어에서 돈다. 한 코어가 `munmap`이나 `mprotect`로 매핑을 바꾸면 다른 코어 TLB에 남은 옛 번역도 지워야 한다. 커널은 해당 코어들에 IPI(inter-processor interrupt, 코어 간 인터럽트)를 보내고 처리가 끝나기를 기다린다. 대상 코어가 많을수록 기다리는 시간이 길어진다. 스레드가 많은 프로세스가 매핑을 자주 바꾸면 코어를 늘려도 성능이 덜 오르는 이유다. 메모리 풀을 재사용해 `munmap` 횟수를 줄이는 것이 흔한 완화책이다.

## 5. 페이지 폴트와 demand paging

### 왜 필요한가

프로세스가 1GiB를 `malloc`하거나 큰 파일을 `mmap`할 때마다 그만큼 RAM을 즉시 잡고 0으로 채운다고 해 보자. 두 가지가 문제다.

- **시작이 느리다.** 쓰지도 않을 메모리를 0으로 채우느라 시간을 쓴다.
- **메모리가 낭비된다.** 큰 버퍼를 잡아 두고 일부만 쓰는 프로그램이 흔하다.

### 핵심 아이디어

**demand paging**은 페이지를 실제로 처음 건드릴 때 물리 메모리를 붙이는 방식이다. 커널은 할당 요청 때는 "이 범위는 써도 된다"는 기록만 남기고 페이지 테이블 엔트리는 비워 둔다.

그러면 처음 접근할 때 CPU는 present 비트가 0인 엔트리를 만난다. CPU는 번역을 멈추고 커널로 넘어간다. 이것이 **페이지 폴트**(page fault)다. 이름은 "fault"지만 대부분은 오류가 아니라 정상적인 동작의 일부다.

### 단계별 동작: 100MiB를 잡고 건드리기

익명 메모리(파일과 연결되지 않은 메모리) 100MiB를 `mmap`한 뒤 4KiB마다 1바이트씩 쓴다고 하자. 7절의 THP는 꺼져 있다고 가정한다.

1. `mmap` 직후: VSZ(가상 메모리 크기)는 100MiB 늘어난다. RSS는 거의 그대로다. 아직 프레임을 하나도 붙이지 않았기 때문이다.
2. 첫 페이지에 쓰기: present 비트가 0이라 페이지 폴트가 난다.
3. 커널 처리: 이 주소가 허용된 범위인지 확인한다. 빈 프레임 하나를 0으로 채우고, 페이지 테이블 엔트리에 그 프레임을 적고 present를 1로 만든다.
4. 복귀: 쓰기 명령을 다시 실행한다. 이번에는 번역이 성공한다.
5. 끝까지 반복: 100MiB / 4KiB = 25,600페이지이므로 폴트도 약 25,600번 난다. 끝나면 RSS가 약 100MiB 늘어 있다.

이 과정에서 디스크는 한 번도 읽지 않았다. 이런 폴트를 minor fault라고 부른다.

### minor fault와 major fault

`getrusage(2)` 매뉴얼은 두 종류를 이렇게 구분한다. **minor fault**는 I/O 없이 처리된 페이지 폴트이고, **major fault**는 I/O가 필요했던 페이지 폴트다.

| 종류 | 예시 상황 | 커널이 하는 일 | 비용 |
| --- | --- | --- | --- |
| minor | 새로 할당한 익명 메모리에 처음 접근 | 빈 프레임을 0으로 채워 연결 | 커널 진입 + 페이지 한 장 처리 |
| minor | `mmap`한 파일 페이지가 이미 페이지 캐시에 있음 | 캐시 프레임을 연결만 함 | 위와 비슷 |
| minor | `fork` 뒤 공유 페이지에 쓰기(Copy-on-Write) | 페이지를 복사해 따로 연결 | 복사 4KiB 추가 |
| major | `mmap`한 파일 페이지가 페이지 캐시에 없음 | 디스크에서 읽어 옴 | 디스크 I/O를 기다림 |
| major | 스왑으로 내보낸 페이지에 다시 접근 | 스왑 영역에서 읽어 옴 | 디스크 I/O를 기다림 |
| 오류 | 허용되지 않은 주소나 권한 위반 | 프로세스에 `SIGSEGV` 전달 | 프로세스 종료가 보통 |

Copy-on-Write 폴트는 [fork와 Copy-on-Write 글](/posts/cs/os/fork-copy-on-write)에서 Redis 예시로 자세히 다룬다.

둘의 차이는 "기다림의 종류"다. minor fault는 CPU가 일하는 시간이고, major fault는 디스크를 기다리는 시간이다. 그래서 major fault가 보이면 지연 시간이 크게 튈 수 있다.

### 직접 세어 보기

Linux의 `ps`는 프로세스별 누적 폴트 수를 보여 준다. `min_flt`와 `maj_flt` 열이다.

```bash
# 프로세스 1234의 누적 minor/major fault 수와 메모리 크기(KiB)
ps -o pid,min_flt,maj_flt,rss,vsz,comm -p 1234

# 명령 하나를 실행하는 동안의 폴트 수
perf stat -e page-faults,minor-faults,major-faults -- ./my-app
```

읽는 법은 간단하다.

- `min_flt`가 꾸준히 오른다: 메모리를 새로 쓰고 있다는 뜻이다. 대개 정상이다.
- `maj_flt`가 계속 오른다: 필요한 페이지가 RAM에 없어서 디스크에서 읽고 있다. 메모리가 부족해 커널이 페이지를 내보내고 있을 가능성이 크다.

### 그래서 생기는 문제

**첫 접근 지연.** demand paging은 비용을 없애는 것이 아니라 첫 접근 시점으로 미룬다. 지연에 민감한 서버라면 요청을 처리하는 도중에 폴트가 몰릴 수 있다. 그래서 시작할 때 미리 건드려 두는 방법을 쓴다. `mmap`의 `MAP_POPULATE` 플래그나 JVM의 `-XX:+AlwaysPreTouch` 옵션이 그런 예다.

**major fault 폭증.** RAM이 모자라면 커널은 어떤 페이지를 내보낼지 골라야 한다. 잘못 고르면 곧 다시 쓸 페이지를 내보내고, 바로 major fault로 다시 읽어 온다. 어떤 페이지를 내보낼지 정하는 방법은 [페이지 교체 알고리즘 글](/posts/cs/os/page-replacement-algorithms)에서 다룬다.

## 6. KPTI의 비용

### 왜 필요했나

Linux는 원래 모든 프로세스의 주소 공간 위쪽에 커널 메모리를 함께 매핑해 두었다. 커널 페이지의 엔트리는 "사용자 모드 접근 금지" 플래그로 막혀 있다. 이렇게 하면 시스템 콜(syscall)로 커널에 들어갈 때 CR3를 바꿀 필요가 없어서 빠르다.

2018년 1월에 공개된 **Meltdown**(CVE-2017-5754)은 이 전제를 깼다. CPU는 권한 검사 결과가 나오기 전에 다음 명령을 미리 실행한다. 이것을 추측 실행(speculative execution)이라고 한다. 미리 실행한 결과는 나중에 버려지지만, 그동안 건드린 캐시 상태는 남는다. 공격자는 이 흔적을 시간 측정으로 읽어 커널 메모리 내용을 알아낸다. 추측 실행 자체는 [파이프라인과 분기 예측 글](/posts/cs/architecture/pipeline-branch-prediction-spectre)에서 다룬다.

플래그로 막아도 매핑이 있는 한 새는 것이다. 그렇다면 매핑 자체를 없애야 한다.

### 핵심 아이디어

**KPTI**(Kernel Page-Table Isolation)는 사용자 모드로 실행하는 동안 커널 매핑을 페이지 테이블에서 거의 다 빼 두는 방법이다. 처음 이름은 KAISER였다.

### 단계별 동작

프로세스마다 페이지 테이블을 두 벌 둔다.

```
                     user-mode table      kernel-mode table
                     ----------------     -----------------
user memory          mapped               mapped
kernel entry code    mapped (minimal)     mapped
rest of the kernel   NOT mapped           mapped


[ CR3 = user table ]      running user code
        |
        |  syscall / interrupt -> write CR3
        v
[ CR3 = kernel table ]    kernel work
        |
        |  return to user -> write CR3
        v
[ CR3 = user table ]      running user code
```

1. 사용자 코드가 도는 동안에는 사용자용 테이블을 쓴다. 커널 쪽은 진입과 복귀에 필요한 최소한의 코드와 데이터만 매핑되어 있다.
2. syscall, 인터럽트, 예외로 커널에 들어오면 먼저 CR3를 커널용 테이블로 바꾼다.
3. 커널 일을 마치고 사용자 모드로 돌아가기 전에 CR3를 다시 사용자용으로 바꾼다.

사용자 모드에는 커널 매핑이 없으니, 추측 실행으로도 번역할 주소가 없다.

### 비용은 어디서 나오나

커널 문서(`Documentation/arch/x86/pti`)가 꼽는 비용 중 성능에 직접 닿는 것은 이렇다.

| 비용 | 내용 |
| --- | --- |
| CR3 쓰기 | 커널 진입과 복귀마다 CR3를 바꾼다. 커널 문서는 한 번에 100사이클 단위, LWN은 syscall당 수백 사이클이 더 든다고 적는다 |
| TLB flush | PCID가 없으면 CR3를 쓸 때마다 TLB 전체가 비워진다. syscall 한 번마다 4절의 미스 폭풍이 온다 |
| global page 해제 | 커널 TLB 엔트리를 모든 프로세스가 공유하던 최적화를 일부 끈다. 문서는 손실이 1%를 넘지 않는다고 적는다 |
| 메모리 | 최상위 테이블이 두 벌이라 프로세스마다 4KiB가 더 든다 |

가장 큰 변수는 두 번째 줄이다. PCID가 있으면 사용자 테이블과 커널 테이블의 엔트리에 서로 다른 태그를 붙여, CR3를 바꿔도 TLB를 유지할 수 있다. Linux는 4.14 개발 주기에 PCID 지원을 넣었다.

### 얼마나 느려지나

비용은 "커널을 얼마나 자주 드나드는가"에 비례한다. 계산 위주 작업은 거의 영향이 없다. 작은 syscall을 많이 하는 I/O 서버가 가장 크게 맞는다.

공개된 수치는 다음과 같다.

- LWN은 KAISER 패치 당시 전형적인 손실을 한 자릿수, 대략 5%로 소개했다. 가장 나쁜 사례는 syscall과 컨텍스트 스위치가 많은 loopback 네트워킹 테스트로, 약 30% 느려졌다.
- Brendan Gregg의 분석에 따르면 CPU당 초당 syscall이 5만 번이면 손실이 약 2%이고, 그보다 많으면 더 커진다. CPU당 초당 1만 번 미만이면 0.5% 미만으로 무시할 만하다고 봤다.
- 같은 분석에서 작업 집합이 10MB를 넘으면 TLB flush 때문에 비용이 더 붙는다. 한 예시에서 PCID가 없는 커널의 손실 약 2.1%가 PCID가 있는 4.14에서 약 0.5%로 줄었다.

정리하면 KPTI 비용은 syscall 빈도, 컨텍스트 스위치 빈도, 작업 집합 크기, 그리고 PCID 유무로 결정된다. 하나의 숫자로 말하기 어렵다.

### 내 서버에서 확인하기

보안 패치 뒤 트래픽은 같은데 sys CPU가 올랐다면 다음을 본다.

```bash
# Meltdown 대응 상태. "Mitigation: ..."이면 대응이 켜져 있다
cat /sys/devices/system/cpu/vulnerabilities/meltdown

# CPU가 PCID를 지원하는가
grep -o -w pcid /proc/cpuinfo | head -1

# 초당 컨텍스트 스위치(cs 열)와 sys CPU(sy 열)
vmstat 1
```

대응은 위험한 것부터 피한다.

- **syscall 수를 줄인다.** 작은 `read`/`write`를 버퍼링해 묶고, 배치 I/O를 쓴다. 가장 안전하고 효과도 크다.
- **영향 없는 CPU를 쓴다.** Meltdown에 취약하지 않은 CPU에서는 위 파일이 `Not affected`로 나오고 KPTI가 켜지지 않는다.
- **끄는 것은 마지막이다.** `nopti` 부팅 옵션으로 끌 수 있지만, 신뢰하지 않는 코드가 같은 머신에서 돌 수 있다면 끄면 안 된다. 위협 모델을 따져 본 뒤에만 고려한다.

## 7. huge page

### 왜 필요한가

4절에서 계산한 TLB reach는 6MiB였다. 메모리를 수십 GiB 쓰는 데이터베이스나 인메모리 캐시는 이 범위를 훌쩍 넘는다. 번역 미스가 계속 나고, 매번 페이지 워크를 한다.

### 핵심 아이디어

**huge page**는 페이지 하나의 크기를 키워서, TLB 엔트리 하나가 더 넓은 범위를 덮게 하는 방법이다. x86-64에서는 2MiB와 1GiB를 쓴다. 커널 문서도 huge page가 보통 2MiB에서 1GiB이며 각각 PMD와 PUD 엔트리로 매핑된다고 적는다.

2절의 구조로 보면 간단하다. 2MiB 페이지는 PD 단계에서 워크가 끝난다. 마지막 PT 단계가 없어지고, 남은 21비트(9 + 12)가 전부 오프셋이 된다.

```
4 KiB page : PML4 -> PDPT -> PD -> PT -> frame     offset 12 bits
2 MiB page : PML4 -> PDPT -> PD -> frame           offset 21 bits
1 GiB page : PML4 -> PDPT -> frame                 offset 30 bits
```

### 숫자로 보기

4절과 같이 엔트리 1,536개짜리 TLB를 가정한다. 실제 CPU는 huge page용 엔트리를 따로, 더 적게 두는 경우가 많으니 아래 표는 원리를 보이는 계산으로만 읽자.

| 페이지 크기 | TLB reach | 미스 때 워크 단계 |
| --- | --- | --- |
| 4KiB | 1,536 x 4KiB = 6MiB | 4 |
| 2MiB | 1,536 x 2MiB = 3GiB | 3 |
| 1GiB | 1,536 x 1GiB = 1.5TiB | 2 |

2MiB 페이지는 같은 엔트리 수로 512배 넓은 범위를 덮는다. 미스가 줄고, 미스가 나도 한 단계 덜 걷는다. 폴트 횟수도 줄어든다. 5절의 100MiB 예시라면 4KiB 페이지는 폴트가 25,600번이지만 2MiB 페이지는 50번이다.

6절의 KPTI와도 이어진다. Brendan Gregg의 같은 분석에서는 huge page를 쓰자 KPTI 손실이 사라지고 오히려 약 3% 빨라진 예시가 나온다. TLB 엔트리가 덜 필요하니 flush의 타격도 줄어든 것이다.

### 쓰는 방법 두 가지

| 방식 | 동작 | 특징 |
| --- | --- | --- |
| hugetlbfs | 관리자가 huge page를 미리 예약하고, 애플리케이션이 명시적으로 요청한다 | 예측 가능하다. 예약한 메모리는 다른 용도로 못 쓴다 |
| THP(Transparent Huge Pages) | 커널이 알아서 2MiB 페이지를 할당하거나, `khugepaged`가 4KiB 페이지들을 2MiB로 합친다 | 코드 수정이 필요 없다. 동작이 덜 예측 가능하다 |

THP 모드는 `/sys/kernel/mm/transparent_hugepage/enabled`에서 고른다. 값은 `always`(가능하면 항상), `madvise`(애플리케이션이 `madvise`로 요청한 영역만), `never`(끔) 세 가지다.

### 그래서 생기는 문제

**메모리 낭비.** 1바이트만 써도 2MiB가 붙을 수 있다. 커널 문서도 4KiB면 될 곳에 2MiB 페이지가 할당될 수 있다고 경고한다. 희소하게 쓰는 프로그램은 RSS가 크게 늘 수 있다. 메모리가 빠듯한 시스템에서 `madvise` 모드를 쓰는 이유다.

**연속 메모리와 지연.** 2MiB 페이지는 물리적으로도 연속된 2MiB가 필요하다. 오래 돈 시스템은 메모리가 조각나 있어서 커널이 페이지를 옮겨 빈 공간을 만들어야 한다(compaction). THP의 `defrag` 설정이 `always`면 할당하는 스레드가 이 작업이 끝날 때까지 멈출 수 있다. 평소에는 빠르다가 가끔 지연이 튀는 원인이 된다.

트레이드오프를 정리하면 이렇다.

| 선택 | 얻는 것 | 잃는 것 |
| --- | --- | --- |
| 4KiB 페이지 | 세밀한 보호, 적은 낭비 | 좁은 TLB reach, 큰 작업 집합에서 미스 증가 |
| 2MiB/1GiB 페이지 | 넓은 TLB reach, 짧은 워크, 적은 폴트 | 내부 낭비, 연속 메모리 필요, compaction 지연 |

## 결론

- 가상 메모리는 모든 메모리 접근에 번역을 끼워 넣어 격리와 큰 주소 공간을 얻는다. x86-64는 48비트 주소를 9/9/9/9/12로 잘라 4단계 표를 따라간다.
- 표를 여러 단계로 나눈 이유는 메모리다. 단일 표는 프로세스마다 512GiB지만, 멀티레벨은 쓰는 영역만큼만 표를 만든다. 대가인 "미스당 최대 4회 참조"는 TLB가 숨긴다.
- 페이지는 처음 건드릴 때 붙는다(demand paging). I/O 없이 끝나는 minor fault는 흔하고 정상이다. 디스크를 기다리는 major fault가 계속 오르면 메모리 부족을 의심한다.
- KPTI는 커널 진입과 복귀마다 CR3를 바꾸는 비용을 낸다. syscall이 잦을수록, PCID가 없을수록 비싸다.
- huge page는 TLB 엔트리 하나가 덮는 범위를 512배 넓힌다. 대신 메모리 낭비와 compaction 지연을 감수해야 한다.

[다음 글](/posts/cs/os/fork-copy-on-write)에서는 이 페이지 테이블과 페이지 폴트를 이용해 `fork()`가 메모리를 복사하지 않고도 자식 프로세스를 만드는 Copy-on-Write를 본다.
