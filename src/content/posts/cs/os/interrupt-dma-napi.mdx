## 개요

[앞 글](/posts/cs/os/page-cache-fsync/)에서는 데이터가 메모리에서 디스크로 내려가는 길을 봤다. 이번 글은 반대 방향, 장치에서 들어온 데이터가 CPU와 메모리에 도착하는 길을 네트워크 수신으로 따라간다.

서버가 초당 수십만 개의 패킷을 받는다. 그런데 CPU 사용률은 100%인데 애플리케이션은 오히려 느려진다. 이럴 때 CPU는 "받은 패킷을 처리"하기보다 "패킷이 왔다는 알림을 처리"하는 데 시간을 쓰고 있을 수 있다.

이 글이 답하는 질문은 두 가지다.

- 패킷 하나는 NIC(네트워크 카드)에서 애플리케이션의 `read()`까지 어떤 경로로 가는가?
- 패킷마다 인터럽트를 받으면 왜 처리량이 올라가다 오히려 무너지고, NAPI는 이를 어떻게 막는가?

I/O 이벤트를 애플리케이션이 어떻게 기다리는지는 [epoll과 io_uring 글](/posts/cs/os/io-multiplexing-epoll-io-uring/)에서 다룬다. 이 글은 그보다 아래, 커널이 NIC에서 패킷을 꺼내는 구간을 다룬다.

---

## 1. 왜 필요한가: CPU가 바이트를 직접 옮길 수는 없다

장치와 CPU가 데이터를 주고받는 방식은 세 가지 개념으로 정리된다.

| 개념 | 하는 일 |
|------|---------|
| PIO(programmed I/O) | CPU가 명령어로 바이트를 하나씩 직접 옮긴다 |
| DMA(Direct Memory Access) | 장치가 CPU 없이 메모리에 직접 읽고 쓴다 |
| 인터럽트(interrupt) | 장치가 "일이 끝났다"고 CPU에 신호를 보낸다 |

PIO는 단순하지만, 10Gbps 링크를 받는 동안 CPU가 복사만 하게 된다. 그래서 현대 NIC는 **DMA로 데이터를 옮기고 인터럽트로 알린다.** CPU는 옮기는 일에서 빠지고, 알림만 받는다.

문제는 알림의 횟수다. 10Gbps 이더넷에서 가장 작은 프레임은 64B이고, 여기에 프리앰블과 프레임 간격이 붙어 선로에서는 84B(672비트)를 차지한다. 그러면 이론상 최대 속도는 다음과 같다.

```text
10,000,000,000 bit/s / 672 bit = 약 14,880,000 pps (초당 약 1488만 패킷)
1 / 14,880,000 s            = 약 67 ns 마다 패킷 1개
```

패킷마다 인터럽트를 받으면 67ns 안에 인터럽트 진입, 핸들러 실행, 복귀를 끝내야 한다. 인터럽트 진입에는 레지스터 저장과 캐시 오염 같은 고정 비용이 든다. 이 비용만으로 한도를 넘기 쉽다.

## 2. 패킷 하나가 소켓까지 가는 경로

수신 경로는 큐의 연속이다. 번호를 따라가 보자.

```text
 [NIC]
   |  (1) driver pre-fills RX ring with empty buffers
   v
 [RX ring in RAM]  <- descriptor + buffer, NIC=producer, driver=consumer
   ^
   |  (2) packet arrives: NIC writes it by DMA, marks descriptor "done"
   |
   |  (3) NIC raises hardirq (IRQ)
   v
 [hardirq handler]  mask RX IRQ, schedule NAPI poll
   |
   |  (4) softirq runs poll(): pop up to "budget" packets from ring
   v
 [IP / TCP / UDP stack]
   |
   |  (5) put payload into socket receive buffer
   v
 [socket buffer] ---- (6) application read() copies it out
```

각 단계를 풀어 쓰면 다음과 같다.

1. **링 준비.** 드라이버가 RX 링(수신 링)의 descriptor(버퍼 주소와 상태를 담은 작은 칸)마다 빈 버퍼의 메모리 주소를 채워 둔다. 링은 고정 크기 원형 큐다. NIC가 생산자, 드라이버가 소비자다.
2. **DMA 쓰기.** 패킷이 도착하면 NIC가 DMA로 그 버퍼에 직접 쓰고 descriptor 상태를 "완료"로 바꾼다. 이 시점에 CPU는 복사하지 않는다.
3. **인터럽트.** NIC가 하드웨어 인터럽트(hardirq)를 올린다.
4. **poll.** 커널은 소프트 인터럽트(softirq)로 poll 함수를 실행해 링에서 패킷을 꺼낸다.
5. **프로토콜 처리.** IP, TCP, UDP 계층을 거쳐 소켓 수신 버퍼에 들어간다.
6. **읽기.** 애플리케이션이 `read()`를 호출하면 그 데이터를 가져간다.

여기서 하드웨어 인터럽트와 소프트 인터럽트의 역할이 갈린다. hardirq 핸들러는 다른 인터럽트를 막은 채 돌기 때문에 최소한만 하고 끝내야 한다. 시간이 걸리는 실제 처리는 softirq로 미룬다.

## 3. 패킷마다 인터럽트를 받으면: 수신 라이브락

가장 단순한 방식은 패킷이 올 때마다 인터럽트를 받고 그 안에서 처리하는 것이다. 부하가 낮을 때는 이게 좋다. 패킷이 오는 즉시 처리하므로 지연이 짧다.

하지만 인터럽트는 보통 일반 프로세스보다 우선한다. 입력이 늘면 이런 일이 벌어진다.

1. 패킷이 빠르게 들어와 인터럽트가 계속 걸린다.
2. 커널은 인터럽트 핸들러를 돌리느라 소켓 버퍼를 비우는 쪽(앱, 상위 프로토콜 처리)에 CPU를 못 준다.
3. 소켓 버퍼가 가득 차면, 이미 인터럽트와 링 처리에 CPU를 쓴 패킷이 끝내 버려진다.
4. 일은 했는데 결과는 없는 상태가 된다.

1996년 Mogul과 Ramakrishnan의 논문은 이 상태를 **수신 라이브락**(receive livelock)이라 정의했다. 시스템이 인터럽트를 처리하느라 다른 필요한 일을 못 하는 상태다. 교착(deadlock)과 달리 멈춘 것은 아니어서 입력이 줄면 회복된다.

입력률과 실제 처리량의 관계를 그리면 이렇다. 모양만 보여 주는 개념도이고 실측값이 아니다.

```text
 throughput
 (delivered)
   ^
   |        .--------------- polling / NAPI / input limit: flat
   |      /
   |     /  .
   |    /     .   interrupt per packet:
   |   /        .   collapses after the peak
   |  /           .
   | /              .
   |/                 .
   +------------------------------------> offered load (pps)
          ^
          MLFRR (max loss-free receive rate)
```

정상 시스템은 손실 없이 받을 수 있는 최대 수신률(MLFRR) 이후에도 처리량이 평탄해야 한다. 처리 능력이 가득 찼을 뿐이기 때문이다. 라이브락 시스템은 입력이 늘수록 처리량이 줄어든다. 인터럽트 처리에 CPU를 다 쓰고 정작 상위 처리가 굶기 때문이다.

## 4. NAPI: 한가할 때는 인터럽트, 바쁠 때는 폴링

핵심 아이디어는 한 문장이다. **첫 패킷에서만 인터럽트를 받고, 그 뒤로는 인터럽트를 끈 채 직접 링을 훑어(polling) 처리하다가, 일이 바닥나면 인터럽트를 다시 켠다.**

리눅스의 NAPI가 이 구조다. 동작은 이렇다.

1. 패킷이 처음 도착하면 NIC가 IRQ를 올린다.
2. hardirq 핸들러는 그 큐의 RX IRQ를 끄고(mask) softirq에 poll을 예약한다.
3. poll은 한 번에 `budget`개까지 링에서 꺼내 처리한다.
4. 꺼낸 개수가 `budget`보다 적으면 일이 바닥난 것이다. 폴링을 끝내고 IRQ를 다시 켠다.
5. `budget`을 다 썼으면 아직 일이 남은 것이다. IRQ를 켜지 않고 다시 poll을 돈다.

의사 코드로 보면 짧다.

```text
hardirq(nic):                          # low load: start from an interrupt
  disable_rx_irq(nic)
  napi_schedule()                      # reserve poll in softirq

poll(budget):                          # high load: process by polling
  n = 0
  while n < budget and ring.has_packet():
      deliver(ring.pop()); n += 1
  if n < budget:                       # out of work -> back to interrupt mode
      napi_complete(); enable_rx_irq()
  return n                             # n == budget: poll again, no IRQ
```

커널 문서도 드라이버가 poll 대기 중에는 장치 인터럽트를 마스크한 채 두고, `napi_complete_done()`이 성공한 뒤에야 풀어야 한다고 설명한다. 한 번에 처리하는 Rx 패킷 수는 `budget`으로 제한된다.

효과는 단순하다. 부하가 높을수록 인터럽트가 줄고 폴링이 늘어난다. 패킷 한 개당 인터럽트 진입 비용을 내지 않고 여러 개를 묶어 처리하므로 패킷당 비용이 떨어진다. 또 `budget`이 있어서 poll 하나가 CPU를 무한정 쓰지도 않는다.

폴링 모드는 한가한 때에도 CPU를 쓸 수 있다는 약점이 있다. NAPI는 부하에 따라 두 모드를 오가며 이 약점을 피한다.

## 5. 패킷이 사라지는 지점과 확인 방법

수신 경로는 큐가 이어진 구조라 큐마다 가득 차는 지점이 있고, 지점마다 남는 흔적이 다르다.

| 번호 | 사라지는 곳 | 원인 | 확인 방법 |
|------|-------------|------|-----------|
| 1 | RX 링 | poll이 늦어 NIC가 쓸 곳이 없다 | `ethtool -S`의 rx_missed 계열(이름은 드라이버마다 다르다) |
| 2 | budget 소진 | 직접 버리지는 않지만, 처리하지 못한 패킷이 링에 남아 1번을 부른다 | `/proc/net/softnet_stat` 3열 time_squeeze |
| 3 | CPU 백로그 | CPU별 입력 큐(`netdev_max_backlog`)가 넘친다. RPS를 켰을 때 주로 지나는 큐다 | `softnet_stat` 2열 dropped |
| 4 | 소켓 버퍼 | 앱이 `read()`를 못 따라간다 | UDP는 RcvbufErrors 증가 |

`softnet_stat`은 CPU마다 한 줄이고 값은 16진수다. 커널 소스(`net/core/net-procfs.c`)를 보면 1열이 처리한 패킷 수, 2열이 백로그에서 버린 수, 3열이 time_squeeze다.

TCP는 4번에서 패킷을 버리기보다 수신 윈도우를 줄여 송신자를 늦춘다(흐름 제어). 1~3번은 TCP에서도 재전송 증가로 드러난다. 링의 소비자가 느릴수록 1번이 먼저 터진다. 가득 찬 원형 큐 문제가 하드웨어에서 일어나는 모습이다.

앱 로그에는 에러가 없는데 재전송이 늘고 `ethtool -S`의 수신 드롭 계열 카운터가 오른다면, 링이 작거나 poll이 늦어 1번이 터진 것이다. 어느 카운터가 늘었는지로 병목 위치를 좁힐 수 있다.

## 6. 트레이드오프 정리

| 방식 | 얻는 것 | 잃는 것 |
|------|---------|---------|
| PIO(CPU 복사) | 하드웨어가 단순하다 | CPU가 바이트 이동에 소모된다 |
| DMA + 패킷당 인터럽트 | 복사 제거, 저부하에서 낮은 지연 | 고부하에서 인터럽트 폭주, 라이브락 |
| 인터럽트 코얼레싱(`ethtool -C`) | 인터럽트 횟수 감소 | 지연 증가(모아서 알림) |
| NAPI(인터럽트와 폴링 혼합) | 부하에 적응, 처리량 유지 | softirq가 CPU를 오래 점유(ksoftirqd), 한 코어 쏠림 |
| busy polling, 커널 바이패스(예: DPDK) | 최저 지연, 최고 처리량 | CPU 상시 점유, 운영 복잡도 |

인터럽트 코얼레싱(interrupt coalescing)은 NIC가 패킷 여러 개를 모았다가 한 번에 인터럽트를 올리게 하는 설정이다. 인터럽트 횟수를 줄이지만 모으는 시간만큼 지연이 늘어난다.

## 7. 운영에서 만나는 문제

**한 코어의 softirq만 100%인 경우.** `top`에서 특정 코어의 `%si`나 `ksoftirqd/N`만 100%이고 다른 코어는 한가하다. `ksoftirqd/N`은 softirq가 계속 밀려들 때 커널이 남은 softirq 처리를 넘기는 코어별 커널 스레드다.

원인은 수신 큐 분산 방식에 있다. 멀티 큐 NIC는 **RSS**(Receive Side Scaling)로 패킷의 흐름(flow) 해시를 계산해 수신 큐를 고르고, 큐마다 다른 CPU가 인터럽트를 받는다. 메모리 글의 RSS(resident set size)와는 이름만 같은 다른 개념이다. 같은 흐름은 늘 같은 큐로 가므로, 큰 단일 흐름이나 해시 입력이 같아지는 터널 트래픽은 한 큐, 한 코어로 몰린다. **RPS**(Receive Packet Steering)는 같은 분산을 커널이 소프트웨어로 하는 기능이고 기본은 꺼져 있다.

**time_squeeze가 늘어나는 경우.** `/proc/net/softnet_stat`의 3열이 오르면 `net.core.netdev_budget`이나 `netdev_budget_usecs`가 부족하다는 신호다.

대응은 이렇다.

- RSS 큐 수와 IRQ 어피니티(어떤 CPU가 그 큐의 인터럽트를 받을지)를 조정해 부하를 코어에 나눈다. NIC 큐가 부족하면 RPS를 켠다.
- 링 크기를 키운다(`ethtool -G`). 대신 큐에 쌓이는 시간만큼 지연이 늘 수 있다.
- budget을 올린다.
- 코얼레싱 설정을 조정한다.

기본값은 커널 버전에 따라 다르다. 바꾸기 전에 현재 값을 먼저 확인한다.

## 결론

- 현대 NIC는 DMA로 패킷을 RX 링에 직접 쓰고, 인터럽트로 CPU에 알린다. 패킷 복사에서 CPU가 빠진다.
- 패킷마다 인터럽트를 받으면 10Gbps 최소 프레임 기준 약 67ns마다 인터럽트가 걸릴 수 있다. 인터럽트가 상위 처리보다 우선이라 입력이 늘수록 처리량이 무너지는 수신 라이브락이 생긴다.
- NAPI는 첫 패킷에서 인터럽트를 받고 이후엔 IRQ를 끈 채 `budget` 단위로 폴링한다. 일이 바닥나면 다시 인터럽트로 돌아가 저부하와 고부하를 모두 감당한다.
- 패킷은 RX 링, CPU 백로그, 소켓 버퍼에서 사라질 수 있고, budget 소진이 그 앞 신호가 된다. 각 지점은 서로 다른 카운터로 확인한다.

패킷이 소켓 버퍼까지 왔다면, 이제 애플리케이션이 수만 개의 소켓 중 어느 것에 데이터가 왔는지 알아내야 한다. [다음 글](/posts/cs/os/io-multiplexing-epoll-io-uring/)에서 그 방법인 select, epoll, io_uring을 본다.
