## 개요

[앞 글](/posts/cs/os/page-replacement-algorithms/)에서는 물리 메모리가 가득 찼을 때 어떤 페이지를 내보낼지 고르는 알고리즘을 봤다. 이번 글은 그 질문을 한 칸 더 넓힌다. 내보낼 페이지조차 없으면 시스템은 어떻게 되는가?

이 글이 답하는 질문은 세 가지다.

- `malloc`이 성공했는데 왜 한참 뒤에 프로세스가 죽는가?
- 메모리가 부족해지면 시스템은 어떤 순서로 나빠지는가? (느려짐 -> 스래싱 -> OOM Kill)
- 컨테이너는 노드에 메모리가 남아 있는데도 왜 `OOMKilled`(종료 코드 137)로 죽는가?

세 질문은 하나의 사실에서 나온다. 리눅스에서 메모리 할당은 약속이고, 비용은 나중에 청구된다.

---

## 1. 왜 약속과 청구가 분리되어 있는가

프로그램이 `malloc(8GB)`를 호출하면 리눅스는 내부적으로 `mmap`이나 `brk`로 가상 주소 공간(virtual address space)만 늘려 준다. 물리 메모리(RAM)는 한 바이트도 쓰지 않는다. 이 시점에 받은 것은 "이 주소 범위를 써도 된다"는 약속뿐이다.

물리 페이지는 그 주소에 **처음 접근하는 순간** 페이지 폴트를 거쳐 붙는다. [가상 메모리 글](/posts/cs/os/virtual-memory-page-table-tlb/)에서 본 demand paging이다.

왜 이렇게 만들었을까. 프로그램이 요청한 메모리를 전부 쓰는 경우가 드물기 때문이다.

- 큰 버퍼나 해시 테이블을 넉넉히 잡아 두고 일부만 쓴다. (희소 사용)
- `fork` 직후 자식은 부모의 메모리를 복사하지 않고 공유한다. 쓰기가 일어나는 페이지만 나중에 복사한다. ([fork와 Copy-on-Write](/posts/cs/os/fork-copy-on-write/)에서 다뤘다.)

예를 들어 RAM 16GB 서버에서 프로세스 5개가 각각 8GB를 `malloc`했다고 하자. 약속한 총량은 40GB지만, 각 프로세스가 실제로 만진 양이 1GB씩이면 물리 메모리는 5GB만 쓴다. 커널은 약속을 넉넉하게 해 주고 평균적인 메모리 효율을 높인다. 이것을 오버커밋(overcommit)이라 한다.

대가가 있다. 5개 프로세스가 약속받은 메모리를 실제로 쓰기 시작하면 청구서가 한꺼번에 도착한다. 이때 약속을 지킬 물리 메모리가 없다. `malloc` 성공은 "메모리가 있다"는 보증이 아니라서, 실패는 할당 시점이 아니라 **첫 접근 시점**에 늦게 드러난다.

## 2. vm.overcommit_memory: 약속을 얼마나 후하게 할 것인가

커널은 약속의 후한 정도를 `vm.overcommit_memory`로 정한다. 값은 세 가지다. 설명은 커널 문서(overcommit-accounting, sysctl/vm)를 기준으로 했다.

| 값 | 이름 | 동작 | 얻는 것 | 잃는 것 |
| --- | --- | --- | --- | --- |
| 0 (기본) | 휴리스틱(heuristic) | 명백한 과다 요청만 거절한다 | `fork`나 희소 사용 패턴에서 메모리 효율 | `malloc` 성공이 보증이 아니다. OOM이 늦게 난다 |
| 1 | 항상 허용(always) | 어떤 요청도 거절하지 않는다 | 거의 0으로 채워진 큰 희소 배열을 쓰는 과학 계산 같은 워크로드 | 훨씬 늦게, 예측하기 어렵게 OOM이 난다 |
| 2 | 엄격(never overcommit) | 약속 총량이 한도를 넘으면 할당 자체를 거절한다 | `malloc`이 실패로 알려 주므로 예측 가능하다 | 실제로 쓰지 않을 예약분만으로도 거절된다. 튜닝이 필요하다 |

모드 2의 한도는 "스왑 + 물리 RAM의 일정 비율"이다. 비율은 `vm.overcommit_ratio`(기본 50%)나 `vm.overcommit_kbytes`(절대값)로 정하고, 둘 중 하나를 쓰면 다른 하나는 0으로 읽힌다. 한도와 현재 약속량은 `/proc/meminfo`의 `CommitLimit`, `Committed_AS`에서 볼 수 있다.

앞의 예(RAM 16GB, 스왑 없음, 비율 50%)를 모드 2에 적용하면 약속 한도는 8GB다. 실제로는 5GB만 써도 프로세스 하나가 8GB를 `malloc`하는 순간 한도에 걸려 거절된다. 모드 2에서는 프로세스가 접근 중에 죽는 일이 일반적으로 줄고, 대신 할당 호출이 오류를 돌려받는다. `fork`를 많이 쓰는 프로그램(예: Redis의 BGSAVE)은 자식이 부모와 같은 크기를 약속받아야 해서 모드 2에서 특히 거절되기 쉽다.

그래서 기본값은 중간인 0이다. 모드 0은 "총량이 터무니없는 요청"만 거르므로, 약속의 합이 RAM을 넘는 상황 자체는 막지 못한다. 그 상황이 실제 메모리 부족으로 이어지면 다음 절의 경로를 밟는다.

## 3. 부족해지는 순서: 회수의 세 단계

물리 메모리가 줄어들면 커널은 곧바로 프로세스를 죽이지 않는다. 먼저 되살릴 수 있는 페이지를 찾는다. 이것을 메모리 회수(reclaim)라고 한다.

```
malloc / mmap       -> 가상 주소만 예약 (물리 메모리 사용 0)
      |
첫 접근 (page fault) -> 물리 페이지 할당 시도
      |
 여유 충분? --- yes --> 매핑하고 끝 (정상)
      |
      no (여유 페이지가 watermark 아래)
      |
 1) kswapd가 백그라운드에서 회수 시작
      |  (못 따라가면)
 2) direct reclaim: 할당을 요청한 스레드가 직접 회수하며 멈춤
      |  (그래도 페이지를 못 만들면)
 3) OOM Killer가 프로세스에 SIGKILL
```

단계별로 보자.

**1단계, kswapd.** 빈 페이지가 기준선(watermark) 아래로 내려가면 커널 스레드 `kswapd`가 깨어나 백그라운드에서 회수를 시작한다. 애플리케이션은 이 작업을 기다리지 않는다. 회수 대상은 크게 세 종류이고, 되살리는 비용이 서로 다르다.

- 깨끗한 페이지 캐시(clean page cache): 디스크에 같은 내용이 있으니 그냥 버린다.
- 더러운 페이지 캐시(dirty page cache): 디스크에 쓴 뒤 버린다.
- 익명 페이지(anonymous page, 힙이나 스택처럼 파일 뒤에 있지 않은 메모리): 스왑 공간이 있어야 내보낼 수 있다. 스왑이 없으면 회수할 수 없다.

**2단계, direct reclaim.** 할당이 회수보다 빠르면 `kswapd`가 따라가지 못한다. 그러면 메모리를 요청한 스레드가 자기 일을 멈추고 직접 회수를 수행한다(direct reclaim). 애플리케이션의 지연이 갑자기 튀는 시점이 바로 이때다. 예를 들어 평소 1ms에 끝나던 요청이 회수를 떠안는 순간 수십 ms 이상 걸릴 수 있다.

**3단계, OOM Killer.** 회수로도 페이지를 만들지 못하면 마지막 수단으로 OOM Killer가 나선다. 5절에서 다룬다.

중요한 점은 2단계까지는 시스템이 죽지 않고 **느려질 뿐**이라는 것이다. 이 느려짐이 어느 선을 넘으면 4절의 스래싱이 된다.

## 4. 스래싱: 죽지는 않는데 아무것도 못 하는 상태

프로세스가 일정 시간 동안 자주 쓰는 페이지 집합을 작업 집합(working set)이라고 한다. 작업 집합의 합이 RAM보다 작으면 문제가 없다. 합이 RAM보다 커지면 상황이 달라진다.

숫자로 보자. RAM 8GB 서버에 작업 집합이 3GB인 프로세스 3개가 있으면 합은 9GB다. 1GB만큼은 항상 디스크에 있어야 한다.

1. 프로세스 A가 디스크에 내려가 있던 페이지를 읽으려고 폴트를 낸다.
2. 커널이 자리를 만들려고 B가 곧 쓸 페이지를 내보낸다.
3. 곧 B가 그 페이지를 다시 읽으려고 폴트를 낸다.
4. 이번엔 A가 쓸 페이지가 밀려난다. 이것이 계속 반복된다.

모든 프로세스가 서로의 페이지를 쫓아내고 있다. 프로세스는 계산하는 시간보다 디스크를 기다리는 시간이 길어진다. 이 상태가 스래싱(thrashing)이다. 앞 글에서 본 페이지 교체 알고리즘이 아무리 좋아도, 작업 집합 자체가 RAM에 들어가지 않으면 이 상태를 피할 수 없다.

스래싱의 특징은 처리량이 완만하게 줄지 않고 **절벽처럼 떨어진다**는 것이다.

```
처리량
  |
  |*****
  |     ***
  |        **
  |          *
  |           *     <- 여기서 급락 (RAM 한계)
  |            *****************
  +----------------------------------
      동시에 올라온 작업 집합의 합 ->
```

(모양만 표현한 개념도다. 정량값이 아니다.)

증상은 특이하다. 노드가 죽지는 않는데 load average는 높고 CPU 사용률은 낮다. 요청 타임아웃과 헬스체크 실패가 이어진다. CPU가 한가한 것은 일이 없어서가 아니라 모두 I/O를 기다리기 때문이다. 이런 모습이면 CPU가 아니라 메모리를 먼저 의심해야 한다.

## 5. OOM Killer: 마지막 수단

회수에 실패하면 커널은 프로세스 하나를 골라 `SIGKILL`로 죽인다. 이것이 OOM Killer다. 죽은 프로세스의 메모리를 통째로 돌려받아 나머지 시스템을 살리려는 선택이다. 프로세스가 죽는 대신 시스템 전체가 멈추는 쪽을 피한다.

누구를 죽일지는 점수로 정한다. 커널은 프로세스마다 0~1000 사이의 badness 점수를 매기는데, 대략 허용된 메모리 중 그 프로세스가 쓰는 비율이다. 여기에 사용자가 조절할 수 있는 `oom_score_adj`를 더한다.

| `oom_score_adj` | 의미 |
| --- | --- |
| +1000 | 점수가 가장 높아져 제일 먼저 죽는 후보 |
| 0 (기본) | 메모리 사용량만으로 판단 |
| -1000 | OOM Kill 대상에서 제외 (badness가 항상 0) |

중요한 프로세스를 `-1000`으로 보호하고 싶은 마음이 들지만, 조심해야 한다. 그 프로세스가 메모리를 계속 쓰면 대신 다른 프로세스가 죽거나, 죽일 대상이 없어 시스템이 멈출 수 있다. 보호는 꼭 필요한 곳에만 한다.

관련 설정도 알아 둘 만하다. `vm.oom_kill_allocating_task`가 0이 아니면 점수를 매기지 않고 메모리를 요청한 그 태스크를 바로 죽인다. `vm.panic_on_oom`이 1이면 프로세스를 죽이는 대신 커널이 패닉한다. 둘 다 기본은 0이다.

OOM Kill이 일어났는지는 커널 로그로 확인한다.

```bash
dmesg | grep -i "killed process"
```

죽은 프로세스는 종료 코드 137을 남긴다. `SIGKILL`의 번호 9에 쉘 규칙의 128을 더한 값이다.

## 6. 컨테이너에서는 다른 경로로 죽는다

컨테이너에 메모리 limit을 주면 OOM은 노드 전체가 아니라 컨테이너 안에서 일어난다. 컨테이너는 cgroup(control group, 프로세스 묶음별로 자원을 제한하는 커널 기능)으로 격리되고, cgroup v2는 메모리 한도를 두 단계로 둔다.

| 설정 | 동작 |
| --- | --- |
| `memory.high` | 넘으면 해당 cgroup의 프로세스를 지연시키고 강한 회수 압박을 건다. 이 한도로는 OOM Killer가 호출되지 않는다 |
| `memory.max` | 하드 한도. 사용량이 이 한도에 닿고 줄일 수 없으면 그 cgroup 안에서 OOM Killer가 호출된다 |

쿠버네티스 문서는 메모리 limit을 커널이 cgroup과 OOM kill로 강제한다고 설명하고, cgroup v2 노드에서 그 하드 한도를 `memory.max`로 부른다. 따라서 이 한도에 닿고 회수로도 줄이지 못하면, 노드의 다른 곳에 메모리가 남아 있어도 그 컨테이너만 죽는다. 이때 상태가 `OOMKilled`, 종료 코드는 137이다.

경로를 3절과 비교하면 이렇다.

```
노드 전체 OOM:  노드 RAM 고갈 -> kswapd/direct reclaim -> OOM Killer(노드 전체에서 희생자 선택)
컨테이너 OOM:   cgroup이 memory.max에 도달 -> cgroup 안에서만 회수 -> 실패 시 cgroup 안에서 OOM Kill
```

컨테이너 경로에서 개발자가 가장 많이 당황하는 상황이 있다. 예를 들어 JVM 컨테이너가 137로 재시작되는데 힙 덤프를 보면 힙은 limit의 60%뿐인 경우다. 원인은 limit이 힙에만 걸리는 것이 아니라 cgroup 전체에 걸린다는 점이다. cgroup 사용량에는 이런 것들이 더해진다.

- 힙 밖의 JVM 메모리: 메타스페이스(metaspace), 스레드 수 x 스레드 스택 크기, direct buffer, 네이티브 라이브러리
- glibc 할당자의 arena 단편화([다음 글](/posts/cs/os/memory-allocator-fragmentation/)에서 다룬다)
- 사이드카나 자식 프로세스
- 회수할 수 없는 페이지: tmpfs, 아직 디스크에 쓰지 못한 dirty page

확인 순서는 이렇다. `memory.events`의 `oom_kill` 카운트로 정말 cgroup OOM인지 확인하고, `memory.stat`으로 항목별 사용량을 본다. 대응은 힙 비율(예: `MaxRAMPercentage`)을 낮춰 힙 밖 메모리의 여유를 남기는 것이다.

```bash
cat /sys/fs/cgroup/.../memory.events   # high, max, oom, oom_kill 카운트
cat /sys/fs/cgroup/.../memory.stat     # 항목별 사용량
```

참고로 `memory.oom.group`을 1로 두면 cgroup 안의 프로세스를 하나씩 고르지 않고 묶음 전체를 함께 죽인다. 하나가 죽으면 나머지가 의미 없는 워크로드에 쓴다.

## 7. 스왑과 압박 지표: 죽기 전에 알아채기

지금까지의 경로에서 스왑이 어떤 역할을 하는지 정리하자. 스왑이 있으면 익명 페이지도 내보낼 수 있어서 일시적인 급증을 흡수한다. 반면 한도를 넘으면 곧바로 죽지 않고 천천히 느려지는 상태가 길어진다. 스래싱이 오래 이어지는 것이다.

| 선택 | 얻는 것 | 잃는 것 |
| --- | --- | --- |
| 스왑 사용 | 일시적 급증을 흡수한다 | 한계를 넘으면 죽지도 못하고 서서히 느려지는 상태가 길어질 수 있다 |
| 스왑 없음 + cgroup 한도 | 빨리 죽고 다시 시작한다(fail-fast) | 순간적인 피크에도 kill이 일어난다 |

정답은 워크로드에 따라 다르다. 지연에 민감하고 재시작이 쉬운 stateless 서비스는 빨리 죽고 재시작하는 편이 낫다. 상태가 큰 서비스는 작은 스왑으로 피크를 흡수하는 편이 안전하다. 어느 쪽이든 죽거나 느려지기 전에 알아채는 지표가 필요하다.

| 도구 | 보는 것 |
| --- | --- |
| `cat /proc/pressure/memory` | PSI(Pressure Stall Information). `some`은 한 태스크 이상이 메모리를 기다린 시간 비율, `full`은 모든 비유휴 태스크가 동시에 기다린 비율이다. `full`이 오래 높으면 스래싱 중이다 |
| `vmstat 1` | `si`/`so`(스왑 입출력), `wa`(iowait) |
| `memory.events` | `high`, `max`, `oom`, `oom_kill` 카운트 |

PSI는 `avg10`, `avg60`, `avg300`(최근 10초, 60초, 300초 평균)과 누적값 `total`을 함께 준다. 여기에 알람을 걸면 OOM이 나기 전 압박 단계에서 먼저 알 수 있다.

---

## 결론

- `malloc` 성공은 가상 주소를 약속받은 것이지 물리 메모리를 확보한 것이 아니다. 청구는 첫 접근(page fault) 때 온다.
- `vm.overcommit_memory`는 약속의 후한 정도를 정한다. 기본 0은 효율을 얻는 대신 실패가 늦게 드러나고, 2는 예측 가능한 대신 쓰지 않을 예약분 때문에도 거절된다.
- 메모리가 모자라면 kswapd 회수, direct reclaim, 스래싱, OOM Kill 순으로 나빠진다. CPU는 한가한데 요청이 느리면 스래싱이다.
- 컨테이너는 `memory.max`에서 cgroup 안의 OOM을 겪는다. 노드에 메모리가 남아도 죽고, limit은 힙이 아니라 cgroup 전체에 적용된다.
- `/proc/pressure/memory`의 PSI 같은 압박 지표를 보고 있으면 죽기 전에 알아챌 수 있다.

힙이 limit보다 한참 작은데도 RSS가 계속 크다면, 커널이 아니라 프로세스 안의 할당자를 의심해야 한다. [다음 글](/posts/cs/os/memory-allocator-fragmentation/)에서 malloc이 메모리를 어떻게 나누고 왜 돌려주지 못하는지 본다.
