## 개요

[앞 글](/posts/cs/os/memory-allocator-fragmentation)까지는 메모리를 다뤘다. 이번 글부터는 I/O로 넘어가, 먼저 디스크 위의 데이터를 이름으로 찾아가게 해 주는 파일 시스템을 본다.

서버에서 `df -h`는 사용률이 12%인데 파일을 만들면 `No space left on device`가 나올 때가 있다. 반대로 큰 로그를 `rm`으로 지웠는데 사용률이 그대로인 경우도 있다. 둘 다 파일 시스템이 "이름"과 "파일"을 따로 관리하기 때문에 생긴다.

이 글이 답하는 질문은 두 가지다.

- 디렉터리, inode, 데이터 블록은 각각 무엇을 갖고 있고, 하드 링크와 심볼릭 링크는 어떻게 다른가?
- 저널링(journaling)은 크래시 뒤에 무엇을 보장하고, 무엇은 보장하지 않는가?

저널링이 지켜 주지 않는 "데이터 내구성"은 [페이지 캐시와 fsync](/posts/cs/os/page-cache-fsync) 글에서 이어서 다룬다.

## 1. 이름과 파일을 왜 분리했을까

파일 시스템이 파일 이름 안에 크기, 권한, 데이터 위치를 모두 넣었다고 하자. 그러면 같은 파일에 이름을 하나 더 붙이려면 정보를 복사해야 하고, 이름만 바꾸는 `rename`도 그 정보를 통째로 옮겨야 한다.

그래서 Unix 계열 파일 시스템은 둘을 나눈다.

> 파일의 실체는 inode가 갖고, 이름은 디렉터리 안의 "이름 -> inode 번호" 항목일 뿐이다.

**inode**(index node)는 파일의 메타데이터를 담은 구조체다. 크기, 소유자, 권한, 시각, 데이터 블록(또는 extent, 연속된 블록 범위)의 위치, 링크 수가 들어 있다. 파일 이름은 여기에 없다.

**디렉터리**는 "이름 -> inode 번호" 목록을 담은 특별한 파일이다.

```text
디렉터리 /data               inode 테이블               데이터 블록
+------------------+       +------------------+       +-----------+
| a.txt -> 1201    |------>| inode 1201       |------>| blocks    |
| b.txt -> 1201    |------>|  link count = 2  |       | 5000-5003 |
| s.lnk -> 1305    |--+    |  size, perm, ... |       +-----------+
+------------------+  |    |  extent 5000-5003|
                      |    +------------------+
                      |    +------------------+
                      +--->| inode 1305       |
                           |  "../x/a.txt"    |
                           +------------------+
```

이렇게 나누면 얻는 것이 세 가지다.

- 한 파일에 이름을 여러 개 붙일 수 있다(하드 링크).
- `rename`은 디렉터리 항목만 바꾸므로 가볍다.
- 이름이 사라져도 열려 있는 파일은 계속 쓸 수 있다.

마지막 항목이 4절의 "지웠는데 공간이 안 돌아오는" 현상의 뿌리다.

## 2. 경로는 어떻게 파일이 되나

`/data/a.txt`를 열 때 커널은 이름을 한 단계씩 따라간다.

1. 루트 디렉터리의 inode를 읽는다. 루트 inode 번호는 알려져 있다.
2. 그 디렉터리의 데이터에서 `data` 항목을 찾아 inode 번호를 얻는다.
3. 그 inode가 가리키는 디렉터리 데이터에서 `a.txt` 항목을 찾는다. 예시에서는 1201이다.
4. inode 1201을 읽으면 데이터 블록 위치를 알 수 있다.

단계마다 디렉터리를 읽어야 해서 느릴 것 같지만, 커널이 한 번 찾은 이름-inode 대응을 **dentry 캐시**(directory entry cache)에 기억해 두므로 같은 경로를 반복해 열 때는 디스크를 거의 보지 않는다.

디렉터리 하나에 파일이 수백만 개 있으면 사정이 달라진다. 이름 탐색, `ls`(`readdir`), 삭제가 느려지고 메타데이터 I/O가 한곳에 몰린다. 파일 이름의 앞 두 글자로 하위 디렉터리를 나누는 샤딩이 흔한 해법이다. 예를 들어 `ab12.jpg`를 `ab/ab12.jpg`로 두면 디렉터리 하나의 크기가 줄어든다.

## 3. 하드 링크와 심볼릭 링크

이름이 inode 번호일 뿐이라면, 같은 번호를 가리키는 이름을 하나 더 만들 수 있다. 이것이 **하드 링크**(hard link)다. 원본과 사본의 구분이 없다. 리눅스 man 페이지도 두 이름이 같은 파일을 가리키며 어느 쪽이 원본인지 구분할 수 없다고 설명한다.

**심볼릭 링크**(symbolic link)는 다르다. 경로 문자열을 담은 별도 inode이고, 열 때마다 그 문자열을 해석한다. 위 그림의 `s.lnk`가 그렇다.

| 구분 | 하드 링크 | 심볼릭 링크 |
|---|---|---|
| 정체 | 같은 inode의 또 다른 이름 | 경로 문자열을 담은 별도 파일 |
| 다른 파일 시스템 | 불가 | 가능 |
| 원본을 지우면 | 다른 이름이 있으면 데이터 유지 | 대상이 사라져 dangling link가 됨 |
| 디렉터리 대상 | 보통 금지 | 가능 |

표의 제약에는 이유가 있다.

- **다른 파일 시스템에 못 거는 이유.** inode 번호는 파일 시스템마다 독립이다. 번호 1201이 다른 파일 시스템에서는 전혀 다른 파일이다. 리눅스는 이 경우 `EXDEV` 오류를 돌려준다.
- **디렉터리에 못 거는 이유.** 디렉터리에 하드 링크를 허용하면 트리에 사이클이 생길 수 있다. 순회와 삭제, 뒤에 나올 참조 수 회수가 망가진다. `link()`는 디렉터리 대상에 `EPERM`을 돌려준다.

심볼릭 링크는 이런 제약이 없는 대신, 가리키는 대상이 사라지면 끊어진다는 대가를 치른다.

## 4. 파일은 언제 사라지나: 링크 수와 열린 파일

inode에는 **링크 수**(link count)가 있다. 이 inode를 가리키는 이름이 몇 개인지 센 값이다. 하드 링크를 만들면 +1, `unlink`(`rm`이 호출하는 시스템 콜)하면 -1이다.

예시를 따라가 보자.

1. `a.txt`를 만든다. 링크 수는 1이다.
2. `ln a.txt b.txt`로 하드 링크를 만든다. 링크 수는 2다.
3. `rm a.txt`를 한다. 링크 수는 1이고 `b.txt`로 데이터를 계속 읽을 수 있다.
4. `rm b.txt`를 한다. 링크 수는 0이다.

그런데 4단계에서 inode와 블록이 곧바로 풀리는 것은 아니다. 커널은 이 파일을 열고 있는 프로세스가 있으면 해제를 미룬다. 리눅스 `unlink(2)` 문서도, 마지막 링크를 지워도 열려 있다면 마지막 파일 디스크립터가 닫힐 때까지 파일이 남는다고 설명한다.

> 파일의 수명은 "이름 수 + 열린 참조 수"가 모두 0이 될 때까지다.

### 지웠는데 df가 줄지 않을 때

흔한 사고는 이렇다. 디스크가 차서 큰 로그 파일을 `rm`으로 지웠다. 그런데 로그를 쓰는 프로세스는 계속 돌고 있다. 링크 수는 0이지만 열린 fd가 있으니 블록은 그대로 점유된다. 이름이 없으니 `ls`와 `du`에는 보이지 않고, `df`는 블록이 여전히 사용 중이라 용량이 그대로다. 그래서 `du`와 `df` 수치가 어긋난다.

`lsof +L1`이 링크 수가 1 미만인(즉 지워진) 열린 파일을 보여 준다.

```bash
$ lsof +L1
COMMAND  PID USER   FD   TYPE DEVICE   SIZE/OFF NLINK  NODE NAME
app     4121 svc    3w   REG  253,1 8589934592     0  1201 /var/log/app.log (deleted)
```

`SIZE/OFF`가 8GiB, `NLINK`가 0이다. 이 프로세스를 재시작하거나 fd를 닫으면 공간이 돌아온다. 재시작할 수 없다면 `/proc/4121/fd/3`을 `truncate`로 비우는 방법도 있다.

그래서 운영 중인 로그 파일은 지우지 않는 것이 좋다. 로그 로테이션 도구가 파일을 잘라 내거나(`truncate`) 프로세스에게 파일을 다시 열라는 신호를 보내는 이유가 이것이다.

## 5. 공간은 남았는데 No space left

디스크가 남았는데도 새 파일을 만들 수 없는 경우를 보자. 에러는 `ENOSPC`(`No space left on device`)다. 같은 에러가 서로 다른 두 자원 부족에서 나온다는 점이 핵심이다.

- **블록 부족.** 데이터를 담을 공간이 없다.
- **inode 부족.** 파일 하나를 만들려면 크기와 상관없이 inode가 하나 필요한데, 빈 inode가 없다.

ext4에서는 inode 개수가 포맷할 때 고정된다. `mkfs`가 "몇 바이트당 inode 하나" 같은 비율로 inode 테이블 크기를 정한다. Red Hat의 솔루션 문서도 inode 풀이 파일 시스템 생성 시점에 정해져, 작은 파일이 많으면 디스크가 차기 전에 inode가 먼저 바닥날 수 있다고 설명한다.

두 자원은 `df`의 옵션으로 따로 본다.

```bash
$ df -h /var/spool/mail
Filesystem      Size  Used Avail Use% Mounted on
/dev/sdb1       100G   12G   88G  12% /var/spool/mail

$ df -i /var/spool/mail
Filesystem      Inodes   IUsed IFree IUse% Mounted on
/dev/sdb1      6553600 6553600     0  100% /var/spool/mail
```

블록은 12%만 썼는데 inode는 100%다. 메일 큐, 세션 파일, 썸네일 캐시처럼 작은 파일이 수천만 개 쌓이는 디렉터리가 전형적인 원인이다.

대응은 다음 순서로 한다.

1. `df -i`로 inode 고갈인지 확인한다.
2. 파일이 몰린 디렉터리를 찾아 정리한다. 디렉터리별 파일 수를 집계하면 된다.
3. 근본적으로는 작은 파일을 한 덩어리로 묶는 설계(아카이브, DB, 오브젝트 스토리지)를 쓴다.
4. 새로 만드는 파일 시스템이라면 inode 비율을 조정한다. XFS는 inode 개수를 미리 고정하지 않고, 전체 공간의 일정 비율(`maxpct`)까지 필요할 때 inode 블록으로 쓰므로 이 문제에 덜 민감하다.

`df -i`가 정상인데도 `ENOSPC`가 난다면 쿼터, 예약 블록, 컨테이너 오버레이의 별도 제한도 후보다.

## 6. 저널링: 여러 블록을 쓰다 죽으면

이제 다른 문제로 넘어가자. 파일 하나를 만들려면 쓸 곳이 여러 군데다.

- 빈 inode를 하나 골라 inode 비트맵에 사용 중으로 표시한다.
- inode 내용을 채운다.
- 디렉터리에 "이름 -> inode 번호" 항목을 추가한다.

세 번의 쓰기 중간에 전원이 나가면 어긋난 상태가 남는다. 비트맵은 사용 중인데 가리키는 디렉터리 항목이 없거나(공간 누수), 디렉터리 항목은 있는데 inode는 비어 있을 수 있다. 예전에는 부팅 때 `fsck`가 디스크 전체를 훑어 고쳤고, 디스크가 클수록 오래 걸렸다.

저널링은 이 문제를 데이터베이스의 [WAL](/posts/cs/database/wal-aries-crash-recovery)(Write-Ahead Logging)과 같은 방식으로 푼다.

> 변경 내용을 먼저 순차 로그(저널)에 기록하고, 나중에 제자리에 반영한다.

동작은 이렇다.

1. 바꿀 블록들의 새 내용을 저널에 쓴다.
2. 다 썼다는 표시인 **커밋**(commit) 레코드를 저널에 쓴다.
3. 저널에 기록된 내용을 원래 위치에 반영한다. 이를 체크포인트(checkpoint)라 한다.

크래시 뒤 복구는 간단해진다. 저널을 읽어 커밋된 기록은 다시 적용(replay)하고, 커밋이 없는 기록은 버린다. 디스크 전체가 아니라 저널 크기만큼만 보면 되므로 빠르다. 결과는 "변경 전" 아니면 "변경 후"이고 중간 상태는 없다.

## 7. 저널링 모드: 무엇을 저널에 쓰나

저널에 데이터까지 쓰면 안전하지만 같은 데이터를 두 번 쓰게 된다. 그래서 ext4는 세 가지 모드를 제공한다. 커널 문서의 설명을 정리하면 다음과 같다.

| 모드 | 저널에 쓰는 것 | 보장 | 비용 |
|---|---|---|---|
| `data=journal` | 데이터와 메타데이터 | 둘 다 일관 | 데이터를 두 번 씀, 가장 느림 |
| `data=ordered` (기본) | 메타데이터만 | 메타데이터 일관, 커밋된 메타데이터는 이미 디스크에 쓰인 데이터를 가리킴 | 중간 |
| `data=writeback` | 메타데이터만 | 메타데이터 일관만 | 보통 가장 빠름, 크래시 뒤 파일에 엉뚱한 내용이 보일 수 있음 |

`ordered`의 순서가 핵심이다. 파일을 늘려 쓸 때 "데이터 블록을 먼저 디스크에 쓰고, 그다음 메타데이터(크기, 블록 위치)를 커밋"한다. 순서가 반대라면 크기는 늘었는데 블록에는 예전 쓰레기가 남을 수 있다. `writeback`은 이 순서를 보장하지 않아서 그런 일이 생길 수 있다.

### 저널링은 데이터 내구성을 보장하지 않는다

가장 흔한 오해는 "저널링을 쓰니 `write` 뒤에 fsync가 필요 없다"는 것이다. 저널링이 지키는 것은 파일 시스템 구조의 일관성이다. 애플리케이션이 쓴 데이터가 안전하게 저장되었다는 약속은 아니다.

`ordered` 모드에서도 아직 커밋되지 않은 데이터는 크래시로 잃을 수 있다. `write`한 내용은 먼저 페이지 캐시에 머물기 때문이다([페이지 캐시와 fsync](/posts/cs/os/page-cache-fsync) 참고).

설정 파일처럼 "옛 내용 아니면 새 내용"이어야 하는 파일은 임시 파일에 쓰고 `fsync`한 뒤 `rename`으로 바꿔치기하고, 마지막으로 디렉터리도 `fsync`한다. 1절에서 보았듯 `rename`은 디렉터리 항목만 바꾸는 연산이라 원자적으로 교체된다. 단계마다 왜 필요한지, `fsync`가 실패하면 어떻게 되는지는 [다음 글](/posts/cs/os/page-cache-fsync)에서 자세히 본다.

## 8. 정리: 증상에서 원인으로

| 증상 | 의심할 원인 | 확인 |
|---|---|---|
| `df -h`는 여유인데 파일 생성이 `ENOSPC` | inode 고갈 | `df -i` |
| 로그를 지웠는데 `df`가 그대로, `du`와 불일치 | 지워졌지만 열려 있는 파일 | `lsof +L1` |
| 디렉터리 `ls`와 삭제가 매우 느림 | 한 디렉터리에 파일이 너무 많음 | 파일 수 집계, 샤딩 |
| 크래시 뒤 파일 내용이 예전 것 | 저널링은 데이터 내구성이 아님 | 임시 파일 + `fsync` + `rename` |

---

## 결론

- 파일 시스템에서 이름은 디렉터리 항목이고, 파일의 실체는 inode다. 이 분리 덕에 하드 링크와 가벼운 `rename`이 가능하다.
- inode는 파일 시스템마다 독립이라, 하드 링크는 같은 파일 시스템 안에서만 만들 수 있다. 심볼릭 링크는 경로 문자열이라 어디든 가리키지만 끊어질 수 있다.
- 파일은 링크 수와 열린 참조 수가 모두 0이 되어야 해제된다. 그래서 지웠는데 공간이 안 돌아오는 일이 생기고, `lsof +L1`로 찾는다.
- `No space left`는 블록 부족과 inode 부족 두 가지이므로 `df -h`와 `df -i`를 함께 본다.
- 저널링은 크래시 뒤 구조의 일관성을 지킬 뿐 데이터 내구성은 보장하지 않는다. 내구성은 `fsync`로 확보한다.
