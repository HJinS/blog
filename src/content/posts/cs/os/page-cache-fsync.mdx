## 개요

[앞 글](/posts/cs/os/filesystem-inode-journaling/)에서는 파일이 디스크에 어떻게 배치되는지, 그리고 저널링이 데이터 내구성까지 지켜 주지는 않는다는 점을 봤다. 이 글은 디스크 위가 아니라 그 앞, 커널 메모리 쪽에서 일어나는 일을 본다.

이 글이 답하는 질문은 두 가지다.

- `write()`가 성공을 반환했는데 전원이 나가면 데이터가 사라질 수 있는 이유는 무엇인가?
- `fsync()`는 정확히 어디까지 내려보내고, 실패하면 애플리케이션은 어떻게 해야 하는가?

DB 시리즈의 [WAL과 ARIES 글](/posts/cs/database/wal-aries-crash-recovery/)은 커밋마다 로그를 `fsync()`로 내려야 한다고 하고, 그 비용을 group commit으로 나누는 방법을 다뤘다. 이 글은 그 앞 질문, 왜 `write()`만으로는 안 되는가를 다룬다.

---

## 1. 왜 캐시가 필요한가: 디스크는 너무 느리다

디스크는 메모리보다 수천 배에서 수만 배 느리다. 파일을 읽거나 쓸 때마다 디스크까지 갔다 오면 프로그램은 대부분의 시간을 기다림에 쓴다.

그래서 OS는 파일 데이터를 메모리에 잡아 둔다. 이 메모리 영역이 **페이지 캐시**(page cache)다. 파일 내용을 페이지(보통 4KB) 단위로 RAM에 보관하는 커널의 캐시다.

핵심 아이디어는 한 문장이다. **읽기는 캐시에서 답하고, 쓰기는 캐시만 고친 뒤 디스크 반영을 뒤로 미룬다.**

읽기부터 보자. `read()`는 요청한 페이지가 캐시에 있으면 디스크를 건드리지 않고 복사만 한다. 없으면 디스크에서 읽어 와 캐시에 넣고 돌려준다.

쓰기가 문제다. `write()`는 보통 이렇게 동작한다.

1. 대상 페이지가 캐시에 없고 페이지 일부만 덮어쓰는 경우, 먼저 디스크에서 읽어 온다.
2. 사용자 버퍼의 내용을 캐시 페이지로 복사한다.
3. 그 페이지에 **dirty** 표시를 한다. 캐시 내용이 디스크 내용과 달라졌다는 뜻이다.
4. 바로 반환한다.

이 방식을 **write-back**이라고 한다. 디스크 반영은 나중에 커널이 알아서 한다. 처음부터 디스크에 같이 쓰는 **write-through**와 대비된다.

write-back을 고르는 이유는 성능이다. 같은 페이지를 100번 고쳐도 디스크 쓰기는 한 번이면 된다. 작은 쓰기를 모아서 한 번에 내릴 수 있고, 디스크 위치 순서대로 정렬해서 내리면 탐색도 줄어든다.

대가는 분명하다. dirty 페이지가 아직 RAM에만 있을 때 전원이 나가면 그 쓰기는 사라진다. 그래서 커널은 "여기까지는 디스크에 확실히 내려라"를 요청할 명시적인 방법을 따로 준다. 그것이 `fsync()`다.

## 2. write()에서 디스크까지의 경로

`write()`가 성공을 반환한 시점과 데이터가 정말 저장된 시점 사이에는 층이 여러 개 있다.

```
 App        write(fd, buf, n)                  fsync(fd)
              |                                    |
              v                                    v
 +--------------------------------------------------------+
 | Page cache (RAM)    page: clean / dirty                |
 |   write() returns here -- data is "in kernel memory"   |
 +--------------------------------------------------------+
              |  writeback (later) or fsync (now)
              v
 +--------------------------------------------------------+
 | File system     block mapping, journal, metadata       |
 +--------------------------------------------------------+
              |
              v
 +--------------------------------------------------------+
 | Block layer     I/O scheduler, request queue           |
 +--------------------------------------------------------+
              |
              v
 +--------------------------------------------------------+
 | Disk            device write cache -> persistent media  |
 +--------------------------------------------------------+
```

각 층에서 "쓰기 완료"가 의미하는 바가 다르다.

| 어디까지 갔나 | 이때 전원이 나가면 |
|---|---|
| `write()` 반환 (페이지 캐시) | 사라진다 |
| writeback으로 블록 계층에 전달 | 아직 장치 캐시에만 있을 수 있어 사라질 수 있다 |
| 장치가 영구 매체에 기록 확인 | 남는다 |

그래서 `write()`의 성공은 "커널 메모리가 데이터를 받았다"는 뜻일 뿐이다. 내구성(durability)은 보장하지 않는다.

참고로 `mmap`으로 파일을 메모리에 매핑하는 것도 같은 페이지 캐시를 프로세스 주소 공간에 직접 연결한 것이다. 복사 한 번이 줄 뿐, 내구성 규칙은 같다.

## 3. dirty 페이지는 언제 내려가나: writeback과 write stall

dirty 페이지가 영원히 쌓일 수는 없다. 커널의 flusher 스레드가 백그라운드에서 내려보낸다. 시점을 정하는 설정은 네 가지다. 모두 커널 문서의 `vm` sysctl에 있다.

| 설정 | 의미 |
|---|---|
| `vm.dirty_background_ratio` | dirty 비율이 이 값에 닿으면 flusher 스레드가 쓰기를 시작한다 |
| `vm.dirty_ratio` | 이 값에 닿으면 쓰기를 일으킨 프로세스가 직접 dirty 데이터를 내려써야 한다 |
| `vm.dirty_expire_centisecs` | 이 시간(1/100초 단위)보다 오래 dirty였던 데이터는 다음 깨어남 때 내려간다 |
| `vm.dirty_writeback_centisecs` | flusher 스레드가 깨어나는 간격 (1/100초 단위) |

비율의 기준은 전체 RAM이 아니라 "free 페이지와 회수 가능한 페이지"의 합이라는 점에 주의하자.

숫자로 따라가 보자. 설명을 위한 가정이다. 기준 메모리가 16GB이고 `dirty_background_ratio`가 10%, `dirty_ratio`가 20%라면 대략 이렇다.

1. dirty가 약 1.6GB에 닿으면 백그라운드 flusher가 내려쓰기 시작한다.
2. 프로세스가 디스크 속도(예: 초당 200MB)보다 빠르게(예: 초당 2GB) 계속 쓰면 flusher가 못 따라간다.
3. dirty가 약 3.2GB에 닿으면, 쓰는 프로세스가 `write()` 안에서 직접 내려쓰기에 끌려 들어가 느려진다.

평소 1ms이던 `write()`가 어느 순간 수백 ms에서 수 초 멈추는 것이 이 때문이다. 이를 **write stall**이라고 부른다. 대량 로그나 백업 직후 지연이 튀는 증상으로 자주 나타난다.

이 증상을 만났을 때 확인할 곳은 다음과 같다.

- `/proc/meminfo`의 `Dirty`와 `Writeback` 값이 임계치 근처인가
- `vmstat`의 `bo`(블록 출력)와 `wa`(I/O 대기), `iostat`의 장치 사용률이 높은가
- 대용량 순차 쓰기나 백업이 같은 디스크의 `fsync`와 경합하는가
- 컨테이너라면 cgroup에 걸린 dirty 한도가 낮은가

완화책으로는 dirty 비율을 낮춰 더 일찍, 더 작게 내려쓰게 하거나, 대량 쓰기를 `sync_file_range` 등으로 나눠 주기적으로 내려보내는 방법이 있다. 한꺼번에 쌓였다 터지는 대신 조금씩 흘리는 것이다.

한편 `free`에서 `used`가 아니라 `buff/cache`가 늘어나는 것은 이상이 아니다. 회수 가능한 clean 캐시는 필요하면 바로 버릴 수 있다. 반면 dirty 페이지는 버리기 전에 디스크로 내려야 하므로 따로 봐야 한다.

## 4. fsync가 하는 일

내구성이 필요할 때 애플리케이션은 `fsync(fd)`를 부른다. `fsync()`는 그 파일의 dirty 페이지를 모두 내려쓰고, 장치가 기록을 확인할 때까지 기다렸다가 반환한다. man page에 따르면 디스크 캐시를 통과해 장치까지 내려보내는 것이 목적이다.

### fsync와 fdatasync

`fdatasync()`는 `fsync()`보다 조금 가볍다. 데이터를 나중에 올바르게 읽는 데 꼭 필요한 메타데이터만 내리고, 나머지는 건너뛴다. 예를 들어 수정 시각 변경은 건너뛸 수 있지만 파일 크기가 바뀐 것은 반드시 내려야 한다. 디스크 쓰기를 줄이는 것이 목적이다.

### 새 파일은 디렉터리도 fsync해야 한다

파일을 `fsync()`해도 그 파일이 들어 있는 **디렉터리 엔트리**가 디스크에 갔다는 보장은 없다. 새로 만든 파일이라면 부모 디렉터리의 fd에도 `fsync()`를 불러야 한다. 파일 내용은 남았는데 이름이 사라져서 파일을 못 찾는 일을 막기 위해서다. 디렉터리 엔트리가 inode, 저널과 어떻게 연결되는지는 [파일시스템 글](/posts/cs/os/filesystem-inode-journaling/)에서 다뤘다.

### 내구성을 요청하는 다른 방법들

| 방식 | 내구성 | 성능 | 비고 |
|---|---|---|---|
| 기본 `write` (buffered) | `fsync` 전에는 없음 | 빠름 | 전원 장애 때 최근 쓰기 유실 |
| `write` + `fsync` | `fsync` 반환 시 보장 (장치가 거짓말하지 않는 한) | 느림 (수 ms 수준) | group commit으로 호출 횟수를 줄인다 |
| `O_SYNC` / `O_DSYNC` | `write`마다 보장 | 매우 느림 | WAL 같은 순차 로그에 쓰기도 한다 |
| `O_DIRECT` | 페이지 캐시를 우회한다 (`fsync`는 별도로 필요) | 앱이 캐싱을 직접 관리 | 정렬 제약이 있어 DB 엔진이 선호한다 |
| `mmap` + `msync` | `msync` 시 보장 | 복사가 줄어듦 | I/O 오류가 `SIGBUS`로 나타나거나 늦게 알려진다 |

`O_DIRECT`에 대해 하나 짚자. 페이지 캐시를 건너뛴다고 저장이 끝나는 것은 아니다. 파일 크기 같은 메타데이터와 장치 캐시는 여전히 남아 있으므로, 내구성이 필요하면 `fsync` 계열 호출이 따로 필요하다. 또 다음 절의 오류 문제를 피하는 근본적인 방법으로 직접 I/O가 거론되지만, 캐싱을 애플리케이션이 직접 책임져야 해서 작업량이 크다.

커밋마다 `fsync`를 부르면 초당 호출 횟수가 곧 한계가 된다. 그 비용을 나누는 group commit은 [WAL 글의 커밋 경로](/posts/cs/database/wal-aries-crash-recovery/)에서 다뤘으니 여기서는 반복하지 않는다.

## 5. 안전한 파일 교체 패턴

설정 파일 하나를 새 내용으로 바꾸는 흔한 작업을 생각해 보자. 기존 파일을 열어 덮어쓰면 쓰는 도중 장애가 났을 때 옛 내용도 새 내용도 아닌 반쯤 쓰인 파일이 남는다.

그래서 다음 순서를 쓴다.

```
1. 같은 디렉터리에 임시 파일을 만들어 새 내용을 쓴다   (write)
2. 임시 파일을 fsync한다                                (내용이 디스크에)
3. rename(임시 파일, 원래 이름)                         (원자적 교체)
4. 부모 디렉터리를 fsync한다                            (교체가 디스크에)
```

각 단계가 빠졌을 때 생기는 문제는 이렇다.

| 빠진 단계 | 크래시 후 일어날 수 있는 일 |
|---|---|
| 2 (임시 파일 fsync) | 이름은 새 파일인데 내용이 비어 있거나 일부만 있다 |
| 3 (rename 대신 덮어쓰기) | 반쯤 쓰인 파일이 남는다 |
| 4 (디렉터리 fsync) | 옛 파일로 되돌아가 있을 수 있다 |

`rename()`의 원자성은 "다른 프로세스가 옛 파일이나 새 파일 중 하나만 보고, 그 이름이 비어 있는 순간은 없다"를 보장한다(`rename(2)`). 새 내용이 디스크에 있다는 보장은 아니다. 2번이 따로 필요한 이유가 이것이다.

## 6. fsync가 실패하면: PostgreSQL fsyncgate

`fsync()`는 쓰기 도중 I/O 오류가 났다면 `EIO` 등으로 보고한다. 그러면 애플리케이션은 어떻게 해야 할까? 직관은 "다시 해 보자"다. 이 직관이 위험하다는 것이 2018년에 알려졌다. PostgreSQL 커뮤니티가 "fsyncgate"라고 부른 사건이다.

### 무슨 일이 있었나

PostgreSQL은 `fsync()`가 성공하면 그 파일에 지금까지 쓴 것이 모두 디스크에 있다고 가정하고, 체크포인트 이후 필요 없어진 WAL을 지우거나 재활용한다. 그런데 Linux에서는 이 가정이 깨질 수 있었다. PostgreSQL 위키가 정리한 내용은 다음과 같다.

- **4.13 이전 커널:** writeback이 실패하면 해당 페이지가 clean으로 표시됐다. 오류는 한 번 보고된다. 그다음 `fsync()`를 다시 부르면 dirty 페이지가 없으니 성공을 반환할 수 있다. 거짓 성공이다.
- **4.13~4.15:** `fsync()`가 파일을 연 뒤에 발생한 오류만 보고했다. PostgreSQL은 파일을 닫았다 다시 열고, `fsync()`를 체크포인터 프로세스에 맡기기 때문에 오류를 못 볼 수 있었다.
- **4.14와 4.16 이후:** 파일을 닫았다 다시 열어도 inode의 첫 오류는 받는다. 다만 오류는 여전히 한 번만 보고되고, 실패한 페이지의 데이터가 버려질 수 있어 읽으면 옛 버전이 나올 수 있다.

단계로 풀면 이렇다.

```
1. write()          페이지가 dirty가 된다
2. writeback 실패   디스크 I/O 오류
3. 페이지 -> clean  오류 기록은 한 번만 남는다
4. fsync() -> EIO   오류를 한 번 보고한다
5. fsync() 재시도   0 반환 (거짓 성공)
```

결과는 이렇다. 디스크에는 데이터가 없는데 DB는 "체크포인트 성공"으로 믿는다. 그러면 복구에 필요한 WAL이 삭제되거나 재활용되고, 나중에 복구할 방법이 없는 손상이 된다.

LWN 기사는 커널 개발자들의 입장도 전한다. 하드웨어 오류가 나면 파일시스템은 보통 해당 페이지의 데이터를 버리고 clean으로 표시한다. 가장 흔한 원인이 이동식 드라이브를 뽑는 경우인데, 실패한 페이지를 계속 dirty로 들고 있으면 메모리가 고갈될 수 있기 때문이다. 커널의 선택에도 이유가 있었던 것이다. 개발자들은 근본 해결책이 직접 I/O라고 보았지만, PostgreSQL 쪽은 그 작업량이 크다고 답했다.

### PostgreSQL의 대응

PostgreSQL 12에서 `fsync()`가 실패하면 서버가 PANIC하도록 바꿨고, 11, 10, 9.6, 9.5, 9.4로 백포트했다. PANIC하면 서버가 내려가고, 재시작할 때 WAL을 재생해서 복구한다. WAL은 아직 지워지지 않았으니 가능하다. PostgreSQL 위키에 따르면 InnoDB(MySQL)와 WiredTiger(MongoDB)도 같은 문제에 대응해 비슷한 변경을 했다.

### 일반 애플리케이션은 어떻게 하나

`fsync`가 `EIO`를 반환했을 때의 원칙은 단순하다.

- 같은 fd로 재시도해서 성공이 나와도 저장됐다고 믿지 않는다.
- 해당 쓰기는 유실됐다고 가정한다.
- DB라면 크래시시키고 로그 재생으로 복구한다. 일반 앱이라면 데이터를 처음부터 다시 만들어서 새 파일에 쓴다.

참고로 `fsync(2)` man page는 `EIO`가 같은 파일에 대한 다른 fd의 쓰기에서 비롯될 수도 있다고 설명한다. 오류가 내 fd의 쓰기 때문만은 아니라는 뜻이다.

## 7. 트레이드오프 정리

설계 선택마다 무엇을 얻고 무엇을 내주는지 한눈에 정리한다.

| 선택 | 얻는 것 | 내주는 것 |
|---|---|---|
| write-back 캐시 | 쓰기 병합, 반복 수정 흡수, 정렬된 I/O로 빠른 쓰기 | 장애 때 최근 쓰기 유실 가능 |
| write-through였다면 | 단순한 내구성 | 모든 쓰기가 디스크 속도로 느려짐 |
| 매번 `fsync` | 내구성 확정 | 호출당 수 ms, 초당 처리량 제한 |
| dirty 비율 낮추기 | write stall 완화 | 병합 이득이 줄고 디스크 쓰기가 늘어남 |
| `fsync` 실패 시 재시도 | 일시적 오류 극복처럼 보임 | 거짓 성공으로 데이터 유실을 놓침 |
| `O_DIRECT` | 이중 캐싱과 오류 은폐 회피 | 캐시, 정렬, 선읽기를 앱이 책임짐 |

---

## 결론

- `write()`는 페이지 캐시의 페이지를 dirty로 만들고 바로 돌아온다. 성공은 "커널이 받았다"는 뜻이지 "저장됐다"는 뜻이 아니다.
- write-back은 쓰기 병합과 성능을 위한 설계이고, 그 대가로 내구성이 필요한 지점을 `fsync`로 명시하게 했다.
- `fsync`는 파일 데이터와 필요한 메타데이터를 장치까지 내리고 기다린다. 새 파일은 부모 디렉터리도 `fsync`해야 하고, 파일 교체는 임시 파일 쓰기, `fsync`, `rename`, 디렉터리 `fsync` 순서로 한다.
- dirty가 한도를 넘으면 쓰는 프로세스가 직접 느려진다. 쓰기 지연 스파이크는 이 지점을 먼저 의심한다.
- `fsync`가 실패하면 재시도해서 성공해도 믿을 수 없다. 쓰기가 유실됐다고 보고 복구 경로로 가야 한다.

지금까지는 데이터가 메모리에서 디스크로 내려가는 길을 봤다. [다음 글](/posts/cs/os/interrupt-dma-napi/)에서는 반대 방향, 장치가 일을 끝냈다고 CPU에 알리는 인터럽트와 DMA를 본다.
