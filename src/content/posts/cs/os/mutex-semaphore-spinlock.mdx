## 개요

[앞 글](/posts/cs/os/cfs-scheduler-cpu-throttling)에서는 스케줄러가 언제 어떤 스레드를 돌릴지 정하는 방식을 봤다. 스케줄러는 스레드가 어떤 코드를 실행하고 있는지 신경 쓰지 않는다. 공유 변수를 반쯤 고친 순간에도 스레드를 멈추고 다른 스레드를 돌린다. 멀티코어라면 아예 두 스레드가 같은 순간에 같은 변수를 건드린다.

이 글이 답하는 질문은 두 가지다.

- `count++` 한 줄도 깨지는 이유는 무엇이고, 락(lock)은 그것을 어떻게 막는가?
- 스핀락, 뮤텍스, 세마포어는 "기다리는 방식"이 어떻게 다르고, Linux는 왜 경합이 없으면 커널에 들어가지도 않는가?

락은 "한 번에 한 스레드만 이 코드를 실행한다"는 약속을 지켜 주는 변수다. 락의 종류는 결국 락을 못 잡았을 때 **어떻게 기다리느냐**로 갈린다. 이 글은 그 차이를 따라간다.

## 1. 경쟁 조건: `count++`는 한 단계가 아니다

스레드 두 개가 공유 변수 `counter`를 각각 100만 번씩 1 올린다고 하자. 결과는 200만이어야 한다. 그런데 실제로 돌려 보면 200만보다 작은 값이 나오고, 실행할 때마다 값이 다르다.

원인은 `counter++`가 CPU 입장에서 한 동작이 아니라는 데 있다. x86에서는 대략 다음 세 명령어가 된다.

```asm
mov  0x8049a1c, %eax    ; 1) load : 메모리에서 counter를 레지스터로 읽는다
add  $0x1, %eax         ; 2) add  : 레지스터 값에 1을 더한다
mov  %eax, 0x8049a1c    ; 3) store: 레지스터 값을 메모리에 쓴다
```

세 명령어 사이 어디서든 다른 스레드가 끼어들 수 있다. `counter`가 50일 때 두 스레드가 거의 동시에 올리면 이렇게 된다.

```
time  Thread 1                 Thread 2                 counter
----  -----------------------  -----------------------  -------
 t1   load  -> eax = 50                                   50
 t2                            load  -> eax = 50          50
 t3   add   -> eax = 51                                   50
 t4                            add   -> eax = 51          50
 t5   store -> counter = 51                               51
 t6                            store -> counter = 51      51
```

두 번 올렸는데 51이다. Thread 2는 Thread 1이 쓰기 전의 값 50을 읽었고, 자기 계산 결과 51로 Thread 1의 결과를 덮어썼다. 증가 한 번이 사라졌다.

이렇게 실행 타이밍에 따라 결과가 달라지는 상황을 **경쟁 조건**(race condition)이라고 한다. 끼어들기는 두 경로로 생긴다.

- **단일 코어:** 타이머 인터럽트가 t1과 t3 사이에 들어와 스케줄러가 Thread 2로 바꾼다.
- **멀티 코어:** 두 스레드가 서로 다른 코어에서 진짜로 동시에 load를 한다.

어느 쪽이든 문제의 본질은 같다. 읽고, 고치고, 쓰는 세 단계가 **중간에 끊기지 않는 한 덩어리**(atomic)로 실행되지 않는다는 것이다.

## 2. 임계 구역과 상호 배제

공유 자원에 접근하는 코드 중 동시에 둘 이상의 스레드가 실행하면 안 되는 부분을 **임계 구역**(critical section)이라고 한다. 위 예시에서는 `counter++` 한 줄이 임계 구역이다.

핵심 아이디어는 한 문장이다. **임계 구역 앞뒤에 락을 걸어, 한 스레드가 안에 있는 동안 다른 스레드는 들어오지 못하게 한다.** 이 성질을 **상호 배제**(mutual exclusion)라고 한다.

```c
lock(&m);
counter = counter + 1;   // 임계 구역: 한 번에 한 스레드만
unlock(&m);
```

락 변수는 두 상태 중 하나다. 아무도 안 잡은 상태(free)이거나, 정확히 한 스레드가 잡은 상태(held)다. 락을 잡은 스레드를 그 락의 소유자(owner)라고 부른다.

### 플래그 하나로는 안 된다

가장 먼저 떠오르는 구현은 정수 플래그 하나다.

```c
int flag = 0;                 // 0: free, 1: held

void lock(void) {
    while (flag == 1)         // 1) test: 잡혀 있으면 기다린다
        ;
    flag = 1;                 // 2) set : 내가 잡는다
}
void unlock(void) { flag = 0; }
```

이 코드는 1절과 똑같은 이유로 깨진다. Thread 1이 `flag == 0`을 확인한 직후 끊기고, Thread 2도 `flag == 0`을 확인한다. 둘 다 `flag = 1`을 쓰고 둘 다 임계 구역에 들어간다. 락을 지키려는 코드 자체가 "확인하고 쓰기"라는 경쟁 조건을 갖고 있다.

그래서 하드웨어의 도움이 필요하다. CPU는 "값을 읽고 새 값을 쓰는" 동작을 한 명령어로 끊김 없이 해 주는 원자 명령(atomic instruction)을 제공한다. 대표적인 것이 **test-and-set**(atomic exchange)이다. 새 값을 쓰면서 이전 값을 돌려준다. 이전 값이 0이었다면 내가 잡은 것이고, 1이었다면 남이 이미 잡은 것이다. 원자 명령이 하드웨어에서 어떻게 보장되는지는 [CAS와 lock-free 글](/posts/cs/architecture/cas-lock-free-aba)에서 다룬다.

### 좋은 락의 기준

OSTEP은 락을 세 가지 기준으로 평가한다. 이 글의 나머지는 이 기준으로 각 락을 비교한다.

| 기준 | 질문 |
|---|---|
| 상호 배제 | 정말 한 스레드만 들어가는가? |
| 공정성(fairness) | 기다리는 스레드가 언젠가는 락을 얻는가? 영영 못 얻는 기아(starvation)가 생기지 않는가? |
| 성능 | 경합이 없을 때, 단일 CPU에서 경합할 때, 여러 CPU에서 경합할 때 각각 얼마나 비싼가? |

## 3. 스핀락: 문 앞에서 계속 확인하기

원자 명령이 생기면 가장 단순한 락을 만들 수 있다. 락을 못 잡으면 잡힐 때까지 계속 다시 시도한다.

핵심 아이디어는 이렇다. **락이 풀릴 때까지 CPU를 쥔 채 반복문을 돈다.** 이렇게 기다리는 방식을 **바쁜 대기**(busy waiting)라고 하고, 이 방식의 락을 **스핀락**(spinlock)이라고 한다.

```c
#include <stdatomic.h>

atomic_int flag = 0;                       // 0: free, 1: held

void spin_lock(void) {
    while (atomic_exchange(&flag, 1) == 1) // test-and-set
        ;                                  // spin: 아무것도 안 하고 다시 시도
}
void spin_unlock(void) {
    atomic_store(&flag, 0);
}
```

`atomic_exchange`가 1을 쓰고 이전 값을 돌려준다. 이전 값이 1이면 남이 잡고 있다는 뜻이므로 다시 시도한다. 확인과 쓰기가 한 명령어라서 2절의 플래그 락처럼 두 스레드가 동시에 들어갈 수 없다.

### 유리한 조건: 짧은 구간, 멀티코어

스핀락이 이득인 상황을 따라가 보자. CPU 0의 Thread A가 락을 잡고, CPU 1의 Thread B가 락을 원한다.

```
time   CPU 0 (Thread A)          CPU 1 (Thread B)
-----  ------------------------  --------------------------
 t0    spin_lock() -> ok
 t1    critical section          spin_lock() -> 1, retry
 t2    critical section          spin_lock() -> 1, retry
 t3    spin_unlock()             spin_lock() -> 1, retry
 t4                              spin_lock() -> 0, got it
```

임계 구역이 명령어 수십 개 정도로 짧다면 B는 잠깐만 돌다가 락을 얻는다. B가 대신 잠들었다면 어땠을까? 잠들 때 한 번, 깨어날 때 한 번 컨텍스트 스위칭(context switching)이 필요하다. [컨텍스트 스위칭 글](/posts/cs/os/process-vs-thread-context-switching)에서 본 추정으로는 스레드 전환 한 번의 직접 비용만 수백 ns이고, 캐시가 식는 간접 비용이 더해지면 수 µs까지 간다. 기다릴 시간보다 잠들고 깨는 비용이 더 크면 차라리 도는 편이 낫다.

조건은 두 가지다.

1. **임계 구역이 짧다.** 도는 시간이 잠들고 깨는 비용보다 작아야 한다.
2. **락을 쥔 스레드가 다른 코어에서 실제로 돌고 있다.** 그래야 B가 도는 동안 A가 일을 끝내고 락을 풀어 준다.

### 생기는 문제: 단일 CPU와 선점

2번 조건이 깨지면 스핀락은 최악이 된다. CPU가 하나뿐이고, A가 락을 쥔 채 타이머 인터럽트로 밀려났다고 하자. 이제 B가 돌면서 락을 기다린다. 하지만 락을 풀어 줄 A는 CPU를 못 받는다. B는 자기 타임 슬라이스를 통째로 헛돈다. 기다리는 스레드가 N-1개라면 N-1개가 모두 슬라이스 하나씩을 버린다.

선점(preemption)이 없는 단일 CPU에서는 더 나쁘다. 도는 스레드가 CPU를 절대 놓지 않으니 A는 영원히 못 돌아온다. 그래서 단일 CPU에서 스핀락이 동작하려면 타이머로 스레드를 끊어 주는 선점형 스케줄러가 꼭 필요하다.

공정성도 보장하지 않는다. 락이 풀리는 순간 누가 먼저 test-and-set에 성공할지는 운이다. 경합이 심하면 어떤 스레드는 계속 진다. 대기 순서대로 번호표를 나눠 주는 티켓 락(ticket lock)이 이 문제를 고친다.

이 비유에는 한계도 있다. 회의실 문 앞에 서서 손잡이를 계속 돌려 보는 사람을 떠올리면 스핀락과 비슷하다. 다만 실제 스핀락에서는 "서서 기다리는 사람"이 CPU라는 공용 자원을 붙잡고 있다. 그래서 단일 CPU에서는 안에 있는 사람이 나올 기회 자체를 막아 버린다. 현실의 회의실에는 없는 문제다.

### 어디서 쓰나

Linux 커널 문서는 커널 락을 잠드는 락(sleeping lock)과 도는 락(spinning lock)으로 나눈다. 잠드는 락은 선점 가능한 태스크 문맥에서만 잡을 수 있다. 인터럽트 처리 중처럼 잠들면 안 되는 곳에서는 스핀락을 써야 한다. 커널의 스핀락은 잡는 동안 선점도 꺼서, 쥔 스레드가 밀려나는 위 문제를 원천적으로 막는다. 실시간용 PREEMPT_RT 커널은 예외로, `spinlock_t`를 잠드는 락으로 바꿔 쓴다.

유저 공간 애플리케이션은 선점을 끌 수 없다. 그래서 순수 스핀락은 위험하고, 뒤에서 볼 "조금 돌다가 잠드는" 방식이 기본이 된다.

## 4. 뮤텍스: 잠들고 깨우기

임계 구역이 길거나 락을 쥔 스레드가 밀려날 수 있다면 도는 것은 낭비다. 차라리 CPU를 다른 스레드에게 넘기는 게 낫다.

핵심 아이디어는 이렇다. **락을 못 잡으면 OS에게 "이 락이 풀리면 깨워 달라"고 하고 잠든다.** 이렇게 잠드는 락을 흔히 **뮤텍스**(mutex, mutual exclusion의 줄임말)라고 부른다. POSIX의 `pthread_mutex_t`가 대표적이다.

### 단계별 동작

CPU 하나에서 Thread A, B, C가 돈다고 하자.

```
step  event                                       running
----  ------------------------------------------  -------
 1    A: lock() -> ok, enters critical section    A
 2    (timer) scheduler switches A -> B           B
 3    B: lock() -> held -> syscall, B sleeps      B
 4    kernel puts B in wait queue, picks C        C
 5    (timer) scheduler switches C -> A           A
 6    A: unlock() -> kernel wakes B (B is ready)  A
 7    (later) scheduler switches A -> B           B
 8    B: lock() -> ok                             B
```

3단계에서 B는 CPU를 쥐고 돌지 않는다. 커널의 대기 큐(wait queue)에 들어가 잠들고, 그동안 C가 CPU를 쓴다. 스핀락의 단일 CPU 문제는 사라졌다.

### 생기는 문제: 잠들고 깨는 비용

대가는 비용이다. B 한 번이 락을 기다리는 데 다음이 든다.

- 잠들 때 시스템 콜 한 번과 컨텍스트 스위칭 한 번(3~4단계)
- 깨울 때 시스템 콜 한 번(6단계)
- 다시 돌 때 컨텍스트 스위칭 한 번(7단계)

컨텍스트 스위칭은 레지스터 교체만이 아니다. 캐시와 TLB가 식는 간접 비용까지 붙는다. 이 비용은 [컨텍스트 스위칭 글](/posts/cs/os/process-vs-thread-context-switching)에서 자세히 다뤘다. 임계 구역이 명령어 몇 개라면 이 비용이 기다릴 시간보다 훨씬 크다.

### 또 하나의 함정: 깨우기 신호를 놓치는 경쟁

잠드는 락에는 미묘한 경쟁 조건이 하나 더 있다. B가 "락이 잡혀 있네, 자야겠다"라고 판단한 직후, 실제로 잠들기 직전에 끊겼다고 하자. 그 사이 A가 unlock을 하고 "깨울 스레드"를 찾는다. B는 아직 큐에 없으니 아무도 깨우지 않는다. 그다음 B가 잠든다. 이제 B를 깨워 줄 사람이 없다.

OSTEP은 이것을 wakeup/waiting race라고 부른다. 해결책의 핵심은 **"확인하고 잠들기"를 커널 안에서 한 덩어리로 처리**하는 것이다. Solaris는 `setpark()`라는 호출을 따로 두었다. Linux는 6절의 futex가 같은 일을 한다.

### 뮤텍스에는 주인이 있다

뮤텍스는 잡은 스레드가 풀어야 한다는 소유권(ownership) 개념을 갖는다. POSIX 표준은 이 규칙을 어겼을 때의 동작을 뮤텍스 종류별로 정해 둔다. 아래 표는 기본인 non-robust 뮤텍스 기준이다.

| 뮤텍스 종류 | 남이 잡은 뮤텍스를 unlock | 주인이 같은 뮤텍스를 다시 lock |
|---|---|---|
| `PTHREAD_MUTEX_ERRORCHECK` | 에러(`EPERM`) | 에러 |
| `PTHREAD_MUTEX_RECURSIVE` | 에러(`EPERM`) | 허용(횟수를 센다) |
| `PTHREAD_MUTEX_NORMAL` | 정의되지 않은 동작 | 교착 상태(deadlock) |
| `PTHREAD_MUTEX_DEFAULT` | 정의되지 않은 동작 | 정의되지 않은 동작 |

기본값으로 만든 뮤텍스를 엉뚱한 스레드가 풀면 표준은 아무것도 약속하지 않는다. 소유권 규칙은 프로그래머가 지켜야 하는 약속이다. 이 소유권이 다음 절의 세마포어와 갈리는 지점이다.

## 5. 세마포어: 개수를 세는 락

락은 "한 번에 하나"만 표현한다. 그런데 자원이 여러 개인 경우가 있다. DB 커넥션 풀에 커넥션이 3개 있다면 동시에 3개 스레드까지는 들어가도 된다. 4번째부터 기다려야 한다.

핵심 아이디어는 이렇다. **남은 자원 개수를 정수로 들고 있다가, 0이면 기다리게 한다.** 이것이 **세마포어**(semaphore)다. Dijkstra가 만든 동기화 도구로, POSIX에서는 두 연산으로 다룬다.

- `sem_wait()`: 값을 1 줄인다. 값이 0이라서 줄일 수 없으면 0보다 커질 때까지 잠든다.
- `sem_post()`: 값을 1 늘린다. 잠든 스레드가 있으면 하나를 깨운다.

Dijkstra는 이 둘을 P와 V라고 불렀다. 교과서에서 P/V가 보이면 같은 연산이다.

### 단계별 동작: 커넥션 3개짜리 풀

값을 3으로 초기화하고 스레드 T1~T5가 차례로 커넥션을 요청한다고 하자.

```
step  event                 sem value  holding      waiting
----  --------------------  ---------  -----------  -------
 1    T1 sem_wait()         3 -> 2     T1
 2    T2 sem_wait()         2 -> 1     T1 T2
 3    T3 sem_wait()         1 -> 0     T1 T2 T3
 4    T4 sem_wait()         0 (block)  T1 T2 T3     T4
 5    T5 sem_wait()         0 (block)  T1 T2 T3     T4 T5
 6    T2 sem_post()         0 -> 1     T1 T3        T4 T5
 7    T4 wakes up           1 -> 0     T1 T3 T4     T5
```

6단계에서 T2가 커넥션을 반납하면 값이 1 늘어난다. 7단계에서 잠들어 있던 T4가 깨어나 그 1을 가져간다. 네 번째 스레드가 동시에 들어가는 일은 없다. 이렇게 0 이상의 임의의 값을 갖는 세마포어를 **카운팅 세마포어**(counting semaphore)라고 한다.

값을 1로 초기화하면 한 번에 한 스레드만 들어간다. 이것을 **이진 세마포어**(binary semaphore)라고 하고, 동작만 보면 락과 같다.

### 뮤텍스와의 차이: 주인이 없다

그렇다면 이진 세마포어와 뮤텍스는 같은가? 아니다. 세마포어에는 소유자가 없다. `sem_post()`는 어떤 스레드든 부를 수 있다. 값을 줄인 스레드와 늘리는 스레드가 달라도 된다.

이 차이는 장점이기도 하고 위험이기도 하다.

**장점: 신호 보내기에 쓸 수 있다.** 값을 0으로 초기화하면 "다른 스레드가 일을 끝낼 때까지 기다리기"를 만들 수 있다. 소비자는 `sem_wait()`로 잠들고, 생산자는 일을 마친 뒤 `sem_post()`로 깨운다. 잡는 쪽과 푸는 쪽이 원래 다른 패턴이라 뮤텍스로는 표현할 수 없다.

**위험: 락으로 쓰면 실수를 못 잡는다.** 이진 세마포어를 락처럼 쓰다가 엉뚱한 스레드가 `sem_post()`를 부르면, 아무 에러 없이 두 스레드가 임계 구역에 들어간다. `ERRORCHECK` 뮤텍스라면 `EPERM`으로 잡혔을 실수다.

주인을 모른다는 것은 우선순위 역전(priority inversion) 대응에도 불리하다. 낮은 우선순위 스레드가 쥔 락을 높은 우선순위 스레드가 기다릴 때, 흔한 대응은 쥔 스레드의 우선순위를 잠시 올려 주는 것이다. 그러려면 누가 쥐었는지 알아야 한다. 세마포어는 그것을 모른다. 실제로 POSIX도 우선순위 상속(`PTHREAD_PRIO_INHERIT`)을 뮤텍스 속성으로만 제공하고, 세마포어에는 이런 옵션이 없다. 우선순위 역전 자체는 [교착 상태와 우선순위 역전 글](/posts/cs/os/deadlock-priority-inversion)에서 다룬다.

| | 뮤텍스 | 이진 세마포어 | 카운팅 세마포어 |
|---|---|---|---|
| 동시에 들어가는 수 | 1 | 1 | 초기값 N |
| 소유자 | 있다(잡은 스레드) | 없다 | 없다 |
| 다른 스레드가 풀기 | 금지(에러 또는 정의되지 않음) | 허용 | 허용 |
| 주 용도 | 임계 구역 보호 | 신호 보내기, 순서 맞추기 | 개수가 정해진 자원 관리 |

정리하면, 임계 구역을 지킬 때는 뮤텍스를 쓴다. 개수를 세거나 스레드 사이에 신호를 보낼 때 세마포어를 쓴다.

## 6. Linux futex: 경합이 없으면 유저 공간에서 끝난다

4절의 뮤텍스에는 아직 큰 낭비가 하나 남아 있다. 락을 잡고 풀 때마다 커널에 들어간다면, **아무도 기다리지 않을 때도** 시스템 콜 비용을 낸다. 그런데 실제 프로그램의 락은 대부분 경합 없이 잡히고 풀린다.

핵심 아이디어는 이렇다. **락 상태는 유저 공간의 정수 하나에 두고 원자 명령으로 바꾼다. 커널은 누군가 정말 잠들어야 할 때만 부른다.** 이것이 Linux의 **futex**(fast user-space mutex)다. `futex(7)` man page는 경합이 없는 경우 futex 동작이 전부 유저 공간에서 끝나고, 커널은 경합이 생겼을 때 중재만 한다고 설명한다.

futex 자체는 4바이트(32비트) 정수다. 64비트 시스템에서도 32비트다. 커널이 제공하는 핵심 연산은 둘이다.

| 연산 | 하는 일 |
|---|---|
| `FUTEX_WAIT(addr, val)` | `*addr`가 아직 `val`이면 잠든다. 값이 다르면 잠들지 않고 바로 `EAGAIN`으로 돌아온다. |
| `FUTEX_WAKE(addr, n)` | `addr`에서 잠든 스레드를 최대 n개 깨운다. |

`FUTEX_WAIT`의 "값 확인, 비교, 잠들기"는 커널 안에서 원자적으로 일어난다. 4절의 "깨우기 신호를 놓치는 경쟁"을 바로 이 한 줄이 막는다. 잠들기 직전에 누가 락을 풀었다면 값이 바뀌었을 테니, 커널은 재우지 않고 돌려보낸다.

### 상태 세 개짜리 뮤텍스

Ulrich Drepper의 "Futexes Are Tricky"는 futex로 뮤텍스를 만드는 과정을 단계별로 보여 준다. 최종 형태는 정수 하나에 세 상태를 담는다.

| 값 | 의미 |
|---|---|
| 0 | 풀림(unlocked) |
| 1 | 잠김, 대기자 없음 |
| 2 | 잠김, 대기자가 있을 수 있음 |

코드는 짧지만 한 줄 한 줄이 의미가 있다(Drepper의 `mutex2`를 C 스타일로 옮겼다). `cmpxchg(v, old, new)`는 `v`가 `old`일 때만 `new`로 바꾸고 이전 값을 돌려주는 원자 명령이다. `atomic_dec`는 1을 빼고 이전 값을 돌려준다.

```c
void lock(int *val) {
    int c;
    if ((c = cmpxchg(val, 0, 1)) != 0) {           // fast path 실패
        do {
            if (c == 2 || cmpxchg(val, 1, 2) != 0) // "대기자 있음"으로 표시
                futex_wait(val, 2);                // 값이 2일 때만 잠든다
        } while ((c = cmpxchg(val, 0, 2)) != 0);   // 깨어나면 다시 시도
    }
}

void unlock(int *val) {
    if (atomic_dec(val) != 1) {   // 이전 값이 2였다 = 대기자가 있을 수 있다
        *val = 0;
        futex_wake(val, 1);       // 한 명만 깨운다
    }
}
```

### 경합이 없을 때: 시스템 콜 0번

T1 혼자 락을 잡고 푼다.

```
step  T1                              val   syscall
----  ------------------------------  ----  -------
 1    lock:   cmpxchg(val,0,1) -> 0   0->1  none
 2    (critical section)              1
 3    unlock: atomic_dec -> old 1     1->0  none
```

원자 명령 두 번으로 끝난다. 커널에는 한 번도 들어가지 않는다. 이것이 "경합이 없으면 유저 공간에서 끝난다"의 실제 모습이다.

### 경합이 있을 때: 그때만 커널로

T1이 락을 쥔 상태에서 T2가 들어온다.

```
step  T1                              T2                               val
----  ------------------------------  -------------------------------  ---
 1    cmpxchg(val,0,1) -> 0, got it                                    1
 2                                    cmpxchg(val,0,1) -> 1, fail      1
 3                                    cmpxchg(val,1,2) -> 1, mark      2
 4                                    futex_wait(val,2) -> sleeps      2
 5    atomic_dec -> old 2                                              1
 6    val = 0; futex_wake(val,1)                                       0
 7                                    wakes; cmpxchg(val,0,2) -> 0     2
```

T2는 3단계에서 값을 2로 바꿔 "기다리는 사람이 있다"고 표시한다. 그래서 T1의 unlock은 5단계에서 이전 값이 2인 것을 보고 `futex_wake`를 부른다. 시스템 콜은 경합이 생긴 이 경우에만 나간다.

7단계에서 T2는 1이 아니라 2로 락을 잡는다. 자기 말고 다른 대기자가 있는지 알 수 없으니 보수적으로 "있을 수 있음"을 택한 것이다. 그 결과 T2의 unlock은 대기자가 없어도 `futex_wake`를 한 번 부를 수 있다. 정확성을 위해 경합 상황에서 조금 더 내는 비용이다.

### 왜 이렇게까지 복잡한가

Drepper가 처음 보여 주는 단순한 버전은 카운터를 계속 올리고, unlock에서 매번 `futex_wake`를 부른다. 대기자가 없어도 시스템 콜을 하는 셈이다. 정확성 버그도 두 개 있었다.

- **라이브락**(livelock): 두 스레드가 번갈아 카운터를 올리면, 상대가 값을 바꿔 놓은 탓에 서로의 `futex_wait`가 값 불일치로 계속 튕겨 나온다. 아무도 잠들지 못하고 카운터만 오른다. Drepper는 이 버그가 NPTL(glibc의 POSIX 스레드 구현)에 몇 달 동안 있었고, 4프로세서 머신의 실제 애플리케이션이 이것을 고친 뒤 8~10배 빨라졌다고 적었다.
- **오버플로**: 대기자가 올 때마다 카운터를 무조건 올리므로 2^32번 뒤에는 0으로 돌아와 락이 저절로 풀린다.

세 상태 버전은 이 셋을 모두 고친 결과다.

`futex_wake(val, 1)`로 한 명만 깨우는 것도 의도된 선택이다. 대기자가 100명일 때 모두 깨워도 락은 한 명만 얻는다. 나머지 99명은 바로 다시 잠든다. 그동안 100개 스레드가 같은 정수가 있는 캐시 라인(cache line, CPU 캐시가 메모리를 옮기는 64바이트 단위)을 두고 CPU 사이에서 주고받으니 비용이 크다.

이 문서의 제목처럼 futex는 까다롭다. Drepper는 futex 제안자들이 배포한 유저 레벨 예제 코드조차 집필 당시 틀려 있었다고 적었다. 애플리케이션 코드에서 futex를 직접 쓸 일은 거의 없다. glibc의 `pthread_mutex_lock`이 이미 futex 위에서 이 일을 해 준다. OSTEP이 소개하는 glibc NPTL 코드는 정수의 최상위 비트를 "잠김" 표시로, 나머지 비트를 대기자 수로 쓴다. 표현은 다르지만 "경합 없으면 원자 명령만, 있으면 futex"라는 구조는 같다.

### 조금 돌다가 잠들기

스핀락과 뮤텍스는 둘 중 하나를 고르는 문제만은 아니다. 락이 곧 풀릴 것 같으면 잠깐 돌고, 그래도 안 풀리면 잠드는 방식이 있다. 이것을 **2단계 락**(two-phase lock)이라고 한다. 이름은 같지만 DB 트랜잭션의 [2PL(two-phase locking)](/posts/cs/database/serializability-2pl-ssi)과는 다른 개념이다. 여기서 두 단계는 "돌기"와 "잠들기"를 뜻한다. OSTEP은 이 아이디어가 1960년대 초 Dahm Lock까지 거슬러 올라간다고 소개한다. 위의 futex 뮤텍스도 fast path에서 원자 명령을 한 번 시도한 뒤 잠드니, 한 번만 도는 2단계 락으로 볼 수 있다.

참고로 공유 메모리에 놓인 futex는 프로세스마다 가상 주소가 달라도 같은 실제 메모리를 가리키면 같은 futex로 취급된다. 그래서 공유 메모리에 정수를 두면 프로세스 사이의 락도 같은 방식으로 만들 수 있다.

### 한 표로 비교

| | 스핀락 | 뮤텍스(매번 커널) | futex 기반 뮤텍스 | 세마포어 |
|---|---|---|---|---|
| 못 잡으면 | CPU를 쥐고 돈다 | 커널에서 잠든다 | 커널에서 잠든다 | 값이 0이면 잠든다 |
| 경합 없을 때 비용 | 원자 명령 1번 | 시스템 콜 | 원자 명령만 | 구현에 따라 다름 |
| 유리한 상황 | 짧은 구간, 멀티코어, 잠들 수 없는 문맥 | 긴 구간 | 대부분의 경우 | 개수 관리, 신호 |
| 주의할 점 | 단일 CPU, 선점, 기아 | 잠들고 깨는 비용 | 직접 구현은 어렵다 | 소유자가 없다 |

## 7. 다음 글 예고: 조건 기다리기와 원자 명령

이 글의 락은 "한 번에 한 스레드만 들어간다"까지만 보장한다. 실제 동시성 코드는 그 이상을 원한다. 예를 들어 "큐에 일감이 생길 때까지 기다리기"는 상호 배제만으로는 깔끔하게 표현되지 않는다. 락을 쥔 채 큐를 계속 들여다보면 스핀락과 같은 낭비가 생긴다. 이 문제는 [조건 변수와 모니터 글](/posts/cs/os/condition-variable-monitor)에서 다룬다.

또 이 글은 test-and-set과 compare-and-exchange 같은 원자 명령을 "하드웨어가 해 준다"고 넘어갔다. 이 명령들이 멀티코어에서 어떻게 원자성을 보장하는지, 락 없이 이 명령만으로 자료구조를 만들면 어떤 문제(ABA)가 생기는지는 [CAS와 lock-free 글](/posts/cs/architecture/cas-lock-free-aba)에서 이어 간다.

## 결론

- `count++`는 load, add, store 세 단계라서 중간에 끼어들기가 생긴다. 락은 이 구간을 한 번에 한 스레드만 지나가게 만든다.
- 락의 종류는 못 잡았을 때 기다리는 방식으로 갈린다. 스핀락은 돌고, 뮤텍스는 잠든다. 짧은 구간과 멀티코어에서는 도는 쪽이, 긴 구간에서는 잠드는 쪽이 싸다.
- 세마포어는 개수를 세는 동기화 도구다. 뮤텍스와 가장 큰 차이는 소유자가 없다는 점이다. 그래서 신호 보내기에는 좋고, 임계 구역 보호에는 뮤텍스가 안전하다.
- Linux futex는 락 상태를 유저 공간 정수에 두고, 경합이 생겼을 때만 커널에 들어간다. `FUTEX_WAIT`가 값을 확인하고 잠드는 것을 원자적으로 처리해 깨우기 신호를 놓치는 경쟁을 막는다.
