## 개요

[앞 글](/posts/cs/os/mutex-semaphore-spinlock/)에서 뮤텍스와 세마포어를 봤다. 뮤텍스는 "한 번에 한 스레드만 들어간다"는 상호 배제를 해결한다. 그런데 "어떤 조건이 참이 될 때까지 기다리기"는 뮤텍스만으로 풀리지 않는다.

이 글이 답하는 질문은 두 가지다.

- 조건 변수(condition variable)는 무엇을 해결하고, 왜 `wait`를 `while`로 감싸야 하는가?
- 신호를 보내는 `signal`과 `notifyAll` 중 무엇을 쓰고, Java의 `synchronized`는 이것과 어떻게 이어지는가?

예시는 처음부터 끝까지 크기가 제한된 생산자-소비자 버퍼 하나로 간다. 뮤텍스와 세마포어 자체는 앞 글에서 다뤘으니 여기서는 다시 설명하지 않는다.

---

## 1. 왜 뮤텍스만으로는 부족한가

크기가 3인 버퍼가 있고, 생산자 스레드가 넣고 소비자 스레드가 꺼낸다. 버퍼가 비어 있으면 소비자는 기다려야 하고, 가득 차 있으면 생산자가 기다려야 한다.

뮤텍스만 쓰면 이렇게 짜게 된다.

```java
// 뮤텍스만 쓴 소비자: 바쁜 대기(busy waiting)
while (true) {
    lock.lock();
    if (!queue.isEmpty()) {
        item = queue.poll();
        lock.unlock();
        break;
    }
    lock.unlock();   // 비었으니 풀고 다시 확인
}
```

동작은 하지만 큐가 빌 동안 CPU를 100% 쓰며 계속 확인한다. 스레드가 100개면 100개가 돌면서 낭비한다.

그렇다고 `sleep(10ms)`을 끼우면 반응이 최대 10ms 늦고, 짧게 줄이면 다시 CPU를 쓴다. 필요한 것은 "조건이 참이 될 때까지 CPU를 쓰지 않고 잠들었다가, 참이 되면 누가 깨워 주는" 장치다.

**조건 변수**는 "조건이 바뀔 때까지 잠드는 스레드들의 대기실"이다. 스레드는 락을 쥔 채로 조건을 확인하고, 거짓이면 대기실에서 잠든다. 조건을 바꾼 스레드가 대기실에 신호를 보내면 깨어난다.

---

## 2. 핵심 아이디어: 락을 풀고 잠드는 동작을 쪼개지 않는다

조건 변수의 연산은 두 개다.

| 연산 | 하는 일 |
|---|---|
| `wait(cv, m)` | 뮤텍스 `m`을 풀고 `cv`의 대기 큐에 들어가 잠든다. 깨어나면 `m`을 다시 잡고 돌아온다. |
| `signal(cv)` / `broadcast(cv)` | 대기 큐의 스레드 하나 / 전부를 깨운다. 대기자가 없으면 아무 일도 일어나지 않는다. |

한 문장으로 줄이면 이렇다. **`wait`는 "락 해제 + 대기 등록"을 쪼갤 수 없는 한 동작(원자적, atomic)으로 처리한다.** POSIX 명세도 `pthread_cond_wait`가 뮤텍스를 원자적으로 풀고 스레드를 블록시킨다고 적고 있다.

그리고 두 번째 약속이 있다. **조건의 "상태"는 변수에 남지만, 신호(signal)는 남지 않는다.** 신호는 이벤트가 아니라 힌트다. 깨울 대기자가 없을 때 보낸 신호는 그냥 사라진다. 그래서 조건은 항상 "상태 변수(술어, predicate)"로 확인해야 한다. 여기서 술어는 "큐가 비어 있지 않다" 같은 참/거짓 식이다.

## 3. 소비자와 생산자의 정석 패턴

의사 코드로 먼저 본다.

```text
// 소비자
lock(m)
while (queue.empty())      // if 가 아니라 while
    wait(cv, m)            // m 해제 + 대기 등록(원자적), 깨어나면 m 재획득
item = queue.pop()
unlock(m)

// 생산자
lock(m)
queue.push(x)              // 조건을 바꾸는 쪽도 같은 락 안에서
signal(cv)
unlock(m)
```

숫자로 따라가 보자. 큐가 비어 있고 소비자 C가 먼저 온다.

1. C가 `lock(m)`을 잡고 `queue.empty()`를 확인한다. 참이다 (크기 0).
2. C가 `wait`에 들어간다. `m`이 풀리고 C는 대기 큐에서 잠든다. CPU는 쓰지 않는다.
3. 생산자 P가 `lock(m)`을 잡는다. 이미 풀려 있으므로 바로 잡힌다.
4. P가 `push(x)` 후 `signal`을 보낸다. 큐 크기가 1이 된다.
5. P가 `unlock(m)`한다. C가 깨어나 `m`을 다시 잡고, `while` 조건을 다시 검사한다. 이제 거짓이므로 `pop()`한다.

여기서 락과 대기가 한 쌍인 이유가 보인다. P가 `m`을 잡을 수 있었다는 사실 자체가 "C가 이미 대기 큐에 등록됐다"는 증거다. 락을 풀 때 등록도 함께 끝났기 때문이다.

---

## 4. 락 없이, 쪼개서 하면 신호를 잃는다 (lost wakeup)

위의 원자성이 깨지면 어떻게 되는지 본다. 검사를 락 밖에서 하고, 그 뒤에 잠드는 코드다.

```text
소비자 C                          생산자 P
---------------------------       ---------------------------
1. 큐 비었나? -> 비어 있음
                                  2. push(x) + signal (대기자 없음)
3. wait() 진입 -> 영원히 잠듦
```

2번의 신호는 대기자가 없어서 사라졌고, C는 이미 큐에 항목이 있는데도 잠든다. 이것이 **lost wakeup**(신호 유실)이다. [앞 글](/posts/cs/os/mutex-semaphore-spinlock/)의 futex가 "값 확인과 잠들기"를 커널 안에서 한 덩어리로 처리한 것도 같은 틈을 막기 위해서였다. 증상이 까다롭다. 특정 타이밍에서만 요청 처리가 멈추고, CPU는 한가하며, 스레드 덤프에 워커 여럿이 `wait` 상태로 찍힌다.

해결은 이미 3절에 있다. 검사와 `wait`를 같은 뮤텍스로 감싸면 P의 2번은 1번과 3번 사이에 끼어들 수 없다. 반대로 조건을 바꾸는 쪽(P)도 같은 락 안에서 바꿔야 한다. 락 없이 `queue`를 바꾸면 C의 검사와 겹쳐 같은 틈이 다시 생긴다.

| 흔한 실수 | 결과 |
|---|---|
| 락 밖에서 조건을 검사하고 `wait` | 검사와 잠들기 사이의 틈에서 신호 유실 |
| 조건을 바꾸는 쪽이 락 없이 변수를 변경 | 소비자의 검사와 겹쳐 유실 |
| `signal` 전에 예외로 빠져나감 | 조건은 바뀌었는데 아무도 못 깨움 |

## 5. 왜 `if`가 아니라 `while`인가

패턴에서 `while (queue.empty())`가 눈에 띈다. `if`로 바꾸면 안 되는 이유는 두 가지다.

**첫째, 가짜 깨어남(spurious wakeup).** POSIX는 신호가 없는데도 `wait`가 반환되는 것을 허용하고, 그러니 술어를 다시 평가하라고 명시한다. Java의 `Object.wait` 문서도 알림, 인터럽트, 타임아웃 없이 깨어날 수 있으니 조건을 검사하고 거짓이면 계속 기다리라고 한다. 실제로는 드물지만 명세상 허용되므로 방어는 필수다.

**둘째, 깨어난 뒤 조건이 다시 거짓이 될 수 있다.** 깨어난 스레드는 락을 곧바로 얻지 못하고, 다른 스레드와 평소처럼 경쟁해서 얻는다. 예를 들어 이렇게 된다.

1. 큐에 항목이 1개 들어온다. 소비자 C1과 C2가 둘 다 깨어난다.
2. C1이 락을 먼저 잡고 항목을 꺼낸다. 큐 크기는 0이다.
3. C2가 뒤늦게 락을 잡고 돌아온다. 깨어났지만 조건은 이미 거짓이다.

`if`였다면 C2는 빈 큐에서 `pop()`을 한다. `while`이면 다시 검사하고 다시 잠든다.

이처럼 "signal한 스레드는 계속 실행하고, 깨어난 스레드는 나중에 락을 경쟁해서 되찾는" 방식을 **Mesa 방식** 모니터라고 부르며, 대부분의 실제 구현이 이 방식이다. 이름은 이 방식을 쓴 Xerox의 Mesa 언어에서 왔다. 반대로 **Hoare 방식**은 signal 즉시 락과 CPU를 대기자에게 넘겨서, 깨어난 스레드가 조건이 참인 상태를 보장받는다. Mesa 방식은 signal한 스레드를 멈춰 세우지 않으므로 구현이 단순하고, 가짜 깨어남도 같은 규칙(다시 검사)으로 흡수한다. 대신 깨어남을 "참일 수도 있다는 힌트"로만 취급해야 하고, 그 대가가 `while` 재검사다(OSTEP 30장).

## 6. 모니터와 Java: `synchronized` + `wait`/`notifyAll`

**모니터**(monitor)는 뮤텍스, 조건 변수, 그 둘이 보호하는 상태를 한 덩어리로 묶은 개념이다. 락과 조건을 따로 다루다 실수하지 않도록, "이 상태는 이 락 안에서만 만진다"는 규칙을 구조로 강제한 것이다.

Java는 모든 객체가 모니터 하나를 가진다. `synchronized`가 락이고, `wait`/`notify`/`notifyAll`이 조건 변수 연산이다. 크기 제한 버퍼는 이렇게 쓴다.

```java
class BoundedBuffer<T> {
    private final Object[] items = new Object[3];
    private int head = 0, tail = 0, count = 0;

    public synchronized void put(T x) throws InterruptedException {
        while (count == items.length) {   // 가득 참: 술어를 while로 검사
            wait();                        // 모니터 해제 + 대기
        }
        items[tail] = x;
        tail = (tail + 1) % items.length;
        count++;
        notifyAll();                       // 소비자(와 다른 생산자)를 깨움
    }

    @SuppressWarnings("unchecked")
    public synchronized T take() throws InterruptedException {
        while (count == 0) {              // 비어 있음
            wait();
        }
        T x = (T) items[head];
        head = (head + 1) % items.length;
        count--;
        notifyAll();                       // 빈 자리가 생겼음을 알림
        return x;
    }
}
```

몇 가지를 짚는다.

- `count`를 읽고 바꾸는 모든 코드가 `synchronized` 안에 있다. 4절에서 본 "조건을 바꾸는 쪽도 같은 락 안에서"를 지킨 것이다.
- `wait`, `notify`, `notifyAll`은 해당 객체의 모니터를 쥐고 있지 않으면 `IllegalMonitorStateException`이 난다. 락 밖 호출을 언어가 막아 주는 셈이다.
- `wait`는 그 객체의 락만 풀어 준다. 다른 객체의 `synchronized`를 중첩해서 쥔 채 `wait`하면 그 락은 계속 잡혀 있으므로 데드락 위험이 있다.
- 한 객체에 대기실이 하나뿐이다. 생산자와 소비자가 같은 대기실에서 잠들기 때문에 `put`의 알림은 소비자뿐 아니라 다른 생산자도 깨운다. 다음 절의 선택과 이어진다.

## 7. signal이냐 notifyAll이냐

위 버퍼에서 `notifyAll`을 `notify`(하나만 깨움)로 바꾸면 어떻게 될까. 따라가기 쉽게 버퍼 크기를 1로 줄이고, 소비자 C1, C2와 생산자 P 하나가 있다고 하자(OSTEP 30장의 예시).

1. 버퍼가 비어 있어 C1과 C2가 둘 다 `wait`로 잠든다.
2. P가 항목 하나를 넣고 `notify`를 한다. C1이 깨어난다(아직 락을 얻기 전이다).
3. P가 하나 더 넣으려 하지만 버퍼가 가득 차 있어 P도 잠든다. 대기실에는 C2와 P가 있다.
4. C1이 락을 얻어 항목을 꺼내고 `notify`를 한다. 누구를 깨울지는 Java 문서에 "구현 재량"이라고 적혀 있다.
5. 운 나쁘게 P가 아니라 C2가 깨어난다. C2는 빈 버퍼를 보고 다시 잠든다.
6. 이제 C1(다음 `take()` 호출), C2, P가 모두 잠들어 있고 깨워 줄 스레드가 없다. 자리가 났다는 사실을 알아야 할 P가 끝내 깨어나지 못한 것이다.

조건이 서로 다른 대기자가 섞여 있으면 "엉뚱한 스레드가 깨어 진행이 멈추는" 일이 생긴다. 반대로 `notifyAll`은 모두 깨워서 각자 술어를 다시 확인하게 하므로 정확성이 단순하다.

| 선택 | 얻는 것 | 잃는 것 |
|---|---|---|
| `signal`(1개 깨움) | 불필요한 깨움이 없어 효율적 | 조건이 섞여 있으면 엉뚱한 스레드가 깨어 진행이 멈출 수 있음 |
| `notifyAll`(전부 깨움) | 각자 재검사하므로 정확성이 단순 | 대기자가 많으면 전부 깨어 락을 경쟁하고 대부분 다시 잠듦 |
| 조건별 조건 변수 분리 | 정확히 필요한 대기자만 깨움 | 설계와 코드가 복잡해짐 |
| 세마포어 | 카운터를 내장해 신호가 유실되지 않음 | 임의의 조건을 표현하기 어렵고, 오용하면 카운트가 어긋남 |

대기자가 모두 같은 조건을 기다리고 하나만 진행할 수 있다면 `signal`이 효율적이다. 조건이 섞여 있으면 `notifyAll`이 안전하다. 대기자가 매우 많아 `notifyAll`이 부담이면 조건별로 대기실을 나눈다.

`notifyAll`의 비용 문제를 **thundering herd**(우르르 깨어남)라고 한다. 100개 스레드가 깨어나도 하나만 일하고 99개는 락을 얻고 조건을 확인한 뒤 다시 잠든다. 문맥 전환과 락 경합만 낭비한다.

같은 모양이 소켓 대기에서도 나타난다. 여러 프로세스가 같은 listen 소켓을 `epoll`로 기다리면 연결 하나에 전부 깨어난다. 이 경우의 대응(`EPOLLEXCLUSIVE`, `SO_REUSEPORT`)은 [epoll 글](/posts/cs/os/io-multiplexing-epoll-io-uring/)에서 다룬다.

Java에서 대기실을 나누려면 `java.util.concurrent.locks.ReentrantLock` 하나에서 `newCondition()`을 여러 개 만들어 `notFull`, `notEmpty`로 분리한다. `Condition` API 문서의 예시가 바로 이 크기 제한 버퍼다. 그러면 `put`은 `notEmpty`에서 기다리는 소비자만, `take`는 `notFull`에서 기다리는 생산자만 깨우므로 5단계 같은 엉뚱한 깨움이 생기지 않는다. 이때도 `await`를 `while`로 감싸는 규칙은 같다.

## 8. 모니터와 virtual thread pinning

`synchronized`가 모니터라는 사실은 가상 스레드(virtual thread)와 만나면 실무 문제가 된다. 기존 글 [Virtual Thread와 pinning](/posts/dev/concurrency/virtual-thread-pinning/)에서 다뤘듯, 가상 스레드가 `synchronized` 안에서 블로킹하면 운반 스레드(carrier thread)를 놓지 못하고 고정(pinning)되는 문제가 있었다.

이 글의 맥락에서 눈여겨볼 점은 `wait`다. 모니터 대기는 "락을 풀고 잠드는" 연산인데, 고정된 상태에서는 잠든 가상 스레드가 운반 스레드까지 같이 붙잡고 있었다. 생산자-소비자 버퍼의 `take()`가 오래 기다리는 구조라면 영향이 크다.

다만 이 동작은 JDK 버전에 따라 다르다. JEP 491은 JDK 24에서 가상 스레드가 `synchronized` 안이나 모니터 대기 중에도 내려올(unmount) 수 있게 했고, `Object.wait()`도 대기 중과 모니터를 다시 얻는 동안 가상 스레드를 내린다고 밝히고 있다. 네이티브 프레임이 스택에 있는 경우 등 일부 고정은 남아 있다. 사용 중인 JDK 버전이 24 이전이라면 위 글의 pinning 논의가 그대로 적용된다.

## 결론

- 뮤텍스는 상호 배제를, 조건 변수는 "조건이 참이 될 때까지 CPU 없이 기다리기"를 해결한다. 둘을 묶은 것이 모니터다.
- `wait`는 락 해제와 대기 등록을 원자적으로 처리한다. 그래서 반드시 락을 쥔 채 호출하고, 조건을 바꾸는 쪽도 같은 락 안에서 바꿔야 신호 유실이 없다.
- 신호는 저장되지 않는 힌트다. 가짜 깨어남과 Mesa 방식 때문에 `wait`는 항상 `while`로 감싸 술어를 다시 검사한다.
- 대기자 조건이 모두 같으면 `signal`, 섞여 있으면 `notifyAll`, 대기자가 많아 비용이 크면 조건별로 대기실을 나눈다.
- Java의 `synchronized`는 모니터이고, 가상 스레드와의 관계는 JDK 버전에 따라 달라진다.

락을 여러 개 쓰기 시작하면 이번에는 스레드끼리 서로의 락을 기다리며 멈추는 문제가 생긴다. [다음 글](/posts/cs/os/deadlock-priority-inversion/)에서 교착 상태와 우선순위 역전을 본다.
