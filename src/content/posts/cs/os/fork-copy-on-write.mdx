## 개요

Redis에 쓰기 트래픽이 많은 상태에서 BGSAVE가 돌면 서버 메모리가 눈에 띄게 늘어난다. 24GB를 쓰던 인스턴스가 스냅샷 중에는 26GB, 심하면 40GB 가까이 가기도 한다. 데이터를 복사해 둔 것도 아닌데 왜 늘어날까?

이 글은 두 가지를 답한다.

- `fork()`는 24GB짜리 프로세스를 어떻게 순식간에(그러나 완전히 공짜는 아니게) 복제하는가
- 복제된 뒤에는 어떤 규칙으로 메모리가 늘어나고, 얼마나 늘어나는가

주소 변환과 페이지 테이블이 낯설다면 [가상 메모리, 페이지 테이블, TLB](/posts/cs/os/virtual-memory-page-table-tlb/)를 먼저 읽으면 좋다. Redis에서 "어떤 값을 어디에 저장할까"를 정하는 이야기는 [Redis vs RDB](/posts/dev/cache/redis-vs-rdb-loss-risk/)에서 다뤘고, 이 글은 그 아래층인 OS가 스냅샷을 어떻게 만드는지에 집중한다.

## 1. 왜 fork()가 필요한가: 움직이는 데이터의 스냅샷

Redis가 RDB 파일을 만들려면 "어느 한 시점의 전체 데이터"를 디스크에 써야 한다. 24GB를 쓰는 데 수십 초가 걸린다. 그 사이 클라이언트는 계속 `SET`을 보낸다.

단순하게 하면 두 가지 방법이 있다.

| 방법 | 문제 |
|---|---|
| 쓰는 동안 요청을 멈춘다 | 수십 초간 서비스 중단 |
| 쓰면서 계속 요청을 받는다 | 파일에 이전 값과 새 값이 섞여 한 시점의 스냅샷이 아니다 |

**핵심 아이디어: 프로세스를 통째로 복제(fork)해서, 자식은 복제 시점의 메모리를 읽어 파일에 쓰고, 부모는 계속 서비스한다.**

그런데 24GB를 정말 복사하면 시간도 오래 걸리고 메모리도 두 배가 필요하다. 그래서 OS는 복사를 미룬다.

## 2. fork()가 실제로 하는 일

`fork()`(프로세스를 복제하는 시스템 콜)는 자식 프로세스를 만들 때 **데이터 페이지가 아니라 페이지 테이블만 복사한다.** 페이지 테이블은 [앞 글](/posts/cs/os/virtual-memory-page-table-tlb/)에서 본, 가상 주소를 물리 페이지에 대응시키는 표다. Linux man page도 fork의 비용을 "부모의 페이지 테이블을 복제하는 시간과 메모리"라고 설명한다.

Redis 문서의 계산을 따라가 보자. 4KB 페이지를 쓰는 24GB 프로세스에서 페이지 테이블의 크기는 이렇다.

```
24GB / 4KB = 6,291,456 페이지
페이지 하나당 항목 8B  ->  6,291,456 x 8B = 48MB
```

48MB를 복사하는 건 24GB를 복사하는 것보다 500배 작은 일이다. 하지만 공짜는 아니다. 이 복사가 끝날 때까지 부모 프로세스는 멈춰 있다. fork 비용은 메모리 크기(페이지 수)에 비례한다.

복사 직후 부모와 자식의 페이지 테이블은 같은 물리 페이지를 가리킨다.

```
부모 PT --+
          +--> [물리 A] [물리 B] [물리 C] ...   (모두 읽기 전용 표시)
자식 PT --+
```

이때 커널은 부모와 자식 양쪽의 페이지를 모두 **읽기 전용**으로 바꿔 둔다. 이 표시가 다음 절의 열쇠다.

## 3. Copy-on-Write: 쓰는 순간에만 복사한다

**Copy-on-Write**(COW, 쓰기 시 복사)의 아이디어는 한 문장이다. **공유하다가, 누군가 쓰려는 순간 그 페이지 하나만 복사한다.**

부모가 페이지 B에 쓰는 순간을 단계별로 보자.

1. 부모의 CPU가 B에 쓰기를 시도한다. 그런데 B는 읽기 전용이라 페이지 폴트(page fault)가 난다. 앞 글에서 본 "present 비트가 0"인 경우와 달리, 이번에는 페이지는 있지만 쓰기 권한이 없어서 커널이 불린다.
2. 커널은 이 폴트가 "COW 대상 페이지에 대한 쓰기"임을 알아본다.
3. 새 물리 페이지 B'를 할당하고 B의 내용 4KB를 복사한다.
4. 부모의 페이지 테이블을 B' (쓰기 가능)로 바꾼다. 자식은 원래 B를 계속 가리킨다.
5. 중단됐던 쓰기 명령을 다시 실행한다.

```
쓰기 전:   부모 PT -> B (RO) <- 자식 PT
쓰기 후:   부모 PT -> B' (RW)      자식 PT -> B (RO)
```

자식은 fork 시점의 B를 그대로 본다. 이것이 스냅샷이 일관되게 유지되는 이유다. 부모가 아무리 값을 바꿔도 자식이 읽는 페이지는 바뀌지 않는다.

이 폴트는 디스크 I/O가 필요 없어 minor fault로 분류된다. 그래도 4KB 복사, 페이지 테이블 갱신, 해당 항목의 TLB 무효화가 들기 때문에 "쓰기 한 번"이 평소보다 눈에 띄게 느려진다.

### 왜 이렇게 설계됐는가

fork로 만든 자식의 대부분은 곧바로 `exec()`로 다른 프로그램을 불러오거나, 읽기만 하고 끝난다. 이런 자식을 위해 부모 메모리 전체를 복사하는 건 낭비다. 페이지 테이블만 복사하고 정말 쓰는 페이지만 나중에 복사하면 평균 비용이 크게 줄고 메모리도 공유할 수 있다. Redis의 스냅샷은 이 설계를 "일관된 시점 복제본을 거의 공짜로 만드는 도구"로 재활용한 경우다.

## 4. 숫자로 따라가는 BGSAVE: 메모리는 얼마나 늘어나는가

다음 상황을 가정한다.

- Redis가 24GB를 쓰고, 4KB 페이지 6,291,456개로 이루어져 있다.
- 값이 작아서 `SET` 한 번은 페이지 하나를 건드린다. 키는 전체에 고르게 퍼져 있다고 본다.
- BGSAVE가 60초 걸린다.

fork 직후에는 새로 늘어난 메모리가 거의 없다(페이지 테이블 48MB뿐). 이후 60초 동안 **서로 다른 페이지가 몇 개나 건드려지는가**가 추가 메모리를 결정한다. 같은 페이지에 두 번 써도 복사는 한 번만 일어난다.

쓰기 $k$번이 전체 $N$ 페이지에 무작위로 떨어질 때 건드려진 서로 다른 페이지 수의 기댓값은 $N \left(1 - e^{-k/N}\right)$이다.

| 쓰기 속도 | 60초간 쓰기 수 | 복사된 페이지 | 추가 메모리 | 총 사용량 |
|---|---|---|---|---|
| 0 (읽기 전용) | 0 | 0 | 0 | 약 24GB |
| 초당 1만 | 60만 | 약 57만 | 약 2.2GB | 약 26.2GB |
| 초당 10만 | 600만 | 약 387만 | 약 14.8GB | 약 38.8GB |
| 초당 100만 | 6,000만 | 약 629만(거의 전부) | 약 24GB | 약 48GB |

쓰기 속도가 10배가 된다고 추가 메모리도 10배가 되지는 않는다. 같은 페이지를 반복해서 건드리게 되기 때문이다. 상한은 24GB, 곧 원래 크기의 2배다. Redis 공식 관리 문서도 쓰기가 많은 워크로드에서 RDB 저장이나 AOF 재작성 중 평소의 최대 2배까지 메모리를 쓸 수 있고, 늘어나는 양은 쓰기로 수정된 페이지 수에 비례한다고 적는다.

실제로는 쓰기가 일부 키에 몰리는 경우가 많아 위 표보다 덜 늘어난다. 반대로 키가 페이지 전체에 흩어져 있고 쓰기가 고르면 표에 가깝다. 이 표는 모델이므로 자기 서비스에서는 BGSAVE 중 `INFO memory`와 `INFO persistence`로 직접 확인해야 한다.

### 부모의 RSS는 그대로인데 서버 메모리는 늘어난다

`ps`로 부모 프로세스의 RSS(실제 물리 메모리를 차지한 양)를 보면 24GB 그대로다. 부모는 B를 놓고 B'를 받았으니 페이지 수가 같기 때문이다. 늘어난 것은 **자식이 붙들고 있는 옛 페이지**다. 자식도 같은 페이지를 공유하므로 자식의 RSS는 24GB로 보이지만 대부분은 부모와 겹친다. 그래서 "프로세스별 RSS 합"이 아니라 시스템 전체의 사용량(`free`나 cgroup 메모리)으로 봐야 한다.

## 5. 문제 1: fork 순간의 멈춤

2절에서 본 대로 fork 동안 부모는 페이지 테이블을 복사하느라 멈춘다. Redis는 명령을 메인 스레드 하나로 처리하므로, 이 시간은 모든 클라이언트의 지연으로 보인다.

Redis의 지연 진단 문서가 제시한 측정값이다(`BGSAVE` 후 `latest_fork_usec`로 측정).

| 환경 | 크기 | fork 시간 | GB당 |
|---|---|---|---|
| 물리 서버 (Xeon 2.27GHz) | 6.9GB | 62ms | 9ms |
| 물리 서버 (미상 HW) | 6.1GB | 80ms | 13.1ms |
| EC2 구형 인스턴스 (Xen) | 6.1GB | 1,460ms | 239.3ms |

같은 6GB인데 구형 EC2 Xen 인스턴스는 물리 서버보다 한두 자릿수 느렸다. 문서의 권고는 현대적인 HVM 기반 인스턴스를 쓰라는 것이다. 이 수치는 문서가 쓰인 당시의 측정이므로 지금 환경에 그대로 적용할 수는 없다. 지금 내 환경의 값은 `INFO`의 `latest_fork_usec`로 직접 재야 한다.

fork 시간은 O(페이지 수)다. 인스턴스가 두 배가 되면 멈춤도 대략 두 배가 된다. 그래서 큰 인스턴스 하나보다 작게 쪼갠(샤딩한) 여러 개가 fork 지연 면에서 유리하다.

## 6. 문제 2: THP가 COW 단위를 키운다

**THP**(Transparent Huge Pages)는 커널이 4KB 페이지 여러 개를 2MB 하나로 묶어 TLB 효율을 높이는 기능이다. 평소엔 이득이지만 COW와 만나면 문제가 된다.

COW의 복사 단위가 4KB에서 2MB로 커진다. 쓰기 한 번에 2MB를 복사하고, 그만큼 메모리가 늘어난다. 같은 24GB를 2MB 페이지로 나누면 12,288개뿐이므로 거의 전부를 건드리는 데 오래 걸리지 않는다.

앞 절의 기댓값 식을 그대로 써 보자(N = 12,288).

| 쓰기 수 | 소요 시간(초당 1만 쓰기) | 복사된 huge page | 추가 메모리 |
|---|---|---|---|
| 1,000 | 0.1초 | 약 960개 | 약 1.9GB |
| 12,000 | 1.2초 | 약 7,650개 | 약 15GB |
| 60만 | 60초 | 거의 전부 | 약 24GB |

4KB 페이지에서 60초 동안 2.2GB였던 증가가 THP에서는 1초 남짓 만에 15GB가 된다. Redis 지연 문서도 같은 현상을 설명한다. fork 뒤 바쁜 인스턴스에서는 이벤트 루프 몇 번만 돌아도 거의 전체 메모리가 COW되어 큰 지연과 메모리 사용이 발생한다는 것이다. 공식 권고는 `/sys/kernel/mm/transparent_hugepage/enabled`를 `never`로 두는 것이다.

## 7. 문제 3: OOM과 fork 실패

두 가지 방향으로 터진다.

**메모리가 모자라서 죽는다.** `maxmemory`를 물리 메모리 한계에 가깝게 잡으면, BGSAVE 중 COW로 늘어난 메모리가 한계를 넘어 OOM Killer(메모리가 바닥났을 때 커널이 프로세스를 골라 죽이는 장치)가 Redis를 죽일 수 있다. OOM Killer가 누구를 고르는지는 [overcommit과 OOM Killer 글](/posts/cs/os/overcommit-thrashing-oom-killer/)에서 다룬다. Redis 문서의 조언은 `maxmemory`를 데이터뿐 아니라 오버헤드와 단편화까지 고려해 정하라는 것이다. 예를 들어 여유가 10GB라고 보이면 8~9GB로 잡는다. 쓰기가 많다면 COW 여유분도 따로 남겨야 한다.

**fork 자체가 실패한다.** `vm.overcommit_memory`가 기본값 0이면 커널은 "새 프로세스가 같은 크기의 메모리를 더 쓸 수도 있다"고 보고, 남은 메모리가 부족해 보이면 fork를 거부할 수 있다. 그러면 BGSAVE가 실패한다. 실제로는 COW 때문에 그만큼 쓰지 않을 텐데도 그렇다. Redis 문서는 `vm.overcommit_memory = 1`로 설정하라고 권한다.

이 둘이 겹치면 더 위험하다. overcommit을 1로 열어 fork는 성공하게 만들고, 그 대신 COW로 늘어나는 메모리는 `maxmemory` 여유로 직접 책임져야 한다.

## 8. 트레이드오프 정리와 완화책

스냅샷을 만드는 방법을 비교하면 fork + COW가 왜 널리 쓰이는지 보인다.

| 방식 | 장점 | 단점 |
|---|---|---|
| fork + COW | 구현이 단순하고 일관된 스냅샷이 보장됨. 부모는 계속 서비스 | fork 순간 멈춤, 쓰기가 많으면 메모리 최대 약 2배 |
| 즉시 전체 복사 | 단순 | 시간과 메모리 비용이 매우 큼 |
| vfork, posix_spawn | exec 직전 용도에는 빠름 | 부모 메모리를 스냅샷으로 남기는 용도로는 부적합 |
| AOF 위주(스냅샷 없음) | 스냅샷 때문에 멈추지 않음 | AOF 재작성 때 결국 fork가 필요하거나 별도 구조가 필요 |

BGSAVE 때 응답이 느려지고 메모리가 급증한다면, 원인은 fork 순간의 멈춤과 이후 쓰기마다 일어나는 COW 복사다. 다음 순서로 점검한다.

1. `INFO persistence`의 `latest_fork_usec`로 fork 멈춤이 얼마나 되는지 본다.
2. THP 설정을 확인하고 켜져 있으면 `never`로 바꾼다.
3. BGSAVE 중 쓰기 비율과 메모리 증가를 함께 본다.

줄이는 방법은 다음과 같다.

- 쓰기가 적은 시간대(off-peak)에 스냅샷을 돌린다.
- 인스턴스를 샤딩해서 프로세스당 메모리를 줄이면 fork 시간과 COW 총량이 함께 줄어든다.
- replica에서 스냅샷을 수행해 primary는 fork 영향을 받지 않게 한다.
- `maxmemory`에 COW 여유를 반영하고 `vm.overcommit_memory`를 1로 둔다.

운영 관점에서 이 이야기는 [Redis vs RDB](/posts/dev/cache/redis-vs-rdb-loss-risk/)의 판단과 이어진다. 그 글은 "유실돼도 괜찮은 값은 Redis에 둔다"는 기준이었다. 그런데 RDB 스냅샷에 의존한다면 복구 지점이 마지막 스냅샷이고, 그 스냅샷을 만드는 비용이 이 글의 fork와 COW다. 저장소를 고를 때는 유실 시 결과뿐 아니라 영속화 방식이 평소 서비스에 내는 비용도 함께 봐야 한다.

## 결론

- `fork()`는 데이터가 아니라 페이지 테이블만 복사하고, 모든 페이지를 읽기 전용으로 공유한다. 24GB 프로세스의 페이지 테이블은 48MB다.
- Copy-on-Write는 쓰기를 시도하는 순간 페이지 폴트로 해당 페이지 하나만 복사한다. 이 덕분에 자식은 fork 시점의 일관된 스냅샷을 볼 수 있다.
- BGSAVE 중 늘어나는 메모리는 "서로 다른 몇 개의 페이지가 건드려졌는가"에 비례하고, 상한은 원래 크기의 2배다.
- 비용은 두 곳에서 나온다. fork 순간의 멈춤(페이지 수에 비례)과 이후 쓰기마다 생기는 COW 폴트와 메모리 증가다.
- THP는 COW 단위를 2MB로 키워 지연과 메모리 증가를 크게 악화시키므로 Redis에서는 끈다.

COW로 메모리가 늘다 보면 언젠가 RAM이 모자라고, 커널은 어떤 페이지를 내보낼지 골라야 한다. [다음 글](/posts/cs/os/page-replacement-algorithms/)에서 그 선택 규칙인 페이지 교체 알고리즘을 본다.
