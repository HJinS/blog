## 개요

[앞 글](/posts/cs/network/tcp-handshake-syn-accept-queue)에서는 3-way handshake로 연결을 맺는 과정을 봤다. 연결이 맺어지면 이제 데이터를 보낸다. 그런데 TCP 아래에 있는 IP는 보낸 패킷이 도착한다고 약속하지 않는다.

이 글이 답하는 질문은 두 가지다.

- TCP는 패킷이 사라졌다는 사실을 어떻게 알아채는가?
- 얼마나 기다렸다가 다시 보내야 하고, 빈 구간이 여러 개면 어떻게 하는가?

손실을 알아채는 길은 두 갈래다. 하나는 타이머가 만료되는 것이고(3장), 다른 하나는 수신자가 보낸 ACK의 모양에서 읽어 내는 것이다(4장, 5장). 두 길 모두 시퀀스 번호와 ACK(2장) 위에서 동작한다.

---

## 1. IP는 유실, 중복, 순서 뒤바뀜을 막아주지 않는다

IP 명세(RFC 791)는 스스로를 이렇게 설명한다. IP는 신뢰할 수 있는 통신 수단을 제공하지 않는다. 확인 응답도 없고, 재전송도 없고, 데이터에 대한 오류 검사도 없다. 헤더 체크섬 하나만 있다.

그래서 IP 위로 보낸 세그먼트(segment, TCP가 IP에 실어 보내는 데이터 단위)에는 다음 일이 생길 수 있다.

| 현상 | 예 |
|---|---|
| 유실(loss) | 혼잡한 라우터가 패킷을 버린다. 체크섬 검사에 실패한 세그먼트도 버려진다 |
| 중복(duplication) | 송신자가 재전송했는데 느렸던 원본도 결국 도착한다 |
| 순서 뒤바뀜(reordering) | 먼저 보낸 패킷이 나중 패킷보다 늦게 도착한다 |
| 손상(corruption) | 전송 중 비트가 바뀐다. TCP 체크섬이 감지하고, 결과적으로 유실과 같아진다 |

반면 애플리케이션은 `write()`로 쓴 바이트가 같은 순서로, 빠짐없이, 한 번씩 `read()`로 나오기를 기대한다. RFC 9293은 TCP가 이 간격을 메운다고 정리한다. TCP는 애플리케이션에 신뢰할 수 있고 순서가 보장된 바이트 스트림(byte stream)을 제공한다.

핵심 아이디어는 한 문장이다. **모든 바이트에 번호를 붙이고, 받은 쪽이 어디까지 받았는지 알려 주고, 소식이 없으면 다시 보낸다.**

| 도구 | 해결하는 문제 |
|---|---|
| 시퀀스 번호 | 순서가 바뀐 세그먼트를 재배열하고, 중복을 버리고, 빈 곳을 찾는다 |
| ACK | 송신자에게 어디까지 도착했는지 알린다 |
| 재전송 | 잃어버린 데이터를 다시 보낸다 |
| 체크섬 | 손상된 세그먼트를 걸러 유실로 바꾼다 |

어려운 부분은 재전송이다. 송신자는 ACK가 안 오는 이유가 "사라져서"인지 "아직 오는 중이라서"인지 구별할 수 없다. 이 글의 나머지는 대부분 이 구별을 어떻게 잘하느냐에 관한 이야기다.

## 2. 시퀀스 번호와 누적 ACK

### 바이트마다 번호를 붙인다

TCP는 패킷이 아니라 **바이트**에 번호를 붙인다. RFC 9293의 표현으로는 연결로 보내는 모든 옥텟(octet, 8비트 바이트)이 시퀀스 번호(sequence number)를 가진다.

- 세그먼트 헤더의 시퀀스 번호는 그 세그먼트에 담긴 **첫 바이트의 번호**다.
- ACK 번호(acknowledgment number)는 수신자가 **다음에 받기를 기대하는 바이트 번호**다.
- ACK 번호가 X라면 "X 직전 바이트까지 전부 받았다"는 뜻이다. 앞부분을 한꺼번에 확인하므로 이를 누적 ACK(cumulative ACK)라고 부른다.

번호는 0부터 시작하지 않는다. 연결을 맺을 때 각자 초기 시퀀스 번호(ISN, Initial Sequence Number)를 고르고, SYN도 번호 하나를 차지한다. 여기서는 데이터의 첫 바이트가 1000번이라고 하자.

### 세그먼트 3개를 따라가 보기

300바이트를 100바이트씩 세그먼트 3개로 보낸다.

```
segment   seq    len   bytes          ACK sent back
-------   ----   ---   ------------   -------------
S1        1000   100   1000 ~ 1099    ACK 1100
S2        1100   100   1100 ~ 1199    ACK 1200
S3        1200   100   1200 ~ 1299    ACK 1300
```

다음 세그먼트의 시퀀스 번호는 항상 `seq + len`이다. ACK 번호도 같은 값이 된다.

누적 ACK에는 장점이 하나 있다. ACK 자체가 사라져도 버틴다. 위에서 ACK 1200이 유실되고 ACK 1300만 도착해도, 송신자는 1299번까지 전부 도착했다는 것을 안다. 뒤의 ACK가 앞의 ACK를 포함하기 때문이다.

### S2가 사라지면

이번에는 S2가 중간에 사라진다.

```
Sender                                       Receiver
  |-- S1 seq=1000 len=100 --------------------->|  keep 1000~1099
  |<---------------------------------- ACK 1100 |
  |-- S2 seq=1100 len=100 ------X               |  (lost)
  |-- S3 seq=1200 len=100 --------------------->|  hold 1200~1299
  |<---------------------------------- ACK 1100 |  still waits for 1100
```

1. S1이 도착한다. 수신자는 1100을 기다린다고 답한다.
2. S2는 사라진다.
3. S3가 도착한다. 수신자는 1200번부터 1299번까지를 버퍼에 보관한다. RFC 9293은 시작 번호가 더 큰 세그먼트를 버리지 말고 나중 처리를 위해 들고 있으라고 권고한다(SHOULD). RFC는 요구의 강도를 MUST(반드시), SHOULD(특별한 이유가 없으면 따른다), MAY(선택) 같은 단어로 표시한다. 이 글에서도 괄호 안에 그대로 적는다.
4. 하지만 1100번부터 1199번까지가 비어 있으므로 ACK 번호는 1100에서 움직이지 못한다. 수신자는 ACK 1100을 다시 보낸다.

중복도 같은 번호로 처리한다. 나중에 S1이 한 번 더 도착하면, 그 바이트는 이미 ACK 번호 앞쪽이므로 수신자는 세그먼트를 버리고 현재 ACK를 다시 보낸다.

### 누적 ACK가 말하지 못하는 것

ACK 1100이 전하는 정보는 "1100부터 없다"뿐이다. "1200번부터 1299번까지는 갖고 있다"는 말은 할 수 없다. 그래서 송신자가 아는 것은 이 정도다.

- 1100 이후 어딘가가 비어 있다.
- S3가 도착했는지는 모른다.

송신자에게 남은 선택은 세 가지다. 타이머가 만료될 때까지 기다리거나(3장), 같은 ACK가 반복된다는 사실을 신호로 쓰거나(4장), 수신자에게 더 자세히 말하게 하는 것이다(5장).

## 3. 재전송 타이머: RTT 측정과 RTO 계산

### 왜 타이머가 필요한가

세그먼트가 전부 사라지거나 ACK가 전부 사라지면 송신자에게는 아무 소식도 오지 않는다. 이때 손실을 알아챌 방법은 시간밖에 없다. 송신자는 세그먼트를 보낼 때 타이머를 켜고, 정해진 시간 안에 ACK가 오지 않으면 다시 보낸다. 이 시간을 재전송 타임아웃(RTO, Retransmission TimeOut)이라고 한다.

RTO를 정하는 일은 생각보다 어렵다.

- **너무 짧으면** 느리게 오는 중이던 세그먼트를 다시 보낸다. 이를 불필요한 재전송(spurious retransmission)이라고 한다. 대역폭을 낭비하고, 네트워크가 막혀 있을 때 부하를 더한다.
- **너무 길면** 진짜로 사라졌을 때 아무것도 안 하고 기다린다.

정답은 "왕복 시간(RTT, Round-Trip Time)보다 조금 길게"다. 문제는 RTT가 경로마다 다르고, 같은 경로에서도 계속 흔들린다는 점이다.

핵심 아이디어는 한 문장이다. **RTO는 RTT의 평균에 RTT 흔들림의 4배를 더한 값이다.**

### 측정과 계산 규칙

송신자는 세그먼트를 보낸 시각과 그 세그먼트를 확인하는 ACK가 온 시각의 차이로 RTT 표본 R을 얻는다. RFC 6298은 RTT마다 최소 한 번은 측정하라고 요구한다(MUST).

표본으로 두 값을 관리한다.

- **SRTT**(smoothed RTT): RTT의 이동 평균이다.
- **RTTVAR**(RTT variation): RTT가 평균에서 얼마나 벗어나는지를 나타내는 값이다.

RFC 6298의 규칙은 다음과 같다. `G`는 시스템 시계의 단위(clock granularity)인데, 여기서는 아주 작다고 보고 무시한다.

```
before any sample:
  RTO    <- 1 second

first sample R:
  SRTT   <- R
  RTTVAR <- R / 2
  RTO    <- SRTT + max(G, K * RTTVAR)                    K = 4

each later sample R':
  RTTVAR <- (1 - beta)  * RTTVAR + beta  * |SRTT - R'|   beta  = 1/4
  SRTT   <- (1 - alpha) * SRTT   + alpha * R'            alpha = 1/8
  RTO    <- SRTT + max(G, K * RTTVAR)

always:
  if RTO is below 1 second, round it up to 1 second
```

순서에 주의해야 한다. RTTVAR를 먼저 갱신하고, 그때는 갱신 **전**의 SRTT를 쓴다.

### 숫자로 따라가기

RTT 표본이 400ms, 560ms, 900ms 순서로 들어왔다고 하자.

| 표본 | R (ms) | RTTVAR (ms) | SRTT (ms) | RTO (ms) |
|---|---|---|---|---|
| 1 | 400 | $400 / 2 = 200$ | 400 | $400 + 4 \times 200 = 1200$ |
| 2 | 560 | $\frac{3}{4} \times 200 + \frac{1}{4} \times 160 = 190$ | $\frac{7}{8} \times 400 + \frac{1}{8} \times 560 = 420$ | $420 + 4 \times 190 = 1180$ |
| 3 | 900 | $\frac{3}{4} \times 190 + \frac{1}{4} \times 480 = 262.5$ | $\frac{7}{8} \times 420 + \frac{1}{8} \times 900 = 480$ | $480 + 4 \times 262.5 = 1530$ |

표본 2의 160은 이전 SRTT 400과 새 표본 560의 차이다. 표본 3의 480은 이전 SRTT 420과 900의 차이다.

표본 3에서 무슨 일이 일어났는지 보자.

1. RTT가 갑자기 900ms로 튀었다.
2. SRTT는 420에서 480으로 60ms만 움직였다. 새 표본의 가중치가 $\frac{1}{8}$이라서 한 번 튄 값에 평균이 휘둘리지 않는다.
3. RTTVAR는 190에서 262.5로 늘었다. 여기에 4를 곱하니 RTO는 1180에서 1530으로 350ms 늘었다.

평균은 천천히 따라가고, 흔들림이 커지면 RTO는 빠르게 넓어진다. RTT가 들쭉날쭉한 네트워크에서는 넉넉히 기다려야 불필요한 재전송을 피할 수 있기 때문이다.

### 최솟값 1초와 초기값 1초

RTT가 작은 환경에서는 사정이 다르다. 데이터센터 안처럼 RTT가 1ms라면 첫 표본으로 계산한 RTO는 $1 + 4 \times 0.5 = 3\text{ms}$다. 하지만 RFC 6298은 계산 결과가 1초보다 작으면 1초로 올리라고 권고한다(SHOULD). 큰 최솟값이 있어야 TCP가 보수적으로 동작하고 불필요한 재전송을 피한다는 연구 결과를 근거로 든다. SHOULD이므로 반드시 지켜야 하는 값은 아니다.

표본이 하나도 없을 때의 RTO도 1초다. 이전 판인 RFC 2988은 3초였는데, RFC 6298은 오늘날 네트워크가 3초를 정하던 시절보다 훨씬 빠르다는 이유로 1초로 낮췄다. 다만 SYN의 응답을 기다리다 타이머가 만료된 적이 있고 쓰던 RTO가 3초보다 작았다면, 데이터 전송을 시작할 때 RTO를 3초로 다시 맞춘다(MUST).

### 타이머가 만료되면: 지수 백오프

RTO가 만료되면 송신자는 세 가지를 한다(RFC 6298 5장).

1. 아직 확인받지 못한 세그먼트 중 가장 앞의 것을 다시 보낸다.
2. RTO를 두 배로 늘린다. 이를 지수 백오프(exponential backoff)라고 한다.
3. 늘어난 RTO로 타이머를 다시 켠다.

RTO가 1530ms일 때 S2가 계속 사라진다면 이렇게 된다.

```
time (ms)   event                       RTO after event
---------   -------------------------   ---------------
0           send S2 (seq=1100)          1530
1530        timeout, resend S2          3060
4590        timeout, resend S2          6120
10710       timeout, resend S2          12240
```

RTO에 상한을 둘 수도 있는데, 둔다면 최소 60초 이상이어야 한다. 매번 두 배로 늘리는 이유는 네트워크가 막혀 있을 때 재전송이 혼잡을 더 키우지 않게 하기 위해서다.

### Karn 알고리즘: 재전송한 세그먼트로는 RTT를 재지 않는다

S2를 재전송한 뒤 ACK 1200이 왔다. 이 ACK는 원본에 대한 것일까, 재전송에 대한 것일까? 송신자는 알 수 없다. ACK에는 "몇 번째 전송분을 받았다"는 정보가 없다.

```
case A: the ACK answers the original (it was only slow)
  t=0       send S2 (original)
  t=1530    send S2 (retransmit)
  t=1600    ACK 1200 arrives
  measured from the retransmit: 70 ms     -> far too small

case B: the ACK answers the retransmit (original was lost)
  t=0       send S2 (original)  -> lost
  t=1530    send S2 (retransmit)
  t=1930    ACK 1200 arrives
  measured from the original: 1930 ms     -> far too large
```

어느 쪽으로 재든 틀릴 수 있다. A처럼 너무 작게 재면 RTO가 줄어 불필요한 재전송이 더 늘어난다. B처럼 너무 크게 재면 RTO가 쓸데없이 커진다.

Karn 알고리즘(Karn's algorithm)의 답은 단순하다. **재전송한 세그먼트로는 RTT 표본을 만들지 않는다.** RFC 6298은 이를 MUST로 요구하고, RFC 9293도 RTO를 RFC 6298대로 Karn 알고리즘을 포함해 계산하라고 MUST로 요구한다. 예외는 타임스탬프 옵션을 쓸 때다. 타임스탬프 옵션(TCP timestamps, RFC 7323)은 송신자가 세그먼트에 보낸 시각 값을 싣고, 수신자가 그 값을 ACK에 그대로 돌려주는 옵션이다. 돌아온 값을 보면 ACK가 어느 전송분에 대한 것인지 구별할 수 있다.

표본을 버리는 동안에는 백오프로 커진 RTO를 그대로 쓴다. 재전송하지 않은 새 데이터가 확인되어 표본이 생기면 위의 계산이 다시 돌고, RTO는 정상 범위로 돌아온다.

### 그래서 생기는 문제

RTO는 느리다. 권고대로라면 최소 1초다. RTT가 50ms인 연결에서 세그먼트 하나를 잃고 타이머로만 알아챈다면, RTT 20번 동안 아무것도 못 한 셈이다. 타이머보다 빨리 알아챌 방법이 필요하다.

## 4. 빠른 재전송: 중복 ACK 3개

### 왜 필요한가

2장에서 S2가 사라졌을 때 수신자는 S3를 받고 ACK 1100을 **다시** 보냈다. RFC 5681은 수신자가 순서가 어긋난 세그먼트를 받으면 즉시 중복 ACK를 보내라고 권고한다(SHOULD). 이 반복되는 ACK 자체가 "1100이 비어 있다"는 신호다. 이걸 쓰면 RTO까지 기다리지 않아도 된다.

핵심 아이디어는 한 문장이다. **같은 ACK 번호가 세 번 더 오면 그 자리가 사라졌다고 보고 타이머 없이 바로 다시 보낸다.** 이를 빠른 재전송(fast retransmit)이라고 한다.

### 중복 ACK의 정의

RFC 5681은 다음 조건을 모두 만족하는 ACK를 중복 ACK(duplicate ACK)로 센다.

- 송신자에게 아직 확인받지 못한 데이터가 있다.
- ACK에 데이터가 실려 있지 않다.
- SYN과 FIN 비트가 꺼져 있다.
- ACK 번호가 지금까지 받은 가장 큰 ACK 번호와 같다.
- 광고한 윈도우 크기가 직전 ACK와 같다.

마지막 조건은 윈도우 크기만 바꾸려고 보낸 ACK를 중복 ACK로 잘못 세지 않기 위한 것이다. 윈도우는 [다음 글](/posts/cs/network/tcp-flow-control-nagle-delayed-ack)에서 다룬다.

### 세그먼트 5개로 따라가기

1000번부터 100바이트씩 5개(S1부터 S5까지)를 보냈고, S2만 사라졌다.

```
Sender                                         Receiver
  |-- S1 seq=1000 -------------------------------->|
  |<------------------------------------ ACK 1100 -|
  |-- S2 seq=1100 -------X                         |
  |-- S3 seq=1200 -------------------------------->|
  |<---------------------- ACK 1100  (dup #1) -----|
  |-- S4 seq=1300 -------------------------------->|
  |<---------------------- ACK 1100  (dup #2) -----|
  |-- S5 seq=1400 -------------------------------->|
  |<---------------------- ACK 1100  (dup #3) -----|
  |-- S2 seq=1100  (fast retransmit) ------------->|
  |<------------------------------------ ACK 1500 -|
```

1. S1에 대한 ACK 1100은 정상 ACK다.
2. S3, S4, S5가 도착할 때마다 수신자는 ACK 1100을 다시 보낸다. 송신자 입장에서는 중복 ACK 1, 2, 3번째다.
3. 세 번째 중복 ACK를 받는 순간 송신자는 RTO를 기다리지 않고 S2를 다시 보낸다.
4. S2가 도착해 빈 곳이 채워진다. 수신자는 보관하던 S3, S4, S5까지 한꺼번에 이어 붙이고 ACK 1500을 보낸다. RFC 5681은 빈 곳을 채우는 세그먼트를 받으면 즉시 ACK하라고 권고한다.

ACK 번호가 1100에서 1500으로 한 번에 뛴다. 누적 ACK이기 때문이다.

### 왜 1개가 아니라 3개인가

중복 ACK는 유실이 아니어도 생긴다. 순서가 뒤바뀌기만 해도 그렇다. S2가 사라진 게 아니라 S3보다 조금 늦게 도착했다고 하자.

```
arrival order   ACK sent
-------------   ------------------
S1              ACK 1100
S3              ACK 1100   (dup #1)
S2              ACK 1300
S4              ACK 1400
```

중복 ACK가 하나 나왔지만 S2는 무사했다. 중복 ACK 하나에 바로 재전송하면 이런 경우마다 쓸데없이 다시 보낸다. RFC 5681은 중복 ACK가 데이터 순서 뒤바뀜 때문에도 생길 수 있다는 점을 들어, 3개를 유실의 신호로 쓴다. 3은 "순서가 조금 바뀐 것"과 "진짜 사라진 것"을 가르는 타협값이다.

### 그래서 생기는 문제

- **손실 뒤에 세그먼트가 3개 이상 있어야 한다.** 응답의 마지막 세그먼트가 사라지면 뒤따라 도착할 세그먼트가 없으니 중복 ACK도 없다. 위 예시에서 S5가 사라졌다면 송신자는 결국 RTO를 기다린다.
- **한 번에 빈 곳 하나만 보인다.** 중복 ACK가 가리키는 곳은 맨 앞의 빈 곳뿐이다. 빈 곳이 여러 개면 하나를 메운 뒤에야 다음 빈 곳이 ACK 번호로 드러난다.
- **속도도 줄여야 한다.** 세그먼트가 사라졌다는 것은 경로가 막혔다는 신호이기도 하다. RFC 5681은 빠른 재전송을 보내는 속도를 줄이는 빠른 회복(fast recovery)과 함께 정의한다. 이 부분은 [혼잡 제어 글](/posts/cs/network/tcp-congestion-control)에서 이어진다.

두 번째 문제를 푸는 것이 SACK이다.

## 5. SACK: 빈 구간이 여러 개일 때

### 왜 필요한가

누적 ACK는 "어디까지 연속으로 받았는가"만 말한다. 그 뒤에 무엇이 도착했는지는 말하지 못한다. RFC 2018은 이 때문에 빈 구간이 여러 개일 때 송신자가 둘 중 하나를 해야 한다고 설명한다.

- 사라진 세그먼트 하나를 알아내는 데 RTT 한 번씩을 기다린다.
- 아니면 이미 잘 도착한 세그먼트까지 다시 보낸다.

핵심 아이디어는 한 문장이다. **수신자가 빈 곳 뒤에 받아 둔 구간을 ACK에 함께 적어 보내면, 송신자는 빈 곳을 한 번에 모두 본다.** 이를 선택적 확인 응답(SACK, Selective ACKnowledgment)이라고 한다.

### 옵션 형식

SACK은 TCP 옵션 두 개로 동작한다.

| 옵션 | kind(옵션 종류 번호) | 길이 | 언제 |
|---|---|---|---|
| SACK-Permitted | 4 | 2바이트 | SYN에만 싣는다. "나는 SACK을 받을 수 있다"는 뜻이다 |
| SACK | 5 | $8 \times n + 2$바이트 | 연결이 맺어진 뒤 ACK에 싣는다. n은 블록 수다 |

블록 하나는 32비트 숫자 두 개다. 왼쪽 끝(left edge)은 받은 구간의 첫 바이트 번호이고, 오른쪽 끝(right edge)은 마지막 바이트 다음 번호다.

TCP 옵션 공간은 40바이트다. `(40 - 2) / 8`을 내림하면 블록은 최대 4개다. 타임스탬프 옵션을 함께 쓰면 그 옵션이 10바이트와 정렬용 2바이트를 차지하므로 `(28 - 2) / 8`을 내림해 3개가 된다.

### RFC 2018의 예시로 따라가기

RFC 2018 7장의 예시를 그대로 쓴다. 송신자의 윈도우 왼쪽 끝, 즉 아직 확인받지 못한 첫 바이트가 5000번이다. 여기서 500바이트짜리 세그먼트 8개를 연달아 보낸다. 그중 2, 4, 6, 8번이 사라진다.

```
seq     5000  5500  6000  6500  7000  7500  8000  8500  9000
        |     |     |     |     |     |     |     |     |
seg       #1    #2    #3    #4    #5    #6    #7    #8
result    ok   lost   ok   lost   ok   lost   ok   lost
```

수신자가 보내는 ACK는 다음과 같다.

| 도착한 세그먼트 | ACK | 블록 1 | 블록 2 | 블록 3 |
|---|---|---|---|---|
| #1 (5000) | 5500 | - | - | - |
| #3 (6000) | 5500 | 6000-6500 | - | - |
| #5 (7000) | 5500 | 7000-7500 | 6000-6500 | - |
| #7 (8000) | 5500 | 8000-8500 | 7000-7500 | 6000-6500 |

블록 순서에도 규칙이 있다.

1. 첫 블록은 이번 ACK를 일으킨 세그먼트가 들어 있는 구간이어야 한다(MUST). 그래서 가장 최근 구간이 맨 앞에 온다.
2. 나머지 자리는 직전에 보고한 블록을 반복해서 채운다(SHOULD).
3. 이렇게 하면 각 구간이 연속된 여러 ACK에 반복해서 실린다. ACK 몇 개가 사라져도 송신자는 구간 정보를 놓치지 않는다.

### 송신자가 읽는 것

마지막 ACK 하나만 봐도 송신자는 빈 곳을 모두 안다.

```
ACK 5500, blocks 8000-8500, 7000-7500, 6000-6500

holes:  5500-6000   6500-7000   7500-8000
```

세 구간을 한 RTT 안에 모두 다시 보낼 수 있다. SACK이 없었다면 ACK 5500만 보고 5500을 다시 보낸 뒤, 다음 빈 곳 6500이 ACK 번호로 드러나기를 기다려야 한다. 빈 곳마다 RTT 한 번씩이다.

8번(8500-9000)은 어떨까? 그 뒤로 도착한 세그먼트가 없으니 어떤 블록도 8500 이후를 언급하지 않는다. 송신자는 8번이 사라졌는지 아직 오는 중인지 모른다. 4장의 마지막 세그먼트 문제는 SACK으로도 풀리지 않는다.

### 빈 곳이 채워지면

RFC 2018의 예시는 이어진다. 재전송한 4번(6500)이 먼저 도착하고, 이어서 2번(5500)이 도착한다.

| 도착한 세그먼트 | ACK | 블록 1 | 블록 2 |
|---|---|---|---|
| #4 (6500) | 5500 | 6000-7500 | 8000-8500 |
| #2 (5500) | 7500 | 8000-8500 | - |

4번이 오자 6000-6500, 6500-7000, 7000-7500이 이어져 블록 하나(6000-7500)로 합쳐진다. 2번이 오자 5000부터 7500까지 빈 곳이 없어지므로 누적 ACK가 7500으로 뛴다. ACK 번호 앞쪽은 더 이상 블록으로 적지 않는다.

### SACK은 참고 정보다

RFC 2018은 SACK이 권고(advisory) 정보라고 못 박는다. 수신자는 SACK으로 알린 데이터를 나중에 버려도 된다. 이를 reneging이라고 부른다. 그래서 송신자 쪽 규칙이 따라붙는다.

- SACK으로 확인된 데이터라도 누적 ACK 번호가 그 위를 지나갈 때까지 송신 버퍼에서 지우면 안 된다(MUST NOT).
- RTO가 만료되면 그동안 받은 SACK 정보를 무시하고 ACK 번호 위치부터 다시 보낸다.

RFC 2018은 옵션 형식과 수신자 규칙은 자세히 정하지만, 송신자의 재전송 방식은 "가능한 구현 하나"로만 보여 준다. SACK을 쓰는 혼잡 제어 알고리즘도 자세히 정하지 않고, 기존 혼잡 제어 동작을 유지해야 한다는 점만 요구한다.

### 그래서 생기는 문제

SACK은 송신자가 아는 정보를 늘린다. 하지만 **수신자의 규칙은 그대로다.** 위 예시에서 6000-6500은 수신자 버퍼에 있지만, 5500-6000이 채워지기 전에는 애플리케이션이 읽을 수 없다.

## 6. 순서 보장의 대가

TCP의 약속은 "순서대로 빠짐없이"다. 이 약속 때문에 빈 곳 뒤의 바이트는 이미 도착했어도 수신 버퍼에서 기다린다. 기다리는 시간은 빈 곳을 메우는 데 걸리는 시간과 같다. 지금까지 본 방법별로 정리하면 다음과 같다.

| 손실을 알아챈 방법 | 조건 | 빈 곳이 메워질 때까지 |
|---|---|---|
| 빠른 재전송 | 손실 뒤에 세그먼트가 3개 이상 도착 | 중복 ACK 3개가 오는 시간 + 재전송 왕복 1번 |
| 빠른 재전송 + SACK | 빈 곳이 여러 개 | 여러 빈 곳을 한 번에 재전송 |
| RTO | 뒤따르는 세그먼트가 없거나 ACK가 모두 사라짐 | RTO(권고 최솟값 1초) 이상, 실패할 때마다 두 배 |

어느 경우든 그동안 빈 곳 뒤의 바이트는 애플리케이션에 전달되지 않는다. TCP는 바이트가 어느 요청에 속하는지 모른다. 그래서 세그먼트 하나가 사라지면 그 뒤에 있는 **서로 관계없는 데이터까지** 함께 멈춘다.

이 성질이 가장 크게 드러나는 곳이 HTTP/2다. HTTP/2는 여러 요청의 스트림을 TCP 연결 하나에 섞어 보낸다. 한 스트림의 세그먼트가 사라지면 다른 스트림까지 기다리는 TCP 레벨 HOL Blocking(Head-of-Line Blocking)이 생긴다. 그 과정과 QUIC이 스트림별로 손실을 처리해 이를 피하는 방법은 [HTTP/2 vs HTTP/3(QUIC) 글](/posts/cs/network/http2-vs-http3-quic)에서 다룬다.

## 결론

- IP는 유실, 중복, 순서 뒤바뀜을 막아 주지 않는다. TCP는 바이트마다 시퀀스 번호를 붙이고, 수신자는 "다음에 받을 바이트 번호"를 누적 ACK로 알린다.
- 소식이 없으면 RTO 뒤에 다시 보낸다. RTO는 $\text{SRTT} + 4 \times \text{RTTVAR}$이고, $\alpha = \frac{1}{8}$, $\beta = \frac{1}{4}$, 초기값 1초, 권고 최솟값 1초다(RFC 6298). 만료될 때마다 두 배로 늘리고, 재전송한 세그먼트로는 RTT를 재지 않는다(Karn).
- 같은 ACK가 세 번 더 오면 타이머 없이 바로 다시 보낸다(빠른 재전송, RFC 5681). 3은 순서 뒤바뀜과 유실을 가르는 타협값이다.
- SACK은 빈 곳 뒤에 받은 구간을 알려 여러 빈 곳을 한 RTT에 메우게 한다(RFC 2018). 하지만 마지막 세그먼트 유실은 여전히 RTO에 기댄다.
- 순서 보장 때문에 빈 곳 뒤의 데이터는 도착해도 기다린다. 이 대가가 HTTP/2의 TCP 레벨 HOL Blocking으로 이어진다.
