## 개요

"ping은 되고 로그인 페이지도 뜨는데, 파일 다운로드만 멈춘다." VPN이나 클라우드 네트워크를 만지다 보면 한 번쯤 만나는 증상이다. 연결은 되는데 큰 데이터만 오지 않는다.

이 글이 답하는 질문은 두 가지다.

- MTU와 MSS는 무엇이고, 왜 숫자가 1500과 1460인가?
- 경로 중간에 더 작은 링크가 있으면 송신자는 그 사실을 어떻게 알고, 그 알림이 막히면 왜 큰 패킷만 사라지는가?

MSS는 TCP handshake 때 SYN의 옵션으로 서로 알리는 값이다. handshake와 옵션 협상의 큰 그림은 [TCP 연결 수립과 SYN/accept queue](/posts/cs/network/tcp-handshake-syn-accept-queue)에서 다뤘다. 이 글은 그중 MSS 값이 어떻게 정해지고 어디서 어긋나는지를 본다.

---

## 1. 왜 패킷 크기에 한도가 있는가

데이터를 아무리 크게 보내고 싶어도, 링크 하나가 한 번에 실을 수 있는 크기는 정해져 있다. 이 한도가 MTU(Maximum Transmission Unit, 최대 전송 단위)다. 링크 계층이 한 번에 실어 나를 수 있는 IP 패킷의 최대 크기이고, 이더넷의 표준값은 1500바이트다.

한도가 없으면 한 호스트가 거대한 패킷으로 회선을 오래 독점한다. 비트 하나만 깨져도 그 큰 패킷 전체를 다시 보내야 한다. 그래서 작게 잘라 보내는 것이 기본이다.

그러면 누가 자를까? 방법은 두 가지다.

- IP 계층이 큰 패킷을 조각내는 방법(단편화, fragmentation)
- TCP가 처음부터 작은 세그먼트로 나눠 보내는 방법

현실에서는 두 번째를 쓴다. 이유는 6절에서 비교한다. 이때 TCP가 한 세그먼트에 담는 데이터의 최대 크기가 MSS(Maximum Segment Size)다.

---

## 2. MTU와 MSS 계산

핵심 아이디어는 한 문장이다. **MTU는 IP 패킷 전체의 한도이고, MSS는 거기서 헤더를 뺀 순수 데이터의 한도다.**

IPv4 헤더와 TCP 헤더는 옵션이 없으면 각각 20바이트다.

```
MTU 1500  (whole IP packet)
+------------+------------+--------------------------+
| IP header  | TCP header |          payload         |
|   20 B     |    20 B    |   MSS = 1500-20-20=1460  |
+------------+------------+--------------------------+
```

- MSS = MTU - IP 헤더(20) - TCP 헤더(20) = 1500 - 40 = 1460
- IPv6는 기본 헤더가 40바이트라서 1500 - 40 - 20 = 1440

MSS는 SYN과 SYN+ACK의 TCP 옵션으로 서로 알린다. 각자 "내 쪽 링크 MTU에서 헤더를 뺀 값"을 적어 보내고, 상대가 알려 준 값보다 큰 세그먼트는 보내지 않는다. 결과적으로 두 값 중 작은 쪽이 그 연결의 상한이 된다.

여기에 함정이 있다. 양 끝 호스트는 자기 바로 앞 링크의 MTU만 안다. 경로 중간의 더 작은 링크는 모른다.

---

## 3. 터널을 지나면 MTU가 줄어든다

VPN, 터널, 오버레이 네트워크는 원래 패킷을 새 헤더로 한 번 더 감싼다. 이를 캡슐화(encapsulation)라고 한다. 바깥 링크의 MTU는 여전히 1500이니, 안쪽 패킷이 쓸 수 있는 공간은 덧붙인 헤더(오버헤드)만큼 줄어든다.

터널이 헤더를 100바이트 더 붙인다고 가정하고 계산해 보자.

| 구간 | 값 | 계산 |
| --- | --- | --- |
| 이더넷 링크 MTU | 1500 | 표준값 |
| 터널 오버헤드 | 100 | 가정 |
| 터널 안쪽 MTU | 1400 | 1500 - 100 |
| 터널 안쪽 MSS | 1360 | 1400 - 20 - 20 |

양 끝 호스트는 둘 다 MTU 1500짜리 이더넷에 붙어 있으니 SYN에 MSS 1460을 적는다. 그런데 실제 경로에서는 1400바이트를 넘는 패킷이 통과하지 못한다. 호스트는 SYN을 주고받는 시점에 이 사실을 알 수 없다.

오버헤드는 터널 종류마다 다르다. 예를 들어 VXLAN(RFC 7348)은 원래 이더넷 프레임 전체를 바깥 IPv4 헤더 20바이트, UDP 헤더 8바이트, VXLAN 헤더 8바이트로 감싼다. 안쪽 이더넷 헤더 14바이트까지 바깥 IP 패킷 안에 들어가므로, 바깥 MTU가 1500이면 안쪽 IP 패킷은 1500 - 20 - 8 - 8 - 14 = 1450바이트까지 쓸 수 있다. 실제 값은 쓰는 터널의 설정을 확인해야 한다.

## 4. Path MTU Discovery

경로 전체에서 통과할 수 있는 가장 큰 패킷 크기를 Path MTU라고 한다. 이것을 자동으로 알아내는 절차가 PMTUD(Path MTU Discovery, RFC 1191)다.

핵심 아이디어는 "일단 크게 보내 보고, 막히면 라우터가 알려 준다"이다. 단계는 다음과 같다.

1. 송신 호스트는 IP 헤더의 DF(Don't Fragment) 비트를 켜고, 첫 홉 링크의 MTU 크기로 보낸다. DF가 켜진 패킷은 중간에서 조각내면 안 된다.
2. 중간 라우터는 다음 링크의 MTU가 패킷보다 작으면, 조각낼 수 없으니 패킷을 버린다.
3. 라우터는 송신자에게 ICMP 메시지를 돌려준다. 종류는 Type 3(Destination Unreachable), Code 4(Fragmentation Needed)이고, 메시지 안의 Next-Hop MTU 칸에 다음 링크의 MTU 값이 들어 있다.
4. 송신 커널은 그 목적지의 Path MTU 캐시를 갱신하고 더 작은 크기로 다시 보낸다.

ICMP(Internet Control Message Protocol)는 오류와 제어 정보를 알리는 IP 계층 프로토콜이다. 3절의 예에서 송신자가 받는 메시지는 "다음 링크 MTU는 1400이다"라는 내용이다.

IPv6에서는 라우터가 아예 단편화를 하지 않는다. RFC 8200에 따르면 IPv6 단편화는 출발지 호스트만 한다. 그래서 라우터는 큰 패킷을 버리고 ICMPv6 Packet Too Big(Type 2, RFC 4443)을 돌려준다. IPv6에서 이 ICMP를 막으면 큰 패킷을 보낼 방법 자체가 사라지므로 PMTUD가 거의 반드시 깨진다.

---

## 5. PMTUD 블랙홀: 큰 패킷만 사라진다

PMTUD는 ICMP 한 통에 전적으로 의존한다. 이 ICMP가 중간에서 사라지면 송신자는 이유를 모른 채 같은 크기를 계속 보낸다. 이것이 PMTUD 블랙홀(black hole)이다.

보안 그룹이나 방화벽에서 "ICMP는 위험하니 전부 차단"을 설정하면 흔히 생긴다. 3절의 터널 예시에, 서버 앞 방화벽이 ICMP를 모두 막는 상황을 더해 순서대로 따라가 보자. 큰 응답을 보내는 쪽은 서버다.

```
Client            Tunnel router           Firewall         Server
MTU 1500         (1400 MTU hop)         (drops ICMP)      MTU 1500
  |                     |                     |               |
  |-- SYN (MSS 1460) ---------------------------------------->|  (1) small: OK
  |<------------------------------------ SYN+ACK (MSS 1460) --|
  |-- ACK, GET /big-file ------------------------------------>|
  |                     |                     |               |
  |                     X<===================== 1500 B, DF=1 =|  (2) too big: dropped
  |                     |-- ICMP 3/4 (1400) ->X               |  (3) ICMP dropped
  |                     |                     |               |
  |                     X<==================== resend 1500 B =|  (4) dropped again
```

1. 3-way handshake는 패킷이 작아서 정상 완료된다. 요청 헤더 같은 작은 데이터도 통과한다.
2. 서버가 MSS 1460에 맞춰 1500바이트짜리 응답 패킷을 DF를 켜고 보낸다. 터널 구간 MTU 1400을 넘으므로 터널 라우터가 버린다.
3. 터널 라우터는 ICMP Type 3 Code 4(MTU=1400)를 서버에게 돌려준다. 그런데 서버 앞 방화벽이 ICMP를 전부 막아 이 메시지가 사라진다.
4. 서버는 ACK가 오지 않으니 타임아웃 뒤 같은 크기로 재전송한다. 이 재전송도 똑같이 버려진다. 큰 패킷은 영원히 도착하지 못한다.

그래서 증상이 독특하다.

- handshake와 작은 요청은 성공하고, 큰 응답에서만 멈춘다.
- `curl`은 응답 헤더까지 받고 본문에서 멈춘다.
- TLS에서는 ClientHello는 가지만, 서버가 인증서를 담아 보내는 큰 응답에서 멈춘다.
- SSH는 로그인은 되는데 `ls` 같은 큰 출력에서 멈춘다.

연결 자체는 맺어져 있고 작은 패킷은 오가기 때문에 "네트워크가 죽었다"는 판단이 틀리게 된다. 그래서 진단이 어렵다. 흔한 원인은 세 가지다.

- 보안 그룹이나 방화벽이 ICMP를 통째로 차단
- VPN, 터널, 오버레이로 경로 MTU가 줄었는데 MSS 클램핑(6절)이 없음
- 한쪽만 점보 프레임(jumbo frame, MTU 9000 안팎의 큰 이더넷 프레임)을 쓰는 비대칭 MTU 설정

## 6. 어떻게 막는가: 방법별 트레이드오프

블랙홀을 피하는 길은 여러 가지이고, 각각 얻는 것과 잃는 것이 다르다.

| 방식 | 얻는 것 | 잃는 것 또는 위험 |
| --- | --- | --- |
| IP 단편화 허용 | MTU가 작은 링크도 통과 | 라우터와 수신자 부하가 늘고, 조각 하나만 유실돼도 전체를 재전송. 방화벽과 NAT가 조각을 버리는 경우가 많음 |
| PMTUD (DF + ICMP) | 최적 크기를 동적으로 학습 | ICMP가 막히면 블랙홀. 첫 패킷이 아니라 큰 패킷에서만 실패해 진단이 어려움 |
| MSS 클램핑 | ICMP 없이도 안전하고 한 번 설정하면 끝 | TCP에만 적용되고 경로를 알고 있어야 하며, 설정을 빠뜨리면 재발 |
| PLPMTUD (RFC 4821) | ICMP 없이 실제 전송의 성공과 실패로 MTU를 탐색 | 탐색하는 동안 지연이 생기고, Linux에서는 항상 켜 두는 설정이 기본이 아님 |
| 점보 프레임 | 헤더 비율이 줄어 처리량 증가, CPU 감소 | 경로 전체가 일치해야 함. 한 구간만 1500이면 같은 블랙홀 문제 |

여기서 단편화를 기본으로 쓰지 않는 이유가 보인다. 조각 하나라도 사라지면 수신자는 원본을 복원하지 못해 전체가 재전송된다. 그래서 단편화를 피하는 것이 기본이고, TCP가 처음부터 MSS로 크기를 맞추는 쪽이 낫다.

MSS 클램핑(MSS clamping)은 게이트웨이가 지나가는 SYN의 MSS 옵션 값을 낮춰 고쳐 쓰는 기법이다. 3절의 예에서 터널 게이트웨이가 MSS를 1360으로 고쳐 쓰면, 양 끝이 처음부터 1400바이트 이하의 패킷만 만든다. ICMP가 막혀 있어도 블랙홀이 생기지 않는다. Linux에서는 iptables의 `TCPMSS` 타깃으로 설정한다.

```bash
# SYN 패킷의 MSS를 경로 MTU에 맞춰 낮춘다
iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN \
  -j TCPMSS --clamp-mss-to-pmtu

# 고정값을 쓰려면 (경로 MTU 1400 -> MSS 1360)
iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN \
  -j TCPMSS --set-mss 1360
```

클램핑은 ICMP 없이도 동작하는 보조 수단이다. 근본 해결은 ICMP Type 3 Code 4(IPv6는 Packet Too Big)를 허용하는 것이다. ICMP를 전부 막지 말고 필요한 종류만 열어 두면 된다.

PLPMTUD(Packetization Layer PMTUD)는 ICMP 대신 전송 계층이 직접 크기를 바꿔 가며 보내 보고, 어느 크기까지 ACK가 오는지로 경로 MTU를 찾는 방식이다. Linux에서는 `net.ipv4.tcp_mtu_probing`으로 켠다. 커널 문서에 따르면 0은 끔, 1은 평소에는 끄고 ICMP 블랙홀이 감지되면 켬, 2는 항상 켬이다.

## 7. 진단하는 방법

큰 패킷만 문제라는 가설은 크기를 바꿔 가며 직접 확인할 수 있다.

```bash
# DF를 켜고 payload 1472바이트 (1472 + ICMP 8 + IP 20 = 1500)
ping -M do -s 1472 <host>

# 실패하면 크기를 줄여 가며 통과하는 최대 크기를 찾는다
ping -M do -s 1372 <host>   # 1372 + 28 = 1400

# 경로 MTU 확인
tracepath <host>

# Fragmentation Needed(Type 3, Code 4)가 도착하는지 관찰
tcpdump -i eth0 -n 'icmp[0] = 3 and icmp[1] = 4'
```

읽는 법은 다음과 같다.

- 1472는 실패하고 1372는 성공하면, 경로 MTU가 1400에서 1500 사이에 있다는 뜻이다. 크기를 반씩 좁혀 가며 정확한 값을 찾는다.
- 큰 ping이 실패하는데 `tcpdump`에도 ICMP가 보이지 않으면, 경로 어딘가에서 ICMP가 막힌 것이다.
- 이 상태에서 `curl`로 큰 파일을 받아 보면 본문 직전에서 멈추는 것으로 재현된다.

## 결론

- MTU는 링크가 실을 수 있는 IP 패킷 크기이고, MSS는 거기서 IP와 TCP 헤더를 뺀 데이터 크기다. 이더넷은 1500 - 20 - 20 = 1460이다.
- 터널을 지나면 오버헤드만큼 MTU와 MSS가 줄어든다. 양 끝 호스트는 SYN 시점에 그 사실을 알 수 없다.
- PMTUD는 DF를 켜고 보낸 뒤 라우터의 ICMP Type 3 Code 4로 경로 MTU를 배운다. 이 ICMP 한 통에 전부를 의존한다.
- ICMP가 막히면 handshake와 작은 패킷은 되고 큰 패킷만 영원히 사라진다. 이것이 PMTUD 블랙홀이다.
- 근본 해결은 필요한 ICMP를 허용하는 것이고, MSS 클램핑은 ICMP 없이도 동작하는 보조 수단이다.
