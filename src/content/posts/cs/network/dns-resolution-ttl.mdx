## 개요

네트워크 시리즈의 첫 글이다. 서비스에 접속하는 거의 모든 요청은 DNS 조회로 시작한다. 그래서 서버가 멀쩡해도 DNS가 막히면 사이트가 사라진 것처럼 보인다.

이 글이 답하는 질문은 두 가지다.

- `www.example.com`이 IP 주소로 바뀌기까지 어떤 서버를 거치고, 어디에 캐시되는가?
- 레코드를 바꿨는데 왜 일부 사용자만 옛 서버로 가고, DNS 장애는 왜 그렇게 넓게 퍼지는가?

DNS(Domain Name System)는 이름을 IP 주소 같은 레코드로 바꿔 주는 계층적·분산형 데이터베이스다. 다음 글에서는 이름을 IP로 바꾼 뒤 TCP 연결을 맺는 과정을 본다. [TCP 연결 수립과 SYN/accept queue](/posts/cs/network/tcp-handshake-syn-accept-queue)로 이어진다.

## 1. 왜 계층 구조인가

도메인 이름 전체를 서버 한 대가 들고 있다고 해 보자. 전 세계의 모든 질의가 그 서버로 몰린다. 새 도메인을 등록하거나 IP를 바꿀 때마다 그 서버 관리자의 허락도 받아야 한다. 병목과 관리 부담이 모두 한 곳에 쌓인다.

DNS는 이름 공간을 트리로 나누고, 각 구간의 관리 권한을 아래로 위임하는 방식으로 이 문제를 풀었다.

핵심 아이디어는 한 문장이다. **이름 공간을 트리로 쪼개 권한을 위임하고, 거의 바뀌지 않는 답은 캐시로 흡수한다.**

```
                .  (root)
                |
      +---------+---------+
      |         |         |
     com       org       kr        <- TLD (top-level domain)
      |
  example.com                      <- domain owner's zone
      |
  www.example.com                  <- A record: IP address
```

각 구간을 책임지는 서버를 권한 네임서버(authoritative name server)라고 한다. 자기 영역(zone)에 대한 최종 답을 가진 서버다. 루트 서버는 `com`을 누가 맡는지만 알고, `com` 서버는 `example.com`을 누가 맡는지만 안다.

DNS가 주고받는 답은 레코드(record) 단위이고, 종류가 정해져 있다. 이 글에는 두 가지가 주로 나온다.

- A 레코드: 이름 -> IPv4 주소. 예: `www.example.com -> 192.0.2.10`
- NS 레코드: "이 영역은 이 네임서버가 맡는다"는 위임 정보. 예: `example.com -> ns1.example.com`

이 구조 덕분에 한 서버가 모든 이름을 알 필요가 없다. 대신 이름 하나를 찾으려면 위에서 아래로 여러 서버를 거쳐야 한다. 이 여정을 대신 해 주는 존재가 다음에 나오는 재귀 리졸버다.

## 2. 누가 찾아다니는가: 스텁, 재귀 리졸버, 권한 서버

내 애플리케이션이 루트부터 직접 돌아다니게 만들면 모든 클라이언트가 같은 일을 반복한다. 그래서 역할을 둘로 나눈다.

| 역할 | 하는 일 | 예 |
|---|---|---|
| 스텁 리졸버(stub resolver) | 질의를 한 번 던지고 최종 답만 받는다. 로컬 캐시를 가진다. | OS, 브라우저, JVM |
| 재귀 리졸버(recursive resolver) | 대신 찾아다니고 결과를 캐시한다. | ISP, 회사 DNS, 8.8.8.8 |
| 권한 네임서버 | 자기 영역의 최종 답을 준다. | 루트, TLD, 도메인 소유자의 NS |

질의 방식도 둘로 갈린다.

- 재귀 질의(recursive query): "끝까지 찾아서 답을 줘"라고 맡긴다. 스텁이 재귀 리졸버에게 하는 질의다.
- 반복 질의(iterative query): 서버가 답 대신 "다음엔 저쪽에 물어봐"라고 가리킨다. 이 안내를 위임(referral)이라고 한다. 재귀 리졸버가 권한 서버들에게 하는 질의다.

스텁은 단순하게 유지되고, 복잡한 일은 리졸버 한 곳에 모인다. 여러 사용자가 리졸버의 캐시를 함께 쓰니 효율도 좋다. 대가는 리졸버가 병목이자 단일 장애점이 된다는 점이다. 또 리졸버의 캐시는 캐시 포이즈닝(cache poisoning, 가짜 응답을 캐시에 심어 다른 사용자까지 엉뚱한 IP로 보내는 공격)의 표적이 된다.

## 3. 한 번의 해석을 따라가기: dig +trace

`dig +trace`는 루트부터 위임을 한 단계씩 따라가며 보여 준다. 정확히는 dig가 리졸버 역할을 직접 하는 것이다. 흐름을 눈으로 보기에 좋다. 아래는 이해를 위해 줄인 출력 형태의 예시다. IP와 서버 이름 일부는 설명용 값이다.

```
$ dig +trace www.example.com A

.                    518400 IN NS  a.root-servers.net.
                     ...
;; Received from 8.8.8.8 (root NS list)

com.                 172800 IN NS  a.gtld-servers.net.
                     ...
;; Received from a.root-servers.net      <- 1) root: "com is over there"

example.com.         172800 IN NS  ns1.example.com.
                     ...
;; Received from a.gtld-servers.net      <- 2) TLD: "example.com is over there"

www.example.com.        300 IN A   192.0.2.10
;; Received from ns1.example.com         <- 3) authoritative: final answer
```

왼쪽 숫자 `518400`, `172800`, `300`이 TTL(초)이다. 한 줄씩 보자.

1. 루트 서버는 `www.example.com`의 답을 모른다. 대신 `com` 영역을 맡은 NS 목록을 돌려준다. 위임이다.
2. `com` TLD 서버도 답을 모른다. `example.com`의 NS 목록을 돌려준다.
3. `example.com`의 권한 서버가 비로소 A 레코드 `192.0.2.10`을 돌려준다. TTL은 300초다.

실제 서비스에서는 이 반복 질의를 재귀 리졸버가 대신 수행한다. 전체 흐름은 이렇다.

```
client   resolver      root       .com TLD    example.com NS
  |  1) www.example.com?  |          |            |
  |------->|              |          |            |
  |        | 2) ask root  |          |            |
  |        |------------->|          |            |
  |        |<-- 3) com NS |          |            |
  |        | 4) ask TLD              |            |
  |        |------------------------>|            |
  |        |<-- 5) example.com NS    |            |
  |        | 6) ask authoritative                 |
  |        |------------------------------------->|
  |        |<-- 7) A 192.0.2.10, TTL 300          |
  |<-- 8) answer (+ cached)          |            |
```

클라이언트가 직접 관여하는 것은 1번 질의와 8번 응답뿐이다. 2번부터 7번까지는 리졸버가 혼자 한다. 이게 재귀 질의와 반복 질의가 나뉘는 지점이다.

전송은 기본적으로 UDP 53번 포트다. 질의와 응답이 작아서 TCP처럼 연결을 맺는 과정 없이 왕복 한 번에 끝낼 수 있다.

응답이 UDP 한도보다 커서 잘리면 응답 헤더의 TC(truncated, 잘림) 비트가 켜진다. 클라이언트는 이 표시를 보고 같은 질의를 TCP로 다시 보낸다. EDNS0은 DNS 메시지에 옵션을 붙이는 확장인데, 이걸로 더 큰 UDP 응답을 받겠다고 알리면 TCP로 다시 묻는 일이 줄어든다.

UDP는 출발지 주소를 쉽게 위조할 수 있어서 가짜 응답(스푸핑)에 약하다. 그래서 응답에 서명을 붙이는 DNSSEC, 질의를 암호화해 보내는 DoT(DNS over TLS)와 DoH(DNS over HTTPS) 같은 보완책이 따로 쓰인다.

## 4. TTL 캐시: 두 번째부터는 왜 빠른가

위 여정은 서버 세 곳을 오가야 하고, 모든 사용자가 매번 이렇게 하면 루트와 TLD 서버가 견디지 못한다. 거의 바뀌지 않는 답을 매번 새로 물을 이유가 없다.

핵심 아이디어는 한 문장이다. **모든 응답에 유효 시간(TTL, Time To Live)을 붙여, 그 시간 동안은 받은 쪽이 마음대로 재사용하게 한다.**

TTL은 위 예시에서 본 대로 응답 레코드마다 붙은 초 단위 숫자다. 리졸버는 최종 답뿐 아니라 위임 정보(NS 레코드)도 캐시한다. 그 효과는 이렇다.

| 상황 | 리졸버가 하는 일 | 서버 왕복 |
|---|---|---|
| 처음 조회 | 루트 -> TLD -> 권한 서버 | 3번 |
| 300초 안에 같은 이름 | 캐시에서 바로 응답 | 0번 |
| 300초 뒤, `com` NS는 아직 유효 | TLD에 물을 필요 없이 `example.com` 권한 서버만 | 1번 |
| `www`가 아닌 `api.example.com` 최초 조회 | 캐시된 `example.com` NS로 바로 | 1번 |

위임 정보가 캐시되기 때문에 루트와 TLD 서버는 사실상 전체 질의의 아주 작은 일부만 받는다. 이 덕분에 소수의 서버로 전 세계를 감당한다.

캐시는 리졸버에만 있지 않다. 층이 여러 개다.

```
app cache (JVM 등) -> OS stub cache -> recursive resolver cache -> authoritative
```

층마다 자기 시계로 TTL을 센다. 이 점이 다음 절의 문제를 만든다.

## 5. 바꿨는데 안 바뀐다: 최종 일관성의 대가

서버를 새 IP로 옮긴다고 하자. 권한 서버의 A 레코드를 `192.0.2.10`에서 `192.0.2.99`로 바꾼다. 이 시점의 TTL이 3600초(1시간)이다.

```
t=0     A 레코드 수정 (authoritative는 즉시 새 IP를 응답)
t=0     리졸버 A: 10분 전에 조회, 캐시 남은 시간 50분 -> 옛 IP 응답
t=0     리졸버 B: 방금 조회, 캐시 남은 시간 60분      -> 옛 IP 응답
t=50m   리졸버 A 만료 -> 새 IP
t=60m   리졸버 B 만료 -> 새 IP
```

권한 서버는 즉시 바뀌지만, 사용자는 어느 리졸버를 쓰는지에 따라 최대 TTL만큼 옛 서버로 간다. DNS는 변경이 서서히 퍼지는 최종 일관성(eventual consistency) 모델이다. 읽기가 압도적으로 많고 쓰기는 드문 데이터라서 이 대가를 감수하고 확장성을 얻었다.

더 곤란한 경우도 있다. 일부 클라이언트는 응답의 TTL을 보지 않고 자기 규칙으로 캐시한다. 대표적인 예가 JVM이다. JVM은 이름 조회 결과를 자체 캐시에 두고, 유지 시간을 보안 속성 `networkaddress.cache.ttl`(초 단위)로 정한다. Oracle 문서에 따르면 보안 관리자(security manager)가 설치된 경우 기본값은 -1, 즉 영구 캐시다. 그러면 DNS는 이미 바뀌었는데 그 애플리케이션만 재시작 전까지 옛 IP로 계속 접속한다.

변경을 안전하게 하는 순서는 이렇다.

1. 변경 며칠 전에 TTL을 60초 정도로 미리 낮춘다. 낮추기 전의 긴 TTL이 지나야 효과가 난다.
2. 레코드를 바꾼다.
3. 옛 서버는 전환 기간 동안 살려 둔다. 늦게 갱신하는 캐시가 아직 옛 서버로 오기 때문이다.
4. 안정되면 TTL을 다시 올린다.

원인을 가를 때는 dig를 두 가지로 쓴다. `dig +trace`는 권한 서버의 실제 답을 보여 주고, `dig @8.8.8.8 www.example.com`처럼 리졸버를 지정하면 그 리졸버의 캐시 상태를 보여 준다. 둘이 다르면 캐시 문제이고, 둘 다 틀리면 레코드 자체가 잘못된 것이다.

## 6. 음성 캐시: 없다는 답도 캐시된다

존재하지 않는 이름을 조회하면 권한 서버는 NXDOMAIN(해당 이름 없음)을 돌려준다. 이 부정적인 답도 캐시한다. 이를 음성 캐시(negative caching)라고 한다.

음성 캐시의 유지 시간은 영역의 SOA(Start of Authority) 레코드에서 정해진다. SOA는 영역마다 하나씩 있는, 그 영역의 관리 정보를 담은 레코드다. 권한 서버는 NXDOMAIN 응답에 이 SOA를 함께 실어 보낸다. RFC 2308은 SOA 자체의 TTL과 SOA의 MINIMUM 필드 중 작은 값을 음성 캐시 시간으로 쓴다고 정한다.

여기서 생기는 문제는 이런 상황이다.

```
10:00  누군가 new.example.com 을 조회 -> NXDOMAIN, 음성 캐시 1시간
10:05  운영자가 new.example.com 레코드 생성
10:10  같은 리졸버를 쓰는 사용자 -> 여전히 NXDOMAIN
11:00  음성 캐시 만료 -> 정상 해석
```

새로 만든 도메인이 특정 네트워크에서만 안 보이는 현상이다. 생성 직전에 누군가 먼저 조회했다면 그 리졸버만 이렇게 된다.

서버 실패(SERVFAIL)는 사정이 다르다. 리졸버가 권한 서버에서 답을 얻지 못했다는 뜻이다. RFC 2308은 리졸버가 이 실패를 캐시해도 되지만 5분을 넘기면 안 된다고(MUST NOT) 정한다. 그래서 실패는 짧게 캐시되고, 만료되면 재시도가 이어진다. 이 차이가 8절의 장애에서 중요해진다.

## 7. 트레이드오프: TTL을 얼마로 둘 것인가

TTL은 변경 속도와 안정성 사이의 다이얼이다.

| 선택 | 얻는 것 | 잃는 것 |
|---|---|---|
| 긴 TTL (예: 1일) | 질의 수와 지연이 줄고, 권한 서버 부하가 낮고, 상위 장애를 캐시가 버틴다 | IP 변경과 failover가 느리게 전파된다 |
| 짧은 TTL (예: 30~60초) | 장애 시 빠른 전환, 트래픽 재분배 용이 | 질의량 증가, 권한 DNS 의존도 증가 |

짧은 TTL이 항상 정답은 아니다. 5초처럼 극단적으로 줄이면 질의량이 크게 늘고, 권한 서버가 죽었을 때 캐시가 금방 만료돼 장애가 훨씬 빨리 퍼진다. 일부 클라이언트와 리졸버는 최소 TTL을 강제하거나 아예 무시해서 기대한 만큼 빨리 바뀌지도 않는다.

그래서 TTL은 레코드의 중요도와 변경 빈도에 맞춰 정하고, DNS 하나에만 failover를 맡기지 않는다. 로드밸런서와 헬스체크 같은 다른 계층과 같이 쓴다.

권한 서버를 anycast(같은 IP를 여러 위치에서 광고해 가까운 곳이 응답하는 방식)로 운영하면 응답이 빨라지고 분산 DoS를 흡수한다. 대신 운영이 복잡해지고 BGP에 의존하게 된다. BGP(Border Gateway Protocol)는 네트워크들이 "이 IP 대역으로 가려면 나에게 보내라"는 경로를 서로 광고하는 프로토콜이다. 광고를 거두면 그 IP로 가는 길이 인터넷에서 사라진다. 다음 절의 사건이 바로 이 지점에서 일어났다.

## 8. 장애는 어떻게 전파되는가: Meta 2021-10-04

2021년 10월 4일 Meta(당시 Facebook)의 서비스가 전 세계에서 몇 시간 동안 열리지 않았다. 공식 글들이 밝힌 흐름은 이렇다.

1. 정비 중 백본 용량을 점검하는 명령이 데이터센터 사이의 백본 연결을 모두 끊었다. 이런 명령을 막아야 할 감사 도구에 버그가 있어 막지 못했다.
2. Meta의 권한 DNS 서버는 데이터센터에 닿지 않으면 스스로 비정상이라고 판단하고, 자기 IP를 BGP로 알리던 광고를 철회하도록 설계돼 있었다. 백본 전체가 끊기자 모든 DNS 서버가 동시에 광고를 철회했다.
3. DNS 서버는 멀쩡히 살아 있었지만 인터넷에서 도달할 수 없게 됐다. 리졸버들은 권한 서버를 찾지 못해 SERVFAIL을 돌려줬다.

Cloudflare의 관찰에 따르면 1.1.1.1과 8.8.8.8은 SERVFAIL을 돌려주고 그 실패 결과를 캐시했다. 앱과 사용자가 재시도를 반복하면서 1.1.1.1의 질의량은 평소의 약 30배까지 늘었다. 한 서비스의 장애가 다른 DNS 인프라의 부하로 번진 것이다. Cloudflare 측정으로 1.1.1.1에서 facebook.com은 약 15:50부터 21:20 UTC까지 해석되지 않았다.

내부에서도 같은 일이 벌어졌다. DNS가 막히자 엔지니어가 쓰는 내부 도구가 함께 멈췄고, 주 네트워크와 대역 외(out-of-band) 접근까지 막혀 직접 데이터센터로 가야 했다. 물리 보안 절차도 복구를 늦췄다. 장애 대응 도구가 장애 대상에 의존한 것이다.

이 사건에서 얻는 설계 교훈은 세 가지다.

| 문제 | 개선 방향 |
|---|---|
| 연결 상실을 "내가 고장 났다"로 해석하는 헬스체크가 전체 단절에서 모든 DNS를 동시에 뺐다 | 전체가 한꺼번에 철회되지 않게 가드를 둔다 |
| 권한 DNS가 한 장애 영역에 모여 있었다 | 별도 장애 도메인이나 제3자 DNS에 권한 서버를 병행한다 |
| 복구 도구가 같은 네트워크와 DNS에 의존했다 | 복구 수단과 접근 경로를 주 네트워크에서 분리한다 |

외부에서 도메인이 해석되지 않을 때 조사 순서도 여기서 나온다. 권한 서버부터 거꾸로 확인한다.

1. `dig +trace`로 위임 체인이 끊기지 않았는지 본다.
2. 권한 NS가 각각 응답하는지 UDP와 TCP로 확인한다.
3. 레지스트라(도메인 등록 업체)에 등록한 NS와 DS 레코드가 실제 권한 서버 설정과 맞는지 본다. DS 레코드는 DNSSEC에서 상위 영역이 하위 영역의 서명 키를 보증하는 레코드다. 이게 어긋나면 서명 검증이 실패해 SERVFAIL이 난다.
4. 권한 서버 IP까지 경로가 살아 있는지 본다. BGP와 anycast 경로다.
5. 리졸버 로그에서 SERVFAIL과 타임아웃을 확인한다.

## 결론

- DNS는 이름 공간을 트리로 나눠 권한을 위임하고, 재귀 리졸버가 위임을 따라가 대신 찾아 준다.
- 모든 응답과 위임 정보는 TTL 동안 여러 층에서 캐시되어 루트와 TLD 서버의 부하를 흡수한다.
- 그 대가로 변경은 최대 TTL만큼 늦게 퍼지는 최종 일관성을 갖고, 없다는 답(NXDOMAIN)도 캐시된다.
- TTL이 짧다고 장애 대응이 항상 좋아지지는 않는다. 권한 서버에 대한 의존이 커진다.
- DNS는 거의 모든 접속의 첫 단계라서, DNS 장애는 서비스 장애를 넘어 복구 도구까지 멈추는 연쇄 장애의 뿌리가 될 수 있다.
