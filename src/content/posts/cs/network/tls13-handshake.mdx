## 개요

[앞 글](/posts/cs/network/tcp-close-time-wait/)까지는 TCP가 연결을 맺고, 데이터를 믿을 수 있게 나르고, 연결을 닫는 과정을 봤다. 그런데 TCP는 내용을 숨기지 않는다. 경로 위의 누구든 패킷을 읽고 바꿀 수 있다. 네트워크 시리즈의 마지막 글은 그 위에 얹는 보안 계층인 TLS를 다룬다.

이 글이 답하는 질문은 두 가지다.

- TLS 1.3은 어떻게 왕복 한 번(1-RTT)에 키 교환과 서버 인증을 끝내고, 왜 서버 개인키가 나중에 유출돼도 과거 트래픽은 안전한가?
- 서버 인증서는 멀쩡한데 왜 어떤 클라이언트에서만 "unable to get local issuer certificate"나 "certificate has expired"가 나는가?

**TLS**(Transport Layer Security)는 통신 상대가 진짜인지, 내용이 읽히지 않는지, 중간에 바뀌지 않았는지를 함께 보장하는 프로토콜이다. HTTPS는 HTTP를 TLS 위에서 돌린 것이다.

## 1. TLS가 지키는 세 가지, 그리고 두 개의 축

평문 HTTP로 로그인한다고 해 보자. 같은 카페 와이파이에 붙은 사람은 비밀번호를 그대로 읽을 수 있다. 중간 라우터는 응답에 광고 스크립트를 끼워 넣을 수 있다. 공격자가 DNS를 속였다면 아예 가짜 서버와 대화하게 된다.

TLS는 이 세 문제를 각각 막는다.

| 성질 | 막는 공격 | 수단 |
|---|---|---|
| 기밀성(confidentiality) | 도청 | 대칭 키 암호화 |
| 무결성(integrity) | 변조 | 암호화와 함께 붙는 인증 태그 |
| 인증(authentication) | 가짜 서버 | 인증서와 서명 |

핵심 아이디어는 한 문장이다. **도청자가 모르는 비밀을 만드는 일(키 교환)과, 그 비밀을 나눈 상대가 진짜 서버인지 확인하는 일(인증)을 따로 해결한 뒤 하나로 묶는다.**

두 축은 실패하는 방식이 다르다. 키 교환이 완벽해도 상대가 가짜면 공격자와 안전하게 대화하는 꼴이 된다. 반대로 인증서가 진짜여도 키 교환이 약하면 내용이 새어 나간다. 운영에서 흔히 마주치는 TLS 장애는 두 번째 축, 즉 인증서 검증 쪽에서 난다. 그래서 이 글도 두 축을 나눠서 본다.

## 2. 키 교환: 공개값만 주고받아 같은 비밀을 만든다

### 왜 어려운가

대칭 키 암호는 빠르다. 하지만 양쪽이 같은 키를 이미 갖고 있어야 한다. 처음 만난 클라이언트와 서버는 공유한 것이 없다. 키를 그냥 보내면 도청자도 그 키를 받는다.

### 핵심 아이디어

**키 교환**(key exchange)은 양쪽이 공개해도 되는 값만 주고받고, 각자 자기만 아는 값과 섞어 같은 비밀을 계산하는 방법이다. TLS 1.3이 쓰는 방식은 **ECDHE**(Elliptic Curve Diffie-Hellman Ephemeral)다. 타원 곡선 위의 디피-헬만 키 교환을, 연결마다 새로 만든 임시 값으로 하는 방식이라는 뜻이다.

물감 섞기로 비유하면 이렇다.

1. 클라이언트와 서버가 공통 노란색을 정한다. 이건 공개다.
2. 클라이언트는 비밀 빨간색을, 서버는 비밀 파란색을 각자 고른다.
3. 각자 노란색에 자기 비밀색을 섞어서 보낸다. 주황색과 초록색이 오간다. 도청자도 이 두 색을 본다.
4. 클라이언트는 받은 초록색에 빨간색을 섞고, 서버는 받은 주황색에 파란색을 섞는다. 둘 다 노랑+빨강+파랑, 같은 갈색이 된다.
5. 도청자는 주황과 초록을 갖고 있지만, 섞인 물감에서 빨강이나 파랑을 다시 뽑아낼 수 없다. 그래서 갈색을 만들 수 없다.

이 비유가 틀리는 지점도 있다. 물감은 물리적으로 분리가 안 되지만, 실제 키 교환은 "되돌리는 계산이 현재 컴퓨터로는 사실상 불가능할 만큼 오래 걸린다"는 데 기대고 있다. 그리고 비유에서도 보이듯, 중간에 끼어든 사람이 자기 물감을 섞어 양쪽에 따로 건네면 막을 방법이 없다. 이 문제는 3절의 서명이 해결한다.

### 비밀에서 키로

공유 비밀이 생기면 바로 암호화 키로 쓰지 않는다. **HKDF**(HMAC-based Key Derivation Function)에 넣어 용도별 키를 여러 개 뽑는다. HKDF는 하나의 비밀에서 서로 독립적인 키를 여러 개 만들어 내는 함수다. 해시와 KDF의 기본 개념은 [비밀번호 저장과 KDF](/posts/cs/security/password-storage-kdf/) 글에서 다룬다.

뽑는 키는 크게 두 종류다.

- 핸드셰이크 키(handshake traffic key): 핸드셰이크 나머지 메시지를 암호화한다.
- 애플리케이션 키(application traffic key): 실제 HTTP 요청과 응답을 암호화한다.

이때 HKDF에는 공유 비밀만이 아니라 **트랜스크립트 해시**(transcript hash)도 들어간다. 트랜스크립트 해시는 지금까지 주고받은 핸드셰이크 메시지 전체를 순서대로 이어 붙여 해시한 값이다. 덕분에 대화 내용이 한 바이트라도 달랐다면 양쪽 키가 달라진다.

## 3. 1-RTT 핸드셰이크를 메시지 단위로 따라가기

### 메시지 흐름

RFC 8446의 전체 핸드셰이크에서 서버 인증만 하는 일반적인 경우를 그리면 다음과 같다. 클라이언트 인증서처럼 선택적인 메시지는 뺐다.

```
Client                                        Server

ClientHello
 + key_share   (client public value)
 + cipher suites, supported_versions
                       ------ 1 ------>
                                              ServerHello
                                               + key_share (server public value)
                                              (server: shared secret -> keys)
                                              {EncryptedExtensions}
                                              {Certificate}
                                              {CertificateVerify}
                       <----- 2 -------       {Finished}
(client: shared secret -> keys)
{Finished}
[Application Data]     ------ 3 ------>
[Application Data]     <-------------->       [Application Data]

{ } : handshake key로 암호화        [ ] : application key로 암호화
```

### 단계별로, RTT 100ms 경로에서

TCP 연결이 이미 맺어졌다고 하고, 클라이언트와 서버 사이 왕복 시간(RTT)이 100ms라고 하자.

**t = 0ms, 화살표 1.** 클라이언트가 `ClientHello`를 보낸다. 지원하는 암호군 목록과 함께 `key_share`, 즉 키 교환용 공개값을 미리 실어 보낸다. 서버가 어떤 방식을 고를지 모르는 상태에서 "아마 이걸 고를 것"이라고 예측해 공개값을 먼저 내미는 것이 1-RTT의 비결이다.

**t = 50ms.** 서버가 `ClientHello`를 받는다. 자기 공개값을 만들고, 클라이언트 공개값과 섞어 공유 비밀을 계산한다. 이 순간 서버는 핸드셰이크 키를 갖는다.

**t = 50ms, 화살표 2.** 서버는 `ServerHello`(자기 공개값 포함)를 보내고, 이어서 나머지를 전부 핸드셰이크 키로 암호화해서 한 번에 보낸다.

- `EncryptedExtensions`: 협상 결과 중 `ServerHello`에 없어도 되는 나머지 설정
- `Certificate`: 서버 인증서 체인
- `CertificateVerify`: 서버 개인키로 트랜스크립트 해시에 한 서명
- `Finished`: 지금까지의 핸드셰이크 전체에 대한 MAC(메시지 인증 코드)

**t = 100ms.** 클라이언트가 `ServerHello`를 받아 같은 공유 비밀을 계산하고, 나머지 메시지를 복호화해 검증한다. 검증 항목은 7절에서 자세히 본다.

**t = 100ms, 화살표 3.** 검증이 끝나면 클라이언트는 `Finished`와 첫 HTTP 요청을 같이 보낸다. 서버를 한 번만 왕복하고 요청을 보냈다. 이것이 1-RTT다.

### CertificateVerify가 왜 필요한가

인증서만 보내면 충분하지 않을까? 아니다. 인증서는 공개 정보라서 누구나 복사해서 내밀 수 있다.

`CertificateVerify`가 없다고 해 보자. 중간자 공격(MITM, man-in-the-middle)을 하는 공격자는 진짜 서버의 인증서를 그대로 클라이언트에 보여 주고, `key_share`만 자기 공개값으로 바꿔치기한다. 클라이언트는 인증서를 보고 안심한 채 공격자와 키를 만든다.

`CertificateVerify`는 서버가 인증서에 대응하는 개인키를 실제로 갖고 있고, **바로 이 핸드셰이크**에 서명했다는 증거다. 서명 대상인 트랜스크립트 해시에는 양쪽 `key_share`가 들어 있다. 공격자가 공개값을 바꾸면 트랜스크립트가 달라져 서명 검증에 실패한다. 개인키가 없는 공격자는 바뀐 트랜스크립트에 새 서명을 만들 수 없다.

`Finished`는 마지막 확인이다. 양쪽이 같은 메시지를 주고받았고 같은 키를 계산했는지를 MAC으로 맞춰 본다.

### 생기는 문제: 예측이 빗나가면

클라이언트가 미리 보낸 `key_share`의 곡선을 서버가 지원하지 않으면 어떻게 될까? 서버는 `HelloRetryRequest`로 "이 곡선으로 다시 보내라"고 답하고, 클라이언트는 `ClientHello`를 다시 보낸다. 왕복이 하나 늘어 2-RTT가 된다. 실제로는 대부분의 클라이언트와 서버가 X25519 같은 널리 쓰는 곡선을 지원하므로 드문 경우다.

## 4. 전방 비밀성: 서버 키가 털려도 과거가 안전한 이유

### 왜 필요한가: 녹화해 두고 나중에 푸는 공격

공격자가 1년 동안 어떤 서버로 가는 암호화 트래픽을 전부 녹화해 둔다. 당장은 읽을 수 없다. 1년 뒤, 서버 백업 유출이나 퇴사자 실수로 서버의 장기 개인키(인증서에 대응하는 키)가 새어 나간다. 이 키로 지난 1년치 녹화를 풀 수 있을까?

TLS 1.2의 **RSA 키 교환**에서는 풀 수 있다. 이 방식에서 클라이언트는 세션 키의 재료(pre-master secret)를 만들어 서버 인증서의 공개키로 암호화해서 보낸다. 그 재료는 녹화본 안에 들어 있다. 서버 개인키만 있으면 녹화된 모든 세션의 재료를 꺼내 세션 키를 다시 만들 수 있다.

### 핵심 아이디어

**전방 비밀성**(forward secrecy)은 장기 키가 나중에 유출되더라도 과거 세션의 키를 복원할 수 없는 성질이다. 방법은 단순하다. 세션 키를 만드는 비밀을 장기 키와 상관없이 연결마다 새로 만들고, 쓰고 나면 버린다.

ECDHE의 E(ephemeral, 임시)가 바로 이것이다.

| 시점 | RSA 키 교환 (TLS 1.2) | ECDHE (TLS 1.3) |
|---|---|---|
| 연결할 때 | 세션 재료를 서버 장기 공개키로 암호화해 전송 | 양쪽이 임시 키를 새로 만들어 공개값만 교환 |
| 연결 끝난 뒤 | 서버 장기 개인키는 계속 보관 | 임시 개인값은 메모리에서 폐기 |
| 1년 뒤 장기 키 유출 | 녹화된 모든 과거 세션 복호화 가능 | 과거 세션 키를 만들 재료가 어디에도 없음 |

ECDHE에서 서버 장기 개인키가 하는 일은 `CertificateVerify`의 서명뿐이다. 서명은 "그때 그 상대가 진짜였다"는 증명이지 세션 키의 재료가 아니다. 그래서 장기 키가 새도 과거 세션 키는 복원되지 않는다. 키가 유출된 뒤에 공격자가 서버를 사칭할 수는 있으므로, 인증서는 즉시 폐기하고 다시 발급해야 한다.

### 그래서 TLS 1.3은 RSA 키 교환을 없앴다

TLS 1.2에서도 ECDHE를 고를 수 있었다. 문제는 "고를 수 있다"는 점이었다. 설정 실수나 오래된 클라이언트 때문에 RSA 키 교환으로 협상되면 전방 비밀성이 조용히 사라진다.

TLS 1.3은 정적 RSA와 정적 DH 키 교환을 아예 제거했다. RFC 8446은 공개키 기반의 모든 키 교환이 이제 전방 비밀성을 제공한다고 명시한다. 그리고 인증은 서명(`CertificateVerify`)으로 분리했다. 키 교환은 매번 새로, 인증은 장기 키로. 1절에서 말한 두 축이 프로토콜 구조에서도 갈라진 것이다.

비용은 연결마다 임시 키 쌍을 만들고 계산하는 일인데, X25519 같은 타원 곡선에서는 그 비용이 작다. 남는 예외는 6절의 0-RTT와, 세션 재개 때 키 교환 없이 사전 공유 키만 쓰는 모드다. 둘 다 전방 비밀성이 약해진다.

## 5. TLS 1.2와 나란히 놓고 보기

TLS 1.2의 전체 핸드셰이크는 왕복이 두 번 필요했다. 첫 왕복에서 암호군을 정하고 서버 인증서를 받은 뒤에야, 두 번째 왕복에서 키 교환 재료를 보냈기 때문이다. TLS 1.3은 클라이언트가 첫 메시지에 공개값을 미리 실어서 이 순서를 한 번으로 줄였다.

| 구분 | TLS 1.2 (RSA 키 교환) | TLS 1.2 (ECDHE) | TLS 1.3 |
|---|---|---|---|
| 전방 비밀성 | 없음 | 있음 | 항상 있음 (정적 RSA 제거) |
| 첫 연결 핸드셰이크 | 2-RTT | 2-RTT | 1-RTT |
| 재연결 | 세션 재개 1-RTT | 세션 재개 1-RTT | 1-RTT, 또는 0-RTT 선택 |
| 인증서 | 평문으로 전송 | 평문으로 전송 | 암호화해서 전송 |
| 주의할 점 | 레거시 호환용 | 약한 암호군이 협상될 수 있음 | 0-RTT 데이터는 재전송될 수 있음 |

RTT 100ms 경로에서 새 연결을 맺고 첫 HTTP 요청을 내보내기까지 걸리는 시간을 따져 보자. TCP 핸드셰이크도 왕복 하나가 든다.

| 조합 | TCP | TLS | 요청을 보낼 수 있는 시점 |
|---|---|---|---|
| TCP + TLS 1.2 | 1 RTT | 2 RTT | 300ms |
| TCP + TLS 1.3 | 1 RTT | 1 RTT | 200ms |
| TCP + TLS 1.3 0-RTT (재연결) | 1 RTT | 0 RTT | 100ms |

해외 리전처럼 RTT가 200ms를 넘는 경로라면 왕복 하나가 사용자가 체감하는 지연이 된다.

인증서 암호화도 의미가 있다. TLS 1.2에서는 수동적인 관찰자가 인증서를 보고 어느 사이트에 접속하는지 알 수 있었다. TLS 1.3에서는 `ServerHello` 이후의 핸드셰이크 메시지가 모두 암호화되어 인증서도 보이지 않는다. 다만 `ClientHello`에 들어 있는 접속 도메인 이름(SNI)은 여전히 평문이다.

## 6. 0-RTT: 왕복을 하나 더 줄이는 대가

### 왜 필요한가

1-RTT도 모바일 환경이나 먼 리전에서는 아깝다. 이미 한 번 연결했던 서버라면, 그때 합의한 비밀로 첫 메시지부터 데이터를 암호화해 보낼 수 있지 않을까?

### 핵심 아이디어

**0-RTT**(early data)는 이전 연결에서 받아 둔 **사전 공유 키**(PSK, pre-shared key)로 첫 요청을 암호화해 `ClientHello`와 같이 보내는 방식이다. 서버는 이전 연결이 끝날 무렵 재연결용 티켓을 클라이언트에 준다. 클라이언트는 다음 연결에서 이 티켓을 내밀고, 티켓에서 유도한 키로 요청을 바로 암호화한다.

```
Client                                        Server

ClientHello
 + early_data, key_share
 + pre_shared_key (ticket)
(Application Data)     ------ 1 ------>       GET /profile 을 바로 처리
                                              ServerHello
                                              {EncryptedExtensions}
                       <----- 2 -------       {Finished}
(EndOfEarlyData)
{Finished}             ------ 3 ------>

( ) : PSK에서 유도한 early data key로 암호화
```

### 생기는 문제 1: 재전송 공격

`ClientHello`와 early data는 서버의 응답을 기다리지 않고 나간다. 그래서 서버가 이번에 새로 만든 값이 하나도 섞이지 않는다. 공격자가 이 첫 비행(flight)을 녹화해서 그대로 다시 보내면, 서버 입장에서는 정상적인 0-RTT 요청과 구별하기 어렵다. 이를 **재전송 공격**(replay attack)이라 한다.

요청이 `GET /profile`이면 두 번 처리해도 결과가 같다. 요청이 `POST /transfer?amount=100`이라면 송금이 두 번 일어난다.

RFC 8446은 서버 쪽 방어 수단 세 가지를 제시한다.

| 방법 | 동작 | 한계 |
|---|---|---|
| 1회용 티켓 | 쓴 티켓은 지우고 모르는 티켓이 오면 전체 핸드셰이크로 | 여러 서버가 티켓 DB를 공유해야 함 |
| ClientHello 기록 | 시간 창 안에서 본 `ClientHello`를 기록해 중복 거부 | 기록 저장소 필요 |
| 신선도 검사 | 티켓 발급 시각과 클라이언트가 말한 티켓 나이로 도착 시각을 추정해, 창(예: 10초)을 벗어나면 거부 | 이것만으로는 부족함 |

RFC는 서버가 적어도 같은 인스턴스에서 같은 0-RTT를 두 번 받아들이지 않게 하라고 요구한다. 하지만 서버가 여러 리전에 있으면, 한 곳에서 거절된 `ClientHello`가 다른 곳에서 받아들여지는 식의 재전송은 TLS 계층에서 완전히 막을 수 없다. RFC도 이 부분은 애플리케이션이 처리해야 한다고 적었다.

그래서 결론은 RFC의 요구 사항 그대로다. 클라이언트는 재전송돼도 안전하다고 판단한 데이터만 early data로 보내야 한다. 실무에서는 부작용 없는 멱등(idempotent) 요청, 예를 들어 `GET`에만 0-RTT를 허용하고, 결제나 상태 변경 요청은 핸드셰이크가 끝난 뒤로 미룬다.

### 생기는 문제 2: early data에는 전방 비밀성이 없다

early data는 이전 연결의 PSK에서 유도한 키로만 암호화된다. 이번 연결의 ECDHE 결과는 아직 섞이지 않았다. 그래서 티켓을 암호화하는 서버 쪽 키가 나중에 유출되면 early data는 복호화될 수 있다. 4절에서 본 전방 비밀성이 0-RTT 구간에서는 성립하지 않는 것이다. early data 이후의 응답과 나머지 트래픽은 재연결에서도 키 교환을 같이 하면(PSK와 ECDHE를 함께 쓰는 모드) 전방 비밀성을 유지한다.

## 7. 인증서 체인 검증: 누가 이 공개키를 보증하는가

### 왜 체인이 필요한가

3절의 `CertificateVerify`는 "상대가 이 인증서의 개인키를 갖고 있다"까지만 증명한다. 그 인증서가 정말 `example.com`의 것인지는 따로 확인해야 한다. 공격자도 자기 키로 `example.com`이라고 적힌 인증서를 얼마든지 만들 수 있기 때문이다.

### 핵심 아이디어

**인증서**(certificate)는 "이 공개키의 주인은 이 도메인이다"라는 문장에 **인증 기관**(CA, Certificate Authority)이 서명한 문서다. 클라이언트는 그 서명을 한 단계씩 거슬러 올라가, 자기가 이미 믿고 있는 루트 인증서에 닿는지 확인한다.

```
[Root CA]          <- client trust store에 미리 들어 있음 (서버가 안 보내도 됨)
    |  signs
[Intermediate CA]  <- 서버가 보내야 함
    |  signs
[Leaf example.com] <- 서버가 보내야 함
```

- **리프 인증서**(leaf certificate): 도메인에 발급된 인증서. 서버 공개키가 들어 있다.
- **중간 CA 인증서**(intermediate certificate): 루트 대신 실제로 리프에 서명하는 CA의 인증서. 루트 개인키를 오프라인에 보관하려고 중간 단계를 둔다.
- **신뢰 저장소**(trust store): OS, 브라우저, JDK 같은 클라이언트 쪽에 미리 깔려 있는 루트 인증서 목록. 체인의 끝은 반드시 여기 있어야 한다.

RFC 8446은 서버가 리프를 맨 앞에 두고, 뒤의 인증서가 바로 앞 인증서를 보증하는 순서로 보내라고 정한다. 클라이언트가 이미 가진 신뢰 앵커(루트)는 생략해도 된다. 반대로 중간 인증서는 클라이언트가 갖고 있다고 기대할 수 없으므로 서버가 보내야 한다.

### 클라이언트가 확인하는 것

1. 체인: 리프부터 서명을 따라 올라가 신뢰 저장소의 루트에 닿는가
2. 유효기간: 체인의 각 인증서가 지금 시각에 유효한가
3. 이름: 리프의 **SAN**(Subject Alternative Name, 인증서가 유효한 도메인 목록)에 접속한 도메인이 들어 있는가
4. 소유 증명: `CertificateVerify` 서명이 리프 공개키로 검증되는가
5. 대화 일치: `Finished`의 MAC이 맞는가

인증서 폐기 여부(revocation) 확인은 OCSP나 CRL 같은 별도 수단으로 하며, 이 글에서는 다루지 않는다.

### 사례: 중간 인증서를 빠뜨린 서버

가장 흔한 실수는 서버 설정에 리프 인증서 파일만 넣고 중간 인증서를 빼는 것이다. 일부러 이렇게 설정해 둔 테스트 서버 `incomplete-chain.badssl.com`에 `openssl s_client`로 붙어 보면 이렇게 나온다(인증서 본문과 세션 정보는 생략했다).

```
$ openssl s_client -connect incomplete-chain.badssl.com:443 \
    -servername incomplete-chain.badssl.com -showcerts

depth=0 CN=*.badssl.com
verify error:num=20:unable to get local issuer certificate
verify return:1
depth=0 CN=*.badssl.com
verify error:num=21:unable to verify the first certificate
verify return:1
...
---
Certificate chain
 0 s:CN=*.badssl.com
   i:C=US, O=Let's Encrypt, CN=YR1
   a:PKEY: RSA, 2048 (bit); sigalg: sha256WithRSAEncryption
   v:NotBefore: Sep 29 20:02:56 2026 GMT; NotAfter: Dec 28 20:02:55 2026 GMT
-----BEGIN CERTIFICATE-----
...
-----END CERTIFICATE-----
---
...
Verification error: unable to verify the first certificate
```

출력을 읽는 법은 이렇다.

- `-showcerts`는 서버가 실제로 보낸 인증서를 전부 찍는다. `Certificate chain` 아래 항목이 `0` 하나뿐이다. 서버가 리프 하나만 보냈다는 뜻이다.
- `s:`는 주체(subject), `i:`는 발급자(issuer)다. 리프의 발급자는 Let's Encrypt의 중간 CA `YR1`이다.
- 정상 서버라면 `1 s:...CN=YR1` 항목이 이어서 나와야 한다. 그 항목이 없으니 클라이언트는 `YR1`의 공개키를 구할 수 없고, 리프의 서명을 검증하지 못한다.
- 그래서 `depth=0`, 즉 첫 인증서에서 바로 `unable to get local issuer certificate`와 `unable to verify the first certificate`가 난다.

까다로운 점은 브라우저에서는 이 사이트가 멀쩡해 보일 수 있다는 것이다. 브라우저는 서버가 빠뜨린 중간 인증서를 다른 경로로 메우기도 한다. 예를 들어 Firefox는 알려진 중간 CA 인증서 목록을 미리 내려받아 로컬 캐시에 넣어 둔다(intermediate CA preloading). Mozilla는 이 기능의 목적을 서버가 중간 인증서를 제대로 설정하지 않아 생기는 연결 오류를 줄이는 것이라고 설명한다. 반면 위처럼 OpenSSL 기반 도구나 서버 간 호출에 쓰는 HTTP 클라이언트는 이런 보충 없이 받은 체인만으로 검증하는 경우가 많아 실패한다. "브라우저에서는 되는데 서버 간 호출만 실패한다"면 먼저 `-showcerts`로 서버가 보내는 체인 개수를 세어 본다.

고치는 방법은 서버에 리프와 중간 인증서를 이어 붙인 파일(Let's Encrypt 클라이언트가 만드는 `fullchain.pem` 같은 파일)을 설정하는 것이다.

## 8. 같은 체인, 다른 결과: cross-sign과 클라이언트 쪽 상태

### 왜 이런 일이 생기는가

7절의 사례는 서버가 체인을 덜 보낸 경우였다. 서버가 체인을 제대로 보냈는데도 클라이언트에 따라 결과가 갈리는 경우가 있다. 원인은 같은 공개키를 가진 인증서가 둘 이상 있을 수 있다는 데 있다.

**교차 서명**(cross-sign)은 새로 만든 루트 CA의 인증서를, 이미 널리 신뢰받는 다른 루트가 한 번 더 서명해 주는 것이다. 새 루트가 아직 신뢰 저장소에 들어가지 않은 오래된 기기에서도 체인이 이어지게 하려는 장치다. 그 결과 같은 키에 대해 "자체 서명 버전"과 "다른 루트가 서명한 버전" 두 인증서가 존재하고, 검증 경로가 두 갈래가 된다.

### 사례: Let's Encrypt의 DST Root CA X3 만료와 OpenSSL 1.0.2

Let's Encrypt의 루트인 ISRG Root X1은 DST Root CA X3에게 교차 서명을 받아 왔다. DST Root CA X3는 2021-09-30에 만료됐다. OpenSSL 프로젝트는 2021-09-13에 이 문제를 미리 공지했다.

```
                 leaf: example.com
                         |
                 intermediate CA
                         |  signed with ISRG Root X1's key
          +--------------+-------------------+
          |                                  |
  path A                             path B
  ISRG Root X1                       ISRG Root X1
  (cross-signed, sent by server)     (self-signed, in trust store)
          |                                  |
  DST Root CA X3                     trust anchor
  (expired 2021-09-30)               -> verify OK
          |
  -> certificate has expired
```

당시 권장 체인에는 DST Root CA X3가 서명한 ISRG Root X1이 들어 있었다. 서버가 보낸 인증서를 따라가면 경로 A, 만료된 루트로 간다. 대부분의 클라이언트는 신뢰 저장소에 자체 서명 ISRG Root X1이 있으면 경로 B로 검증을 끝낸다.

OpenSSL 1.0.2는 달랐다. 신뢰 저장소보다 서버가 보낸(검증되지 않은) 체인을 항상 먼저 따라가는 방식이라 경로 A를 택했다. 그래서 신뢰 저장소에 ISRG Root X1이 있어도 인증서가 만료됐다고 보고했다.

OpenSSL 공지가 권한 대응은 세 가지였다.

| 대응 | 어디서 | 단점 |
|---|---|---|
| 신뢰 저장소에서 DST Root CA X3를 빼고 ISRG Root X1 추가 | 클라이언트 | 영향받는 호스트를 전부 갱신해야 함 |
| `-trusted_first` 옵션 또는 `X509_V_FLAG_TRUSTED_FIRST` 플래그 사용 | 클라이언트 | 기본값이 꺼져 있어 코드 변경이 필요할 수 있음 |
| 교차 서명을 뺀 대체 체인으로 서버 설정 | 서버 | 자체 서명 ISRG Root X1이 없는 일부 구형 Android가 연결을 거부함 |

### 생기는 문제: 검증 결과는 서버만의 것이 아니다

이 사례가 보여 주는 점은 검증 결과가 "서버가 보낸 체인 + 클라이언트의 신뢰 저장소 + 클라이언트의 경로 탐색 구현" 세 가지의 조합으로 정해진다는 것이다. 서버 인증서를 갱신하고 브라우저로 확인해도, 오래된 JDK나 OS 이미지, IoT 기기, 오래된 OpenSSL을 쓰는 배치 서버는 다른 결론을 낼 수 있다.

그래서 "신형 브라우저는 괜찮은데 구형 클라이언트만 실패한다"는 증상이 나오면 순서대로 확인한다.

1. `openssl s_client -showcerts`로 서버가 실제로 보내는 체인을 본다. 중간 인증서가 빠졌는지, 만료된 교차 서명 인증서가 끼어 있는지 확인한다.
2. 실패하는 클라이언트의 신뢰 저장소에 새 루트가 있는지 확인한다.
3. 그 클라이언트의 TLS 라이브러리 버전과 경로 탐색 옵션(OpenSSL이라면 `-trusted_first`)을 확인한다.

## 결론

- TLS는 키 교환(도청자가 모르는 비밀 만들기)과 인증(그 상대가 진짜인지 확인하기)을 따로 풀고, 서명이 트랜스크립트 전체를 덮게 해서 둘을 묶는다.
- TLS 1.3은 클라이언트가 첫 메시지에 키 교환 공개값을 미리 실어 핸드셰이크를 1-RTT로 줄였고, 그 뒤의 메시지는 인증서까지 전부 암호화한다.
- 정적 RSA 키 교환을 없애고 연결마다 임시 키를 쓰게 해서, 서버 장기 키가 나중에 유출돼도 과거 트래픽은 풀리지 않는다. 0-RTT는 이 성질과 재전송 안전성을 일부 내주고 왕복 하나를 더 줄이므로 멱등 요청에만 쓴다.
- 인증서 검증 실패는 서버 체인, 클라이언트 신뢰 저장소, 경로 탐색 구현의 조합에서 나온다. 의심되면 `openssl s_client -showcerts`로 서버가 보내는 체인부터 본다.

TCP 위의 TLS 1.3은 TCP 핸드셰이크 1-RTT 뒤에 TLS 1-RTT를 따로 치러야 한다. QUIC은 TLS 1.3 핸드셰이크 메시지를 자기 전송 계층에 직접 실어 이 두 단계를 하나로 합친다. 그 구조와 HOL blocking 문제는 [HTTP/2 vs HTTP/3(QUIC)](/posts/cs/network/http2-vs-http3-quic/) 글에서 이어서 볼 수 있다.
