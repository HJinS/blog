## 개요

Java 21에서 정식 출시된 Virtual Thread(Project Loom)는 "몇십만 개의 가상 스레드를 수십 개의 OS 스레드로 멀티플렉싱해 C10K 문제를 해결한다"는 약속을 했다.

> **2026-11-05 업데이트: JDK 24 이후 내용이 달라졌다.**
> 이 글은 처음에 Java 21 기준으로 썼다. JDK 24의 [JEP 491](https://openjdk.org/jeps/491)부터는 `synchronized` 때문에 생기는 pinning이 거의 사라졌다. 그래서 아래 설명 중 `synchronized`와 관련된 부분에는 "JDK 21~23"이라고 적어 두었고, 달라진 점은 각 절과 결론에 반영했다.

실제로는 그렇게 단순하지 않다.

```
이상적인 시나리오: Virtual Thread가 I/O 대기 중이면 Carrier Thread 전환
→ 매우 가볍고 빠름

현실(JDK 21~23): synchronized 블록에서 Virtual Thread가 "고정(pin)"되면
→ Carrier Thread가 블로킹되고 다른 Virtual Thread들은 대기
→ 성능 이득 상실
```

JDK 24 이상에서는 이 "현실" 시나리오가 `synchronized`에서는 더 이상 일어나지 않는다. 다만 pinning 자체가 완전히 없어진 것은 아니다. 남은 경우는 2절에서 정리한다.

## 1. Virtual Thread의 기본 구조

### Carrier Thread vs Virtual Thread

```
OS 레벨
┌──────────────────────────────────────────┐
│  [Carrier Thread 1]  [Carrier Thread 2]  │ (OS가 관리)
│      (Platform Thread)                   │ (1:1 매핑)
└──────────────────────────────────────────┘
         ↑                      ↑
    스케줄러 멀티플렉싱    스케줄러 멀티플렉싱
         ↓                      ↓
JVM 레벨
┌──────────────────────────────────────────┐
│ Virtual   Virtual   Virtual   Virtual    │ (수천~수만 개)
│ Thread 1  Thread 2  Thread 3  Thread 4   │ (경량, 수 KB)
│ ...       ...       ...       ...        │
└──────────────────────────────────────────┘
```

- **Carrier Thread**: 실제 OS 스레드, CPU 코어에 1:1 매핑
- **Virtual Thread**: 경량 사용자 레벨 스레드, 스택 크기 ~1 KB (Platform Thread 대비 1/1000)

### 스케줄러의 동작

Virtual Thread는 I/O 대기 등의 이유로 block되면 Carrier Thread를 해제하고, 다른 Virtual Thread가 그 Carrier Thread를 점유한다.

```
시간 →

[Carrier Thread A]
  ├─ Virtual Thread 1 실행
  │  ├─ Socket.read() ← I/O 대기
  │  └─ [블로킹, Carrier 해제]
  │
  ├─ Virtual Thread 2 실행 ← Carrier Thread A 재사용
  │  ├─ 계산
  │  └─ I/O 완료 시 다시 블로킹
  │
  └─ Virtual Thread 3 실행 ← 또 다시 Carrier Thread A 재사용
```

이론상 100,000개 Virtual Thread도 수십 개 Carrier Thread (= CPU 코어 수)로 처리 가능하다.

## 2. Pinning: Virtual Thread가 Carrier Thread를 "고정"하다

### Pinning이란?

Virtual Thread가 Carrier Thread를 해제하지 않고 계속 점유하는 현상을 **pinning**이라 부른다.

```
[Carrier Thread A] ← Virtual Thread 1이 "핀닝"됨
  └─ Virtual Thread 1
     ├─ synchronized block 진입
     │  (다른 Virtual Thread들이 대기 중인데도)
     │  └─ Lock 경합 발생
     │     └─ park() 호출 → Carrier Thread 해제 불가!
     │
     └─ Carrier Thread A는 Virtual Thread 1의 lock 대기로 블로킹
```

결과: **Carrier Thread A가 아무 일도 안 하면서 점유 중** → 다른 Virtual Thread들이 대기

이 그림은 JDK 21~23에서 `synchronized` 블록 안에서 블로킹할 때의 모습이다.

### Pinning이 발생하는 경우

**1. synchronized 메서드/블록 (JDK 21~23)**

```java
// ❌ JDK 21~23에서는 핀닝 발생
synchronized void blockingMethod() {
    Thread.sleep(1000);  // I/O 대기처럼 보이지만...
    // Virtual Thread가 Carrier를 해제할 수 없음
}
```

이유는 JVM이 모니터(monitor)를 추적하는 방식에 있다. JVM은 어떤 모니터를 누가 쥐고 있는지를 **Virtual Thread가 아니라 그 Virtual Thread를 태운 Carrier**(플랫폼 스레드)로 기록한다. 이 상태에서 Virtual Thread가 내려오면(unmount) 같은 Carrier에 다른 Virtual Thread가 올라타고, JVM은 그 스레드도 같은 모니터를 쥔 것으로 본다. 상호 배제가 깨진다. 그래서 JVM은 `synchronized` 안에서는 Virtual Thread가 내려오지 못하게 막는다. 모니터를 이미 다른 스레드가 쥐고 있어서 기다릴 때, 그리고 `synchronized` 안에서 `Object.wait()`을 부를 때도 Carrier가 같이 막힌다.

**JDK 24부터는 달라졌다.** JEP 491은 JVM이 모니터를 Virtual Thread 단위로 추적하도록 `synchronized` 구현을 바꿨다. 이제 Virtual Thread가 `synchronized` 안에서 블로킹해도 Carrier를 풀어 준다. 모니터를 얻으려고 기다릴 때와 `Object.wait()`에서 기다릴 때도 마찬가지다. JEP 491은 이로써 Virtual Thread가 플랫폼 스레드에 고정되는 경우의 거의 전부가 사라진다고 설명한다.

**2. 네이티브 프레임 위에서 블로킹 (JDK 24 이후에도 남는다)**

네이티브 메서드(JNI)나 Foreign Function & Memory API로 네이티브 코드를 호출했는데, 그 네이티브 코드가 다시 자바 코드를 부르고 그 자바 코드가 블로킹하면 Virtual Thread는 고정된다. 스택에 네이티브 프레임이 끼어 있으면 내려올 수 없기 때문이다.

```java
// 네이티브 코드를 거쳐 다시 자바로 돌아온 뒤 블로킹하면 핀닝
// (예: JNI 콜백 안에서 블로킹 I/O)
```

단순히 네이티브 메서드를 부르는 것만으로 고정되는 것은 아니다. 네이티브 프레임이 스택에 있는 동안 블로킹이 일어날 때가 문제다.

**3. 클래스 로딩과 클래스 초기화 (JDK 24 이후에도 남는다)**

JEP 491은 `synchronized`와 무관하게 아직 남은 경우로 다음 세 가지를 든다.

- 클래스를 로딩하다가 블로킹될 때
- 클래스 초기화(`static` 초기화 블록) 안에서 블로킹될 때
- 다른 스레드가 하는 클래스 초기화를 기다릴 때

JEP는 이런 경우가 문제가 되는 일이 드물 것이라고 보고, 문제가 되면 다시 살펴보겠다고 한다.

**참고: ReentrantLock은 원래 핀닝하지 않는다.**

```java
// ✅ JDK 21부터 핀닝 안 함
Lock lock = new ReentrantLock();
lock.lock();
try {
    // Virtual Thread가 여기서 블로킹돼도 Carrier는 풀린다
} finally {
    lock.unlock();
}
```

그래서 JDK 21~23에서는 `synchronized`를 `ReentrantLock`으로 바꾸는 것이 해결책이었다. JEP 491은 JDK 24부터 이 이행이 필요 없다고 하고, 이미 `ReentrantLock`으로 바꾼 코드를 되돌릴 필요도 없다고 한다. 새 코드에서는 편의성을 위해 `synchronized`를 기본으로 쓰고, 공정성·타임아웃·인터럽트 같은 기능이 필요할 때 `ReentrantLock`을 쓰라는 것이 JEP의 안내다.

## 3. Pinning 검출하기

### JDK 24 이상: JFR 이벤트로 확인하기

JDK 24부터 `jdk.tracePinnedThreads` 시스템 프로퍼티는 제거됐다. 이 옵션을 줘도 아무 효과가 없다. 대신 JDK Flight Recorder(JFR)의 `jdk.VirtualThreadPinned` 이벤트로 남은 pinning을 확인한다. JEP 491은 이 이벤트를 유지하고, 네이티브 프레임 때문에 고정되는 경우에도 기록하도록 바꾸며, 고정된 이유와 Carrier 스레드 정보를 담도록 강화한다고 한다.

```bash
java -XX:StartFlightRecording=filename=rec.jfr,duration=60s MyApp
jfr print --events jdk.VirtualThreadPinned rec.jfr
```

### JDK 21~23: jdk.tracePinnedThreads 옵션

JDK 21~23에서는 JVM 시작 시 다음 옵션으로 pinning을 추적할 수 있다:

```bash
java -Djdk.tracePinnedThreads=short \
     -Djdk.virtualThreadScheduler.parallelism=4 \
     MyApp
```

**출력 예:**

```
[pinned] VirtualThread "VirtualThread-1" (runnable)
  at java.lang.Object.wait(Object.java:335) @bci 0
  at my.service.SocialUnlinkService.unlinkAsync(SocialUnlinkService.java:42)
  - locked <0x00007f8c4b2a0100> (a java.lang.Object)
```

### 수동 검출 (코드 분석)

```java
// 이 코드는 JDK 21~23에서 pinning을 유발한다 (JDK 24 이상에서는 아니다)
public class SocialUnlinkService {
    private Object lock = new Object();
    
    public void unlinkAsync() {
        synchronized(lock) {  // ← pinning 발생
            callExternalApi();  // I/O
        }
    }
    
    private void callExternalApi() {
        // Redis, MySQL, HTTP 호출 등
        // I/O 대기 중 Carrier Thread 해제 불가
    }
}
```

## 4. Virtual Thread와 스레드풀의 백프레셔 차이

### Platform Thread (Tomcat 기본)

```
[ThreadPool: size = 100]
  ├─ [Thread 1] busy
  ├─ [Thread 2] busy
  ├─ ...
  ├─ [Thread 100] busy
  └─ [요청 101] 큐에서 대기 ← 백프레셔 발생
```

스레드 풀이 가득 차면 새 요청이 큐에 들어가서 대기한다. 이를 **백프레셔**(backpressure)라 부르며, 시스템이 과부하 상황을 인지할 수 있다.

```
[ALB]
  └─ max_connections 초과 → 요청 거부
     (또는 큐 크기 초과 → 에러)
```

### Virtual Thread (무제한 생성)

```
[Virtual Thread Scheduler]
  ├─ [Virtual Thread 1] waiting
  ├─ [Virtual Thread 2] waiting
  ├─ ...
  ├─ [Virtual Thread 10,000] waiting
  └─ [Carrier Thread 1] blocking
     [Carrier Thread 2] blocking
     ... (모든 Carrier Thread 고갈)
```

Virtual Thread는 제한 없이 생성되므로 백프레셔가 없다. 모든 Carrier Thread가 고갈될 때까지 계속 Virtual Thread가 쌓인다.

결과: **메모리 부족, GC 스톱**, 응답 불가 상태 돌입

```
이상적 시나리오 (백프레셔 있음):
부하 증가 → 스레드풀 가득 → 요청 거부 → 클라이언트 재시도

Virtual Thread 시나리오 (백프레셔 없음):
부하 증가 → Virtual Thread 무제한 생성 → 메모리 폭발 → JVM 크래시
```

## 5. 성능 테스트: Pinning의 영향

### 벤치마크 설정

```java
// 시나리오: Redis 조회 (원격) + MySQL 쿼리 (로컬)

@Benchmark
public void redisQueryWithPlatformThread() {
    jedis.get("key");      // 블로킹
    mysql.query("SELECT"); // 블로킹
}

@Benchmark
public void redisQueryWithVirtualThread() throws Exception {
    Thread.ofVirtual().start(() -> {
        jedis.get("key");      // 블로킹 (pinning 발생 가능)
        mysql.query("SELECT"); // 블로킹
    }).join();
}

@Benchmark
public void redisQueryWithVirtualThreadAndReentrantLock() throws Exception {
    ReentrantLock lock = new ReentrantLock();
    Thread.ofVirtual().start(() -> {
        lock.lock();
        try {
            jedis.get("key");
            mysql.query("SELECT");
        } finally {
            lock.unlock();
        }
    }).join();
}
```

### 예상 결과

**처리량 (높을수록 좋음):**

```
Platform Thread (Tomcat):           ~5,000 ops/sec
Virtual Thread (no sync):           ~50,000 ops/sec (10배 향상)
Virtual Thread (synchronized):      ~3,000 ops/sec  (오히려 악화)
Virtual Thread (ReentrantLock):     ~45,000 ops/sec (거의 10배)
```

위 수치는 개념을 보여주기 위한 가상의 값이며 실측이 아니다. JDK 21~23에서 `synchronized` 안에서 블로킹하면 Carrier Thread 고갈로 성능이 크게 떨어진다. JDK 24 이상에서는 이 Carrier 고갈 문제가 사라지지만, 모니터를 놓을 때 Virtual Thread를 스케줄러에 올려야 해서 성능 특성이 플랫폼 스레드와 다를 수 있다고 JEP 491은 밝힌다. 그러니 JDK 24 이상에서도 측정은 필요하다.

## 6. 실무 적용 전략

### 패턴 1: 전역 Virtual Thread 활성화 (비추천)

```yaml
# application.yml
spring:
  threads:
    virtual:
      enabled: true  # ❌ 모든 요청을 Virtual Thread로 처리
```

**문제:**
- JDK 21~23: 기존 코드에 `synchronized`가 있는지 전수 검사 필수
- JDK 21~23: synchronized 라이브러리(Jedis, 구형 MySQL 드라이버) 사용 시 pinning 폭주
- JDK 24 이상: `synchronized` 때문에 전수 검사를 할 필요는 줄었다. 네이티브 프레임과 클래스 초기화처럼 남은 경우는 JFR로 확인한다
- JDK 버전과 무관하게, 4절에서 본 것처럼 Virtual Thread는 백프레셔가 없다는 점은 그대로다

### 패턴 2: 선택적 도입 (권장)

```java
@Configuration
public class VirtualThreadConfig {
    
    @Bean(name = "virtualTaskExecutor")
    public Executor virtualThreadExecutor() {
        // I/O 바운드 작업 전용 Executor
        return Executors.newVirtualThreadPerTaskExecutor();
    }
    
    @Bean
    public Executor platformThreadExecutor() {
        // CPU 바운드 작업, synchronized 필요한 작업용
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(Runtime.getRuntime().availableProcessors());
        executor.setQueueCapacity(100);
        return executor;
    }
}
```

### 패턴 3: 라이브러리 검증

JDK 21~23을 쓴다면 Virtual Thread 사용 전에 라이브러리를 확인해야 한다. 아래 목록은 글을 처음 쓴 시점의 정리이며, 각 라이브러리의 현재 버전에서 사실인지는 다시 확인해야 한다. JDK 24 이상에서는 `synchronized` 사용 자체가 pinning의 원인이 아니므로 이 확인의 중요도가 낮아진다.

```java
// ✅ Virtual Thread 안전
// - Lettuce (Redis 드라이버)
// - Spring WebClient (비동기 HTTP)
// - Project Reactor (Reactive Streams)
// - Spring Data R2DBC (Reactive DB)
// - Jakarta EE WebClient

// ❌ Virtual Thread 위험 (synchronized 사용)
// - Jedis (구형 Redis 드라이버, synchronized 사용)
// - MySQL JDBC (synchronize된 Connection)
// - HttpURLConnection (synchronized)
```

**검증 방법:**

```bash
# 의존성 분석
mvn dependency:tree | grep jedis

# 소스 코드에서 synchronized 검색
grep -r "synchronized" ./src

# 또는 라이브러리 문서 확인
```

### 패턴 4: 부분 마이그레이션 (점진적)

```java
@Service
public class UserService {
    
    @Autowired
    @Qualifier("virtualTaskExecutor")
    private Executor virtualExecutor;
    
    // ✅ I/O 바운드: Virtual Thread 사용
    public CompletableFuture<User> findUserAsync(Long id) {
        return CompletableFuture.supplyAsync(
            () -> userRepository.findById(id),  // Redis 조회
            virtualExecutor
        );
    }
    
    // ⚠️ Mixed: 신중하게 선택
    public CompletableFuture<Void> withdrawUserAsync(Long id) {
        return CompletableFuture.runAsync(() -> {
            // 트랜잭션, Redis, MySQL 모두 필요
            // synchronized 사용 가능성 검증 필수
            withdrawalService.execute(id);
        }, virtualExecutor);  // 또는 platformExecutor
    }
}
```

## 7. Pinning 영향도 분석

아래 두 절은 JDK 21~23에서 `synchronized` 때문에 pinning이 일어났을 때의 모습이다.

### 메모리 측면

Pinning 발생 시 메모리 구조:

```
Carrier Thread 1 (pinned)
├─ Virtual Thread A (synchronized 블록)
│  ├─ Carrier Thread 해제 불가
│  └─ 메모리: ~1 KB (Virtual Thread) + 8 MB (Carrier)
│
Carrier Thread 2 (pinned)
├─ Virtual Thread B
│  └─ 메모리: ~1 KB + 8 MB

Carrier Thread 3 (idling)
└─ Virtual Thread C, D, E, ... (모두 waiting)
   └─ 메모리: 많은 Virtual Thread 적재되지만 실행 불가
```

**결과:**
- Virtual Thread 생성은 저비용이지만, Carrier Thread 고갈로 인한 컨텍스트 스위칭 폭주
- 메모리 폭발 (Virtual Thread는 쌓이는데 처리 불가)

### CPU 측면

```
Carrier Thread 중단 상황에서의 컨텍스트 스위칭:
1. Virtual Thread A가 synchronized 진입
2. Carrier Thread가 Virtual Thread A를 실행 중
3. 다른 Virtual Thread B도 같은 lock 필요
4. Carrier Thread가 switching overhead 없이 대기
   (Virtual Thread 스케줄러가 개입할 수 없음)
5. CPU 사이클 낭비 (spin-waiting, 또는 OS 커널 lock wait)
```

## 8. 권장 체크리스트

Virtual Thread 도입 전:

- [ ] 애플리케이션의 병목이 정말 스레드 수인가? (프로파일링 필수)
- [ ] 사용하는 JDK 버전은? (24 이상인가, 21~23인가)
- [ ] 의존성 라이브러리가 Virtual Thread 안전한가?
  ```bash
  # JDK 21~23
  -Djdk.tracePinnedThreads=short 로 테스트 실행
  # JDK 24 이상: 위 옵션은 제거됨. JFR의 jdk.VirtualThreadPinned 이벤트로 확인
  ```
- [ ] JDK 21~23이라면 기존 코드에 `synchronized` 사용이 많지 않은가? (JDK 24 이상이면 네이티브 프레임과 클래스 초기화 안에서 블로킹하지 않는지만 본다)
- [ ] 네트워크 I/O (DB, HTTP)에 Lettuce/WebClient 같은 비동기 드라이버 사용 가능한가?
- [ ] 메모리 설정이 충분한가? (Virtual Thread 대량 생성 시)
- [ ] 모니터링: JMX 메트릭에서 Carrier Thread 활용도, Virtual Thread 수 추적

## 결론

Virtual Thread는 강력하지만, JDK 21~23에서는 synchronized 블록의 pinning 때문에 성능 이득이 순식간에 사라질 수 있었다. JDK 24(JEP 491)부터는 이 문제의 거의 전부가 해결됐다.

**실무 원칙:**
1. **측정 먼저**: 프로파일링으로 병목 확인
2. **JDK 버전 확인**: 24 이상이면 `synchronized` 때문에 코드를 고칠 필요가 크게 줄었다. 21~23이면 `synchronized` 안에서 블로킹하는 코드를 찾아 `ReentrantLock`으로 바꾸거나 JDK를 올린다
3. **선택적 도입**: 전역 활성화 말고 I/O 바운드 작업만
4. **남은 pinning 확인**: 네이티브 프레임과 클래스 초기화 안의 블로킹은 JFR의 `jdk.VirtualThreadPinned` 이벤트로 확인
5. **점진적 전환**: 신규 코드/기능부터 적용
6. **모니터링과 백프레셔**: Virtual Thread는 개수 제한이 없으므로 동시 처리량을 제한하는 정책(세마포어 등)을 직접 세운다

처음 이 글을 쓸 때의 결론은 "synchronized 없는 코드 아키텍처가 필수 전제조건"이었다. 이것은 JDK 21~23에만 해당하는 말이다. JDK 24 이상에서는 필수 전제조건이 아니다.
